## Build, test, lint

Multi-module Go workspace; **no root `go.mod`**, so `go build ./...` from root fails. The common gates are wrapped by `scripts/test`:

```sh
scripts/test               # `go test -race ./...` in every registered module
scripts/test coverage      # the same, plus the aggregate coverage gate
scripts/test lint          # `golangci-lint run ./...` in every registered module
scripts/test verify        # lint THEN schema-sync THEN tests + patch-scoped coverage — the runner's verify gate
scripts/test verify --no-tests      # every verify leg except the test loop + patch coverage
scripts/test lint --in-gate-image   # lint / `verify --no-tests` inside the pinned gate image (CI parity)
scripts/test single -run TestName ./backend/internal/version/   # passthrough
```

**Gate image (E51.17 / #3966).** `--in-gate-image` (on `lint` and `verify`) runs the Docker-free legs inside `deploy/gate-image`'s pinned toolchain image, after checking that image's tool versions against this checkout's pins (a mismatch refuses); `verify` holds the HOST verify lock and gives the container a private one. Image: `FISHHAWK_TEST_GATE_IMAGE` (default `ghcr.io/kuhlman-labs/fishhawk-gate:main`) — never `FISHHAWK_GATE_IMAGE`, which switches a spawned runner onto the container path; this repo's runners DO carry it, as `FISHHAWK_GATE_IMAGE=fishhawk-gate:local` together with `FISHHAWK_GATE_SERVICES=postgres` (the runner-provisioned Postgres gate service, #2137; activated #4040 after the green walk), in the fishhawk MCP server env and `.env`. Rebuild that local image after any `deploy/gate-image/` change or pin bump (`docker buildx build --load -t fishhawk-gate:local deploy/gate-image`); fallback `FISHHAWK_GATE_ISOLATION=clone`. No in-repo `gate_container` build is declared: the runner builds with `--network=none` and this Dockerfile needs the network (#4060). `--in-gate-image` itself is CI parity, not isolation. Long-form: `deploy/gate-image/README.md`, `scripts/README.md` § "Gate image".

**`scripts/test verify` stage order.** It takes the per-repository verify lock, then runs `lint` → the ARCHITECTURE.md doc-line budget → a schema-sync drift check (re-runs `scripts/sync-schemas`, fails on drift the sync introduces) → the gate harnesses (`_verify_gate_harnesses`: the coverage, lease, `scripts/dev`, Helm and other `scripts/test-*` harnesses) → the site voice, site IA and ADR record gates → the gate-image pin check (`scripts/check-gate-image`) → the pipefail grep guard (`scripts/check-pipefail-grep`, #4233) → the `go test -race` loop with the patch-scoped coverage gate folded in. The aggregate coverage gate is omitted to bound runtime. The runner's committed-tree implement gate runs this same command, so a format, schema-sync or harness failure fails in-loop instead of red-lining CI after the agent is terminal (#1064/#1772). Long-form: `scripts/README.md` § "`scripts/test verify`: the lint and schema-sync legs".

**Scoped verify (E68.39 / #3315).** `scripts/test verify --packages <repo/rel/pkg,...>` (env fallback `FISHHAWK_VERIFY_PACKAGES`) restricts only the test loop to the listed packages and SKIPS the patch-coverage gate with a printed reason; every other leg is unchanged, and an unknown or undecodable package widens to the FULL loop. The runner verifies scoped on each fix iteration and re-verifies the passing SHA in full before reporting success. Long-form: `scripts/README.md` § "Scoped verify + the per-repository verify lock", `runner/README.md` § "Scoped verify".

**The verify lock: never start a concurrent `scripts/test verify`, and never retry or poll one that refuses (#3315, #2645).** `verify` takes `<git-common-dir>/fishhawk-verify.lock`, shared by every worktree; the runner's independent-clone gate is pointed at the PRIMARY's lock via `FISHHAWK_VERIFY_LOCK_PATH` (ADR-063 / #2134). A shell invocation meeting a live holder refuses immediately, and that refusal is terminal: run `scripts/test single -run TestX ./your/package/...` instead. A runner-marked invocation (`FISHHAWK_VERIFY_LOCK_OWNER=runner`) waits up to 600s and then displaces only a SHELL holder, never a runner one. Long-form: `scripts/README.md` § "The verify lock", `runner/README.md` § "Gate isolation".

**Lint.** `scripts/test lint` runs `golangci-lint run --allow-serial-runners ./...` per registered module: CI's invocation plus that one flag, so a second concurrent lint (another run's verify, or a shell beside one) waits for golangci-lint's global lock instead of failing (#3962). `.golangci.yml` enables the `gofmt`/`goimports` formatters, so `lint` also catches format drift with no separate gofmt run. `lint` and `verify` fail closed when golangci-lint is absent from PATH. CI pins golangci-lint v2.8.0 (see the pinning rule below). Long-form: `scripts/README.md` § "Lint".

Per-module without the wrapper (still useful for `go build` and `golangci-lint`):

```sh
go build ./backend/...
golangci-lint run ./backend/...
```

`.golangci.yml` is **v2 format** (`version: "2"` at top). Local install must be golangci-lint v2.x; v1 binaries reject this config.

**Backend tests share ONE testcontainers Postgres (#1174, was #972).** Call `pgtest.NewPool(t)` / `pgtest.NewURL(t)`: one reused `fishhawk-test-postgres` container, with a per-test `CREATE DATABASE ... TEMPLATE` clone. Do NOT hand-roll a per-package `tcpostgres.Run`. The one exemption is `backend/internal/postgres/postgres_test.go` (MigrateUp/MigrateDown need raw databases): it starts its own containers and terminates each in a `t.Cleanup`, including on the start-error path (#3122). **Inside the runner's gate container (#2137)** there is no Docker daemon: the runner pins `FISHHAWK_GATE_CONTAINER=1` and, with `FISHHAWK_GATE_SERVICES=postgres`, `FISHHAWK_TEST_PG_URL` (a unix-socket DSN to a per-exec, least-privilege Postgres). `pgtest` then uses that server as its shared base without testcontainers and FAILS (never skips) on any error there; the `postgres` package's raw-database helper creates throwaway `fh_raw_<uuid>` databases on it instead of starting containers; with the marker but no URL both fail naming the runner remedy. A new test that starts its own container outside `pgtest` breaks the container-path verify. Knobs: `FISHHAWK_TEST_P` (default 4; set `2` on a constrained daemon) and `FISHHAWK_TEST_TIMEOUT` (default `20m`, dev-only). `scripts/test` disables ryuk and removes the container on exit through a lease refcounted across concurrent invocations (#1792), plus a generation-keyed orphan sweep (#3122). Long-form: `scripts/README.md` § "Container lease + generation-keyed orphan sweep" (§ "The shared container", § "Lease refcount and the atomic lock", § "Anonymous volumes").

**Pin executable tooling fetched inside CI/release `run:` steps.** Any tool a workflow downloads and executes at run time — install scripts piped to a shell (`curl … | sh`), `npx` packages — MUST be pinned to a specific immutable tag or version, never `master`/`main`/`latest`/a floating major. A third-party repo can change its `master` install script or publish a new `@latest` and red-line the entire pipeline (including `main`) with zero change on our side — exactly what happened when golangci-lint's `master/install.sh` broke CI (#607/#608).
Current pins: golangci-lint `install.sh` → the `v2.8.0` tag (all four workflows: `ci.yml` + the three `*-release.yml`); the gate image's `deploy/gate-image/Dockerfile` ARGs (`GO_VERSION`, `GOLANGCI_LINT_VERSION`, `HELM_VERSION`, `CHECK_JSONSCHEMA_VERSION`) — a pin site enforced by `scripts/check-gate-image` in `scripts/test verify`, so bumping the golangci-lint tag or a `go` directive without the matching ARG (in the same change) fails verify; `@redocly/cli` → `2.31.5` (in `ci.yml` and the `docs/api/` lint/preview commands — keep these in sync). GitHub Action refs (`actions/checkout@vN`, etc.) are the exception: they stay on floating major tags because `.github/dependabot.yml`'s `github-actions` entry bumps them deliberately and reviewably. npx-in-run-step pins are not yet Dependabot-tracked, so bump them by hand.

**Coverage gate**: aggregate ≥ 80% across **all** registered modules, excluding sqlc-generated `*/db/` packages (CI uses `--exclude '/db/'` so new sqlc packages auto-skip). Tiered targets in `docs/ARCHITECTURE.md` §9. CI fails `CI Pass` if the threshold drops. CI runs the tests as a parallel matrix of legs (`scripts/ci-test-leg`, #3882) and gates the merged profiles in `Go (coverage gate)`; `scripts/test coverage` runs the same check locally as one serial loop.

**Every test loop runs EVERY module and aggregates — none aborts at the first failing one (#3403, #4036).** `test`, `verify` (full, its patch-coverage loop, and scoped) and `coverage` each end with a stderr summary naming every failed module and exit non-zero, so one failed verify surfaces every module's failures to the runner's fix agent; a failed full-verify loop exits before the patch-coverage gate. `coverage` additionally deletes each module's stale `coverage.out` before the run, classifies each failure as BUILD or TEST, and gates the profiles that survived. Long-form, including the loop's shape: `scripts/README.md` § "Per-module coverage aggregation".

**Patch-scoped coverage gate (#1887 / ADR-059), in-loop in `scripts/test verify`.** Lines the branch added or changed (merge-base → work tree, untracked `.go` files included, `/db/` excluded) must be ≥ 85% covered, with a 5-statement floor. Coverage is folded into verify's existing test loop, not a second run. The change set is snapshotted and digest-anchored BEFORE the tests run, so a test that rewrites the tree cannot turn the gate into a skip (#2124). Precondition failures (no git, no merge base, no changed Go packages) fail open with a printed reason; integrity failures fail closed. The knobs `FISHHAWK_PATCH_COVERAGE_THRESHOLD`, `FISHHAWK_DIFF_BASE` and `FISHHAWK_SKIP_PATCH_COVERAGE` are DEV-ONLY: the runner's gate env is a default-deny allow-list, so an agent cannot disable the gate. Its harnesses `scripts/test-check-coverage` and `scripts/test-patch-coverage` run inside verify. Long-form: `scripts/README.md` § "Patch-scoped coverage gate".

**`scripts/test-helm-render` gates the Helm chart (E62.2 / #2301).** It drives the real chart through `helm template`/`helm lint` inside `scripts/test verify` and asserts on rendered output: the credential contract, migrate Job timing, `envFrom` wiring, `NOTES.txt`, and registry existence of every rendered image. It SKIPS with a printed reason and exits 0 when `helm` is absent from PATH, so on a helm-less host the chart is unguarded. Its CI half is operator-installed (`.github/workflows/**` is forbidden to the implement stage). Long-form: `deploy/helm/fishhawk/README.md` § "Render gate", `scripts/README.md` § "Helm chart render gate".

**A plan-review prompt change needs recorded two-arm catch-rate evidence (E55.4 / #2245).** `scripts/check-review-prompt-eval` is a standing, path-triggered check: when a review-prompt path (`backend/internal/prompt/`, `backend/internal/repodoc/`, the agenteval catch harness, its gate command or its corpus/conventions fixtures) changed since the merge base with `origin/main`, it requires `(cd backend && go run ./internal/agenteval/catchrategate)` to pass, which decides OFFLINE from the committed evidence record and fails closed on an absent, stale, under-powered or regressed one. It runs OUTSIDE `scripts/test verify` (the live measurement needs a model key the gate env denies; only its harness `scripts/test-review-prompt-eval` runs in verify), every undecidable precondition exits 2 rather than skipping, and until an operator records and pins the first baseline it FAILS on every such change, by design. An implement agent cannot record evidence: a run that changes a trigger path leaves that to the operator (`docs/compliance/planreview-catchrate-evidence.md`). Its CI job is operator-installed. Long-form: `scripts/README.md` § "Review-prompt eval check", `backend/internal/agenteval/README.md` § "Plan-review catch-rate gate".

### Schema change checklist

Before opening a PR that adds or modifies a field in `docs/spec/`:

1. **Additive or breaking?** New optional fields within the current major version (e.g., `standard_v1.x`, `workflow-v0.x`) are additive — proceed. A new *required* field in an existing major version is a breaking change and must be avoided: bump the major version instead (`standard_v2`, `workflow-v1`). Use the `x-intended-required` annotation (see below) to signal a field whose required promotion is deferred through a soak period.

2. **Soak period.** When a field is introduced as optional but is intended to become required in a future version, declare the soak window in the PR body under `## Notes`. The soak period duration is determined per-PR; no minimum is set yet (TBD in a follow-up issue). During the soak, both the old and new schema versions are validated by the backend.

3. **Version advertising.** After the schema change merges, update every surface that advertises supported schema versions:
   - Plan validator (`backend/internal/plan/`) — add the new version string to the recognized set.
   - Runner `/healthz` schema-versions endpoint (once #466 lands) — add the new version to the advertised list.
   - **A NEW workflow MAJOR** (ADR-046 / #1381 stood up `workflow-v1` as the keystone): add the canonical `docs/spec/workflow-vN.schema.json`, run `scripts/sync-schemas` to mirror it into `backend/internal/spec/schemas/` + `cli/internal/spec/schemas/` (the `workflow-v*` glob routes it — no script edit), append a `{Major: N, Path: …}` entry to the `embeddedSchemas` routing table in BOTH `backend/internal/spec/parse.go` and `cli/internal/spec/spec.go` (this is what makes the version-routed validator dispatch to the new major instead of failing closed), add an `EmbeddedSchemaHashVN()` + the `workflow-vN` `/healthz` `schemas`-map entry in `backend/internal/server/handlers.go`, and register the new mirror set as its own self-referential surface-sweep pattern in `backend/internal/server/surface_sweep.go`.

4. **`x-intended-required` annotation.** When a field is optional now but will become required in the next major version, annotate it in the JSON Schema:
   ```json
   "some_field": {
     "type": "string",
     "x-intended-required": true
   }
   ```
   JSON Schema Draft 2020-12 §10.3 collects unknown keywords as annotations without affecting validation, so this annotation is safe to add to any schema without breaking existing validators.

### Auth change checklist

Before opening a PR that adds or tightens handler-side authorization (scope check, role check, audience check), the PR body must include:

1. **Impact inventory.** Which active tokens would lose access if the change shipped as-is? Run `fishhawkd token migrate --db $FISHHAWKD_DATABASE_URL` (dry-run, no `--apply`) to enumerate affected tokens. Paste the summary line into `## Notes`.

2. **Migration path.** State how affected tokens will be brought up to the new requirements. Options in order of preference:
   - `fishhawkd token migrate --apply` — promotes tokens whose scope set is a strict subset of the operator default (see #529).
   - Re-issue the token with `fishhawkd token issue --subject <s>`.
   - Manual DB update (last resort; document the exact SQL).

3. **Safe-to-ship determination.** The PR is safe to ship without operator-side action only when the impact inventory is empty (step 1 produced `scanned=N migrated=0`). If the inventory is non-empty, the migration path must be completed before or immediately after deploy, and this must be stated explicitly.

Cross-reference: this checklist codifies the rollout discipline introduced by #529; see #472 for the analogous schema-change discipline.

### Audit-category change checklist

A **new audit category** — any string literal reaching `audit.Entry` / `ChainAppendParams` / `AppendChained` / an emit helper — obliges `backend/internal/audit/categories.go` in the SAME plan scope. The committed-tree verify gate's `TestKnownCategoriesCoversEmittedCategories` fails on an unregistered emitted category, and an implement agent whose scope omits the registry cannot reach the file (run 49f642b8 / #3410 discovered the obligation only by failing that gate and burning a scope amendment on it).

1. **Scope the registry.** Add `backend/internal/audit/categories.go` (modify) to `scope.files` alongside the emitter — a one-line registration.
2. **The plan gate flags the omission.** The plan-gate surface sweep's audit-category rule (`backend/internal/server/audit_category_sweep.go`) reads the plan's own prose for a snake_case token named as an audit category/entry/row/event, drops the ones `audit.IsKnownCategory` already registers, and — when the plan touches `backend/` without the registry — records a `new audit category requires registry` finding rendered to the plan reviewer as `NEW AUDIT CATEGORY`. It is exemptible via `surface_sweep_exemptions` `{pattern: "new audit category requires registry", sibling: "backend/internal/audit/categories.go"}` ONLY when the token is not in fact a category (a runner log event, a tool name); an exemption is recorded and reviewer-challengeable.
3. **Operator-visible categories also oblige `backend/internal/issuecomment`'s `activityCategories`** (#3392/#3406) — the activity-comment renderer's allow-list — so the entry surfaces on the issue thread; and any new issue-comment surface still obliges `docs/issue-comment-surfaces.md` (the path-triggered "audit kind requires surfaces doc" pattern).
4. **In a fix loop, do not retry.** When the verify output names the registry (`add them to backend/internal/audit/categories.go`), the fix prompt lists it under `OUT-OF-SCOPE PATHS` with the mid-stage scope-amendment recipe — file the amendment; an in-scope workaround is the #1170 silent wrong-fix class.

### Rebuild matrix

`scripts/dev up` auto-detects which binaries need rebuilding by diffing `origin/main...HEAD` (falling back to `main...HEAD` with a warning if origin is unreachable) against the table below. `fishhawkd` always rebuilds as the baseline; the others rebuild only when their source changed. `scripts/dev up --all` forces all five. Each rebuild prints a line naming the trigger (`baseline`, `--all`, or the path that matched).

| If PR touches | Rebuild |
|---|---|
| `backend/cmd/fishhawkd/` or `backend/internal/{server,prompt,plan,spec,runner,webhook,notifier,github,storage,db,...}` | `fishhawkd` |
| `backend/cmd/fishhawk-mcp/` | `fishhawk-mcp` |
| `backend/internal/mcpserver/` (extracted MCP tool library, E66.7 / #2408) | `fishhawk-mcp`, `fishhawkd` |
| `backend/cmd/fishhawk-mcp-shim/` | `fishhawk-mcp-shim` |
| `runner/cmd/fishhawk-runner/` or `runner/internal/...` | `fishhawk-runner` |
| `cli/cmd/fishhawk/` or `cli/internal/...` | `fishhawk` CLI |
| `backend/internal/plan/` or `backend/internal/spec/` (shared libs) | `fishhawkd`, `fishhawk-mcp`, `fishhawk-runner`, `fishhawk` (NOT the shim — it carries its own trigger glob, so it rebuilds rarely) |

**Only a `README.md` basename is carved out of the matrix (#2403).** A README-only diff rebuilds nothing beyond the `fishhawkd` baseline and fires no MCP banner. Every other doc-shaped file (a `CHANGELOG.md`, a nested `docs/*.md`) and every embedded asset still triggers, deliberately: the predicate `_path_affects_build` is a deny-list that fails toward over-notifying. Long-form: `scripts/README.md` § "Rebuild detection and the `README.md` carve-out".

**Rebuilt-on-disk is not the same as live.** What it takes for a rebuilt binary to actually take effect differs per binary:

| Binary | Activation after a rebuild |
|---|---|
| `fishhawkd` | rebuilt **and restarted** by `scripts/dev up`/`reload` |
| `fishhawk-runner` | picked up automatically — spawned fresh from `bin/` on each `fishhawk_run_stage` |
| `fishhawk-mcp` | **auto-swapped** by the registered [`fishhawk-mcp-shim`](backend/cmd/fishhawk-mcp-shim/README.md) (ADR-060 / #1922) — the shim SHOULD hot-swap the rebuilt child, and `up`/`reload` print a one-line auto-swap note saying so. **That is an expectation, not an observation** (#2831): `scripts/dev` cannot probe the harness-owned shim, so CONFIRM with a version-returning tool call reflecting the new GitSHA. If it still reports the old SHA the swap did not happen — run `bin/fishhawk-mcp-shim --status` for the recorded reason (`deferred_in_flight` names the request holding it off; `deferred_no_initialize_recorded` means the session cannot be replayed at all), then `/mcp`. A manual `/mcp` reconnect is also the fallback when the shim is **not** registered (the Claude Code harness owns the MCP server process, so `scripts/dev` cannot restart it) |
| `fishhawk-mcp-shim` | rebuilt on disk but a **shim-binary** change needs a manual `/mcp` reconnect — the shim swaps its *child*, not itself, so the harness-owned shim process stays on the old code until you reconnect |

**Dev builds are GitSHA-stamped (#1007).** `scripts/dev` stamps the short HEAD SHA (`-dirty` on a dirty tree) into all five binaries, so `/healthz` `git_sha`, every binary's version surface (`fishhawk version`, `fishhawk-runner version`, `fishhawkd version`, `fishhawk-mcp --version`, `fishhawk-mcp-shim --version`) and the MCP handshake (`<Version>+<GitSHA>`) report the build commit; `Version` stays `dev`. The single `-X` source is `scripts/release-ldflags <component> <version> <sha>` (POSIX sh, so release jobs without zsh can call it, #4117): `_build_ldflags` runs it as a child process, and `backend/Dockerfile`'s literal stanza is byte-pinned to it. A wrong `-X` package path is a silent no-op, so a moved version package is caught by `scripts/test-dev` and `scripts/test-release-ldflags` (which builds all five binaries and reads each surface back). A `go install`ed CLI is unstamped and reports `dev`. Long-form: `scripts/README.md` § "GitSHA-stamped dev builds" and § "Release stamping".

**`post-merge` and `reload`.** `scripts/dev post-merge [<issue>] [--start-deps]` is the per-PR post-merge walk: `git pull --ff-only`, `scripts/cleanup-merged`, a guarded, non-fatal Go build-cache trim when the cache is past its threshold (#3901), an optional warn-only issue-closed check, then `reload` last. `reload` (down-then-up) always forces `--all`, because after a merge the `origin/main...HEAD` diff is empty and would rebuild nothing. Both REFUSE while any `fishhawk-runner` process is live (E68.7 / #2897), or while fishhawkd's `GET /v0/restart-blockers` reports a review round a restart would LOSE (one the next boot would not re-dispatch — since E72.59 / #4077 the boot sweep re-dispatches an eligible advisory orphaned round instead of failing it) or a run it could not decide (E83.30 / #3974), before any teardown or git step; `post-merge` also refuses on an undispatched decomposition child, because its `git pull` is what strands it, while `reload` ignores one. `--force` overrides both; `reload --when-quiet` instead waits, bounded (`FISHHAWK_RELOAD_QUIET_TIMEOUT`, default 3600 s), until nothing is live, exiting 1 on timeout. Long-form: `scripts/README.md` § "`post-merge` and `reload`", § "Live-run guard for reload / post-merge" and § "Restart-blocker guard for reload / post-merge".

**Stale-worktree warning and `sweep` (#1917).** `up` warns, and never fails, when a `.claude/worktrees/*` checkout is already merged into `origin/main`. `scripts/dev sweep [--days N] [--yes] [--dry-run]` removes merged-clean operator worktrees, aged run litter and keyed `/tmp` sidecars after one confirmation; a non-tty without `--yes` removes nothing, and it never passes `--force` to `git worktree remove`. Past `FISHHAWK_GOCACHE_MAX_GB` (sampled size) the same confirmation also trims Go build-cache entries unused for >`FISHHAWK_GOCACHE_TRIM_HOURS`, guarded, and a refused trim makes `sweep` exit 1 (#3901). Long-form: `scripts/README.md` § "Stale operator-worktree warning + `sweep`".

**MCP banner (ADR-060 / #1922).** `up`/`reload` print exactly one closing banner, in fixed precedence: schema-major > shim-rebuilt (needs one `/mcp`) > reconnect (mcp changed, shim NOT registered) > auto-swap (mcp changed, shim registered) > none. The auto-swap note states an EXPECTATION, not an observation (#2831): confirm with a version-returning tool call showing the new GitSHA; if it shows the old one, run `bin/fishhawk-mcp-shim --status`, then `/mcp`. Long-form: `scripts/README.md` § "MCP banner selection", `backend/cmd/fishhawk-mcp-shim/README.md` § "`scripts/dev` integration".

**Schema-major banner (#1422, #2349).** A `.fishhawk/workflows.yaml` `version:` MAJOR bump fires the schema-major banner even when nothing was rebuilt, because a stale stdio `fishhawk-mcp` validates against its old embedded schema and breaks every `fishhawk_start_run`. With the shim registered (and not itself rebuilt), the banner asks you to verify, for example with `fishhawk_doctor` reporting `spec.valid: true`; otherwise run `/mcp`. Server side, `annotateStaleSpecError` adds a `run /mcp to reconnect` hint to the unsupported-version error. Long-form: `scripts/README.md` § "Schema-major banner".

**Readiness gate verifies listener identity (#965, nonce #1018).** `up`/`reload` refuse to spawn onto an occupied fishhawkd port. After `/healthz` turns healthy, they require it to echo the per-spawn `start_nonce` (`.fishhawk/dev.nonce`), so a stale daemon squatting on the port cannot pass as the new one; a mismatch exits 1 with a log tail (#628). `down` falls back to the port and kills only a nonce-verified or fishhawkd-named listener. Long-form: `scripts/README.md` § "Readiness gate: listener identity".

**ZERR trap and zsh `set -e` rules (#631).** `up`/`reload` install a `TRAPZERR` trap that prints `scripts/dev: command failed (exit <code>) at line <file:line>` on any abort in an untested context. When writing zsh under `set -e`, use `(( ++i ))` or `i=$(( i + 1 ))`, never `(( i++ ))`: it returns 1 when `i==0` and aborts the script. Likewise use `if [[ cond ]]; then x=1; fi`, not `[[ cond ]] && x=1`. `scripts/test-dev` guards both. Long-form: `scripts/README.md` § "ZERR diagnostic trap".

**Local Kubernetes (`scripts/dev k8s` / `k8s-down`, #852).** `scripts/dev k8s` (`make k8s-up`) builds the fishhawkd image, loads it into the node when Docker Desktop's kind-based provisioner does not share the host image store, `helm upgrade --install`s the chart with `values-local.yaml`, port-forwards `svc/fishhawk` to 8080 and gates on `/healthz`. Its fail-closed image-identity gate then requires the pod's image config digest and `/healthz` `git_sha` to match the build (#3344, #3530); `FISHHAWK_K8S_SKIP_IDENTITY=1` is the only bypass. It is an operator smoke test, not run in CI. Long-form: `docs/deploy/kubernetes.md` § "Image identity", `scripts/README.md` § "Local k8s ergonomics".

## Adding a Go module

1. `mkdir <name> && cd <name> && go mod init github.com/kuhlman-labs/fishhawk/<name>`
2. Append `use ./<name>` to `/go.work`.
3. Verify: `(cd <name> && go build ./... && go test ./... && golangci-lint run ./...)`.
4. **Wire the module into `backend/Dockerfile`** if the image build must resolve it. The image runs `go mod download` against the whole `go.work` workspace inside the container, so EVERY module listed in `go.work` must have its `go.mod` copied before that step — add `COPY <name>/go.mod[ <name>/go.sum] ./<name>/` to the first COPY phase (omit `go.sum` if the module has none) and `COPY <name> ./<name>` to the source phase. A module added to `go.work` but not the Dockerfile fails `go mod download` with `cannot load module ../<name>` — and this was invisible at PR time until the PR-CI `docker-build` gate landed (#735), because the on-disk workspace the `go` job builds against always has the module present (the #733 / #672 break: red main for 5 merges).

## Git flow

**Issue → feature branch → PR → docs + follow-ups → close issue → update relevant issues.**

1. Pick a child issue from Project #7. If a blocking ADR is open, resolve it first.
2. Branch from `origin/main`: `<issue-slug>-<desc>`, e.g. `e3.1-backend-skeleton`.
3. Commit with `git commit -s` (DCO is mandatory; PRs without sign-off are rejected). Imperative-mood title, no conventional-commits prefix. Use HEREDOC for multi-line messages.
4. **Update docs in the same PR**, before opening:
   - New package / HTTP route / env var / flag → a pointer row in `docs/ARCHITECTURE.md` "Where to look" (path + ≤1 sentence, no history — the verify gate caps line length at 1000 chars) with the long-form contract in the owning package's `README.md`; operator-facing inputs also → component `README.md`.
   - Spec or schema change → `docs/spec/<x>.md` + every embedded copy (CI's schema-sync diff fails otherwise).
   - HTTP API change → `docs/api/v0.openapi.yaml` (source of truth) + `docs/api/v0.md`.
   - Add / remove / rename an issue-comment surface (Notifier method or audit kind) → `docs/issue-comment-surfaces.md`.
   - Voice/naming → `BRAND_FOUNDATIONS.md`. New trap / build workflow → `AGENTS.md`, plus any `.agents/skills/` skill that cites it (see Documentation surfaces; operator-authored, so a run files it as a follow-up). Autonomy convention → `METHODOLOGY.md`.
   - Ratified ADR → its `docs/adr/NNN-slug.md` record (tracker body verbatim, front matter per `docs/adr/README.md`) + `scripts/check-adr --write-index` + the README Records row + the superseded record's `superseded_by` when the ADR states a supersession — in the same change that records the ratification, or the change immediately after. ADR-081 onward are added one by one (upkeep rule, E78.3 / #3724).
5. **File issues for deferred work** before the PR opens. Any TODO, "follow-up PR", "deferred to E…", or obvious operability gap gets a tracking issue. **Prefer `fishhawk_file_issue`** (the work-management tool, #1005) over the hand-rolled `gh issue create` + four labels + `gh project item-add` + GraphQL-status dance: it applies this repo's `work_management` conventions automatically — the `[E<parent>.<n>]` / `[ADR-NNN]` title format, the `type:*` default label, the per-type body skeleton, `Status=Backlog`, ADR numbering, and the parent-epic link — so you pass `type` + `summary` + the `area:*/autonomy:*/phase:*` labels + `relations.parent_epic` and it renders a conventions-complete item. For a numbered type (`adr`) ADR numbering is now discovered server-side from the tracker (#1269), so `existing_numbers` is OPTIONAL — the backend searches the existing numbered titles (open and closed) and allocates the next one. Pass `existing_numbers` only to override/hint that discovery, or seed `existing_numbers:[0]` (which yields 1) if discovery is unavailable for the target provider; a genuine discovery failure fails closed with `work_item_invalid` (`details.discovery_failed`) rather than allocating a wrong number (the #1265 empty-list guard remains the last line for a provider without discovery). Reference the filed issue from the PR body's `## Notes` so the deferral is reviewable.
   - **Board placement** is automatic (`boarded:true`) when `FISHHAWKD_PROJECTS_TOKEN` (a `project`-scoped PAT/UAT) is configured; without it the tool still files the conventions-complete issue but degrades to `boarded:false` with a logged `boarding_error` — board it manually then: `gh project item-add 7 --owner kuhlman-labs --url <issue-url>`. WHY that token is required, what each degradation reason means, and the per-forge picture: `docs/board-capability-matrix.md`.
   - **For Fishhawk product friction** (a bug in the tooling itself hit during a run), prefer **`fishhawk_report_product_issue`** with the run's id — it attaches a redacted, fingerprint-deduped diagnostic bundle (#1006).
6. Open PR — body uses `## Summary` / `## Test plan` / optional `## Notes` / `Closes #<issue>`. Match #80, #81.
7. After merge, walk the dependents:
   - Verify parent epic progress via its sub-issue links and the tracker Status field — epic bodies don't carry a hand-maintained checklist to check off (sub-issues + Status are the source of truth, E34.10 / #1617).
   - Update sibling issues if scope shifted (e.g., a CI fix bundled here means another sibling no longer needs it).
   - If an ADR was resolved, edit its body's Decision section and close.

Run `scripts/cleanup-merged` to delete local branches that have been merged into `origin/main` (optional; can be wired into a post-merge git hook).

Force-pushing a feature branch is fine with `--force-with-lease`; ask before force-pushing if there are review comments. Never force-push `main`.

## Traps

- **`t.Parallel()` and `t.Setenv`/`t.Chdir` are mutually exclusive — a test calling both PANICS** (`testing: test using t.Setenv or t.Chdir can not use t.Parallel`). `backend/internal/postgres` (except `startcontainer_test.go`) and `backend/internal/integration/mcp` run every top-level test with `t.Parallel()` (#3881), so a new test needing `t.Setenv`/`t.Chdir` must go in a non-parallel file instead.
- **macOS bash is 3.2** — no associative arrays. Use zsh, gawk, or awk lookups for scripts that need them.
- **Never pipe into a quiet grep (`| grep -q`, `-Fxq`, `--quiet`, …) in a script that enables `pipefail` (#4233).** `grep -q` exits on its first match and closes the pipe, so a writer with unwritten bytes gets EPIPE/SIGPIPE and `pipefail` FAILS the pipeline even though grep matched. It never fires on small input and fails every time once the input passes the pipe buffer (a first-line match at >= 100 KiB on macOS, >= 160 KiB in the gate image). That is how `scripts/check-site-ia` reported false IA violations. Use a here-string (`grep -Fxq -- "$x" <<< "$list"`) in production scripts. In a test harness, use the pipe-only drain helper `grep_q`, which each harness defines itself (a terminal on stdin blocks it). `scripts/check-pipefail-grep` enforces this as its own `scripts/test verify` leg. It also flags a `grep_q` call in a file that does not define the helper, because an undefined helper exits 127 and a negated assertion would then pass vacuously. A reviewed exception takes `# check-pipefail-grep: allow <reason>` on the same line. Long-form, including the guard's text-matching limits: `scripts/README.md` § "Pipefail grep guard".
- **A container image build must derive `GOARCH` from BuildKit's `TARGETARCH` automatic platform ARG (declared inside the stage that uses it), never a literal** — a hardcoded `GOARCH=amd64` is invisible on an amd64 CI runner and only surfaces as emulated execution on an arm64 host/node (#2912); `scripts/test-dev` pins the shipped directive.
- **A host behind a TLS-inspecting corporate egress proxy fails `docker build -f backend/Dockerfile` with `x509: certificate signed by unknown authority`** during `go mod download` — the tell: the same command run directly on the host (outside the container) succeeds, because the container's trust store doesn't carry the interception CA that the host's does; registry/base-image pulls are unaffected (#2918). Fix + full diagnostic: `docs/deploy/kubernetes.md` § "When the build fails with `x509: certificate signed by unknown authority`".
- **On Docker Desktop for macOS, a LOCKED SCREEN makes every `docker pull` under your own docker config hang with no output and no error (E51.5 / #2138; cause found and runner fixed in E51.26 / #4046).** The default `~/.docker/config.json` carries `"credsStore": "desktop"`, the CLI consults it even for an anonymous public pull, and `docker-credential-desktop get` → `docker-credential-osxkeychain` blocks in `SecItemCopyMatching` for as long as the screen is locked (operator spike 2026-10-06, unified log) — not a pending prompt. Tell: a `docker-credential-desktop get` child under the pulling `docker` process. **The runner is immune by default**: every post-selection runtime CLI call runs under a runner-owned, credential-free `DOCKER_CONFIG` (`{"auths":{"fishhawk.invalid":{}}}` + `cliPluginsExtraDirs`, no `credsStore`/`credHelpers`; the empty placeholder entry is load-bearing, because under a bare `{"auths":{}}` the CLI auto-detects `docker-credential-osxkeychain` from `PATH` and calls it anyway), so container-path gates pull public images on a locked laptop; a private image needs `FISHHAWK_GATE_DOCKER_CONFIG=<dir>`, whose helpers are probed under a 20s bound and fail fast as category C `container_credentials_blocked`. Your interactive config is never used for credentials by the runner. **What still hangs** is anything pulling under YOUR config: a hand-run pull, `scripts/test lint|verify --in-gate-image`, the docker-gated runner fixtures. Remedy there (anonymous public pulls only): unlock the screen, or `DOCKER_CONFIG` at a fresh `{"auths":{"fishhawk.invalid":{}}}` config (no `credsStore`, no `credHelpers`, no credential in `auths`) plus an explicit `DOCKER_HOST=unix://$HOME/.docker/run/docker.sock`; it cannot pull a private image. Contract: `runner/internal/gateiso/README.md` § "Runtime CLI credentials"; operator walk: `docs/deploy/self-hosted.md` § "Docker Desktop: a locked screen and the credential helper".
- **Do NOT start a second concurrent `scripts/test verify`, and NEVER poll one that refuses (#3315).** The runner runs the verify gate against the committed tree after an implement/fix-up agent finishes — in an independent throwaway clone whose verify is pointed at the PRIMARY's lock via `FISHHAWK_VERIFY_LOCK_PATH` (ADR-063 / #2134) — and it holds the per-repository verify lock while it does. A shell verify meeting a live holder exits non-zero with an actionable message; that is terminal for that invocation, so a retry loop just burns the stage budget (the shape that killed run a662ed6f category-A). Narrow to `scripts/test single -run TestX ./your/package/...` and report what you have. Two concurrent verifies also contend on golangci-lint's global lock and the shared testcontainers Postgres — the same #2645 hazard as two concurrent implement stages.
- **`go.work` is committed**; `go.work.sum` is not. `go.sum` will appear on first external import.
- **Project #7 Status field** has 6 options (Backlog/Up Next/In Progress/In Review/Blocked/Done) set via GraphQL `updateProjectV2Field` with `singleSelectOptions` (undocumented input field). Repeat the same workaround if creating new projects.
- **Project #7 owner is `kuhlman-labs` as a `user`, not an `organization`** — a GraphQL query taking an owner login must use `user(login:"kuhlman-labs")`, not `organization(...)`, or you get a NOT_FOUND. It is user-owned Projects v2, which is also why an App installation token cannot reach it (#1114) — see `docs/board-capability-matrix.md`.
- **Project #7 has > 100 items.** GraphQL caps `items(first:N)` at 100, so the project's item list silently truncates: query the ISSUE's `projectItems(first:10)` and filter by `project.id` instead. The enumeration rule this implies for product code (read `repository.issues`, never a board item list; a full `projectItems` page missing the target fails closed as `board_state_undecidable`) is in `docs/board-capability-matrix.md`.
- **jsdom rejects `__Host-` cookies under HTTP.** The default vitest jsdom URL is `http://localhost/`, but `__Host-` requires Secure, and tough-cookie won't honour it over HTTP. `frontend/vite.config.ts` sets `test.environmentOptions.jsdom.url = 'https://localhost/'` so cookie semantics in tests match production. Browsers treat `localhost` as a secure context anyway, so dev still works.
- **Vite's `server.fs.deny` default `**/.git/**` denies EVERY file in a `.git`-nested checkout (#3030).** A run worktree lives under `<repo>/.git/fishhawk-worktrees/run-<id>/`, so its served root matches that rule and every frontend module load is refused — surfacing as a MISLEADING `Error: Cannot find module '/src/test-setup.ts'` / `Does the file exist?`. The resolved config root is the full nested path (the `.git` segment is NOT stripped), so the file is denied, not missing, and an absolute-path `setupFiles` fix is a dead end. The carve-out lives in `frontend/vite-fs-deny.ts`: it drops only that one rule, and only when the config dir has a `.git` path segment (normal checkouts keep stock posture). Details: `frontend/README.md`.
- **`scripts/test` exports `GIT_CONFIG_GLOBAL=/dev/null` + `GIT_CONFIG_SYSTEM=/dev/null`** so temp-repo test commits never inherit the operator's global `commit.gpgsign` (#912).
