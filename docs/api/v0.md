# Fishhawk Backend API — v0

This is the human-readable companion to [`v0.openapi.yaml`](./v0.openapi.yaml).
The OpenAPI document is the source of truth; this file exists to give agents
and humans a faster way to grok the surface than reading 900 lines of YAML.
If the two disagree, the OpenAPI document wins.

## Why `/v0`

`/v0` is the prefix for everything the Web UI, CLI, and runner call. It is
**unstable by design** — fields may be renamed, endpoints may move, request
bodies may grow required fields — until the v1 cut at the end of phase 4
(MVP_SPEC §13). Once `/v1` ships, `/v0` and `/v1` coexist for one minor
version cycle, then `/v0` is retired.

The webhook receivers (`/webhooks/github`, `/webhooks/gitlab`) are
**unversioned** because the forge controls the request shape; the backend
adapts as the forge evolves.

## Auth at a glance — ADR-005 (#69)

Three security schemes for three caller classes; no other auth is supported
in v0.

| Scheme | Used by | Carrier |
|---|---|---|
| `sessionCookie` | Web UI (browser) | `Set-Cookie: fishhawk_session=…; HttpOnly; Secure; SameSite=Lax`; CSRF token via `X-CSRF-Token` matching `__Host-csrf` |
| `bearerToken` | CLI, programmatic | `Authorization: Bearer <opaque>` — server-issued, scope-bound, immediately revocable |
| `githubOIDC` | Runner action only | `Authorization: Bearer <github-oidc-jwt>` — verified against GitHub's JWKS per request, no server state |

Default for all UI/CLI endpoints is `sessionCookie OR bearerToken`. Runner-
facing endpoints override this individually; webhook ingestion uses neither
(GitHub HMAC over the body).

**Repo-scoped visibility on reads (ADR-057 Amendment A2 / #2071).** Authentication
admits a caller to a workspace account; it does not admit them to every
repository inside it. On top of the existing account scoping, read surfaces are
narrowed for a **non-admin `sessionCookie` caller** to the repositories that
caller holds at least `read` on at the forge, mirrored per identity with a TTL
(`FISHHAWKD_REPO_ACL_TTL`, default 15m):

| Surface | Behavior for a non-visible repo |
|---|---|
| `GET /v0/runs`, `GET /v0/campaigns`, `GET /v0/audit` | rows are **omitted** from the page |
| `GET /v0/runs/{id}` + its stage / artifact / concern / per-run-audit reads | **403 `repo_forbidden`** |
| `GET /v0/campaigns/{id}`, `/items`, `/status` | **403 `repo_forbidden`** |
| Refinement session reads (once the session has been filed) | **403 `repo_forbidden`** |
| Any WRITE (run/stage mutations, approvals, refinement `PATCH`/`POST`) | **not filtered** — see below |

This is a **read-visibility** filter only. Writes and approvals are never
gated on it: the mirror is a non-authoritative TTL'd cache of a forge read
permission, so a cached deny must not block a caller whose current live forge
permission authorizes the action, nor pre-empt the live decision-point
permission check an approval already makes.

Four postures are deliberately NOT filtered: `bearerToken` / MCP identities
(bounded by token ownership and scope), anonymous callers, a workspace `admin`
member, and any deployment with no repo-ACL mirror wired (no database or no
identity provider configured) — the last restores the pre-#2071 surface exactly.
Cross-forge rows are default-denied without any forge call: a GitHub login never
sees GitLab-installation data. Global-chain audit entries (no `run_id`) carry no
repository to authorize against, so they are admin-only for a filtered caller.

Two failure classes are kept distinct and never collapsed. A **forge** fault
(outage, or `identity.ErrRateLimited`) means the permission is UNKNOWN: that one
repo is treated as not visible for this request, nothing is memoized, the rest of
the request proceeds, and the server logs it at WARN naming the repo and reason —
so an operator can tell "you lack access" from "we could not ask the forge". A
**mirror-store** fault means the filter itself cannot function, and the request
fails `503 service_unavailable` rather than returning a silently short page.

Because a page is narrowed AFTER it is fetched, a list response may be shorter
than `limit` while `next_cursor` is non-empty. Following the cursor to exhaustion
still yields every visible row exactly once.

## Conventions

- **JSON everywhere** except `POST /v0/runs/{run_id}/trace`, which uploads
  `application/gzip` bytes and signs them via `X-Fishhawk-Signature`.
- **Cursor pagination** for every list endpoint. Response: `{ items, next_cursor }`.
  `next_cursor` is `null` at the end. Cursors are opaque; clients pass them back
  unmodified.
- **Error envelope** is `{ error: { code, message, details? } }`.
  - `code` is snake_case, stable, machine-readable. Clients switch on it.
  - `message` is human, may change between versions.
  - `details` is structured per-code; the keys ARE part of the contract for
    that code.
- **Timestamps** are RFC 3339, always UTC, always with `Z`.
- **IDs** are UUIDv7 strings; `format: uuid` in the schema.
- **Idempotency** — `POST /v0/runs` and `POST /v0/campaigns` honor an
  `Idempotency-Key` header: a replay with the same `(repo, key)` returns the
  existing resource (200) instead of minting a duplicate. The cancel endpoint
  and approval submission are idempotent on equal inputs.
  On `POST /v0/runs` the replay is resolved BEFORE the admission gates (#2366):
  a retry of a successful create returns the existing run even when the blocking
  budget tripped or `applies_to` stopped accepting the change in between, and it
  appends no second `run_admitted_applies_to_override` /
  `run_admitted_budget_override` entry. Request and spec validation still run
  first, so a replayed malformed body keeps its 400/422.

# Audit export contract (Export v1)

The producer half of the audit-grade verifier contract (ADR-008 / ADR-054).
`GET /v0/audit/export` emits the EXACT wire shape the external verifier
consumes so an out-of-band party can chain-verify without trusting the
backend.

- **Whole-run page bounding.** `limit` bounds the number of RUNS per page;
  a run's chain is never split, so each page independently passes the
  verifier's `VerifyExport` from every run's nil-`prev_hash` genesis entry.
- **Header-borne continuation.** The verifier's `ParseExport` uses
  `DisallowUnknownFields`, so the body is exactly `{schema, exported_at,
  runs}` — nothing else. Partiality and the opaque keyset cursor ride the
  `X-Fishhawk-Export-Complete` (`true`/`false`) and
  `X-Fishhawk-Export-Next-Cursor` response headers. Never silent
  truncation: a partial page always advertises `false` + a cursor.
- **Per-account run-less partitions, scoped to the caller (#2097).**
  Run-less entries (token issue/revoke, OAuth) chain per `account_id`
  (ADR-057 / #1828) and export as one `runs`-map key per account
  partition, each an independently verifiable chain: a tenant partition
  under its account-UUID key, the untenanted partition under the reserved
  nil-UUID key `00000000-0000-0000-0000-000000000000`. All carry `run_id:
  null`; the verifier walks every key as an opaque independent chain, so
  no verifier change is needed. Which partitions a caller receives is
  tenant-scoped: a tenant caller (token bound to an account) gets ONLY
  its own account partition — never another tenant's, never the
  untenanted nil-UUID partition, which is operator-only. An operator /
  no-account caller keeps the full view: the untenanted partition (even
  when empty, so consumers can tell "no run-less entries" from "not
  included" — never silently dropped) plus every tenant partition (each
  only when it has entries). Emitted on the FIRST page only (empty
  cursor). Opt out of all of them with `include_global=false`.
- **Filter mutual exclusivity.** An explicit `run_id` set (repeatable;
  a missing run is a fail-closed 404) is mutually exclusive with the
  `repo`/`from`/`to` filter shape (`repo` via the runs join, dates on run
  `created_at`). Combining them is a 400.
- **Auth: `read:audit-export` scope required** (E9.5/#1608, ADR-054) on
  ALL export surfaces — this endpoint, the CSV projection, and the
  agent-changes report (both renders). Anonymous callers get 401
  `authentication_required`; a bearer token without the scope gets 403
  `insufficient_scope` with `details.required_scope` named;
  cookie-session operators bypass scope checks per the standard
  contract. The scope is in the operator default set (`fishhawkd token
  issue` grants it; `fishhawkd token migrate --apply` promotes existing
  subset tokens), and is deliberately distinct from per-run reads so
  export-capable tokens are enumerable and revocable independently.
- **Redaction posture (ADR-054).** Exports carry entry payloads
  (redacted at write time where applicable) and content-hash POINTERS
  only — trace bundle bytes are NEVER inlined, and the raw-variant
  bundle stays behind the existing compliance gate (no read endpoint
  serves it). Pinned by test over a run with raw traces present.

## CSV export (`GET /v0/audit/export.csv`)

A flat CSV rendering of the same export for spreadsheet compliance
workflows (#1605). It is a **projection** over the JSON export's shared
run-selection and per-run assembly layer (`resolveExportPage` +
`assembleRunData`) — never a parallel query path — so its rows are a
field-for-field projection of the JSON `Export v1` body for the same
run-level filter set. A parity test locks this.

- **Columns.** One audit entry per row:
  `ts,run_id,repo,category,actor_kind,actor_subject,sequence,entry_hash,payload_summary`.
  `ts` is RFC3339 UTC; nil `actor_kind`/`actor_subject` and the global
  partition's `run_id`/`repo` are empty cells; `sequence` is a base-10
  integer; `payload_summary` is the compacted payload JSON bounded at 256
  runes (rune-boundary safe — never splits a multi-byte character) with a
  `...(truncated)` suffix when cut. Full payloads stay JSON-export-only.
- **Entry-level filters (CSV-only).** `approver` keeps only
  `approval_submitted` rows whose `actor_subject` equals the value;
  `category` keeps only rows of that exact category. Both compose (ANDed)
  with each other and with the inherited run-level filters. Entry-level
  filtering is CSV-only by design: dropping entries from the JSON body
  would break the verifier's hash-chain walk, so these filters are not
  offered on `GET /v0/audit/export`.
- **Download headers.** `Content-Type: text/csv; charset=utf-8` and
  `Content-Disposition: attachment; filename="fishhawk-audit-export-<UTC
  timestamp>.csv"`. Rows use RFC 4180 quoting (fields with commas,
  quotes, or newlines are double-quote wrapped, embedded quotes doubled);
  line endings are LF (accepted by Excel, Numbers, and Google Sheets).
- **Bounding & continuation.** Identical to the JSON export: `limit`
  bounds RUNS per page (not rows), and the same
  `X-Fishhawk-Export-Complete` / `X-Fishhawk-Export-Next-Cursor` headers
  drive continuation. Because bounding is whole-run, an entry-filtered
  page can legitimately have zero data rows while `Complete` is `false`.
- **No partial CSV on failure.** The whole page is buffered before any
  bytes are written, so a per-run assembly error is a clean JSON `500
  internal_error` with no half-written CSV.
- **Formula-injection non-goal.** Cells are raw audit values — no `=`/`+`/
  `-`/`@` escaping is applied, because prefixing an escape would mutate
  audit values and break the CSV-equals-JSON-projection guarantee. Import
  untrusted payload summaries via a spreadsheet's data-import flow rather
  than double-click-opening the file. Hardening, if wanted, belongs with
  the redaction sibling (#1608).

## CLI consumer & end-to-end external verification (`fishhawk export`, E9.4 / #1607)

The `fishhawk export` verb is the reference consumer of both export
endpoints. It follows the `X-Fishhawk-Export-Complete` /
`X-Fishhawk-Export-Next-Cursor` header continuation **automatically**,
assembling one complete bounded file so the operator never hand-stitches
pages:

- **JSON assembly.** Each page is decoded keeping every `runs` value and
  the `schema`/`exported_at` values as raw JSON, so run subtrees are
  byte-preserved (the entry hashes and Ed25519 signatures still verify).
  The per-page `runs` maps are unioned — disjoint because the run-less
  chain partitions ride the first page only — and re-marshalled as exactly
  `{schema, exported_at, runs}`, so the assembled file byte-parses through
  the verifier's `DisallowUnknownFields` `ParseExport`. A run key appearing
  on two pages, or a page reporting incomplete with no continuation cursor,
  is a hard error (never a silent merge or an infinite loop).
- **CSV assembly (`--csv`).** Pages are concatenated keeping only the first
  page's header row; a later page whose header differs is a hard error.
- **Atomic `--out`.** The assembled file is written temp-file-then-rename,
  so a mid-pagination failure never leaves a partial file at the
  destination; without `--out` the export streams to stdout.
- **Server-authoritative filters.** The CLI passes `--run` (repeatable) or
  the `--repo`/`--from`/`--to` shape through unchanged and renders the
  server's `400 validation_failed` on the mutual-exclusion violation
  verbatim rather than pre-checking.

End-to-end external-verification procedure (the audit-grade pitch):

1. Issue a `read:audit-export`-scoped token for the auditor (or export
   yourself with an operator token).
2. `fishhawk export --from <RFC3339> --to <RFC3339> --repo owner/name --out
   export.json` (or `--run <UUID>...` for an explicit set; `--csv` for the
   spreadsheet rendering). The assembled `export.json` is exactly the
   verifier's Export v1 wire shape.
3. Hand `export.json` — carrying each run's public signing key and full
   chained audit trail — to the external party.
4. `fishhawk-verify --export export.json` recomputes every entry hash and
   chain link with no backend trust required, exiting `0` (all chains
   verified), `1` (one or more issues, e.g. `kind=hash_mismatch` on a
   tampered entry), or `2` (usage error). A pgtest-backed round-trip test
   (`backend/internal/server/audit_export_roundtrip_test.go`) exercises
   this whole path against real Postgres data with `--limit 1` forcing
   multi-page assembly, plus a tamper case proving the verifier fails.

A worked instance of this whole procedure — Fishhawk's own development audit
log exported over the E31 window and published as a repo artifact with
provenance and verification instructions — lives at
[`docs/compliance/`](../compliance/) (E9.6 / #1609).

## Agent-changes report (`GET /v0/reports/agent-changes[.md]`)

The E9.3 canned compliance report (#1606): every agent-authored change in a
run range, with who approved / what reviewed / what validated each one. Like
the CSV endpoint it is a **projection** over the JSON export's shared
run-selection and per-run assembly layer (`resolveExportPage` +
`assembleRunData`) — never a parallel query path — so it inherits the SAME
run-level filters (`repo`/`from`/`to`/`limit`/`cursor`, `run_id` mutually
exclusive with the filter shape) and `created_at`-DESC keyset paging. It does
NOT offer the CSV-only `approver`/`category` entry filters. One report model
feeds both the JSON and the `.md` render (one-model-two-renders parity, locked
by a test).

- **Per-change evidence.** For each selected run that produced a change (a
  `pull_request_opened` entry): the PR (`pr_url`/`pr_number`/`branch`/
  `head_sha`); merge status (`merged`/`merger`/`head_sha`/`base_sha`) from
  `pr_merged`; approvals (subject/decision/timestamp) from
  `approval_submitted` + `pr_approved_on_github`; reviews (stage/reviewer
  model/verdict) from `plan_reviewed` + `implement_reviewed`; acceptance
  (verdict/failure_mode/evidence_hashes/content_hash) from
  `acceptance_outcome_recorded`; the audit-chain span (first/last sequence +
  entry hashes + entry count); and redacted-tier evidence links
  (run/audit/export/artifact API pointers per ADR-054, `ExternalURL`-prefixed
  when configured else relative — never inlined trace bundles).
- **Human-led reduced evidence.** Runs whose `workflow_id` is
  `human_led_change` render in a SEPARATE `human_led_changes` section with
  `reviews`/`acceptance` omitted (reduced evidence). Runs that produced no PR
  are excluded from both lists but counted in `totals.runs_without_change`.
- **Continuation is in-band here.** UNLIKE the verifier-strict `Export v1`
  body, this report is not strict-decoded by any verifier, so `complete` and
  `next_cursor` appear in BOTH the response headers
  (`X-Fishhawk-Export-Complete` / `X-Fishhawk-Export-Next-Cursor`) AND the
  report body. The markdown render carries an explicit `PARTIAL REPORT —
  resume with cursor …` banner on a partial page. These body continuation
  fields are report-only; they never appear on `GET /v0/audit/export`.
- **Markdown download.** `GET .../agent-changes.md` serves
  `text/markdown; charset=utf-8` as `Content-Disposition: attachment;
  filename="fishhawk-agent-changes-<UTC timestamp>.md"`.
- **Malformed payloads never fail the report.** A single corrupt audit
  payload is skipped with a logged warning, not a `500` — a compliance report
  must not black-hole on one bad row.
- Auth scope (`read:audit-export`) is deferred to E9.5/#1608 for all export
  surfaces, exactly as the export endpoints state.

## Release notes (`GET /v0/releases/notes/preview`, `POST /v0/releases/notes`)

The E33.2 evidence-derived release-notes surface (#1587, ADR-051 option B):
render the merged-run evidence between two refs into release-notes markdown,
optionally persisting it as a durable artifact. Both endpoints assemble through
the same `releaseevidence.Assembler` (the E33.1 assembly layer over the run /
audit / concern / artifact repositories plus a GitHub commit-walk resolver) and
render through the same `releasenotes.Render`.

- **Preview (`GET /v0/releases/notes/preview?repo=&from=&to=`).** Assembles the
  merged PRs in `(from, to]` and renders release-notes markdown WITHOUT
  persisting. Per change: the plan summary + link, the reviewer verdicts
  (`reviewer_model: verdict`), the acceptance outcome (verdict + failure mode
  when present), and any deferred concerns. The header carries the ref range, the
  advisory semver-bump hint, and the per-release cost rollup. The semver hint is
  the heuristic `suggested bump: <level> (because …)` line from
  `releaseevidence.ClassifyBump` (E33.4), wired into `releasenotes.Render` in
  E33.5 so both the preview and the persisted notes carry it. It is advisory
  only — the operator ratifies the actual version at cut time; a wrong hint has
  no failure mode beyond an operator override. Served as
  `text/markdown; charset=utf-8`. Authenticated read-only (anonymous → `401`, no
  scope gate beyond that).
- **Persist (`POST /v0/releases/notes`).** Same assemble+render, then stores the
  rendered notes as a `release_notes` artifact (admitted by migration 0051)
  keyed to the caller-supplied `stage_id` in a JSON content object
  `{repo, from, to, markdown}`. Because `artifact.Create` is stage-scoped and no
  first-class release stage type exists yet, the artifact attaches to a
  caller-chosen stage exactly as every other artifact is keyed. A persisting
  write — anonymous → `401`; an authenticated bearer token additionally requires
  the `write:runs` scope (`403 insufficient_scope` otherwise). Body:
  `{repo, from, to, stage_id}` (all required); response `201`:
  `{artifact_id, stage_id, repo, from, to, content_hash, markdown}`. A valid-UUID
  `stage_id` that keys no stage row fails the artifact FK and returns `404
  stage_not_found` (a client mistake, not a `500`).
- **Honesty constraint (ADR-051).** A merged PR in range with no resolvable
  Fishhawk run — a human-led / loop-bypassing change — is rendered as an
  explicitly-marked reduced-evidence entry naming why the evidence is reduced,
  omitting the verdict/acceptance/cost fields rather than fabricating them.
- **Fails closed.** The merged-PR resolver fails closed: a `CompareCommits` /
  `ListPullRequestsForCommit` failure propagates as `502
  release_notes_assembly_failed` rather than rendering from a partial walk. A
  missing repository (`503 release_notes_unconfigured`), an unconfigured GitHub
  client (`503`), or an App not installed on the repo (`503
  github_app_not_installed`) all fail closed.

## Release cut (`POST /v0/releases/cut`)

The E33.5 cut endpoint (#1590, ADR-051): record the operator's ratified release
version as a `release_cut` audit entry
(`{repo, version, artifact_id, bump_level, content_hash}`, system actor) on the
release run's chain, after validating that `artifact_id` names a persisted
`release_notes` artifact. `content_hash` is the artifact's own stored hash — it
pins WHICH notes were cut.

- **Records the DECISION only.** The endpoint appends the audit entry and
  performs NO git tag push and NO GitHub write. Tagging the release stays a
  human git action per the delegating posture — the operator pushes the tag out
  of band once the cut is recorded. (This is why cut needs no GitHub client:
  only the artifact + audit repositories.)
- **`bump_level` is advisory.** The optional `bump_level`
  (`patch`/`minor`/`major`) is recorded verbatim and never validated, mirroring
  the advisory classifier hint — the operator's ratification is the source of
  truth, not the heuristic.
- **Auth.** A persisting write — anonymous → `401`; an authenticated bearer
  token additionally requires the `write:runs` scope (`403 insufficient_scope`
  otherwise). Body: `{repo, run_id, artifact_id, version, stage_id?, bump_level?}`
  (`repo`/`run_id`/`artifact_id`/`version` required; `run_id` required — the
  audit entry needs a non-nil run). Response `201`:
  `{version, artifact_id, content_hash, bump_level, recorded}`.
- **Fails closed.** A missing artifact (`404 artifact_not_found`), a
  non-`release_notes` artifact (`409 artifact_wrong_kind`), a nil artifact/audit
  dependency (`503 release_cut_unconfigured`), or a durable audit-append failure
  (`500 release_cut_audit_failed`) all fail closed with no false success.

## Release publish (`POST /v0/releases/publish`)

The E33.3 publish integration (#1588, ADR-051 option B, publish half): given a
published GitHub Release (by `tag`) and a persisted `release_notes` artifact (by
`artifact_id`), set the Release body to the persisted notes markdown and attach
the notes as a fixed-name markdown asset (`release-notes.md`) via the App
installation token, then record a `release_published` audit entry
(`{tag, release_url, artifact_id, content_hash}`, system actor) on the release
run's chain. The endpoint is the backend primitive an operator drives
post-pipeline; the MCP verb is E33.5's follow-up.

- **No permission change.** The Releases REST endpoints (`GET
  /releases/tags/{tag}`, `PATCH /releases/{id}`, `DELETE
  /releases/assets/{id}`, `POST {uploads.github.com}/…/assets`) are covered by
  the App's existing `contents:write` grant (ADR-051 accepted-condition 3,
  confirmed on #1588). Asset uploads target the separate `uploads.github.com`
  host, not `api.github.com`.
- **Content-hash idempotency for BOTH surfaces.** A re-invoke is a full no-op
  (`200 {published:false, idempotent:true}`, zero PATCH/upload/audit) only when
  the desired notes hash equals the last recorded `release_published` hash AND
  the live Release body already hashes to the desired notes. When the hash
  differs it PATCHes the body AND replaces the asset (delete the fixed-name
  asset, then upload) so the body and asset can never diverge.
- **Auth.** A persisting write — anonymous → `401`; an authenticated bearer
  token additionally requires the `write:runs` scope (`403 insufficient_scope`
  otherwise). Body: `{repo, tag, run_id, artifact_id, stage_id?}` (`stage_id`
  optional; `run_id` required — the audit entry needs a non-nil run). Response
  `200`: `{release_url, tag, artifact_id, content_hash, published, idempotent}`.
- **Fails closed.** A missing artifact (`404 artifact_not_found`), a
  non-`release_notes` artifact (`409 artifact_wrong_kind`), no Release for the
  tag (`404 release_not_found`), an App not installed (`503
  github_app_not_installed`), a nil artifact/audit/GitHub dependency (`503
  release_publish_unconfigured`), a GitHub round-trip failure (`502`), and a
  post-update audit-append failure (`500 release_publish_audit_failed`,
  durable-before-response) all fail closed.

POST   /v0/work-items                        — file a work item via the repo's work-management conventions (#1005)
                                               body: {repo, type, summary, body?, sections?, title_vars?,
                                                 labels?, complexity?, status?, relations?, existing_numbers?, run_id?}

                                                 relations) → dispatches to the provider (github_projects;
                                                 jira interface-only) → returns the created item.
                                               summary is the mandatory one-liner (fills {summary}, is the
                                                 required Summary field). 422 work_item_invalid on a conventions
                                                 violation; 501 provider_unimplemented (typed, names the provider)
                                                 when the conventions name an unregistered provider.
                                               epic + child-number auto-derivation (#1958): for a child type whose
                                                 title_format is [E{epic}.{n}], when relations.parent_epic is set
                                                 and title_vars omits them, the handler derives BOTH server-side —
                                                 {epic} from the parent epic's leading [E<n>] title token, and {n}
                                                 as the next number after the epic's existing children (open and
                                                 closed) — so title_vars can be omitted entirely; a supplied value
                                                 overrides. The number is collision-free within one deployment
                                                 (concurrent omitted-n filings against one epic are serialized),
                                                 not globally unique. Fails closed (no client/installation,
                                                 unparseable parent, or no [E<n>] token → {epic} left unresolved →
                                                 the 422 below; a failed child-number lookup → 422 with
                                                 details.n_discovery_failed) rather than a wrong title.
                                               sections fail loud: with body omitted, every sections key must
                                                 match the type's body_skeleton exactly; an off-skeleton key is
                                                 422 work_item_invalid, never a silent drop.
                                               relations.depends_on (optional): issue references (#N or N) this
                                                 item depends on, among the epic's children. Persisted as a
                                                 `Depends on: #X, #Y` body marker (no native GitHub relation) and
                                                 read by the campaign epic-children query to assemble its wave DAG

                                                 campaign-assembly time (E25.3).

                                                 GitHub provider discovers the in-use numbers server-side from
                                                 the tracker when omitted (#1269); supply the list only to
                                                 override/hint discovery. A genuine discovery failure is 422
                                                 work_item_invalid with details.discovery_failed (a provider
                                                 lacking discovery still 422s on the #1265 empty-list guard).

                                                 the handler then resolves the App installation for the target
                                                 repo (no-installation repo fails closed). Run-absent is
                                                 operator-only — a run-bound agent token omitting run_id is
                                                 rejected 403 run_scoped_filing_required.

                                                 budget 3 → 409 amendment_budget_exhausted) OR draft (a direct

                                                 the same revision → 409 decision_already_recorded. Writes the

                                              — file the approved draft into tracker items (E34.3 executor,
                                                 ADR-052). body: {repo}. Files the epic first, then children in

                                                 the plan-approval gate — no new token scope).

## MCP tool surface (`/mcp`) — ADR-076 slice 2 (#2390)

fishhawkd serves the SAME Fishhawk MCP tool registry the `fishhawk-mcp` stdio
binary serves, over the streamable-HTTP transport, on its own listener. Both are
built from one `mcpserver.NewServer` call — the route reaches it through an
injected factory rather than a direct import, for import-cycle reasons detailed
in `backend/internal/server/README.md` — so there is a single tool-registration
path and no second registry to drift. The stdio binary is unchanged and remains
the headless/CI path.

**Auth.** The route sits inside the ordinary middleware chain and is
authenticated by the same `bearerAuth` pass as every REST route. It requires a
BEARER identity — `fhk_` or `fhm_`, with no special-casing between them. A
browser cookie session is refused `401 authentication_required`, which is what
makes the route's CSRF exemption safe: the exemption cannot become a
browser-driven CSRF path onto the tool surface. A missing bearer and an unknown
bearer return the same envelope, deliberately: discriminating them would leak
token validity. Clients present a Fishhawk bearer token today;
specification-compliant OAuth is slice 3 (#2391).

**Privilege parity.** Every tool reaches data by calling this same REST API
with the caller's token, so a tool call is exactly as privileged as the
equivalent REST call — including its denials. A token REST refuses with `403
insufficient_scope` is refused identically through `/mcp`.

**Per-request bearer binding.** The handler runs the MCP SDK in STATELESS
mode, so the tool server is constructed per REQUEST rather than per session:
the token authorizing a tool call is provably the token on the request that
triggered it. There is no session registry to leak, GC, or hijack, and no
`Mcp-Session-Id` response header — that absence is expected, not a fault.

**The cost of stateless, stated plainly.** A stateless server holds no session
to stream from or tear down:

- `GET /mcp` answers `405` with `Allow: POST` — the streamable-HTTP
  specification's prescribed response for a server offering no standalone
  event stream.
- `DELETE /mcp` also answers `405` with `Allow: POST`, whatever
  `Mcp-Session-Id` it presents. Through go-sdk v1.6.1 this was a `204`
  no-op; v1.7.0 removed session handling from stateless mode outright
  (SEP-2567), so there is no longer a session id to no-op ON. Refusing is
  the stronger contract: it is what proves a fabricated session id buys the
  caller nothing.

All three methods are still registered so every leg reaches the refusal ladder
rather than a bare 404 that would misreport a disabled route. In-request
notifications are NOT lost: the progress heartbeats Fishhawk's long-running
tools emit ride the POST response's own stream, and are covered by a test that
drives a tool call with a `progressToken` over `POST /mcp` and asserts the
notification arrives. Slice 3 revisits the transport mode if a tool ever needs
sampling, elicitation, or subscriptions.

**Refusal ladder**, evaluated in this order:

| Condition | Response |
|---|---|
| `--mcp-route=off` / `FISHHAWKD_MCP_ROUTE=off` | `404 route_not_found` |
| No tool-server factory wired (embedder gap) | `503 mcp_route_misconfigured` |
| Listen address is not a valid `host:port` | `503 mcp_route_misconfigured` |
| Listen address is a hostname that cannot be classified | `503 mcp_route_misconfigured` |
| Listener is reachable off-host | `403 mcp_route_loopback_only` |
| Embedder-supplied self URL is not loopback | `503 mcp_route_misconfigured` |
| Embedder-supplied self URL is `https://` with a hostname | `503 mcp_route_misconfigured` |
| No bearer identity (absent, unknown, or a cookie session) | `401 authentication_required` |

**Loopback-only (ADR-033).** The shipped `FISHHAWKD_ADDR` default `:8080` binds
every interface, so `/mcp` answers `403` until the address is set to
`127.0.0.1:8080`. The unspecified host is deliberately NOT clamped to loopback:
fishhawkd has already bound every interface by the time the route is resolved,
so treating `:8080` as loopback would serve the tool surface off-host behind a
bare bearer.

**Self URL.** The base URL the per-request tool client dials back on is DERIVED
from the validated listener — there is no `--mcp-self-url` flag, so no
operator-settable knob can aim the loopback round-trip (and every caller's raw
bearer) off-host. It is always built from a resolved loopback IP literal, never
a hostname: a hostname would be re-resolved by the HTTP client at call time, so
a DNS change after startup would carry bearers off-host. For the same reason an
embedder self URL that is `https://` with a HOSTNAME is refused at startup —
pinning hands the client an IP literal, so TLS would verify against a
certificate issued for a name the dialled host no longer carries and every tool
call would fail in the handshake; `https://` with an IP literal is accepted
unchanged.

**The listener binds the pinned IP too.** When the route is served and the
listen address names a HOST, fishhawkd binds the loopback IP that host resolved
to at startup rather than handing the name to `net.Listen`, which would
re-resolve it at bind time and could put the bare-bearer surface on an off-host
interface the route still classified as loopback. If the bound address is not
loopback while the route is enabled, startup fails closed on the whole listener
instead of serving REST with an exposed `/mcp`. Any other verdict binds the
configured address verbatim.

The route verdict is resolved ONCE at startup from immutable config. No request
pays a DNS lookup, and a resolver outage cannot intermittently flip a serving
route to 403.

**Conditional loopback lift + discovery challenge (#2391).** When the daemon
binds a non-loopback address AND the OAuth AS is enabled, the ADR-033 loopback
refusal is LIFTED: the route serves in authenticated-only mode, accepting ONLY
an audience-validated `fho_` OAuth identity (RFC 8707). A bare `fhk_`/`fhm_`
token is refused off-host with the same `401` — so network exposure and auth
tightening land together, and ADR-033's no-bare-bearer-off-host invariant holds.
With no AS (or `--oauth-require-loopback` on a public bind, which keeps BOTH
surfaces loopback-only) the `403` refusal stands. In the lifted posture the
bearer-forwarding dial-back stays on loopback for an unspecified bind
(`127.0.0.1`); for a specific non-loopback bind it addresses that same
locally-assigned address (a documented NARROWING — see the server package
README). The `401` carries an RFC 6750 §3 `WWW-Authenticate: Bearer` challenge
with the RFC 9728 §5.1 `resource_metadata` pointer when the AS is enabled (the
realm-only form otherwise), emitted byte-identically on the missing-bearer,
unknown-bearer and off-loopback bare-token paths so token validity never leaks.


## OAuth 2.1 authorization server (`/v0/oauth/*`) — ADR-076 slice 3 (#2436)

fishhawkd embeds an OAuth 2.1 authorization server so a spec-compliant MCP
client can obtain a Fishhawk access token by an authorization-code + PKCE flow
against a registration-free client (Client ID Metadata Document, RFC 8414) or a
pre-registered client. Four routes: RFC 8414 discovery metadata, the
authorization endpoint (GET consent + POST decision), and the token endpoint.

**Three-verdict enablement, resolved ONCE at server construction.** The AS is
one of three states, and every one of the four routes reads the same verdict:

| Verdict | Trigger | Behavior |
|---|---|---|
| DISABLED | no `--oauth-issuer` | all four routes `503 oauth_as_unconfigured` |
| ENABLED | a valid https issuer + a valid RFC 8707 resource + a non-nil store + a non-nil CIMD fetcher | routes served |
| MISCONFIGURED | an issuer supplied but a defect: bad issuer, bad resource, nil store, or nil CIMD fetcher | all four routes `503 oauth_as_unconfigured`, never a partial metadata document |

A nil CIMD fetcher is MISCONFIGURED, not a conditional advertisement — so a
server that cannot fetch a CIMD can never serve metadata advertising
`client_id_metadata_document_supported`. When ENABLED, every metadata field is
an unconditional literal.

**`GET /.well-known/oauth-authorization-server`** — unauthenticated,
`Cache-Control: no-store`. Fields: `issuer`, `authorization_endpoint`
(`<issuer>/v0/oauth/authorize`), `token_endpoint` (`<issuer>/v0/oauth/token`),
`response_types_supported: ["code"]`, `grant_types_supported:
["authorization_code","refresh_token"]`, `scopes_supported` (the operator scope
vocabulary), `code_challenge_methods_supported: ["S256"]`,
`authorization_response_iss_parameter_supported: true` (RFC 9207),
`client_id_metadata_document_supported: true`,
`token_endpoint_auth_methods_supported: ["none"]`.

**`GET /v0/oauth/authorize`** — renders an HTML consent page for an
authorization-code + PKCE request. Signed out → `302` to forge sign-in. Query
params: `client_id`, `redirect_uri`, `response_type=code`, `code_challenge`,
`code_challenge_method=S256`, `resource` (RFC 8707), `scope`, `state`. An
invalid request (RFC 6749 §4.1.2.1) is answered in-place (an RFC 6749 §5.2 JSON
error, not HTML) for the two UNREDIRECTABLE cases — an unresolvable `client_id`
and a `redirect_uri` mismatch, where the error must not be handed to an unverified
destination — and otherwise as a `302` redirect back to the client carrying
`error`, `state`, and `iss`. The
consent GET MINTS the `__Host-csrf` cookie when the request carries none: that
cookie is `SameSite=Strict` and is not sent on the cross-site top-level
authorize navigation.

**A request carrying no scope token is DEFAULTED, not refused.** RFC 6749 §3.3
allows either; this server defaults (#2466), so a client that never sends `scope`
— the shape of Claude Code's client-ID metadata document — onboards. An absent
`scope` key and a present-but-empty `scope=` carry zero scope tokens and are
treated identically. The default is the client's registered `scope` intersected
with the server vocabulary when the registration pins one, otherwise the whole
advertised `scopes_supported` set; a registration naming no supported scope is
refused `invalid_scope`. Every PRESENT value still validates as before — an
unknown scope, a whitespace-only value, and a scope exceeding the client's
registration all fail `invalid_scope`. The consent page lists exactly the scopes
that will be granted, and its form submits that resolved set, so what the user
approved is what the code is minted with even if the registration changes between
the page render and the submission.

**Loopback redirect URIs are answered on the port the client asked for.** RFC
8252 §7.3 has a native client register a PORTLESS loopback `redirect_uri`,
because it cannot know its ephemeral listening port at registration time. The
authorization response — the success redirect AND every error/deny redirect — is
therefore delivered to the port the request carried, not to the registration.
Only the port carries over: scheme, host and path all come from the registered
URI, and the matching rules are unchanged. The authorization code is bound to
that same port-bearing URI.

**`POST /v0/oauth/authorize`** — the consent decision, form-encoded
(`approve`/`deny`). CSRF is enforced by the `__Host-csrf` cookie with a narrow
path-scoped `csrf_token` form-field fallback. Approve → `302` to `redirect_uri`
with `code`, `state`, `iss`. Deny → `302` with `error=access_denied`, `state`,
`iss` (RFC 9207 §2), both to the loopback port the request carried. Every
redirected outcome carries `state` and `iss`. A
submission with no authenticated session is refused `401 auth_required`; a CSRF
failure `403`; both use JSON (the standard Fishhawk `Error` envelope), as do the
unredirectable authorization errors (RFC 6749 §5.2 `OAuthError`) — none are HTML.

**`POST /v0/oauth/token`** — `grant_type=authorization_code` or
`refresh_token`, PUBLIC client (`none`) only. Form-encoded; `client_id` is read
from the form body. ANY `Authorization` header is refused `401 invalid_client`
with a `WWW-Authenticate` header, since a public client presents no client
credential. The `redirect_uri` on an `authorization_code` exchange is compared
BYTE-EXACTLY against the authorization request's (RFC 6749 §4.1.3) — for a
loopback client that is the PORT-BEARING URI the authorize request carried, so
presenting the registered portless URI instead is refused `invalid_grant`.
Success body: `access_token`, `token_type=Bearer`, `expires_in`,
`refresh_token`, `scope`. Errors are the RFC 6749 §5.2 flat JSON `{"error",
"error_description"}` shape — NOT the standard Fishhawk error envelope — and both
success and error carry `Cache-Control: no-store`.

The `503 oauth_as_unconfigured` refusal on any of the four routes uses the
standard Fishhawk error envelope. Handler-side contract and the provider-key
resolution wart: `backend/internal/server/README.md`.

**CIMD amplification limiter + loopback gate (#2441).** The two unauthenticated
routes (`GET /v0/oauth/authorize`, `POST /v0/oauth/token`) trigger an outbound
CIMD fetch on a store-miss `client_id` URL. A two-bucket token limiter
(per-source AND global) bounds the rate/volume of those fetches, consulted ONLY
on the store-miss branch — a pre-registered `client_id` is never throttled. A
refusal answers `429` with a `Retry-After` header (RFC 9110 §10.2.3
delta-seconds, ≥ 1) and the RFC 6749 §5.2 flat body with
`error: temporarily_unavailable` (a deliberate departure at the token endpoint,
whose §5.2 list omits that code — HTTP 429 is the normative signal, the body
advisory). On authorize the refusal renders IN PLACE and is never redirected
(RFC 6749 §4.1.2.1). Separately, a code-enforced loopback gate
(`--oauth-require-loopback`, DEFAULT OFF) adds a fourth verdict: when set on a
non-loopback bind, all four routes answer `403 oauth_as_loopback_only`
(`details.listen_host`). It defaults off so it does not silently 403 the live-walk
deployments that need a public bind; the limiter is what protects an operator who
leaves it off. Tuning flags: `--oauth-cimd-rate-burst` /
`--oauth-cimd-rate-interval` / `--oauth-cimd-global-rate-*` — there is no off
switch; raise the burst to loosen it.

**RFC 9728 protected-resource metadata (#2391).** Two additional unauthenticated
routes (served only when the AS is ENABLED, `Cache-Control: no-store`, else
`503 oauth_as_unconfigured`) complete the discovery loop from the `/mcp` `401`:

- `GET /.well-known/oauth-protected-resource` — the bare well-known path, an
  interop convenience serving the identical document.
- `GET /.well-known/oauth-protected-resource/{resource_path}` — the RFC 9728
  §3.1 path-suffixed form (origin + well-known path + the resource's own path),
  the URL the `/mcp` challenge advertises. A suffix that is not this deployment's
  resource path answers `404 route_not_found`, so the document is never served
  under a URL claiming a different resource.

The document carries `resource` (the RFC 8707 identifier), `authorization_servers`
(this AS's issuer), `scopes_supported` (identical to the AS metadata's),
`bearer_methods_supported: ["header"]`, and `resource_name`. A client walks:
unauthenticated `POST /mcp` → `401` + `resource_metadata` → this document →
`authorization_servers[0]` → AS metadata → authorize → token → authenticated
`/mcp`.

`GET /v0/stages/{stage_id}/checks` injects a self-derived
`fishhawk_audit_complete` row for review stages (published to GitHub as a
required Check Run, #229/#231). Its `missing[]` entries each carry a `kind`
the SPA branches on. Most kinds (`plan_missing`, `trace_missing`,
`pr_missing`, `chain_invalid`, `chain_unrecoverable`, `foreign_commit`) are
hard gaps → state `fail`. Two are **pending-flavored** → state `pending`
when they are the only gaps: `head_fetch_failed` (couldn't read the live PR
HEAD) and `review_pending` (#947 — a configured agent implement-review was
dispatched but has not reached a terminal verdict). `review_pending` is the
pre-merge **presence** gate: it holds the required check pending — not
failing — until the review lands, then auto-republishes green. ADR-027's
advisory verdict stays non-blocking; ANY terminal review kind clears it, and
a hard backstop (`ReviewBudget.Cap` × configured agents) clears a reviewer
that died emitting nothing.

### CLI: kick off a run, watch it finish

```
POST /v0/runs                              → { repo, workflow_id, workflow_sha, trigger_source: "cli", workflow_spec: "<YAML>" }
GET  /v0/runs/{run_id}                     → poll until state in {succeeded, failed, cancelled}
GET  /v0/runs/{run_id}/stages              → final stage breakdown
```

For issue-triggered runs the CLI (and MCP server) also ship an inline
`issue_context` — title, body, url, number, the issue's `comments`, and
its `labels` (see the `IssueContext` schema) — captured via `gh issue
view` so the plan agent reads comment-borne refinements without a
backend-side GitHub fetch (#415, #618, #2226).

`labels` is the sole producer for a workflow's `applies_to` `labels`
criterion (E53.3 / #2226). It is persisted inside the existing
`runs.issue_context` JSONB snapshot — additive, no migration — and that
snapshot is immutable for the life of the run, so both `applies_to`
evaluation points read one value rather than re-reading mutable forge
state. An absent or empty array is an EMPTY label set and FAILS CLOSED
against a labels-declaring workflow; it is never read as match-all.

`POST /v0/runs` also accepts an optional `applies_to_override` (boolean)
and `applies_to_override_reason` (string). When the requested workflow
declares an `applies_to` predicate the change does not satisfy, the run
is refused with `422 workflow_not_applicable` **before any run row is
created** (E53.3 / #2226 / ADR-066 fork 4). Only the `labels` and
`trigger` criteria are evaluated at admission; `paths` is deferred to
the plan gate, where the approved plan's `scope.files` is the first
authoritative — and binding — path set. `applies_to_override: true`
forces the run past and records a RUN-SCOPED
`run_admitted_applies_to_override` audit entry; that entry, not the
request, is the override's source of truth, and the plan gate looks it
up to suppress its own deferred rejection. The entry is recorded even
when ADMISSION accepts the change, because `paths` is enforced later:
an override that only existed when admission refused would be
unreachable in the common case of satisfied labels plus an
out-of-declaration plan scope. Auditing the bypass is a PRECONDITION of
granting it, at BOTH writes: the pre-insert grant is recorded on the
global chain and an append failure there refuses the run with `503
audit_unavailable` creating no run row; the post-insert run-scoped entry
needs the run id, so a failure there **cancels** the just-created run
and returns the same `503`. A run that outlived its own entry would be a
bypass no run-scoped audit read returns, and for an admission-only
(`labels` / `trigger`) violation nothing downstream re-checks it. This
is deliberately the opposite posture from the REFUSAL audit (a refusal
already went the safe way, so an audit outage must not soften it). The
reason is REQUIRED — an empty or whitespace-only value is a `400
validation_failed` and admits nothing. The MCP `fishhawk_start_run` tool
exposes both as `applies_to_override` / `applies_to_override_reason`.
The CLI exposes them as `fishhawk run start --applies-to-override
--applies-to-override-reason "<why>"`, rejecting an empty or
whitespace-only reason locally, before the round-trip. There is no
override on the webhook-dispatch path.

`POST /v0/runs` also accepts an optional `budget_override` (boolean).
When the resolved workflow declares an `enforcement: blocking` periodic
cost budget whose current calendar-period spend has reached `limit_usd`,
a new run is refused with `402 budget_exhausted` (#688 / ADR-030);
`budget_override: true` forces the run past and records a
`run_admitted_budget_override` audit entry. The CLI exposes this as
`fishhawk run start --override-budget` and the MCP `fishhawk_start_run`
tool as `budget_override`. There is no override on the webhook-dispatch
path — a webhook-triggered run that crosses a blocking budget is simply
refused (a `run_rejected_budget` audit entry, no run row). In-flight runs
and CI-retry / decomposition-child continuations are never gated.

`POST /v0/runs` also accepts an optional `upstream_run_id` (uuid). It
names the upstream `feature_change` run whose `ci_green` / `review_merged`
a standalone deploy-only `release` run's deploy-stage `required_upstream`
pre-flight gate evaluates (E23.11 / #1417). A deploy-only run has no
implement/review stage of its own, so the gate evaluates the referenced
upstream instead; omitting it (the appended-deploy / non-deploy default)
leaves the gate evaluating the current run. It is DISTINCT from
`parent_run_id` (#216) — a deploy-gate safety reference, not a
follow-up/lineage link, so it carries none of the get_plan-resolution /
resume-retry / decomposition-provenance semantics `parent_run_id` does.
Because the referenced run directly controls a safety-critical deploy gate,
the gate validates its provenance at evaluation time: the upstream must be a
`feature_change` run IN THE SAME REPO as the deploy run. A reference to a
different repo or a non-`feature_change` workflow is treated as unresolved and
fails the gate closed, so a release run cannot be made to gate on an unrelated
run's CI state. Persisted on the run row and echoed back as `upstream_run_id`
on the Run resource. The MCP `fishhawk_start_run` tool exposes it as the
optional `upstream_run_id` input field, and the CLI `fishhawk run start`
exposes it as the `-upstream-run-id` flag; both validate the value is a
well-formed UUID locally before the round-trip.

`POST /v0/runs` also accepts an optional `drive` (boolean) — the per-run
drive-mode override (#1023 / #996 theme 1). When present it wins over the
workflow spec's `drive` default; when omitted the run inherits the spec
value (false when the spec doesn't set one or no spec is resolved). The
resolved flag is snapshotted onto the run row at create time — a spec
edit mid-run can't change an in-flight run — and echoed back as `drive`
on the Run resource (always present; `false` for legacy rows). Under
drive, the engine (`backend/internal/drive`) auto-advances the
mechanical transitions and records a `run_auto_advanced` audit entry per
advance; `GET /v0/runs/{run_id}` distills those entries into the
`auto_advanced` list, the current `next_action`, and the derived
`awaiting_merge` / `ci_failed` (#1045) presentation status (see the Runs
section above). A plan-gate revise that re-opens the plan stage is one
such mechanical transition (`revise_replan`, #1256): on a `github_actions`
run the orchestrator re-dispatches via `workflow_dispatch`; on a `local`
run it parks with a `run_plan_stage` `next_action` (the runner is
host-spawned per ADR-024, so the operator re-dispatches the plan stage),
surfaced on the authoritative run resource exactly as the
`plan_approved_dispatch` `run_implement_stage` park already is. The same
mechanical-park shape covers two more local re-open paths (#1271): a
`retry_stage` that re-opens a failed plan/implement stage to pending
(`retry_reopen`) and a `resume_run`/`recover` in-place decomposition-child
re-drive (`recover_redispatch`). On a `github_actions` run each
re-dispatches via `workflow_dispatch`; on a `local` run each parks with the
appropriate `run_<stage>_stage` `next_action` (`run_plan_stage` or
`run_implement_stage`) surfaced on the run resource, exactly as
`plan_approved_dispatch` and `revise_replan` already do. Judgment
points — gate approvals, concern routing, merge — always park. A
distilled host-dispatch `next_action` is display-only and lags the
stage it names (nothing re-stamps the parked entry until reviews
settle), so `GET /v0/runs/{run_id}` and the stage-wait read SUPPRESS a
`run_plan_stage`/`run_implement_stage` action once its named stage has
advanced past the host-spawnable states `{pending,
awaiting_host_dispatch}` — a parked entry no longer names a dispatch the
operator already performed (#1961). The suppression is best-effort and
fails OPEN to today's surface on a stage-read error.

The `awaiting_merge` `merge_pr` `next_action.detail` is qualified with the
run's outstanding advisory verdicts (#2487): it keeps the clean merge
invitation only when zero reviewer rejects (round-scoped to the latest
implement-review round) and zero open concerns (run-wide) remain, and
otherwise leads with `all blocking gates resolved` — never `all gates
resolved` — states the two counts, and names the dispositions; when the
advisory state cannot be read it degrades to a read-first hedge pointing
at the gate view. The drive rule, `next_action.action`, derived status,
and audit event are unchanged — only the operator-facing detail prose is.

### Version coordination

`GET /healthz` advertises three version-coordination fields alongside `status` and `version`:

| Field | Type | Notes |
|---|---|---|
| `git_sha` | string | Commit SHA the backend binary was built from. scripts/dev stamps the short HEAD SHA (`-dirty` suffix on a dirty tree) into dev builds; `"unknown"` only for unstamped builds |
| `min_runner_version` | string | Minimum `fishhawk-runner` version the backend accepts; `"dev"` means no constraint |
| `schemas` | object | Map of schema-name → sha256 hex hash of the embedded JSON schema. Keys: `plan-standard-v1`, `workflow-v0`, `workflow-v1`, `workflow-v2` |

`/healthz` also carries an optional `start_nonce` (string): a per-start opaque identity token echoed verbatim from the operator-supplied `--start-nonce` flag / `FISHHAWKD_START_NONCE` env var, and omitted entirely when unset. `scripts/dev` generates a nonce per spawn and requires it to round-trip through its readiness gate (and consults it in `down`'s port fallback), proving the listener on the port is the daemon it started even across OS pid reuse (#1018).

The runner receives `min_runner_version` in the `GET /v0/stages/{stage_id}/prompt` response body. When the field is present and the runner's own version is older, the runner must exit with code 3 (`version_skew`) rather than invoking the agent.

`fishhawk doctor` uses all three fields to surface drift warnings to the operator:
- backend `git_sha` vs local `HEAD` (warns if the local tree is ahead and the binary hasn't been rebuilt). The comparison is prefix-wise after stripping a `-dirty` suffix, so a stamped short dev SHA matches the full local HEAD — meaningful for dev builds, not just releases
- runner schema hash vs backend's `plan-standard-v1` hash (warns if runner and backend are built from different schema versions)
- CLI version vs `min_runner_version` (warns if the CLI is too old)

### Scope-bounded implement commit

On implement stages the `GET /v0/stages/{stage_id}/prompt` response carries
`scope_files` — the approved plan's `scope.files`, each an object of `path`
(repo-relative) + `operation` (`create` / `modify` / `delete`). The runner
stages exactly these declared paths at the commit boundary (and when computing
the policy diff) instead of `git add -A`, so stray dirty files — dev `.pid`
artifacts, editor scratch, unrelated local edits — cannot leak into a
Fishhawk-attributed commit (#581). Dirty-but-undeclared paths are excluded
(never staged) and surfaced as a `scope_drift` signal rather than blocking the
commit, matching the spec's flag-only scope-drift treatment. When `scope_files`
is absent (no approved plan, i.e. `plan_missing_for_implement`) the runner
falls back to `git add -A`.

On a recovery run the same prompt response additionally carries
`scope_exemptions` — the operator's `exempt_scope_files` (#1229), each a
`{path, reason}` marking a DECLARED `scope.files` path
operator-justified-unchanged. The runner subtracts these from its
`MissingScopeFiles` shortfall gate, so a category-B run that failed SOLELY on a
declared-but-unchanged file recovers without a replan. It is the inverse of
`add_scope_files`: it subtracts from the gate, it does not widen scope (no
amendment row). Resolved from the run's own `plan_reused_from` provenance;
absent on every non-recovery run.

When the stage's workflow declares the workflow-v1.6 `diff_coverage`
constraint (ADR-059 / #1888), the prompt response also carries a
`diff_coverage` object — `{command, report_path, format?,
min_new_line_coverage, base_ref?}`. It tells the runner what coverage command
to run, where that command writes its report, and what threshold the BACKEND
will hold the measurement to. The runner MEASURES (executing the command
under the same containment as the verify gate: a THROWAWAY `git worktree`
checkout of the stage's committed tree, bounded timeout, process-group kill,
default-deny gate env) and emits the result inside the stage's
`gate_evidence` event; the backend re-evaluates the threshold from the
uploaded bundle and owns the category-B verdict. An omitted `base_ref` means
the run's base branch, which the RUNNER resolves at measurement time
(`--base-branch` > `GITHUB_REF_NAME` > `main`) — an empty ref never reaches
git. The object is absent for every workflow that does not declare the
constraint, in which case the runner runs no coverage command and the gate
never fires.

On an implement stage the prompt response also carries `implement_model` — the
backend-resolved implement model id (#1013). When present, the runner pins the
agent spawn to it (the claudecode adapter appends `--model <implement_model>`).
The backend resolves it through the implement-model ladder: operator gate
decision < plan `model_recommendation.implement_model` < spec `executor.model`
< deployment default. When `implement_model` is absent (no rung supplied a
model — the common case), the runner leaves the model unset and the agent
spawns on the adapter's built-in default, byte-identical to today.

### App bot commit identity

The same prompt response also carries `commit_author_name` and
`commit_author_email` — the GitHub App bot account's git author identity,
resolved backend-side from the App itself (slug via `GET /app`, bot user-id
via `GET /users/<slug>[bot]`, both App-JWT authed and cached for the process
lifetime). The runner sets these as the commit author so App-backed commits
attribute to the App's bot account (`<slug>[bot]`, e.g.
`<bot-user-id>+<slug>[bot]@users.noreply.github.com`) rather than a hardcoded
default (#722). Both fields are absent when the backend can't resolve the
identity (no App JWT wired — dev / CLI / local-runner); the runner then falls
back to its default bot identity (`fishhawk-runner[bot]`).

### Decomposed child slice-branch routing

When a run is a decomposed child the `GET /v0/stages/{stage_id}/prompt`
response carries `decomposed_from_run_id` (the parent run) and `slice_index`
— the child's 0-based `sub_plan` position (ADR-041 / #1141). The runner routes
the child's commit onto its own **sole-writer slice branch**
`fishhawk/run-<shortID(decomposed_from_run_id)>/slice-<slice_index>`, cut fresh
from the declared base, rather than the pre-ADR-041 single shared
`fishhawk/run-<parent>` branch every sibling force-pushed onto. Because each
slice branch is minted once and owned by one child, the runner drops the
shared-branch push coupling (no `--force-with-lease`, no remote-rebase, no
tracking-ref materialization) and bounds each child's policy diff against the
base. `slice_index` is omitted (treated as `0`) for standalone runs and for
slice 0. Fan-in of the slice branches onto the consolidated branch is
ADR-041 / E24.2.

When the child's plan declares a decomposition, the implement prompt narrows
`scope_files` to the child's own slice, matched by the persisted `slice_index`
(not a fragile string match on the issue body). If that slice cannot be
resolved — the `slice_index` is out of range for the parent plan's `sub_plans`,
or the matched sub-plan declares no scope files — both `GET
/v0/stages/{stage_id}/prompt` and `GET /v0/stages/{stage_id}/prompt-render`
**fail closed** with `409 decomposed_scope_unresolved` rather than silently
serving the parent's full scope (which reopened #1669 when campaign-minted
parents fanned out children with a nil cached issue context, #1721). The error
`details` carry `run_id` (the child), `slice_index` (its 0-based index, or `-1`
when the row carries none), and `parent_run_id` (the `decomposed_from` run). A
run whose loaded plan carries no decomposition is unaffected — it keeps the
plan's top-level scope.

### Acceptance-stage containment inputs

On acceptance stages both prompt responses carry two E31.7 (#1535) fields and
one E31.18 (#1569) field, absent on every other stage type:

- `egress_target_hosts` — the acceptance stage's FULL spec-declared egress
  target-host list (the E31.4/#1532 grammar), each a host or host:port. The
  runner feeds it into the ADR-050 egress proxy's allow-list before spawning
  the acceptance agent. Distinct from the prompt TEXT's target-instance line,
  which renders only the first host. Absent when the spec declares no egress
  block — the proxy then admits only model + backend hosts (fail-closed: the
  agent simply cannot reach any target).
- `acceptance_criteria_ids` — the approved plan's
  `verification.acceptance_criteria` id list (the E31.1 join keys) in plan
  order. The runner validates the shipped verdict's `criteria[].id` join keys
  against this set, failing closed on an unknown id. Absent when the approved
  plan carries no criteria.
- `acceptance_expected_head_sha` — the run's merge-candidate identity: the
  newest `head_sha` across the run's reported-head ledger entries
  (`pull_request_opened` / `child_pushed` / `fixup_pushed`, the same ADR-035
  lineage source `fixup_expected_head_sha` resolves from). The runner's
  pre-spawn target-identity gate compares the declared acceptance target's
  `/healthz` `git_sha` against it before spawning the acceptance agent, so
  acceptance validates the merge candidate rather than whatever build answers
  at the declared host (E31.18 / #1569). Absent when backend-side ledger
  resolution fails (empty ledger or read error, WARN-and-omit) — the runner
  then treats the target as unverifiable and warns-and-proceeds rather than
  blocking the stage.

### Fix-up re-dispatch routing

When an implement stage is an operator-triggered implement-review fix-up pass
(`fishhawk_fixup_stage`, #762), the prompt response carries `fixup: true` and
`fixup_branch` — the existing PR branch the fix-up commit must land on. The
runner takes its same-branch `RebaseFromRemote` path (fetch + checkout + pull
--rebase) and pushes onto `fixup_branch`, advancing the open PR's head rather
than opening a new one. `fixup_branch` is derived to match the runner's branch
formula exactly: non-decomposed
`fishhawk/run-<shortID(run_id)>/stage-<shortID(stage_id)>`, decomposed
`fishhawk/run-<shortID(decomposed_from_run_id)>` (shortID = first 8 chars of the
UUID). A backend-side mismatch would re-create the `checkout -b <existing
branch>` already-exists failure (#784). Both fields are absent on a normal
implement dispatch — branch routing falls through to the per-stage branch.

A fix-up dispatch also carries `fixup_expected_head_sha` — the run's recorded
head: the newest `head_sha` across the run's reported-head ledger entries
(`pull_request_opened` / `child_pushed` / `fixup_pushed`), the same audit
source the ADR-035 branch-lineage verifier treats as the run's legitimate
tips. Before invoking the agent the runner establishes its own git base
(fetch + checkout of `fixup_branch`) and fails fast when the fetched tip
differs from this value, so a fix-up never runs against the operator's
incidental checkout (#967). The field is absent when resolution fails
backend-side (or from an older backend); the runner then proceeds with the
checkout only, skipping the comparison.

### Verify gate fields

When the stage's `executor.verify` block is set, both prompt responses carry
`verify_command` (shell command run as the in-band test gate) and
`verify_timeout_seconds` (wall-clock cap; 0 or absent means the runner's
10-minute fallback). They also carry `verify_max_iterations` — the verify-fix
loop budget from `executor.verify.max_iterations`: `0` or absent preserves the
single-shot demote-on-failure gate; `>0` caps the total verify-fix agent
invocations across the stage. The runner's `--verify-cmd` / `--verify-timeout` /
`--verify-max-iterations` flags override the spec-sourced values. All three
fields are omitted when the spec declares no verify block.

### Operator-agent: drive a campaign from an epic

```
POST /v0/campaigns                         → { repo, epic_ref: "issue:1439" }   (201 → Campaign)
GET  /v0/campaigns/{campaign_id}/status    → poll: { campaign, items, rollup, next_action }
   next_action.action == "start_run"       → POST /v0/campaigns/{id}/runs for next_action.issue_ref (E26.2 —
                                              campaign-aware, DAG-gated, links the run; pass runner_kind:local
                                              to drive it through the local loop), then re-poll. The status
                                              re-poll settles each run as it reaches terminal (reconcile-on-read).
   next_action.action == "attention"       → a failed item needs retry/abandon (FAILED wins over eligible)
   next_action.action == "resume"          → the auto-driver paged a human at a gate (E25.7); handle the
                                              gate, then POST /v0/campaigns/{id}/resume to continue
   next_action.action == "attend_human_led" → the only deps-satisfied item(s) are autonomy:low (human-led);
                                              fires only when eligible is empty (start_run wins otherwise).
                                              A human must lead it — do NOT start an agent run; handle it
                                              out-of-band, then re-poll
   next_action.action == "wait"            → items running/blocked; re-poll later
   next_action.action == "complete"        → every item terminal; the campaign is done
```

The create is **runless**: with no run row to carry it, the handler resolves
the repo's GitHub App installation directly (the same path `POST /v0/runs`
uses) so the provider can query the epic's children. **Idempotency-Key is
honored** (E25.13): a retried `POST` with the same `(repo, key)` returns the
existing campaign (200, `idempotent: true`) instead of minting a second one,
backed by an `idempotency_key` column + partial unique index, mirroring `POST
/v0/runs`. `next_action` precedence is
strictly FAILED-wins: a failed item surfaces `attention` regardless of whether
eligible items also exist.

## Common error codes

These are the codes the backend currently emits. The list grows as endpoints
are implemented; codes are additive and never repurposed.

| Code | Status | Meaning |
|---|---|---|
| `unauthenticated` | 401 | No valid session, token, or OIDC token |
| `forbidden` | 403 | Authenticated, but not authorized for this resource |
| `csrf_required` | 403 | Session-cookie POST/PUT/PATCH/DELETE missing or with mismatched `X-CSRF-Token` header (E4.6 #152). Bearer-token clients bypass this check. |
| `mcp_route_loopback_only` | 403 | `POST/GET/DELETE /mcp` — the MCP route is loopback-only per ADR-033 and this daemon listens on an address reachable off-host (#2390). `details.listen_host` names the rejected host. Set `FISHHAWKD_ADDR=127.0.0.1:8080` to enable the route, or `--mcp-route=off` to disable it explicitly. |
| `mcp_route_misconfigured` | 503 | `POST/GET/DELETE /mcp` — the route cannot be served safely (#2390): the listen address is not a valid `host:port`, a hostname listen address could not be classified, or an embedder-supplied self URL is not a loopback base URL (serving would forward every caller's bearer off-host) or is `https://` with a hostname (pinning the host to its resolved IP would fail TLS on every tool call). The message carries the specific diagnosis. |
| `route_not_found` | 404 | `POST/GET/DELETE /mcp` — the MCP route is disabled on this deployment via `--mcp-route=off` / `FISHHAWKD_MCP_ROUTE=off` (#2390). Distinct from an unrouted path: the explicit code lets a client tell "turned off" from "not built". |
| `budget_exhausted` | 402 | `POST /v0/runs` — the resolved workflow declares an `enforcement: blocking` periodic cost budget whose current calendar-period spend has reached `limit_usd` (#688 / ADR-030). No run row is created. `details` includes `workflow_id`, `period`, `limit_usd`, and `spent`. Clear it by raising `limit_usd`, switching the budget to `enforcement: advisory`, or retrying with `budget_override: true`. The same gate runs on the webhook-dispatch path (no override there). In-flight runs and CI-retry / decomposition-child continuations are never gated, and neither is a replay: an `Idempotency-Key` that resolves to an existing run returns it with 200 before this gate is evaluated, so a retry of an already-created run is not re-charged against the budget (#2366). |
| `workflow_not_applicable` | 422 | `POST /v0/runs` — the requested `workflow_id` declares an `applies_to` predicate the change does not satisfy (E53.3 / #2226 / ADR-066 fork 4). Fail-closed and pre-insert: no run row is created. `details` carries `criterion` (the predicate criterion that failed), `required`, `observed`, `satisfying_workflows` (which workflows WOULD accept the change) and `absent_issue_context`. Only `labels` and `trigger` are evaluated here; `paths` is deferred to the plan gate against the approved plan's `scope.files`. An issue-less run (`trigger_source` `cli`/`ui`) carries an EMPTY label set and is refused by any labels-declaring workflow — by design, and the message names the absent issue context rather than reporting a generic mismatch. Clear it by amending the workflow's `applies_to` declaration, starting the run under a workflow that accepts the change, or retrying with `applies_to_override` plus a required reason (which records a run-scoped `run_admitted_applies_to_override` audit entry). A replay never reaches this gate: an `Idempotency-Key` that resolves to an existing run returns it with 200 before the gate is evaluated (#2366). |
| `audit_unavailable` | 503 | `POST /v0/runs` — `applies_to_override` was set but the bypass could not be recorded in the audit log (append failure, or no audit store configured) (E53.3 / #2226). Auditing the bypass is a PRECONDITION of granting it, not a best-effort record written afterwards, so the run never proceeds on an unrecorded bypass — the opposite posture from the `workflow_not_applicable` REFUSAL audit, whose append failure is best-effort because that decision already went the safe way. | `provider_unimplemented` | 501 | `POST /v0/work-items` — the repo's conventions name a work-item provider that is not registered (e.g. `jira`, interface-only in v0) or a config typo (#1005). Fails closed rather than dispatching against a nil provider. `details.provider` names the missing id; `details.registered` lists the available providers. |
| `work_item_filing_failed` | 502 | `POST /v0/work-items` — reserved for a failure where no durable issue exists: the GitHub create-issue call failed, or the App installation for the target repo could not be resolved (#1005, #1107). `details.error` carries the provider message, which the `fishhawk_file_issue` tool surfaces verbatim. Board-placement / epic-link failures are **no longer** 502: they are best-effort (the created issue is the durable result), so they return `201` with `boarded` / `epic_linked` `false` and the cause in `boarding_error` / `epic_link_error` (also WARN-logged server-side). |
| `run_lookup_unconfigured` | 503 | `POST /v0/work-items` with a `run_id` on a deployment without the run repository wired (#1005). Omit `run_id` to file without the in-flight audit. |
| `run_not_entitled` | 403 | `POST /v0/work-items` — a `run_id` was supplied by a caller that is not that run's own run-bound agent token (`mcp:run:<uuid>`) (#1005). Only the run's bound token may drive a `work_item_filed` audit entry onto its chain, so an arbitrary authenticated caller cannot inject an entry under their own actor_subject by knowing the run UUID. `details.run_id` names the run. |
| `run_repo_mismatch` | 403 | `POST /v0/work-items` — the entitled `run_id` belongs to a different repository than the filing target (#1005). A run_id is honoured only when its repo matches `repo`, so a run-bound token cannot borrow an unrelated repository's installation context. `details` carries `run_repo` and `requested_repo`. |
| `product_feedback_disabled` | 403 | `POST /v0/runs/{run_id}/product-reports` — the run's repo conventions set the `product_feedback` kill-switch to `enabled: false` (#1006). No report is filed and no audit is written. `details.repo` names the repo. |
| `product_report_failed` | 502 | `POST /v0/runs/{run_id}/product-reports` — the dedup search against the upstream product repo, or the upstream file/comment, failed (#1006). `details.error` carries the provider message. The entitlement gate is widened from `/v0/work-items` (#1274): a run-bound token bound to a DIFFERENT run → 403 `run_not_entitled`; a non-run-bound operator/operator-agent bearer WITHOUT `write:runs` → 403 `insufficient_scope` (`details.required_scope: write:runs`); a non-run-bound bearer WITH `write:runs` (or a cookie-session operator) may file for ANY run (operator scope = deployment). `provider_unimplemented` (501) behaves as for `/v0/work-items`. |
| `run_not_found` | 404 | `run_id` does not exist |
| `stage_not_found` | 404 | `stage_id` does not exist |
| `artifact_not_found` | 404 | `artifact_id` does not exist |
| `token_not_found` | 404 | `token_id` does not exist |
| `invalid_state_transition` | 409 | Run/stage cannot move to the requested state from its current state |
| `signing_key_already_issued` | 409 | A run may have only one signing key |
| `signature_invalid` | 401 | `X-Fishhawk-Signature` did not verify against the run's public key |
| `webhook_signature_invalid` | 401 | `X-Hub-Signature-256` did not verify |
| `webhook_token_invalid` | 401 | `X-Gitlab-Token` did not match the configured secret |
| `webhook_secret_unconfigured` | 503 | The forge's webhook secret is not configured (receiver disabled) |
| `webhook_store_unconfigured` | 503 | The shared webhook delivery store is not configured |
| `oauth_as_unconfigured` | 503 | Any of the four OAuth 2.1 AS routes (`/.well-known/oauth-authorization-server`, `GET`/`POST /v0/oauth/authorize`, `POST /v0/oauth/token`) when the AS resolved DISABLED (no `--oauth-issuer`) or MISCONFIGURED (issuer supplied but a defect — bad issuer, bad RFC 8707 resource, nil store, or nil CIMD fetcher) at server construction (ADR-076 slice 3 / #2436). Standard error envelope. The token endpoint's OWN grant errors are instead the RFC 6749 §5.2 flat JSON `{error, error_description}` — see the OAuth AS section above. |
| `validation_failed` | 400 | Request body or query parameter failed schema validation. `details.field` names the offending field |
| `cursor_invalid` | 400 | The pagination cursor is malformed or stale |
| `repo_forbidden` | 403 | A point read whose resource belongs to a repository the caller does not hold at least `read` on at the forge (ADR-057 Amendment A2 / #2071). Applies to non-admin `sessionCookie` callers only — bearer/MCP identities, workspace admins, and deployments with no repo-ACL mirror wired are never repo-filtered. List endpoints OMIT such rows instead of returning this code, and WRITES / approvals are never gated on the mirror at all. A repo whose permission could not be resolved because the forge was unreachable or rate-limited is also not visible and answers this code (logged at WARN); a mirror-STORE fault answers `503 service_unavailable` instead, so a filter fault is never mistaken for a permission answer. |
| `service_unavailable` | 503 | The auth middleware could not validate the presented credential because the database was unreachable (connection refused, closed pool) — distinct from a bad credential, which still returns 401 on a healthy DB (#764). Surfaced at the auth boundary on **any** authenticated endpoint, ahead of the per-handler logic. `message` is `database unavailable; retry shortly`; the condition is transient — retry with backoff. An error-classification signal only: no token loses access, and healthy-DB behavior is unchanged. |

endpoints intentionally have no 2XX response) and `no-server-example.com`
(the localhost server URL is intentional for local-loop testing).

## Where this lives in code

The eventual handler implementations land in `backend/internal/server/`. Each
operation in the OpenAPI document corresponds to one handler function whose
name matches the `operationId`. The router is plain `net/http` `ServeMux`
(per `docs/ARCHITECTURE.md` §3 — Go 1.22+ is required).
