# ADR-144: Proof of presence: a passkey step-up for decisions only a human may take

**Status: accepted (ratified 2026-11-13).**

## Context

Some decisions are meant to be a human's alone. Candidates include clearing a server-synthesized concern (ADR-084 rule 5), captain and delegation actions (ADR-083 (#3751)) and approving a production deployment (ADR-132 D4). The server enforces "human" from the credential a request carries.

That cannot be made sound by telling channels apart. A stdio MCP call, a CLI call and a plain HTTP call load the same stored credential and send the same bearer request: the stdio server loads its credential through `credstore.Load` (`backend/cmd/fishhawk-mcp/main.go:137`), it sends a plain `Authorization: Bearer` request with caller-set extra headers (`backend/internal/mcpserver/client.go:7273-7285`), and `/mcp` re-dials REST with the caller's own bearer (`backend/internal/server/mcproute.go:462-475`). ADR-084 Amendment A1 records the same limit: "A credential's subject does not say who is using it." A browser cookie session is separable from an agent's shell, but not from an agent that drives a browser on the same profile. A credential says which identity acts, never whether a person is present.

A passkey (WebAuthn with user verification: a fingerprint, a face or a device PIN) gives a signed assertion of an enrolled authenticator's user-verification result, over a challenge the server chooses. Under the assumption that enrolment is trustworthy and the authenticator's user-verification mechanism is outside the agent's control, an agent may prepare the decision and initiate the browser ceremony but cannot complete the required verification unaided. The assertion proves the authenticator's verification result for the bound challenge; it does not prove that the person understood the decision or protect against a compromised browser, host or authenticator. The product has no such mechanism today.

The cost that matters is attention. A proof asked for on every routine approval is given without reading, and then proves nothing.

## Options

- **A. No mechanism.** Human-only decisions keep the credential and channel rules their records set. Cheap, and it leaves the browser-driving agent and every CLI flow unanswered.
- **B. A proof-of-presence step-up, required per action.** An action is registered as requiring presence; the server then accepts the decision only with a fresh assertion bound to that decision.
- **C. Presence on every human decision.** One rule, no registration. It turns every approval into a prompt.

## Recommendation

Option B. This record decides the mechanism and adopts it for no action.

- **D1. The primitive, and it is additional.** A proof of presence is a WebAuthn assertion with user verification, from an authenticator enrolled to the acting identity, over a server-issued challenge. The server verifies it; nothing the caller states about itself counts. Presence is an additional requirement, not an authorization credential. A decision that requires presence is accepted only when it carries a valid proof and also meets every other rule that governs the action: its scope, account, eligibility and quorum checks, the credential-kind rules of the records that decide them (ADR-123 for stage approval gates, ADR-113 for ratification), and the agent-subject and delegated-request refusals. A proof never admits a credential kind that those rules refuse. A proof is submitted only by the Web UI session that completes the decision (D4), whether the person started the decision there or a caller opened it. No bearer request carries a proof, and this record adds no rule that makes a credential kind human. A browser-confirmed decision is attributed to the eligible human approver; an initiating agent may receive its result but gains no authority to perform the action. A channel restriction in an accepted record is relaxed only by an amendment of that record that names the proof.
- **D2. Bound to one decision.** The challenge is the digest of a canonical statement of the decision: action, target, content digests, acting subject, account, nonce and expiry. The implementing change defines its byte format once (a version tag, then the action and the fields above, one per line in a fixed order, UTF-8, LF line endings), names the digest as SHA-256 and the challenge encoding as unpadded base64url, and pins all of it by test; a later version carries a new tag and the audit entry records the tag. Each proof authorizes one immutable decision, including, for a proposed clear, its concern revision, head, judgment, reason and evidence references. A proof is single-use and expires within a bound the deployment declares, at most five minutes. At commit the server revalidates the authoritative target revision and the authority; if the target has changed, the proof no longer matches. The server consumes the proof atomically with the mutation and its audit row, and serialises concurrent submissions so that one proof has at most one effect. Where a gate counts several approvals, each counted approval carries its own proof.
- **D3. A server-owned registry, empty here.** A product action requires presence only when it is in one product-owned registry that the guards read. A completeness test fails when a verb that performs a registered action does not pass the presence guard. Whether this is its own registry or a mark in an existing registry of human-only actions is the implementing change's choice; there is one source of truth per action. The registry governs adoption by consuming product actions and is empty here: the product ships no default entry, and this record lists no action. D6's proof requirements for managing authenticators are intrinsic requirements of the mechanism and apply independently of that registry. A repository cannot remove an entry and a deployment setting cannot disable one. An entry is removed only by an amendment of the record that added it, and the adopting amendment states whether a change that removes or disables the entry raises a server-synthesized concern (ADR-084 rule 5). An action is added by an amendment of the record that governs it. For an identity with no enrolled authenticator, that amendment states who else may take the action or how the identity becomes an enrolling one. This mechanism never waives a requirement (D6). A path outside it, such as an unverified fallback claim (ADR-083 rule 4), exists only where the adopting amendment names it and scopes the registry entry so that the path is outside the entry's requirement; it is then not a waiver, the completeness test and D1's proof rule do not apply to it, and it is shown as unproven on every surface that shows the decision.
- **D4. The hand-off.** A caller on a channel that cannot collect a proof (the CLI, an MCP tool) asks the server to open a pending decision. The server fixes the action, target, content and account at that moment, records who opened it and on what credential kind, and returns an opaque reference. The canonical statement is built when the completing session asks for its challenge, from that fixed content, the session's subject, a fresh nonce and the expiry. Opening is an authenticated write: it passes the account check for the target, a proposal-write scope or session-role predicate declared by the adopting amendment, and a per-opener limit whose value that amendment declares; a run-bound token cannot open a decision unless the adopting amendment admits it. Proposal authority is separate from authority to complete the action. Opening proves no authority. The acting subject is the identity of the session that completes the decision. Before displaying a pending decision or its referenced objects, issuing its challenge, or returning its outcome, the server authenticates the requester and enforces the target's current account and read-access rules. Possession of the reference grants no access. Outcome retrieval through the reference additionally requires the original opener; the completing session is shown the result of its own completion. Completion applies D1's action-authority checks at commit. The reference is never a session or a bearer and is never exchanged for one. ADR-123 Decision 1 holds: "Sessions are minted only by the forge sign-in callback.", so no bearer credential is exchanged for one. A decision a person starts in the Web UI is opened as a pending decision by that session and follows the same path. The decision completes only in a Web UI session, on a page that renders the decision from server state; the server issues the challenge to that session only, with that session's forge identity as the statement's acting subject, accepts the assertion for that decision and that subject once, and applies the decision when the proof verifies. The session's challenge expires within D2's bound. A pending decision has its own lifetime, which the adopting amendment declares, and is void if its target changes. No proof or token returns to the caller. A CLI or MCP caller is never a carrier of the proof: a channel is admitted for an action by an adopting amendment that lets it open a pending decision, and the decision completes in a Web UI session. Where that amendment admits an MCP transport for a server-check clear, it changes ADR-084 Amendment A1's refusal and lists ADR-084 in its `amends`. A decision opened by an agent subject, or on a human-bound bearer, is shown as such on the page. Residual: a process that drives the person's browser can start a decision, time its prompt and shape the page around it. It cannot supply a biometric or a hardware touch, but it can complete the verification where that is a typed secret the agent knows, or where the credential provider reports verification without a fresh gesture (Direction 8). A proof shows that the enrolled authenticator reported user verification for a challenge that commits to this decision, not that a person was at it or read the decision.
- **D5. On the record.** The audit entry for the decision carries the decision's canonical statement, which holds identifiers, digests and references only and never a payload that the record governing the action keeps out of the audit chain (ADR-126 D3), and its digest; the authenticator data, client data JSON and signature as received; the credential id, the RP ID and origin, the signature counter; and the server's verification result labelled as the server's claim. Enrolment, removal and recovery of an authenticator are chained audit entries that carry the credential id, its COSE public key and algorithm identifier, its AAGUID, attestation format and attestation data, the registration's client data JSON and authenticator data as received, the RP ID and origin, and the subject. A verifier recomputes the challenge from the statement, checks the client data's type, challenge and origin and the authenticator data's RP ID hash and user-verified flag, and checks the signature under the key from the enrolment entry. A removed or rotated key leaves earlier proofs verifiable: each decision identifies its enrolment audit entry, and an authorized offline export includes the statement and assertion bytes, historical public key and algorithm, relevant enrolment and removal entries, and the versioned challenge-construction rules. Verification requires no live credential store and is relative to the audit chain. The decision's entry also carries who opened it, on what credential kind and its pending-decision reference, separately from the completing approver (D4). The enrolment and decision entries carry the declared delay, sign-in bound, proof lifetime and origin in force, together with the server-observed forge-sign-in completion, enrolment, challenge issuance and proof-consumption times needed to repeat the temporal checks. The authorized export includes those observations and their audit references, labelled as server claims. The enrolment entry is the only source of the key and has no anchor outside the deployment, unlike the forge-published keys of ADR-113's SSH approvals, so neither a rewrite of the chain nor an enrolment entry written by the server is detected by this record.
- **D6. Enrolment.** An identity enrols its first authenticator from a session minted by a forge sign-in completed within the deployment-declared bound before the enrolment, at most a maximum that the implementing change fixes and pins by test; this does not show that a person was present. That enrolment is audited, pages the identity and the captain of each repository the identity can act on, and cannot satisfy a presence requirement until a delay has passed; the deployment declares the delay above a non-zero minimum that the implementing change fixes and pins by test. A deployment that declares no sign-in bound, delay or proof lifetime satisfies no presence requirement and holds the action with a diagnostic naming the missing declaration. The page and the delay provide detection time only: this record supplies no cancellation path for an owner who does not control the first authenticator. Residual: the page mitigates only where it reaches the person on a channel the enrolling process does not read. Enrolling a further authenticator, or removing one, requires a proof from an authenticator already enrolled to that identity and past its first-enrolment delay; the proof's statement commits to the affected credential id and public key through its content digests (D2), and the change is paged as a first enrolment is. A further enrolment registers the new credential as pending first; the proof's statement then commits to that credential id and public key (D2). A pending credential is not enrolled and satisfies no presence requirement until that proof is consumed. A static subject has no forge session and does not enrol. An identity with no enrolled authenticator cannot satisfy a presence requirement, and the requirement is refused, never waived. No action is added to the D3 registry, and no gate-level declaration (Direction 7) takes effect, until recovery from the loss of every authenticator, and the response to a first enrolment the owner does not control, are decided by an amendment of this record.
- **D7. What the person is shown.** The confirmation page renders the object of the decision (the diff, the artifact, the flagged location) from server state, identified by the same digests the challenge commits to, and shows who proposed the decision and on what credential kind. Text supplied by the proposer is shown as the proposer's and never in place of the object. Residual: the display is not attested; the proof does not show what the person saw.
- **D8. No agent path.** No delegation, grant or timed window lets an agent satisfy a presence requirement. A proof admits one decision and leaves no verified state behind it. The existing agent-subject and delegated-request refusals stay in front of the proof check, and a valid proof never admits a request they refuse. The server refuses any assertion whose authenticator data does not carry the user-verified flag. This does not claim to stop an agent that drives the enrolling browser: the first enrolment of an identity is trusted on first use, and D6's page and delay give detection time only.
- **D9. Origin.** A presence requirement can be satisfied only where the deployment declares one origin for the Web UI page that runs the ceremony: an https origin, or a loopback `localhost` origin with its scheme and port, where the browser accepts the Secure session cookie and the `__Host-csrf` cookie the product sets. An origin whose host is an IP literal, including the default local stack's `127.0.0.1:8080`, is unsupported. Where none is declared, the requirement stands and the action is held. The server takes the RP ID and expected origin from that declaration, never from a request header. Deployment validation is the operator's check, recorded in the deployment's own notes, that enrolment and confirmation work on the declared origin with the configured RP ID, browser trust, an authenticated session and CSRF protection; the server holds on the declaration alone. An undeclared or unsupported origin holds the action with a diagnostic naming the reason and does not remove the requirement. A change of the declared origin is audited and paged; the operator repeats the deployment validation on the new origin, and the server does not hold on that. An authenticator is bound to its RP ID, so a change of RP ID invalidates every authenticator enrolled under the old one; a change of origin that keeps the RP ID does not. Direction 5 must treat a change of RP ID as a path to re-enrolment that a holder of the deployment's settings can force. The default local stack is plain-http `fishhawkd` on `127.0.0.1:8080`, with an opt-in TLS front end on `:8443` (`docs/local-tls.md:3-6`); neither is a declared origin, so a local deployment holds every presence-required action until it declares one.

## Decision

**Accepted 2026-11-13** by the Captain (manual ratification path; approver, errata and hashes in the ratification comment). **Option B**, i.e. D1–D9 as stated in the Recommendation: a WebAuthn user-verified proof of presence, additional to every existing authorization rule (D1), bound to one decision (D2), required only for actions in a product-owned registry that this record leaves empty (D3), collected in the Web UI session after a hand-off from any other channel (D4), recorded for offline verification (D5), with enrolment (D6), the confirmation surface (D7), no agent path (D8) and a declared origin (D9), and with recovery and each adoption as named directions. It amends no record; each adoption is an amendment of the record that governs the action. This record builds nothing by itself.

## Consequences

- ADR-143 (#5231) addresses channel restrictions for server-check clears. A CLI or MCP channel qualifies for an action only by opening a pending decision that a Web UI session completes (D4); it never carries a proof. Letting a CLI or MCP caller open a pending decision for an action requires an amendment of the record that restricts that channel; this record does not establish an interim rule for other human-only actions. Where a record speaks of a channel that carries a proof for an action, or of a proof that restores a bearer channel for it, under this mechanism that is a channel whose opened decision is completed with a proof (D4); the action itself is committed by the Web UI session.
- A confirm step for a proposed clear (#5229), where one is built, is a clear of a server-synthesized concern and takes the requirement once the clear is adopted (Direction 1).
- Production approval takes the requirement only through Direction 2, under ADR-132 D4; this record does not bring production promotion forward.
- **Enablement prerequisites.** Before an adopting amendment takes effect for an action, it carries an enrolment-readiness inventory of the identities that can take that action, a migration path and a safe-to-ship statement (`docs/review/security-conventions.md:15`), and states what stays held when they cannot be met.
- **Residuals.** The first enrolment is trusted on first use (D8). The server accepts the authenticator's own statement that it verified the user; a software authenticator the session holder installs before first enrolment is not detected. The display is not attested (D7). A person who approves without reading defeats D7 (Context). The deployment must protect the authenticator.
- **What this amends.** Nothing until an action is adopted. ADR-113 D2, ADR-123 D1 to D3, ADR-132 D4 and ADR-084 rule 5 with Amendment A1 are unchanged, because a proof is additional (D1) and this record adopts it for no action (D3).
- **Directions (not decided here).** Each adoption is an amendment of the record that governs the action.
  1. Adoption for server-check clears, covering every verb that clears a server-synthesized concern, with one proof per concern until batch confirmation (Direction 6) is decided: an amendment of the record that decides channel restrictions for server-check clears (ADR-143 (#5231)), once that record is on main, listing ADR-084 in its `amends`, and changing A1's MCP refusal where an MCP transport is admitted.
  2. Adoption for production approval, covering every counted approval of an ADR-132 production-class deployment intent, including a recovery that requires a new intent (ADR-132 D7): an amendment of ADR-132 D4, whose challenge commits to the approval statement ADR-132 D4 defines, not a separate one.
  3. Adoption for ratification: ADR-113 Direction H, an amendment of ADR-113 D2 that adds a `ratify.methods` value, decides how a Web UI session completion (D4) composes with D2(a)'s refusal of cookie sessions, and has the challenge commit to the canonical statement ADR-113 D2 defines, not a separate one.
  4. Adoption for captain, delegation and seat actions: an amendment of ADR-083 (#3751) once its record is on main, giving a static-subject incumbent a path (ADR-083 rules 4 and 5).
  5. Recovery from the loss of every authenticator (D6), including a change of declared origin (D9), and the response to a first enrolment the owner does not control. The candidate for recovery is delayed re-enrolment from a fresh forge sign-in, paged, and cancellable by any surviving authenticator. The candidate for a first enrolment is that, until the delay has passed, a session minted by a fresh forge sign-in of that identity can cancel the pending enrolment without a proof, with the cancellation audited and paged; a browser-driving agent can use the same session, and the decision must weigh that. A static subject does not enrol (D6) and so has nothing to recover; what a static-subject incumbent does for an action is stated by that action's adopting amendment (D3), and for the captain actions by Direction 4.
  6. Batch confirmation (D2): what a batch proof commits to, its bound, and what happens when one member's target changes.
  7. The gate-level workflow declaration (D3). It extends D3 at that gate only, may only add the requirement, is read from the default-branch blob only (ADR-113 D2), never from a branch under review or a break-glass override, is a schema change decided with the first gate that adopts it, and makes removing a declared requirement a permission widening, which is an amendment of ADR-084 rule 5's permission-drift surfaces.
  8. Authenticator acceptance: whether attestation is required and which credential providers (device-bound, synced, software) satisfy a requirement. It may be declared per action by the adopting amendment, and can only narrow what D1 accepts.

### Validation

A conforming implementation runs against a test-only action that the test registers and the product registry never contains, through the real middleware, session and CSRF path. It demonstrates a successful end-to-end hand-off, with the browser executing exactly the displayed decision and the initiating caller receiving only its result. It shows each of the following, with a counterfactual that fails when the check is removed:

- a presence-required action without a proof is refused on every credential kind, including `session`;
- an invalid signature, modified signed bytes, and completion from a different session or account are each refused;
- an otherwise valid proof presented without the action's required credential kind, scope or eligibility is refused;
- a proof for another decision, a reused proof, an expired proof and a proof whose target has moved are each refused;
- an assertion without the user-verified flag is refused;
- an assertion for the wrong origin or RP ID is refused;
- an assertion from an authenticator enrolled to another identity is refused;
- the statement's acting subject is the completing session's forge identity, never a value the opener or the request supplies, and a challenge issued to one session is refused from another;
- a proof presented on a bearer request is refused, and the opener receives no proof or token;
- opening a pending decision is refused for a target in another account, for a run-bound token, and beyond the per-opener limit; outcome retrieval through the reference by anyone other than the original opener is refused, while a different eligible human session with current target read access can preview and complete the pending decision and is shown the result of its own completion;
- a same-account read-only caller is refused before any pending-decision write;
- a requester without read access to the target, holding a valid reference, sees nothing: its preview, challenge and outcome requests are each refused;
- an agent subject or a delegated request is refused even with a valid proof;
- a further enrolment or any removal without a proof from an already-enrolled authenticator is refused;
- first enrolment succeeds only through D6's fresh-sign-in bootstrap: one from a bearer or from a session not minted by a fresh forge sign-in is refused, and an authenticator inside its first-enrolment delay can neither satisfy a presence requirement nor authorize a further enrolment or a removal;
- first enrolment emits the required pages to the identity and the captain of each repository the identity can act on;
- a lifecycle proof whose affected credential id or public key differs from the committed content is refused, and a successful further enrolment and a removal each emit the pages a first enrolment emits, to the identity and the captain of each repository the identity can act on;
- a credential pending a further enrolment can neither satisfy a presence requirement nor authorize an enrolment or a removal;
- the decision's audit entry names the opener, its credential kind and the pending-decision reference separately from the approver, and the page shows an agent or bearer opener as such;
- where a gate counts several approvals, one proof counts for one approval only;
- a static subject cannot enrol;
- concurrent submissions of one proof have at most one effect;
- a removed authenticator is refused;
- a failed audit write leaves no effect;
- a hand-off reference cannot be exchanged for a session or a bearer, and no route mints a session from a bearer;
- a deployment that declares no sign-in bound, delay or proof lifetime holds the action and never waives it;
- an undeclared or unsupported origin holds the action and never waives it, and a change of the declared origin is audited and paged;
- a forged Origin or Host header changes neither the RP ID nor the expected origin, and an IP-literal origin is refused;
- proposer-supplied text never replaces the object on the confirmation page;
- the audited statement carries identifiers, digests and references only;
- after authenticator removal or rotation, an offline verifier recomputes the challenge and verifies the earlier assertion using only the authorized export, with the live credential store unavailable;
- an offline fixture detects a stale bootstrap sign-in and an overlong challenge despite otherwise valid assertion signatures;
- a pinned test fixes the product registry's contents, empty in this record, so that adding or removing an entry is a visible change.

Recovery and batch cases go with their Directions.
