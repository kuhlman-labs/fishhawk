# ADR-130: Coordinate projects across repositories while preserving repository-local authority

**Status: accepted (ratified 2026-11-04).**

## Context

Prepared at the Captain's request on 2026-10-31.

The [Universe announcement](https://github.blog/news-insights/company-news/github-universe-2026-evolving-every-layer-of-the-stack/) describes agent work across multiple repositories. A solo developer's product may also span application, shared library and infrastructure repositories. A shared outcome can require ordered work even when each repository is governed correctly.

Charter §1 makes the repository the unit of governance and names a future project as a unit of coordination; §2 D9 excludes project coordination from alpha, §3 N9 forbids project-level authority bypass and atomic cross-repository merges, and the former N7 was retired on 2026-10-31 (charter §6 amendment; `.fishhawk/charter.md:35`, `.fishhawk/charter.md:126`, `.fishhawk/charter.md:179`, `.fishhawk/charter.md:184`, `.fishhawk/charter.md:271`). ADR-080 explicitly preserved N7 and made the repository the unit and the solo-captain, local experience alpha's boundary. The Captain opened the strategic direction on 2026-10-31 without making it an alpha requirement.

The decision is whether a project may coordinate existing repository-local campaigns without becoming a new authority above them. A "project" here is not the GitHub Projects board, a tracker replacement, or the ADR-101 authorization charter; because `work-management-v0` already uses the `project:` key for the board connection (`docs/spec/work-management-v0.schema.json:22`), the coordination record's configuration key, routes and audit categories use a distinct identifier. Existing customer trackers remain authoritative for work items.

Separate records: [ADR-127 / #4880](https://github.com/kuhlman-labs/fishhawk/issues/4880), [ADR-128 / #4881](https://github.com/kuhlman-labs/fishhawk/issues/4881) and [ADR-129 / #4882](https://github.com/kuhlman-labs/fishhawk/issues/4882) address repository-local improvement and do not depend on project coordination.

## Options

- **A. Keep cross-repository coordination outside the product indefinitely.** Smallest scope; the captain must maintain shared readiness and dependencies elsewhere.
- **B. A project coordinates goals, dependencies and readiness; repositories retain governance (recommended).** Deliver visibility first, consider execution only under additional explicit contracts.
- **C. One global workflow, captain and policy spanning repositories.** Reject: silently changes repository authority and encourages treating non-atomic merges as one transaction.

## Recommendation

**Option B.**

**D1. Unit and identity.** The repository remains the unit of charter, workflow policy, approvals, delegated capability, run evidence and merge authority. A project is a versioned coordination record referencing existing repository-local campaigns/work items, a shared objective, explicit completion criteria and milestone edges. Project dependency edges relate project-level milestones only. A member campaign's own dependency graph remains derived from its tracker under ADR-047, and no campaign driver reads a project edge as a campaign dependency. The project record owns only its membership, shared objective, completion criteria and milestone edges; the customer's tracker keeps work-item status and relations (charter N2, `.fishhawk/charter.md:161`). The record is a governance input that defines what 'complete' means for the visibility projection, not a plan of the customer's work: it assigns no work, owner, date or priority, and deleting it loses no tracker data. It does not own a second copy of tracker status. Initial scope is repositories within one Fishhawk tenant (one `accounts` row); cross-tenant federation is excluded.

No implicit global captain or inherited token scope exists. Project editing authority and repository action authority are distinct. An authorized project editor may propose an objective or milestone edge; that act approves nothing inside a member repository. Adding a private repository requires authorized membership and must not reveal its existence to unauthorized viewers.

**D2. Visibility first.** The first feature is a read-only projection of member progress and evidence against a human-authored project definition, rendered only to non-run-bound callers on the authenticated bridge under each member repository's own visibility gate; run-bound `mcp:run:*` subjects are refused and no agent tool reads it, so the projection is not built as an agent-readable coordination surface, the class ADR-064 Decision 3 excludes for the board. No agent-kind subject (`backend/internal/server/actor.go:43`) reads it through this surface; the residual (`backend/internal/server/actor.go:40`) is that an agent session presenting a human operator's token is indistinguishable from that human. Collecting or rendering it must not reconcile or mutate member campaign state, dependencies or dispatch holds; the visibility design must provide a side-effect-free source path and test that viewing the project causes no member-state writes. The campaign status read is not such a path today: it reconciles items on read (`backend/internal/server/campaigns.go:2121`) and refreshes dependency edges (`backend/internal/server/campaigns.go:2138`). Show ready, blocked, failed, unknown or stale with the source/cutoff. Call the aggregate complete only when every required criterion has current qualifying evidence; unknown never becomes success. Evidence references bind the campaign instance identity (as the D7 amendment defines it), configuration and commit/artifact identity, not a floating branch or prose claim.

A repo's current merge eligibility is evaluated by that repo, not inferred from an old project snapshot. A hidden dependency cannot be silently dropped to make the project look complete. A full-project verdict requires access to every required member and evidence source. The first projection contract admits no optional reference: every member, criterion and evidence source a definition names is required for the view. A caller who cannot read every one of them, or who does not pass every member's ADR-126 D5 gate, is refused the project view with the same response as a caller with no access to the project at all. Partial views remain unavailable until a reviewed projection contract, introduced by a new ADR carrying amends: ["ADR-130"] (ADR-113 D6), proves that their labels, verdicts, revision indicators and metadata do not disclose hidden membership or dependencies. That amendment's validation must compare otherwise identical authorized views with zero, one and multiple hidden required members. Residual until then: a caller served the view before a private member was added and refused after it can infer the addition; that amendment, or a definition-read audience rule in the D7 amendment, must close or name it.

**D3. Dependencies without workflow conditionals.** A bounded acyclic graph may relate typed project-level milestones such as a required version/artifact being published or a repository-local campaign reaching a completion state the D7 amendment defines (no campaign carries a declared completion criterion today, `backend/internal/campaign/campaign.go:207`). No arbitrary expressions, scripts, new stage types or cross-repo agent tool sharing. Reject cycles and unresolved required references; stale or unverifiable evidence is shown as stale or unknown on the milestone that owns it, and a milestone that depends on that milestone is shown blocked. Referencing a repository does not authorize an agent in another repository to read its code or secrets.

The closed milestone vocabulary and the evidence contract are settled by the D7 amendment. Membership, objective, criteria and milestone-edge changes create a new definition revision and invalidate affected aggregate verdicts.

**D4. Execution is a later phase and a direction requiring its own ADR; this record does not authorize it.** A future execution ADR, a new ADR carrying amends: ["ADR-130"] (ADR-113 D6) and, where a member repository runs under ADR-101, amending ADR-101 only as far as its intake eligibility (D6) and identity (D5) rules must admit a coordinator principal (a coordinator's request is agent-originated as ADR-101 D6 is written), must decide scoped coordinator grants, per-repository principals, idempotent dispatch identities, revocation fencing, reservations/budget ownership and cross-repository recovery; a charter's one-repository, one-host scope (ADR-101 D2, D4) is not widened. Required invariant: dependency readiness only permits a REQUEST through existing repository-local admission; it grants no approval, merge permission, extra budget or bypass. Where the member repository runs under ADR-101, that request is subject to whichever ADR-101 class admits it and to ADR-101 D3's non-delegable list exactly as a local request would be.

The future execution ADR must define durable dispatch identities and reconciliation across retries, project revisions, member removal and re-addition, campaign restarts, and references from multiple projects. A project-definition edit must not by itself cause an existing member operation to be dispatched again. Already-started work is reconciled after restart; the coordinator cannot duplicate a campaign or transplant an approval. Each member's existing merge queue remains authoritative. Define per-repository and project expenditure without double counting before admission. Charter leases and authority are checked again at each side effect; a project grant cannot widen a repository grant.

**D5. Partial failure is explicit.** Repositories cannot be merged atomically. If one member lands and another fails, the visibility projection reports partial delivery, preserves landed evidence and marks dependent project milestones blocked; it changes no member campaign state. A future coordinator may withhold its own undispatched requests. Any hold on repository-local work requires a separately decided, locally authorized mechanism. Recovery, compensating changes and reverts are separate repository-local work requiring their own authorization. Cancelling the project does not force-push, roll back merged changes or silently cancel member runs. Any future cancellation propagation must be explicit and locally authorized.

Cross-repository integration/acceptance evidence must bind exact component versions and a separately approved environment/access contract; repository-local green checks alone do not prove product compatibility. Coordinated releases are a later decision, after real two-repository delivery and recovery experience.

**D6. Charter and phase.** This is a post-alpha direction only; alpha's current done-means are unchanged. The charter already carries this phase boundary: §2 D9 excludes project coordination from alpha, §3 N9 permanently forbids project-level authority bypass and atomic cross-repository merges, and N7 is retired with its identifier never reused (amendment of 2026-10-31; `.fishhawk/charter.md:126`, `.fishhawk/charter.md:179`, `.fishhawk/charter.md:184`, `.fishhawk/charter.md:271`). This ADR decides the technical direction under those ids and changes no charter text. The strategic amendment requested by the Captain does not ratify this ADR's technical decisions (`.fishhawk/charter.md:275`).

Revisit implementation only after a concrete product change spanning at least two repositories demonstrates recurring manual coordination the current campaign surfaces cannot represent. Record that example and the expected reduction in coordination work before ranking an implementation epic. Visibility precedes dispatch; coordinated releases follow only with a separate decision.

**D7. Portability and confidentiality.** Use provider-neutral stable repository/work-item identities, existing tracker adapters and per-source ACLs. Keep original evidence in the run and account audit chains where it was recorded; project observations reference it and do not mint stronger evidence. Apply ADR-126 confidentiality per member repository: a caller who is served sees a member's security-tied items as class and location references only (ADR-126 D3). Security-tied means a source row that is a `category=security` concern, a crew finding from the `security` role or a security finding, or whose opening or resolving reference resolves to one; an item whose security tie cannot be read is treated as security-tied. Filtered views for callers who fail a gate are part of the deferred partial view (D2). Project definition storage, who may revise a definition, APIs, permission checks, audit categories and the visibility contract (the closed milestone vocabulary, qualifying evidence and freshness rules, the producer and consumer of each evidence binding, and how campaign changes and restarts identify new evidence) are settled by a new ADR carrying amends: ["ADR-130"] (ADR-113 D6) before any visibility implementation slice begins; this record does not invent a schema in prose and claim it is executable. The coordination record's configuration key, API routes and audit-category prefix use an identifier distinct from `project`, which `work-management-v0` already uses for the board connection (`docs/spec/work-management-v0.schema.json:22`), so a future declaration surface cannot shadow the board key; the project-level milestone term is likewise kept distinct from tracker milestones and the workflow-v2 `milestone` action class (`docs/spec/workflow-v2.schema.json:1100`).

**Validation.** A future capstone of the D7 amendment joins an application and a library repository's exact evidence bindings into an expected complete verdict, shows that verdict prevented by an unavailable source, revoked access, a changed definition, a stale artifact or a differing campaign, configuration or artifact binding, refuses cycles and unresolved required references, demonstrates no execution and no member-state write, runs a non-Fishhawk fixture through the production resolver per ADR-110 rule 3(a), and shows that an unknown or hidden required criterion never yields complete. A caller refused for one unreadable required member or evidence source receives a response byte-identical to a caller with no access to the project at all, across definitions with zero, one and several such members, including after an authorized caller has populated any cache (any cache is keyed to the caller's scope and is never served across scopes); an operator-agent, run-bound `mcp:run:*` or first-officer-seat subject is refused, including after an authorized non-agent caller has populated any cache, and removing the audience filter must fail that fixture. Before execution is considered, test restart duplication, conflicting local policies, authority revocation between readiness and dispatch, exhausted budgets and one-sided delivery. An unrelated private repository must not leak through graph metadata, and a caller who fails one member's ADR-126 D5 gate receives the same refusal, whether or not any security-tied item exists. A served caller sees each security-tied item, including an item whose security tie cannot be read, as class and location references only, in every milestone state, blocking reason and evidence reference, and a fixture whose source row's tie is unreadable renders exactly as one whose row is a `category=security` concern; removing either the projection reduction or the unreadable-tie classification must fail the corresponding fixture.

## Decision

**Accepted 2026-11-04** by the Captain (1 of 1; manual ratification path, the ADR-113 D2 verb is not yet built; approver and hashes in the ratification comment). **Option B**, i.e. D1–D3 and D5–D7 as stated in the Recommendation, decided as constraints any project feature must satisfy; D4 and coordinated releases are directions requiring their own ADR. It amends ADR-080 only as the Relationships bullet states. This record authorizes no implementation and changes no runtime permission.

## Consequences

- **Value:** the product can eventually represent a customer's whole outcome while preserving repository ownership and existing tools.
- **Costs:** a project definition, cross-source ACL-safe reads, evidence freshness and eventual distributed recovery. The visibility feature is not merely a dashboard filter.
- **Residuals:** cross-repository compatibility and partial delivery remain real operational risks; a shared objective does not make local decisions interchangeable.
- **Phase:** post-alpha exploration; no alpha commitment, hosted-service requirement, second-forge blocker or cross-tenant execution.
- **Sequence:** on ratification D1–D3 and D5–D7 are decided as constraints any project feature must satisfy; D4 and coordinated releases are directions requiring their own ADR; this record authorizes no implementation and changes no runtime permission.
- **Deferred:** partial views, to the amendment that introduces them; and project definition storage, revision authority, APIs, permission checks, audit categories and the visibility contract, to the D7 amendment. This record decides neither.
- **Relationships:** amends ADR-080 only where it relies on N7: the Vocabulary 'Fleet' row's '(N7 still holds)' and the Consequences line 'Unchanged. Non-goals N1–N8' now read against charter D9/N9 and the retired N7; the fleet definition and ADR-080's alpha definition are unchanged. ADR-099 partially supersedes ADR-080 only as to the First officer vocabulary row and does not touch the rows amended here. ADR-047 campaigns, ADR-064 board directionality ("the board is never read back for in-flight decisions — projection only"), ADR-101 grants, ADR-110 portability and repository-local approval/merge contracts remain authoritative. Supersedes none.
- **Charter provenance:** the charter amendment of 2026-10-31 (D9, N9, retired N7) was made by the maintainer in its own change and is already in force. This record decides only the architecture it points to and does not ratify or alter charter text. The amendment opens the direction and records the revisit trigger; it does not enable project orchestration.
