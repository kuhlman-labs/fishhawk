# ADR-131: Distinct dev, stage, and production delivery environments

**Status: accepted (ratified 2026-11-04).**

## Context

Prepared at the Captain's request on 2026-10-31.

This ADR amends Decision §2 of [ADR-073](https://github.com/kuhlman-labs/fishhawk/blob/main/docs/adr/073-kubernetes-helm-single-deployment-substrate.md), tracker [#2298](https://github.com/kuhlman-labs/fishhawk/issues/2298), and refines its Decision §3 for this repository's deployed-service profile.

ADR-073 selected dev and prod and rejected a staging tier 'for now' on cost grounds at pre-revenue scale, with a revisit trigger of prod carrying partner data. That trigger has not fired: no production deployment exists today (`.fishhawk/workflows.yaml:1281-1282`; `.github/workflows/deploy.yml:11-14` is a validation stub). This ADR revisits early, at the Captain's request, because release qualification needs a stable target before the first production deployment, not after the first customer-facing incident. The Captain has now requested a lifecycle with three distinct environments: dev, stage, and production. A changing integration target cannot simultaneously serve as a stable release-qualification target. Separating those purposes makes the evidence attached to a release candidate meaningful.

This is an adoption decision for Fishhawk's own deployment profile, not a requirement for all repositories using the product. It preserves Kubernetes/Helm, external pipeline ownership, the image supply chain, and the exclusion of deployment mechanics from Fishhawk itself. The charter's alpha definition (§2) and exclusion D1 are unchanged; ADR-080 set that boundary.

## Options

- **A. Keep two environments.** Lower operating cost; release qualification competes with continuous integration or pauses it.
- **B. Three logically and operationally distinct environments (recommended).** Dev integrates continuously; stage qualifies a named candidate; production serves real users.
- **C. Require a separate cluster/account for every environment.** Stronger infrastructure separation, but unnecessarily prescribes the topology before resource and threat-model review. Production isolation must be demonstrated even where infrastructure is shared.

## Recommendation

Adopt option B through the following decisions, amending ADR-073's environment policy while preserving its other decisions.

### Three-environment deployed-service profile

**D1. Amend Decision §2.** The two-tier list in ADR-073 §2 is amended to the three-role table below; the `production` row's source and approval cells take effect with D7, and until then D2 states the interval rule. §2's statement that the production tier carries Fishhawk's own dogfood account and, later, hosted Mode 2 partners stands. §2's sentence "Two clusters or two namespaces on one cluster is an implementation choice; the cost note above argues for namespaces at beta scale." is withdrawn: shared infrastructure is governed by D3. The rest of §2 is retired with the list, except its production trigger, which D7 governs.

| Environment | Deployment source | Purpose and authority |
|---|---|---|
| `dev` | Merged `main` heads meeting the pipeline-declared eligibility predicate, which at minimum requires a succeeded image build and signature; deploy each such head or coalesce to the newest one, recording every skipped head | Continuous integration, synthetic data, test integrations. Automatic deployment is an explicit adopted pipeline policy. |
| `stage` | An explicitly selected immutable release candidate | Stable release qualification, production-like topology and relevant configuration, representative synthetic data, controlled test integrations. A qualification attempt owns its target generation. |
| `production` | The approved candidate's same immutable artifacts | Real users and data. Explicit human deployment approval; the release's approved migration and recovery procedures govern execution. |

The stage target is not a continuously moving alias for main. It may be replaced after its qualification attempt ends; records retain which candidate and environment generation were tested. Until the promotion contract (#4898) is ratified and implemented, those records are operator-kept pipeline records. PR previews remain separate disposable targets and are not a fourth required long-lived environment.

**D2. Environment identity is explicit.** `dev`, `stage`, and `production` are display names backed by distinct registered target identities, classes, configuration revisions, and credential boundaries. Legacy names are explicitly mapped during migration — in this repository `staging` becomes the `stage` declaration, and `prod` is kept as the forge environment behind the `production` declaration — and aliases must not evade production controls. In this repository's `.fishhawk/workflows.yaml` the production target, when declared, is declared as the literal `production`, the only name ADR-053 Decision 3's acceptance guard recognises (`docs/spec/workflow-v2.md:599`, `:602`); `prod` is the forge environment name behind it, never the declared environment. The product-side rule that an environment's class is never inferred from a display name or hostname belongs to the promotion contract (#4898); this profile depends on that rule and decides nothing product-wide. The promotion contract (#4898) is the proposed home of the generic environment registration contract; citing it ratifies nothing. Until the promotion contract (#4898), which carries that registration contract, is ratified and implemented, environment identity for this repository is the operator-declared target configuration in the pipeline installation. In that interval ADR-073 §2's production trigger and its required-reviewers gate remain the production policy on record, and this ADR enables no production deployment path of its own. No workflow implements that trigger, and the `prod` environment's main-only branch policy (`scripts/check-deploy-environment.py:14-19`, run from `.github/workflows/infra-apply.yml:67`) does not admit a tag deploy as installed. Any production deployment in the interval also requires an explicit recorded Captain decision and, where infrastructure is shared, D3's isolation assessment.

**D3. Isolate data, credentials, and external effects.** Dev and stage have separate state and target credentials and cannot resolve production credentials. Stage uses sandbox integrations or deliberately constrained substitutes; it must not send real payments, customer notifications, or destructive external actions as a side effect of qualification. Production snapshots are not automatically copied to stage. Any proposed sanitized-data import requires an explicit handling review and cannot be assumed from this decision.

Shared infrastructure requires an operator-authored isolation assessment approved by the Captain before production activation. It identifies the shared components, permitted cross-environment flows, credential and storage boundaries, resource limits, common failure modes, and accepted residual risks. Validation must demonstrate that dev/stage identities cannot obtain production credentials, read or modify production state, or change production workloads, and must exercise the declared resource and failure-containment limits. Missing evidence blocks shared-infrastructure activation. Where infrastructure is shared, this assessment is a prerequisite of production activation. Separate namespaces alone do not demonstrate that isolation. No requirement for three paid clusters is introduced.

**D4. Promote artifacts; declare configuration differences.** Build a candidate once and sign it by digest (a later signature on the same digest is not a rebuild; ADR-137, #4926), qualify its immutable component digests in stage, and deploy those same digests to production. Today `backend-build.yml` builds main heads (`.github/workflows/backend-build.yml:32`) and `backend-release.yml` rebuilds at a `backend/v*` tag (`.github/workflows/backend-release.yml:229`), so a tag build is a different digest from the one dev ran; which build produces the candidate is left to a reconciliation outside this ADR, and no digest is treated as qualified until then. ADR-073 Decision §4's "They stay exactly as they are." (`docs/adr/073-kubernetes-helm-single-deployment-substrate.md:97`) is what a declared amendment of ADR-073 §4 would have to change if that reconciliation changes either workflow; neither this ADR nor, as drafted, the promotion contract (#4898) makes that amendment, so for this repository D4 is policy only, and no digest is treated as qualified, until the separate ADR-073 §4 amendment, ADR-137 (#4926), is implemented. Environment-specific endpoints, capacity, credentials, and flags may differ only through declared target configuration. Stage qualification records those differences and which production claims it cannot establish. Migration and compatibility evidence binds to the deployed artifact set and configuration, not just a source commit.

The stage test configuration is frozen for the qualification attempt. A conflicting deployment or relevant configuration change invalidates the attempt; it cannot silently share an earlier pass. Credentials remain external; records contain opaque version references where needed, never values or guessable hashes of secrets.

**D5. Bootstrap the delivery path early.** Before partners, exercise the D6 recovery drill, including a rolled-back image running against a forward-migrated database, on the stage target; this precondition from ADR-073 Decision 3 does not wait for the promotion contract (#4898). Before committing the broader customer-facing deployed-service release promise, ratify a narrowly scoped bootstrap release brief with synthetic-data criteria and separately approve its target activation. The bootstrap brief follows ADR-079's ordinary feasibility and ratification sequence, as amended by ADR-136 (#4901), with no exemption. Under that brief, the promotion contract (#4898) and the separate ADR-073 §4 amendment named in D4, ADR-137 (#4926), once each is ratified and implemented, demonstrate a minimal signed build, dev deployment, stage qualification, approved production deployment, and recovery. Use the resulting evidence in feasibility review (ADR-079) of the broader release promise. Pipeline workflow changes are operator-authored under the existing `.github/workflows/**` forbidden path (`.fishhawk/workflows.yaml:746-747`); Terraform and Helm changes are governed work and are not path-forbidden today. Fishhawk onboarding does not implicitly create cloud resources, register production targets, or grant deployment authority.

The exact production activation is separately approved; this ADR itself creates no environment and changes no live pipeline configuration. The bootstrap demonstration can precede broad product functionality without becoming a condition on ADR-080's local-only alpha.

**D6. Refine Decision §3: recovery is exercised against data evolution.** Keep Helm `--atomic --wait` as the pipeline's rollout recovery mechanism. Require stage evidence for forward migration, old/new application compatibility where promised, a failed rollout, and recovery with a forward-migrated database. Prefer staged expand/migrate/contract changes when compatibility requires them; schema contraction and irreversible deletion are separately approved steps.

Recovery objectives, backup ownership, restore evidence, and the point beyond which rollback is unsafe are declared per release/service. A successful Helm rollback does not establish database recovery or behavioral correctness. Observe and verify the resulting state. Progressive delivery controllers remain deferred; three environments do not require a canary controller.

**D7. Production triggers are adopted configuration, not incidental tag effects.** D7 takes effect only when the promotion contract (#4898) is ratified and implemented. Until then ADR-073's text on the production trigger stands, and no production promotion is enabled by this ADR. When D7 takes effect it retires ADR-073 §2's rule that production deploys from a `backend/v*` tag. No workflow implements that rule today, so the change is to policy, not to a live path: `.github/workflows/backend-release.yml:36-38` triggers on that tag and publishes images and a GitHub Release (`.github/workflows/backend-release.yml:285-286`), and `.github/workflows/deploy.yml:11-14` is a validation stub. A tag may identify/publish a candidate; production dispatch must consume the exact approved candidate and target intent under that contract. Required GitHub environment reviews remain an additional provider control. This repository's pipeline installation must prevent tag pushes or manual workflow dispatch from bypassing that contract.

**D8. Phase boundary.** This is the target profile for Fishhawk's deployed service. It does not require Kubernetes or three environments for the local solo-captain alpha, nor add obligations to unrelated repositories. Scheduling the deployed-service work and its live acceptance is a separate Captain decision.

## Decision

**Accepted 2026-11-04** by the Captain (1 of 1; manual ratification path, the ADR-113 D2 verb is not yet built; approver and hashes in the ratification comment). **Option B**, i.e. D1–D8 as stated in the Recommendation, decided now. It amends ADR-073 §2 and §3 as D1 and D6 state. ADR-073 §4 is amended separately by ADR-137 (#4926), and for this repository D4 is policy only until that record is implemented. This record enables no production deployment path, changes no running environment and grants no authority.

## Consequences

Stage adds infrastructure cost and maintenance but prevents integration churn from invalidating release evidence. Environment differences remain a source of uncertainty and must be recorded rather than described as perfect parity.

After ratification: update the deployment runbooks, operator-authored pipelines, environment registrations, and relevant Helm/IaC configuration. Reconcile the actual current files before editing: the historical ADR body names paths that may since have moved or been removed. In the interval before the promotion contract (#4898), D2 states the production policy.

- **Costs:** `scripts/check-deploy-environment.py:12` and `.github/workflows/infra-apply.yml:34` accept only `dev` and `prod` today, so adding `stage` changes both, and `prod` remains the GitHub environment name that D2's `production` display name maps to. This repository's `release` workflow deploy stage (`.fishhawk/workflows.yaml:1275-1286`) still dispatches `deploy.yml` at `git_ref: main` with `allowed_environments: [staging]`; its target ref and environment name are reconciled with D1 and D2 before the stage target is activated. `allowed_environments: [staging]` is a live name, and ADR-053 Decision 3's staging-only acceptance guard (`docs/spec/workflow-v2.md:602`) recognises only the literal name `production`; `stage` is ADR-053's staging target, the migration maps `staging` to `stage`, and any Fishhawk-side declaration of the production target spells `production` (D2), never `prod`.
- **Residuals:** stage's cost and the operating load of three environments on one developer; synthetic-data fidelity, since stage qualifies against synthetic data rather than production's. How stage represents a multi-cell production and ADR-062's directory service is not decided here; the Captain's scheduling decision under D8 must name where it is settled before stage is activated, and ADR-062's per-region deploy topology issue is the natural home.

### Validation

Each clause below naming a Fishhawk record describes the target state of the promotion contract (#4898); until that contract is ratified and implemented, those records are the operator's pipeline records.

- Stage and dev target identities, credentials, and storage cannot be confused or cross-resolved; the operator's pipeline enforces this.
- The `prod` and `staging` names resolve to registered `production` and `stage` targets and no alias lowers a production control; the operator's pipeline enforces this by binding each Fishhawk-declared target to exactly one forge environment at the deploy workflow's job-level `environment:` (the product passes no environment to the pipeline; `backend/internal/server/approvals.go:5403-5411`, `.github/workflows/deploy.yml:16-34`), and `scripts/check-deploy-environment.py` verifies only that forge environment's protections.
- Stage qualification sends no real payments, customer notifications, or destructive external actions (D3); the operator's pipeline enforces this through stage's target configuration.
- Dev/stage identities cannot obtain production credentials, read or modify production state, or change production workloads, and the declared resource and failure-containment limits are exercised (D3); the operator's platform and credential configuration enforces this, and the operator's isolation assessment records the demonstration.
- The dev pipeline cannot deploy to the stage target, and a stage deployment or relevant configuration change made during a qualification attempt invalidates that attempt; the operator's pipeline enforces the target restriction, and a Fishhawk record carries the invalidation.
- Once the separate ADR-073 §4 amendment (D4), ADR-137 (#4926), is implemented, production deployment uses the exact stage-qualified artifact digests; the operator's pipeline refuses a tag resolving to a different digest, and the Fishhawk deploy record names the digests it consumed. Until then this bullet is not checkable, and D2's interval rule governs until the promotion contract (#4898) is ratified and implemented.
- Before production activation, the operator demonstrates that production dispatch stays within D2's interval rule until the promotion contract (#4898) is ratified and implemented; before D7 takes effect, this bullet tests only that rule. Once D7 takes effect, the operator also demonstrates that tag pushes and manual workflow dispatch cannot change production without a valid approved candidate and target intent, even when they name the correct stage-qualified digests. The operator's pipeline enforces these refusals, and a Fishhawk record retains the activation evidence.
- Relevant stage drift invalidates its qualification attempt; expected environment differences are visible; a Fishhawk record carries both.
- Rollback and restore drills cover a migrated database and distinguish rollout completion from behavioral recovery; the operator's pipeline runs the drills, and a Fishhawk record retains their evidence.
- The D5 bootstrap demonstration completes a signed build, dev deployment, stage qualification, approved production deployment, and recovery under its ratified brief; a Fishhawk record retains the evidence for the feasibility review.
- This ADR introduces no product default: no product code reads the names `dev`, `stage` or `production` from this record (the literal `production` the ADR-053 rule 3 guard recognises predates it and is unchanged), and a repository with a different layout operates under its own declarations.
