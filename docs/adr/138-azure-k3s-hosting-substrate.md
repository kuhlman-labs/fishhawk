# ADR-138: Azure with single-node K3s as the hosting substrate (supersedes ADR-001)

**Status: accepted (ratified 2026-11-04).**

## Context

Prepared at the Captain's request on 2026-11-04.

ADR-001 chose the cloud: "Recorded 2026-04-30: AWS." (`docs/adr/001-cloud-target-aws-gcp-other.md:30`). ADR-073 §1 chose "EKS — stay on AWS" (`docs/adr/073-kubernetes-helm-single-deployment-substrate.md:70`), accepting "roughly **$73/month per cluster control plane before nodes, per regional cell**" (`:74`).

The tree shows nothing hosted: `.github/workflows/deploy.yml:11-14` is a validation stub, and `.fishhawk/workflows.yaml:1282` says "no production target exists to deploy to". `infra/terraform/` is AWS only (`providers.tf:4`, `backend.tf:25`). The tree cannot show what a cloud account holds (Consequences, AWS/ECS retirement).

On 2026-11-04 the Captain confirmed accepting the substance of the 2026-11-01 note in #4902: Azure replaces AWS; Kubernetes and Helm are kept, on single-node K3s rather than AKS; the initial infrastructure budget is about USD 120/month; there are three environments. That confirmation is this record's authority. The note itself changes no record (ADR-113 D6), and #4902 and #4903 are sources of proposed detail only.

## Options

- **A. AWS/EKS (ADR-073 §1).** Gain: no amendment; a managed control plane and multi-node path; ADR-073 §4's kept Terraform stays usable, though it has never applied (`:24`); ADR-001's reason holds: "AWS is the default expectation in fintech/healthtech" (`:44`). Cost: the $73 figure alone is about 60% of USD 120 before any node, database or storage.
- **B. Azure/AKS.** Gain: a managed control plane and multi-node path, so less lifecycle work than C and no substrate change on growth (assumption 1). Cost: all Terraform is rewritten; ADR-001's procurement reason is given up; no AKS price is sourced here, so its fit to the budget is not established.
- **C. Azure/K3s on one VM (recommended, per the Captain's decision).** Gain: an operating simplification, one VM with no managed-cluster service to configure; #4902 estimates USD 105-113/month before tax, model usage and CI (assumption 2); same chart and rollout command (assumption 3). No cost advantage over B is claimed: D2 rests on the Captain's confirmation, as D1 does. Cost: the same rewrite and procurement loss; no high availability; one failure domain for every environment; the control plane and OS join the lifecycle ADR-073 `:107` accepted. No chart file or deploy doc names K3s, so the first install is unexercised. Partners converge with Fishhawk on the chart, not the distribution.
- **D. AWS/K3s on one instance.** Gain: no EKS fee; ADR-073 §4's Terraform stays adaptable. No cost comparison separates C from D; the choice of Azure rests on the Captain's stated reason (D1).

## Recommendation

Adopt Option C through D1-D6. This record supersedes ADR-001 in full and amends ADR-003, ADR-009, ADR-016 and ADR-073 only as D1 and D2 state.

**D1. Azure replaces AWS as the cloud for Fishhawk's own hosted service.** This supersedes ADR-001 in full: its "Recorded 2026-04-30: AWS.", service list and region (`:30-39`) no longer select anything, and its procurement reasoning (`:44`) is given up. The Captain's stated reason: "Technical skills align with Azure", meaning the maintainer's operating skills. Region stays open. No other repository or Mode 1 install gains a requirement. ADR-003's "AWS S3 (production)" (`:36`) no longer selects a production store; its layout rules (`:38-44`) and local-development decision stand. The production object store (an Azure-native implementation behind `tracestore.Storage`, `backend/internal/tracestore/tracestore.go:92`, or an S3-speaking store) is decided by its own plan under those rules, with each S3-named rule (`:42-43`) mapped to the chosen store's equivalent, or recorded as unmet and approved as unmet by the Captain, not here. ADR-016's choice of Terraform for everything under `infra/terraform/` stands. Its AWS-specific items (`:40-41`, `:43`: the AWS provider pin, the S3/DynamoDB state backend and the OIDC-to-IAM deploy role) lapse with D1; the no-long-lived-keys property they carried stands as the default for every deploy credential, and a long-lived credential is admissible only where the first reviewed provisioning plan (Validation 1) records why a federated one is unavailable and the Captain approves that departure. Their Azure equivalents are decided by that plan, not here. Its workspace model (`:42`) stands for environment-owned resources, as workspaces `dev`, `stage` and `production`; the state unit that owns the shared node is decided by the infrastructure design D4 requires, not by any environment's workspace. This record amends ADR-003 and ADR-016 to that extent. ADR-009's AWS hosting selections (`:31-40`: ECS Fargate, CloudWatch Logs, AWS Secrets Manager, OIDC to IAM) no longer select anything; ADR-073 already displaced its ECS runtime. Its container image decisions stand. This record amends ADR-009 to that extent. #4902's Blob, Key Vault and managed PostgreSQL are not decided here; the off-node database and the secret store D4 implies are decided by the first reviewed provisioning plan (Validation 1), under ADR-131 D3's credential and storage boundaries.

**D2. The substrate is K3s on one Azure VM; the chart stays the single artifact.** This amends ADR-073: it replaces §1 (`:70-74`), and §4's "**Keep and adapt** `network.tf`, `rds.tf`, `dns.tf`, `secrets.tf`, `iam.tf`." (`:93`) lapses, since those files declare AWS resources (for example `infra/terraform/rds.tf:58`). The rest of ADR-073 stands as amended: Option 2 (`:68`), §2 as ADR-131 D1 amends it, §3 as ADR-131 D6 refines it, and §4's delete list, with §4's image-supply-chain sentence as ADR-137 amends it.

**D3. The initial infrastructure budget is about USD 120/month.** It binds the estimate: the figure is the monthly Azure infrastructure charge for the three environments before tax, including state storage, off-node state and backups, networking, DNS and logging, and excluding model usage and CI minutes. The first provisioning plan's itemised estimate on that basis is reviewed against it, and a figure above it returns to the Captain. It is not a billing cap (assumption 4). It lowers no control: where the ADR-131 D3 assessment needs separation the figure cannot buy, the choice is more budget or no production activation.

**D4. `dev`, `stage` and `production` share the one node.** ADR-131 D1 decides the roles; this record decides placement only, and `production`'s is conditional on the composition below. Each environment has its own namespace, chart release, credentials and application data; its deploy identity on the K3s API is scoped to that namespace, no deployment pipeline holds a cluster-wide credential, the identity that creates or changes the node is the shared-infrastructure authority the design below separates from every environment's deploy identity and is never held by an environment's automatic apply or deploy path, and the node's admin credential is held by the operator outside any pipeline. Namespaces, each environment's Role and RoleBinding, ResourceQuota and NetworkPolicy objects, and the minting of each deploy credential are created by the shared-infrastructure authority, never by an environment's own deploy identity. Before enabling any apply path, an operator-authored infrastructure design, approved by the Captain and preceding the first provisioning plan, must identify the sole Terraform state owner and writer for shared resources, separate shared-infrastructure authority from environment deployment authority, and define serialization across every path that can change the shared node. Durable application state stays off the node: the chart offers in-cluster Postgres and RustFS only "for local development" (`deploy/helm/fishhawk/Chart.yaml:7-8`). Cluster state does not: single-node K3s keeps its datastore, including every environment's Secret objects, on the node's disk (assumption 6), so node-level access reaches all three environments' credentials. The ADR-131 D3 assessment names that path and its control; until it does, `production` carries no credential on the node. No runner, agent or image build runs on the node, and fishhawkd's local reviewer subprocess flags (`FISHHAWKD_ENABLE_LOCAL_CLAUDE_REVIEWER`, `FISHHAWKD_ENABLE_CODEX_REVIEWER`) stay off there.

**D5. E62 #2299.** Its aim stands: the hosted service on Kubernetes through the chart customers install. So do items 2 to 6 (chart posture, Helm deploy pipeline, rollback drill, ECS removal, docs), under ADR-131 and ADR-132 where they govern. Item 1's EKS provisioning and AWS Terraform adaptation lapse, as does its `dev` + `prod` topology. Whether E62 or #4902/#4903 carries the work is open for filing; nothing here forces it.

**D6. Authorship and authority.** Infrastructure and workflow changes under this record are operator-authored and human-led: a path control for `.github/workflows/**` (`.fishhawk/workflows.yaml:747`), procedure for `infra/terraform/` (ADR-073 `:110`), which ADR-131 D5 notes is "not path-forbidden today". This record provisions nothing, enables no production deployment and grants no authority. Scheduling stays with ADR-131 D8; charter D1 is unchanged (`.fishhawk/charter.md:118`).

### Composition with ADR-131, ADR-132, ADR-133 and ADR-137

Where one of these records constrains the scope of #4902 or #4903, that record governs the issue. The section decides nothing beyond D1-D6.

- **ADR-131.** A shared node triggers its D3: "Shared infrastructure requires an operator-authored isolation assessment approved by the Captain before production activation." and "Separate namespaces alone do not demonstrate that isolation." The node, its OS, the K3s control plane and datastore, any off-node store or secret vault serving more than one environment, and any cluster-scoped operator or store object through which a namespace obtains values from that vault (the chart's `externalSecrets` mode references a `ClusterSecretStore` by default, `deploy/helm/fishhawk/values.yaml:570`) are shared components the assessment must identify and bound. "Missing evidence blocks shared-infrastructure activation." This record enables no production path ADR-131 holds back; its D2 interval rule and D7 apply as written. Its D2 names govern: #4902's `staging` and `prod` read as `stage` and `production`.
- **ADR-132.** No change. The guarded promotions to prod that #4902 and #4903 describe wait on it: "Guarded production promotion is unavailable until ADR-121's bindings and this contract are implemented"; a production deployment under ADR-131 D2's interval rule is held by that rule, not by this bullet.
- **ADR-133.** No change. "Production smoke cannot be enabled until the promotion contract (#4898), its checker-identity extension and ADR-121's bindings are implemented." Its D4 holds on a shared node.
- **ADR-137.** No change to where images come from. The chart pulls by tag today (`deploy/helm/fishhawk/templates/_helpers.tpl:307`), so digest deployment is owed chart work.

## Decision

**Accepted 2026-11-04** by the Captain (1 of 1; manual ratification path, the ADR-113 D2 verb is not yet built; approver and hashes in the ratification comment). **Option C**, i.e. D1–D6 as stated in the Recommendation, decided now. It supersedes ADR-001 and amends ADR-003, ADR-009, ADR-016 and ADR-073 only as D1 and D2 state. This record provisions nothing, enables no production deployment and grants no authority.

## Consequences

- **Subject.** `infra/terraform/` moves from AWS to Azure, and `.github/workflows/infra-apply.yml` is its AWS-credentialed apply path (`:95`).
- **Costs.** A push to `infra/terraform/**` fires that workflow (`:22-26`) with AWS credentials, so before Azure Terraform lands under that path the workflow is narrowed so that it cannot apply it, which is a change, not a removal or replacement of the AWS management path, so ADR-134's procedure is not yet engaged. The only durable trace store wired is S3 (`backend/cmd/fishhawkd/serve.go:2839`), so it needs an Azure implementation or an S3-speaking store (assumption 5), and the chart's AWS-named credentials follow (`deploy/helm/fishhawk/README.md:421-422`). The chart expects an IngressClass and ClusterIssuer it does not install (`deploy/helm/fishhawk/values-prod.yaml:31`, `:37`), and no template declares a NetworkPolicy, ResourceQuota or Role; installing the ingress controller and cert-manager on the node, outside any environment's deploy pipeline, or changing the class, is owed by the operator, and both are shared components for the ADR-131 D3 assessment.
- **AWS/ECS retirement also follows ADR-134.** Before removing or replacing its management path, the operator records an authoritative resource and state inventory, with unknown or inaccessible accounts remaining unresolved. The removal boundary follows ADR-134's dossier, readiness and authorization procedure, which first needs the ADR-134 D8 declarations (the approvals predicate and the dossier home) this repository does not carry today; until they land, no AWS management path is removed. Any discovered live resources require an explicit migration or retirement decision; removing code grants no authority to delete resources, state, backups or retained data.
- **Positioning.** ADR-001's procurement reason (`:44`) is given up: the hosted service no longer runs on the cloud the v0 ICP expects. Mode 1 partners install the chart in their own perimeter (ADR-073), which bounds the effect to Mode 2.
- **Single-node residuals.** Where no procedure is decided here, the artefact is owed by the operator.
  - **No high availability.** A node failure, reboot or upgrade stops all three environments; no uptime commitment can rest on this.
  - **Noisy neighbour.** `dev` deploys merged `main` heads (ADR-131 D1) on the node that hosts `production`; a dev defect or rollout competes for the node's resources, and on a burstable VM can spend the CPU credits all three share (assumption 7). The ADR-131 D3 assessment declares and exercises the per-namespace resource limits; none exist in the chart today.
  - **Upgrades.** Owed: a K3s and OS upgrade procedure, saying how an upgrade reads under ADR-131 D4 and ADR-132 D5.
  - **Backup and restore.** Owed under ADR-131 D6: Postgres, trace bundles, secrets, cluster state (assumption 6).
  - **Node loss.** All three stop. Keeping application databases and trace bundles off-node avoids losing those stores solely through node loss. Recovery of the complete service remains conditional on an inventory of node-local cluster state, secrets and keys, with each item either reproducible from an external source or recoverable from a tested off-node backup; until demonstrated, data loss and incomplete recovery remain residual risks. Owed: a rebuild runbook with measured recovery times.
  - **Exit.** The chart is what moves (ADR-073 `:39`). Owed: a runbook to a larger target; none is chosen here.
  - **Revisit trigger.** Any of: the assessment cannot support `production` here; partner data in production; a customer uptime commitment; measured load beyond the node; actual cost above D3's figure; a tenant whose data must sit in another region (ADR-057).
  - **Cells.** The node is one cell at most; ADR-131's residual on ADR-062 stands.
- **Assumptions to verify before provisioning.** (1) AKS offers a managed control plane and multi-node path. (2) #4902's prices, SKUs and total. (3) K3s runs the chart and `helm upgrade --atomic --wait` unchanged, and its bundled ingress is not the `nginx` class `values-prod.yaml:31` names. (4) Azure budget alerts notify and do not stop spending. (5) Azure Blob has no S3 API. (6) Single-node K3s keeps cluster state on the node's disk. (7) #4902's B2ms VM is burstable, and spent CPU credits throttle it.

- **Related:** ADR-057, ADR-062, ADR-113, ADR-131, ADR-132, ADR-133, ADR-134, ADR-137, E62 #2299, #4902, #4903.

### Validation

1. A reviewed Terraform plan and price estimate precede any provisioning, at or under D3's figure or with a recorded Captain decision raising it.
2. Once ADR-134's procedure completes and the replacement lands, `infra/terraform/` and `.github/workflows/` hold no AWS provider, AWS credential step or ECS file; the replacement provider, state backend and deploy identity are decided by the first reviewed provisioning plan. Before the AWS management path is removed or replaced, the operator's inventory of AWS resources and state exists and names what it could not resolve, and no resource, state, backup or retained data is deleted without ADR-134's separate authorization.
3. On `dev`, demonstrate first-install and failed-rollout behavior on K3s (assumption 3). Before partners, perform ADR-131 D5-D6's recovery drill on `stage`, including forward migration, old/new application compatibility where promised, a failed rollout and recovery with the forward-migrated database; verify the resulting application behavior separately from Helm's completion status.
4. `production` does not activate until the ADR-131 D3 assessment exists, approved by the Captain, with its demonstration covering node-level paths (the node's cloud identity and metadata endpoint, the cluster admin credential, host access, the admission control bounding what a namespace-scoped identity's workloads may request of the node (privileged containers, host namespaces and host paths), the shared datastore, the path by which each environment's workloads obtain secrets from any shared secret store and the identity that path presents to the store, the K3s API's network exposure and each pipeline's route to it, each environment's deploy credential's form, custody and namespace scope, and the shared-infrastructure apply identity's rights over the node), and ADR-131 D2 permits the dispatch. The demonstration lists the workloads running on the node and shows none is a runner, an agent or an image build.
5. A node rebuilt from source redeploys a recorded release on a non-production environment, with durable state intact and the time recorded. Separately, restore the inventoried persistent stores and non-reproducible secrets or cluster state into an isolated recovery target, verify application behavior and data completeness, and record achieved recovery time and data loss against the service's declared recovery objectives.
6. Each listed assumption is checked against the provider's current documentation before the first plan.
