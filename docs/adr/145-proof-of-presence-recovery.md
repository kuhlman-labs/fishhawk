# ADR-145: Recovery and the response to an unowned enrolment for the proof of presence (amends ADR-144)

**Status: accepted (ratified 2026-11-13).**

## Context

ADR-144 D6 holds every adoption until recovery from losing every authenticator, and the response to a first enrolment the owner does not control, are decided. ADR-144 D6 reserves both matters to an amendment of ADR-144; this is that amendment. Direction 5's candidates rest on "a fresh forge sign-in".

- The product's own clients cannot force a fresh forge sign-in: neither its GitHub nor its GitLab authorize request forces re-authentication (`backend/internal/auth/github_oauth.go:115-123`, `gitlab_oauth.go:94-104`). As of 2026-11-13, no documented GitHub parameter forces re-authentication or returns an authentication time; this is an assumption. A process driving a signed-in browser completes the redirect unaided. A session records issue, last use and expiry, not a forge authentication time (`backend/internal/auth/auth.go:103-110`), and lives 24 hours sliding, 7 days absolute (`auth.go:51-54`).
- Run events reach people as forge comments to the captain (`backend/internal/issuecomment/ping.go:547-551`) and through the webhook, Slack and email sinks: run events only, one static recipient set, at most once (`docs/notifications.md:9`, `:81`, `:95`). No path delivers identity events; the obligation to page a captain is recorded only (`backend/internal/captain/README.md:50-52`).
- Nothing in the product is pending, cancellable and then effective after a delay.

## Options

- **A.** Self-service recovery from a forge sign-in, delayed and paged (Direction 5); the sign-in adds nothing an agent in the browser lacks.
- **B.** Re-enrolment approved by a second enrolled human; no identity, a captain included, has power over another's credentials (`backend/internal/captain/transition.go:88-197`), and a single operator has none.
- **C.** Two authenticators; recovery by an off-machine code, a delay and a delivered notification, cancellable by any session of the identity.
- **D.** No recovery.

## Recommendation

Option C.

- **R1. Two authenticators.** A presence requirement is that of an action in the D3 registry or of a gate-level declaration (Direction 7). An identity satisfies one only with at least two enrolled authenticators, each past any delay applying to it. The server counts distinct enrolled credential ids, once each across synced copies; the count shows no independence of devices, providers, sync accounts or failure domains, nor a lost credential. Refusing an authenticator class is Direction 8. D6's proofs that manage authenticators, R2's reissue and R7's removal by proof are outside this rule: each needs a proof from one enrolled authenticator past its first-enrolment delay. An identity left with one enrols another this way; a further enrolment has no delay of its own. An identity with no enrolled authenticator, other than through R8, enrols again as a first enrolment under D6 and R5, and any outstanding recovery code is void.
- **R2. Recovery codes.** Whenever an identity comes to meet R1 while it has no outstanding code set (the first time, after a recovery, or after enrolling again under R1), the server issues single-use codes from a cryptographically secure random source, each of at least 64 bits, stored only in a form resistant to offline guessing (a keyed digest or a salted password hash). The set size is fixed and pinned by test; the remaining count is shown. Codes issued when the identity comes to meet R1 are shown once, only in the Web UI session completing that enrolment; replacement codes issued by a proof-authorized reissue are shown once, only in the session completing that reissue. Both displays instruct the person to keep the codes off the machine; codes never appear in an audit entry, notification or log. A lost display is answered by a reissue with a proof, which voids the old set. Refused codes are rate-limited per identity over a window, never by a permanent lock nor so as to block R4 or cancellation; the first refusal in a window is audited and delivered (R6), with a count of later refusals at the window's end. A code is not a proof: it satisfies no presence requirement and only opens a recovery (R3). Residual: a process driving the browser at display reads them.
- **R3. Recovery.** A Web UI session of the identity, minted by a forge sign-in within D6's sign-in bound, opens a recovery with a valid code and registers a new authenticator as pending; the server does not infer or verify loss. Opening consumes the code, holds the identity's presence-required actions at once, and voids any credential pending a further enrolment. At most one recovery is pending per identity. It takes effect when the recovery delay (R5) passes without cancellation (R7): the pending authenticator becomes the only enrolled one, past its first-enrolment delay since the recovery delay is never shorter, and every earlier authenticator, outstanding code, unconsumed challenge and other pending item of the identity is void. The recovered identity cannot complete a pending decision (D4) opened before the effect; another eligible session can, and its opener can open it again; earlier proofs stay verifiable offline (D5). Effect and cancellation are atomic, audited and survive a restart: never two activations, nor one after a committed cancellation.
- **R4. Recovery without a code.** An identity that cannot open a recovery under R3, having no recovery code, is recovered only by the deployment holder: a command run on the server host with the deployment's own host privilege, reachable through no HTTP route, MCP tool, bearer or session. It names the identity by subject and account and authorizes it to open one recovery without a code within a time bound the command states, capped by a pinned maximum; the authorization satisfies no presence requirement and is not a grant in D8's sense. The identity then proceeds as in R3 from its own Web UI session, under the same delay, notification and cancellation. The command can also, on its own, revoke every session of that identity. Each use is a chained audit entry recording the invoking host user as the server's claim, and is delivered (R6). Residual: the identity's first Web UI session to open the recovery uses it; the owner's remedy is cancellation (R7). Every recovery path needs a Web UI session of the identity, and ADR-123 Decision 1 holds: "Sessions are minted only by the forge sign-in callback." Losing the forge account is outside this amendment.
- **R5. Delays.** A first enrolment counts toward a presence requirement only after at least 24 hours; a recovery takes effect only after at least 72. A deployment declares both and may lengthen either, never below these floors; the recovery delay is never shorter than the first-enrolment delay. A declared delay below a floor, a recovery delay declared shorter than the first-enrolment one, or an undeclared recovery delay, holds every presence-required action with a diagnostic, as a missing declaration does under D6. Recovery openings are rate-limited per identity over a window, the limit and window pinned by test, never by a permanent lock; a limit that is reached ends when the window passes.
- **R6. Notification that leaves the host.** Without a declared identity-event channel, a presence-required action is held with a diagnostic naming the missing declaration. The server refuses a channel whose declared endpoint host (webhook URL, Slack URL, SMTP relay) is a loopback or IP-literal host or the Web UI origin; it does not check what a name resolves to, so this guards against misconfiguration and does not show the endpoint is off the host. That each declared channel reaches a person outside the browser the ceremony runs in, and its recipients the person of each identity that can enrol, is the operator's check, recorded with D9's deployment validation. Delivered to the deployment's declared recipients: every enrolment, removal, recovery opening (naming R3 or R4), cancellation, recovery effect and code issue; refused codes as R2 states; every change to a declaration that D6, D9 or this amendment names. The server records the channel set and recipients as a digest, and the declared origin, RP ID, sign-in bound, proof lifetime and both delays as audited declarations, and compares them at start, where a difference is a change. A change of channel or recipients also goes to each earlier channel still declared, and voids the clock-start receipt of each pending first enrolment and recovery, whose event the server delivers again under the new declaration; only a recorded success of that delivery restarts its full delay, and earlier receipts cannot start or advance it. Further enrolments and pending decisions are unaffected. Success is the endpoint's acceptance (a 2xx for a webhook or Slack channel, the SMTP server's for email), never a claim or enqueue. Each success is its own chained audit entry bound to the event and the declaration used, and only one that starts a delay also binds the pending item, identity, pending credential and delay in force. A failed audit write starts no clock; a duplicate or stale outcome advances no other item. A pending first enrolment's or recovery's delay starts at the first recorded success on any declared channel; every channel is still attempted, and retried with a backoff until it succeeds or the item ends; failed attempts are audited up to a per-item bound and a success always; the backoff and the bound are fixed and pinned by test. An item without a success stays pending and cancellable, shown as undelivered to the identity and by R4's command. Where no channel delivers, the exit is the deployment holder repairing or re-declaring it, after which retry resumes. Identities without a pending item are unaffected. Enrolment and recovery entries carry the delays in force, the reference and time of the success that started it, and the time of effect or cancellation, as server claims in D5's authorized export. Residuals: acceptance is not receipt by a person; a channel a change drops receives nothing; the notification protects no person the declared recipients miss, nor one whose channel the enrolling process reads.
- **R7. Cancellation, and an enrolment the owner did not make.** Before it takes effect, any pending enrolment, first or further, or pending recovery is cancelled by any Web UI session of the identity without a proof, or by a proof from any enrolled authenticator of the identity. A cancellation is audited and delivered (R6) with the count of cancellations across the identity's pending items, and makes no other change, except that a cancelled recovery's hold ends; a consumed code stays consumed. Cancellation grants no completion authority. While a first enrolment is inside its delay, D6 makes any other enrolment a further one needing a proof past delay, so a second unproved enrolment is refused and audited, and delivered as R2 delivers refused codes; the owner's response is to cancel the first. A process holding a session of the identity can deny its enrolment or recovery indefinitely by cancelling; this is accepted. The response: contain the browser or host, revoke the identity's sessions (logout revokes only the caller's, `backend/internal/server/auth.go:369-372`; revoking all is R4's command), restore trusted access, and open a new attempt under the full delay and notification; a spent code set ends at R4. No count or threshold ever activates anything. A process with a recovery code or deployment-holder authority can complete a recovery with a credential it controls if the owner does not cancel in time. An authenticator the owner did not enrol, past its delay, is removed by a proof from another enrolled authenticator or, where there is none, by recovery: R3 where the identity holds a recovery code, otherwise R4. Decisions it approved are identified from the audit record (D5) for review and are not undone.
- **R8. A change of RP ID.** The server records the RP ID from the first declared origin. A later declaration with a different RP ID holds every presence-required action with a diagnostic and invalidates nothing until the deployment holder confirms it by a command of R4's class; confirmed, it is a change of RP ID, audited and delivered (R6), and invalidates every enrolled authenticator permanently (D9); a return to the earlier RP ID restores none. Every pending enrolment or recovery is bound to the RP ID in force when it opened and is void on a change. Each identity that had an authenticator past its first-enrolment delay is in recovery: it satisfies no presence requirement until it completes R3 or R4 under the recovery delay, which the change shortens for no one. An identity whose only authenticator was pending or inside its delay enrols again as a first enrolment.

**What this changes in ADR-144.** Where this amendment and ADR-144's text differ, this amendment governs. R1 adds a condition to D1 and D6 and removes none: where D3, D6 and the Enablement prerequisites speak of an identity with no enrolled authenticator, or of enrolment readiness, they now cover every identity that does not meet R1. In D6, R5's floor replaces the "non-zero minimum that the implementing change fixes" and the first-enrolment delay starts as R6 states; "this record supplies no cancellation path for an owner who does not control the first authenticator" no longer holds (R7), and D6's and D8's "detection time only" narrow accordingly. A recovery that takes effect (R3, R4, R8), and R7's cancellation of a first enrolment still inside its delay, are the only exceptions to D6's rule that a further enrolment or a removal needs a proof, and to the matching Validation item; a first enrolment inside its delay is enrolled for R7's cancellation by proof and for nothing else. A recovery's authenticator is registered under R3, not D6's first-enrolment bootstrap or its Validation item. R6's channel and R5's recovery delay are further declarations whose absence holds the action, beside D6's sign-in bound, delay and proof lifetime. D6's pages to the identity and the captain stand; its last sentence, the hold, is lifted as the Consequences state. R8 discharges D9's instruction to Direction 5, and puts a hold and the deployment holder's confirmation before D9's invalidation of authenticators on a change of RP ID; a change of origin that keeps the RP ID stays under D9. Direction 5 is decided: its two candidates, fresh-sign-in recovery and cancellation by a freshly signed-in session, are not adopted; its static-subject sentence stands. In the Decision section, "with recovery and each adoption as named directions" now covers adoption only. "Recovery and batch cases go with their Directions." now covers batch cases only; recovery cases are this amendment's Validation.

## Decision

**Accepted 2026-11-13** by the Captain (manual ratification path; approver, errata and hashes in the ratification comment). **Option C**, i.e. R1 to R8 as stated in the Recommendation, with "What this changes in ADR-144": two enrolled authenticators before an identity satisfies a presence requirement (R1); recovery codes (R2); recovery by a code, a delay and a delivered notification (R3), or through the deployment holder where no code remains (R4); delay floors of 24 and 72 hours (R5); a declared notification channel that leaves the host, whose first recorded success starts a delay (R6); cancellation by any session or enrolled authenticator of the identity (R7); and a change of RP ID as recovery for every identity it affects (R8). It amends ADR-144 as that paragraph states. This record builds nothing by itself.

## Consequences

- R5 to R7 and the removal path are the whole response to an enrolment the owner does not control. An adopting amendment takes effect only on an implementation that passes ADR-144's Validation section and this amendment's.
- A change of RP ID holds the presence-required actions of each identity that had an authenticator past its first-enrolment delay for at least 72 hours, until it has recovered and meets R1; every other identity enrols again under R1 and R5.
- Residuals. A deployment holder can recover any identity (R4, R8). A process with a shell on the deployment host, as on the default single-host local stack, holds the deployment; R4, R6 and R8 then protect only through what the owner sees on a channel that process cannot change. For a first authenticator the owner does not control, R7's window of at least 24 hours is the only in-product protection.
- Directions, not decided here: recovery approved by a second enrolled human, where one exists; per-identity recipients on R6's channel; forced forge re-authentication where a forge supports one, as added hardening.

### Validation

Against ADR-144's test-only action, an implementation walks end to end a two-authenticator bootstrap, replacement of one lost authenticator, a code recovery, a code-free R4 recovery and a change of RP ID, and shows each of the following, with a counterfactual that fails when the check is removed:
- a registration whose credential id is already enrolled to the identity is refused and does not raise the count;
- one authenticator satisfies no presence requirement but gives lifecycle proofs; a second restores presence; one left with none enrols only as a first enrolment, and its earlier codes are refused; a code set is issued only when an identity comes to meet R1 with none outstanding, never at a recovery's effect, and is shown once, only in the session completing that enrolment;
- a recovery code satisfies no presence requirement, is consumed by opening an R3 recovery, is refused on reuse, after cancellation or reissue, and is never logged, audited or notified; refused codes are rate-limited per identity, with one delivered refusal and one count per window;
- an R3 recovery without a valid code, an R4 recovery without an unexpired, unused authorization, and a recovery opened by another identity's session, on a bearer credential or from a session minted outside D6's sign-in bound are refused, as are cancelling on a bearer and openings beyond the per-identity limit; only one recovery is pending per identity, and opening one voids a credential pending a further enrolment;
- a pending recovery holds the action at once but changes no authenticator before its delay; an authenticator inside its first-enrolment delay cannot authorize a further enrolment, removal, code reissue or adopted action, but can cancel under R7; a second unproved enrolment inside a first's delay is refused, audited and delivered;
- a delay below a floor, a recovery delay shorter than the first-enrolment one, an undeclared recovery delay, and a missing channel each hold the action, and a loopback, IP-literal or Web UI origin channel is refused;
- neither delay starts before a qualifying delivery succeeds, and a failed one is retried; any recorded declaration changed while the server was down is delivered at start; a change of channel or recipients reaches each earlier channel still declared, and restarts each pending first enrolment's or recovery's delay only on a success of its event redelivered under the new declaration;
- cancelling any pending item, by any session or a proof, ends a cancelled recovery's hold, makes no other change, and is audited and delivered; concurrent effect and cancellation yield one outcome;
- effect voids every earlier authenticator, each with a removal entry (D5), every outstanding code, unconsumed challenge and pending enrolment, and the recovered identity cannot complete a pending decision (D4) opened before it; its authenticator needs no further delay;
- R4's command and R8's confirmation are unreachable from HTTP, MCP and any token, and each use is audited and delivered; the command cannot make a recovery effective early, and its revocation ends every session of the named identity;
- a declaration with a different RP ID holds the action and invalidates nothing before confirmation; restoring the original lifts the hold; confirmation leaves every earlier authenticator refused, also after a return, voids pending items, and shortens no recovery delay; an identity whose only authenticator was pending or inside its delay enrols again as a first enrolment, with no recovery.
