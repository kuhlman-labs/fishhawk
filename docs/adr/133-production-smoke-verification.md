# ADR-133: Deterministic production smoke verification

**Status: accepted (ratified 2026-11-04).**

## Context

Prepared at the Captain's request on 2026-10-31. ADR-053 permits staging-only post-deploy acceptance and requires a separate security re-review before production-facing acceptance agents are allowed. ADR-050 assumes an acceptance agent may be prompt-injected. ADR-086 (#3791, tracker-only; record not landed) adds scoped credentials and target provisioning without making arbitrary production exploration safe. ADR-103's adversarial probes explicitly require disposable non-production targets.

The lifecycle needs a narrower immediate production question: did the approved deployment leave the intended service functioning? Pre-approved deterministic smoke checks can answer that without an agent choosing actions against real users and data. Detailed requirement acceptance stays in preview and stage; ongoing telemetry remains the monitoring system's responsibility.

## Options

- **A. Treat a successful deployment pipeline as verification.** Insufficient: a rollout can complete while critical behavior fails.
- **B. Deterministic smoke checks executed by the delegated pipeline, with authenticated evidence and a governed disposition (recommended).** Adds bounded operational assurance without an agent in the production data path.
- **C. Permit an acceptance agent to explore production using scoped credentials.** Deferred. This needs its own threat model, containment proof, and explicit amendment of ADR-050/053. A host allow-list alone is insufficient.
- **D. Build continuous monitoring/on-call into Fishhawk.** Rejected under ADR-053 and MVP_SPEC §9. External monitors detect; Fishhawk consumes bounded evidence and alerts.

## Recommendation

Adopt option B as a distinct production verification mode within delegated deployment evidence. Do not add a stage type, shell executor, or deterministic executor branch to `acceptance`.

### D1. Checks run outside Fishhawk's agent execution path

The operator-owned deployment pipeline runs a versioned smoke suite after the rollout establishes an observed target identity. Fishhawk receives and evaluates its bounded structured results through the promotion contract's authenticated evidence channel. Fishhawkd neither executes the checks nor directly accesses the production runtime. The agent receives no production credential, response stream, or ability to choose additional requests.

The deploy execution outcome and smoke outcome are separate records/views. The pipeline may finish while verification evidence is missing; that is a deployed-but-unverified release, never an implied pass. Implement the release-completion interlock before enablement: a workflow opting into required production smoke cannot report a verified release, or advance a dependent promotion that no current temporary exception covers, while those checks are failed, missing, or unknown. The Fishhawk backend owns a durable verification record and hold for each deployment attempt requiring production smoke. Rollout completion may terminalize the deploy stage, but callback and polling paths must preserve this hold independently of run completion. Both completion paths exist today: the callback at `backend/internal/server/deployment.go:385` and the polled path at `backend/internal/server/trace.go:9292`. Verified-release claims and dependent promotion dispatches consult the same persisted assessment. Missing evidence at the declared deadline records unknown and creates a durable operator decision; restart resumes that decision. A continued-operation disposition records an accepted operational risk for that attempt and stops further paging for it; it leaves verification held and the release unverified. Dependent-promotion eligibility is released only by a separately recorded temporary exception that names the promotion it covers, satisfies the same approval predicate, expires, and never marks the release verified. D7 declares that predicate. Validate these transitions through both deployment completion paths and across restart. Do not infer eligibility from the deploy stage's `succeeded` state alone.

The opt-in to required production smoke is a declaration added through the spec-change checklist. It composes with ADR-038's terminal outcomes and does not change them; "verified" is a separate record beside the deploy stage's outcome. New audit categories go through the registry (`backend/internal/audit/categories.go:395`). Schema and storage are for the implementation plan.

Existing `acceptance` stages, including deployment-consuming ones, retain their present non-production boundary. This ADR admits production evidence from approved external deterministic checks; it does not remove the staging-only validation guard or permit a production hostname under a staging alias. Generic target classification is a precondition supplied by the promotion contract (#4898 D2) once it is ratified and implemented; it is never a string comparison. Until then the only product guard is workflow-v2 rule 3's literal `production` environment-name check, which does not detect an alias or a production host behind a staging declaration, and production smoke cannot be enabled (`docs/spec/workflow-v2.md:599`, `docs/spec/workflow-v2.md:602`).

### D2. A human adopts the check policy before execution

The registered suite identifies the fixed checks, immutable executable/configuration revision, the checker workload identity from which Fishhawk accepts results and its permission set (the identity must differ from the rollout delegate identity registered for the target), the permitted evidence destinations, allowed target resources and operations, required results, thresholds, observation window, freshness, request/concurrency limits, timeout, retry bound, and response/evidence limits. These judge inputs are Tier I under ADR-121. The suite registration is a repository declaration read from the default-branch blob and recorded by blob SHA, naming the suite's immutable executable and configuration revision by digest. Its home is the workflow spec file (a derived ADR-121 D2 binding) or a file whose path is declared in `protected_paths`. A candidate cannot weaken the suite evaluating its own deployment, once ADR-121's bindings, `protected_paths` declaration, seams and adoption gate are implemented for the repository. Until then a suite registration has no tier-I enforcement point and production smoke cannot be enabled (`docs/adr/121-protected-judge.md:147`, `docs/adr/121-protected-judge.md:183`).

A change to the suite or its thresholds is a tier-I change adopted under ADR-121 D5 when it is made. Approving a deployment separately binds that adopted suite revision into the intent. A deployment approval, delegated or not, never adopts a suite revision. A threshold change produces a new policy revision and assessment, not a retroactive pass. Existing in-pipeline automatic rollout recovery is separately identified; the smoke checker itself acquires no recovery authority.

### D3. First delivery has declared, bounded side effects and is low-volume

Initially permit checks whose declared side effects have been reviewed and bounded: target/build identity, health/readiness, authentication with a dedicated synthetic account (its session, audit and notification side effects are declared in the suite), a bounded read of synthetic fixture data, and, only inside the D8 observation window, read-only queries against a monitoring source named in the suite registration, with the checker's permission on that source recorded in its registered permission set. HTTP method alone does not establish safety; a GET can mutate or expose sensitive data. The suite must specify the actual operation and data boundary.

Exclude broad customer-data scans, real payments or notifications, load/stress tests, fuzzing, and adversarial probes. For a product whose essential smoke needs a synthetic write transaction, report that coverage gap and use stage evidence; do not silently widen the first production policy. A later revision must define isolated test-tenant writes, cleanup/compensation, idempotency, and external-effect containment before such a check is enabled.

Limits are enforced by the external execution environment and target permissions, not just stated in a prompt. The check identity cannot deploy, administer the service, read arbitrary customer records, or cross the registered target. Tokens are short-lived where the provider supports them, otherwise scoped and rotated through the customer's secret owner. Fishhawk stores binding/version references, never production secret values.

### D4. Separate the rollout identity from the checker identity

The deployment pipeline may need powerful rollout credentials. The smoke process runs in a separate isolated job/workload with only its check credentials; it must not inherit the rollout job's environment, workspace secret files, service-account permissions, credential helpers, or debug dumps. The registration names the provider identity attribute by which Fishhawk tells the checker's workload identity from the rollout delegate's; two workloads that present one provider-issued identity are one identity, and enablement is refused where the provider cannot issue the checker a distinguishable one. Immutable check code and the adopted configuration execute through the registered checker identity. Fishhawk accepts smoke results only from that identity and refuses any submission from the rollout identity.

Direct and indirect network access is restricted to declared target and evidence destinations and, only inside the D8 observation window, the monitoring source named in the suite registration, under the external runner's enforced policy. Refuse enablement where the required isolation cannot be demonstrated. This extends neither the interim customer-responsibility egress fallback in ADR-050's Consequences nor the Linux env-only posture recorded in ADR-103 D3 into a production permission grant (`docs/adr/050-acceptance-agent-egress-credential-posture.md:73`, `docs/adr/103-adversarial-security-probe.md:74`, `docs/adr/103-adversarial-security-probe.md:128`).

### D5. Evidence binds what ran to what was deployed

Each result binds the deployment intent/attempt, a separately identified verification attempt, check-execution ID and retry ordinal, candidate hash, environment identity and generation, observed component identities, suite revision, check ID, start/end time, outcome, and bounded evidence references. The backend records each verification attempt's adopted policy, deadline and evidence cutoff before accepting results. Duplicate and conflict handling is scoped to the check-execution ID; late results remain attributed to their original attempt and cannot satisfy a later recheck. The promotion contract's authentication, callback replay protection, and conflict handling apply, extended to authenticate the registered checker identity of D2 as a principal distinct from the target's rollout delegate. Until the promotion contract carries that extension, production smoke cannot be enabled. No unbound JSON upload, model-written pass, or pipeline URL alone counts as verified evidence.

The checker records the target generation/identity, as observed through the registered platform verifier, before and after the check window; Fishhawk compares the two recorded observations against the deployment intent and never probes the target itself. A changed or partially unidentifiable target makes the affected result unknown. For services with several replicas or components, the suite declares the coverage and rollout-completion observation needed to establish the intended version set; one response from one healthy replica cannot silently establish full rollout completion.

Use a closed outcome vocabulary for each required check: pass, fail, unknown. Preserve attempt history through retries. A retry is bounded and records why it occurred; a later pass does not erase an earlier failure. Required absent, expired, unexecuted, contradictory, or unverified checks yield unknown/hold. A deterministic evaluator computes the aggregate result under the pinned policy; an agent cannot reclassify it. The adopted Tier-I policy specifies aggregation, fail-versus-unknown precedence, and whether and under what conditions a bounded retry may satisfy a previously failed check. A required-smoke policy must contain at least one required check; verified completion requires every required check to be satisfied under that policy using authenticated, complete and fresh evidence. Missing aggregation or retry semantics hold verification. Validation covers fail-then-pass, fail-plus-unknown, exhausted retries, zero required checks and the resulting promotion eligibility while preserving all history.

### D6. Keep sensitive runtime data out of the model and audit payloads

Prefer statuses, durations, bounded counts, and cryptographic artifact identities over response bodies. Use an allow-list evidence schema, size limits, and customer-side redaction before upload; deny arbitrary log/HTML/request dumps. Synthetic-account identifiers and internal topology can also be sensitive and follow repository/target ACLs.

Raw troubleshooting material remains with the external operator-controlled system. A source reference grants no additional read authority. The smoke channel carries no security-finding payload. A suspected finding enters only as a proposal into ADR-126's confidential intake, under its human-disposition gate and D4 declaration. If that path is unavailable, retain only safe identifiers, hold verification as unknown, and never fall back to ordinary evidence storage or public filing. Before activation, test a smoke result containing synthetic secrets, reproduction text and sensitive references through ingestion, audit, logs, gate views, notifications, MCP reads and prompts; unauthorized projections must contain only permitted metadata, including on error and retry paths. A failed or unknown result is not itself a security finding; reporting one is an ADR-126 filing with its own declaration (ADR-126 D4). If a check cannot produce safe evidence, its result is unknown until an authorized review resolves the operational decision.

### D7. Failures route to a decision, not arbitrary agent recovery

A failed or unknown required result holds verified completion and pages the configured operator through the existing notification mechanisms. The operator decision is recorded on the verification hold's own decision surface, not on a stage gate. That surface admits only the forge-verified, non-delegated identities named below on every channel that can record it, and it refuses any channel that cannot apply that predicate. The evidence states whether the problem is an observed regression, an unavailable check, stale identity, or an inconclusive result. Monitoring alerts can independently enter ADR-053's incident intake.

The operator chooses a recheck, a separately approved rollback/roll-forward, or continued operation under an explicit recorded risk decision bound to the exact deployment attempt and the failing or unknown results. Starting a recheck is recorded on the same decision surface under the same identity predicate as the decisions below. A recheck is a new verification attempt under D5 and the same adopted policy, distinct from a checker retry inside an attempt. Its count is bounded by the adopted policy, it keeps every earlier attempt's record, and it can satisfy verification only where the policy's retry and aggregation rule says so. An exhausted bound leaves the hold in place for the decision below. That decision, and any temporary exception, must satisfy a repository-declared approval predicate specifying eligibility and quorum, namely the opting-in deploy stage's gate `approvals` and never a product identity constant (`docs/spec/workflow-v2.md:530`, `docs/spec/workflow-v2.md:1235`), bound to the repository, exact deployment attempt and affected results; an opt-in on a deploy stage that declares no `approval` gate is refused at validation, and a policy that is missing or unverifiable at decision time holds the decision. Every counted approval requires a forge-verified credential of kind `session`, `oauth` or `oauth_as`, derived as ADR-123 Decision 1 derives them, applied here to every counted approval whatever legs the gate declares because this surface is not a stage gate and ADR-123's scope does not reach it; and a non-agent subject; no delegated submission or standing order covers it. Continued operation records an accepted operational risk for that attempt and stops further paging for it; it does not change a failed/unknown check to pass, label the release verified, or release dependent-promotion eligibility. Only a separately recorded temporary exception releases that eligibility (D1). Any temporary exception has an owner, scope, expiry, and follow-up, names the promotion it covers, and never marks the release verified; target-identity, checker-identity and evidence-authentication failures cannot be converted into valid verification evidence by an exception, while a failed synthetic-account check is an ordinary failed check that continued operation or an exception may cover. An exception never releases a promotion after a target-identity, checker-identity or evidence-authentication failure.

Recovery uses the exact-deployment selection and fencing in the promotion contract (#4898). After recovery, check the newly observed artifact/configuration under a fresh verification attempt. A successful rollback pipeline alone does not establish a recovered service. Neither a smoke failure nor an agent's diagnosis permits changing production data or code in place.

### D8. The observation window is bounded

Immediate smoke and a short, declared stabilization window can include metric results queried and reported by the customer-side checker through the same authenticated evidence channel, if their source, query revision, population, baseline, and missing-data behavior are adopted in advance. Metrics enter only as checker-reported evidence. Missing traffic, absent baseline, or an unavailable monitor means insufficient evidence, not zero errors. No statistical reliability claim is inferred from a few synthetic requests.

At the end of the window, ongoing health belongs to existing observability/on-call systems. ADR-079 consumes later product outcomes and ADR-053 consumes alerts. Fishhawk does not run an indefinite release stage waiting for the service's lifetime.

### Amendment scope

This amends ADR-053 Decision 4 and the MVP_SPEC section 9 wording it decided: post-deploy verification evidence is admitted from approved external deterministic checks as well as from the existing acceptance machinery, and bounded external metrics are admissible evidence inside a declared window (D8). That wording is recorded in ADR-053 itself: `docs/MVP_SPEC.md:440` does not carry it, and `docs/MVP_SPEC.md:8` keeps §9 as the historical record of the original plan. ADR-053 Decisions 1 to 3 are not changed by this ADR, including the staging-only acceptance boundary. The Known limitation recorded under forks 2 and 3 is narrowed, not removed: `hotfix_change` still does not deploy or verify the deploy (`docs/spec/workflow-v2.md:1479`), and post-deploy acceptance still cannot run against the alerting production environment; what changes is that a follow-on deploy-bearing workflow that opts in under D1, such as a `release` run, can now close the loop on that environment with deterministic smoke evidence, never with an acceptance agent.

ADR-053 Decision 3 is not changed by this ADR for acceptance targets and acceptance agents: no production host is permitted to an acceptance stage, and the gated re-review it requires (least-privilege, read-only synthetic-check accounts for acceptance) is not performed by this ADR. The external checker identity of D3/D4 is not an acceptance account. It may perform only the declared authentication side effects, and that departure from Decision 3's read-only parenthetical is deliberate and confined to the external checker. ADR-050, ADR-086, and ADR-103's agent containment/target boundaries are not widened.

This is not the bespoke smoke-check runner ADR-053 rejected: Fishhawk builds and operates no check runner, and the acceptance machinery that rejection preferred is barred from production targets by ADR-053 Decision 3.

## Decision

**Accepted 2026-11-04** by the Captain (1 of 1; manual ratification path, the ADR-113 D2 verb is not yet built; approver and hashes in the ratification comment). **Option B**, i.e. D1–D8 as stated in the Recommendation, decided now. It amends ADR-053 Decision 4 and the MVP_SPEC §9 wording only as its Amendment scope states; ADR-053 Decisions 1 to 3 are not changed. Production smoke cannot be enabled until the promotion contract (#4898), its checker-identity extension and ADR-121's bindings are implemented. This record grants no production access and starts no work.

## Consequences

The production release gains reproducible smoke evidence while keeping agents out of the runtime credential path. The price is a trusted external checker, authenticated ingestion, target identity verification, explicit aggregation/freshness, and operator handling for failed or unavailable checks. A compromised approved pipeline or checker remains a threat; its identity and integrity are part of the adopted supply-chain boundary, not solved by signing its output alone.

First implement and validate the protocol on a non-production target whose repository declaration carries the target registration, identity verifier and delegate identity fields the promotion contract (#4898 D2) proposes; before #4898 and ADR-121's bindings are implemented, that validation runs against an unenforced, non-Tier-I registration and establishes no production eligibility. Then perform an operator-approved production activation. Existing deployments remain legacy/unverified until explicitly migrated. Production suite installation is Tier I; callback/evaluator machinery follows ADR-121 Tier M controls. No alpha milestone or autonomous production authority is added.

- **Dependency.** This depends on the release candidate and promotion contract (#4898) being ratified and implemented, carrying the checker-identity extension this record's D5 requires, and on ADR-121's D2 bindings, D4 seams and D5 adoption gate being implemented for the repository, before production enablement. Production smoke cannot be enabled on a production-class target before both. Protocol validation on a non-production target comes first; before those are implemented it runs against an unenforced, non-Tier-I registration and establishes no production eligibility. No production access is authorized by this ADR.
- **False-assurance residual.** A smoke suite can be green while the service is broken: a narrow synthetic path observes only what it exercises. "Verified" is not a correctness claim about the service.
- **Synthetic-account residual.** Synthetic production accounts and fixtures carry an operational cost. Production hosts synthetic data, which can pollute analytics, billing and tenant records, and the account itself is a standing production credential.

### Validation

- Deployment succeeds but every smoke check is missing: result is unverified and completion is held.
- Wrong candidate/replica, an alias resolving to an unapproved target or bypassing its registered class, changed generation, or unverifiable identity cannot pass; a valid alias preserves the approved target identity and class.
- Forged, replayed, cross-repository, expired, oversized, or conflicting evidence is rejected/held with a safe reason.
- The checker cannot obtain rollout credentials or read non-synthetic customer records; requests and retry bounds are enforced, and the isolation is demonstrated by a recorded operator drill in the production environment before activation.
- Enablement is attempted with a registration whose checker identity equals the rollout delegate identity, or whose isolation attestation and recorded operator drill are absent: enablement is refused and the reason names the missing or shared item. Shared environment, workspace and credential-helper isolation cannot be observed by Fishhawk and is evidenced only by the recorded operator drill.
- Enablement on a production-class target is refused while target classification or the ADR-121 bindings, seams and adoption gate are not implemented for the repository, and the refusal names the missing item.
- A smoke result is submitted under the rollout identity: Fishhawk refuses it and it counts as no evidence.
- An `acceptance` stage consuming the deployment of a deploy stage whose `allowed_environments` includes `production` is still rejected under ADR-053 Decision 3 (workflow-v2 rule 3); admitting smoke evidence does not relax that guard, and a production host behind a `staging` declaration remains undetected until #4898 D2 target classification is implemented.
- Missing telemetry/traffic cannot appear as a favorable baseline; a failed first attempt stays visible after a retry passes.
- A candidate edits the checker or thresholds: the governing policy remains the separately adopted revision.
- Failure, unknown, authorized continued operation, rollback failure, and verified recovery remain distinguishable end to end.
- Recording continued operation or an exception under a delegated, standing-order, agent or static-token identity is refused on every channel. A forge-verified non-agent caller who fails the declared eligibility predicate cannot contribute an approval; duplicate approvals from one subject cannot satisfy a larger quorum, an insufficient quorum cannot record the disposition, and missing or unverifiable approval policy holds the decision.
- An opt-in to required production smoke on a deploy stage that declares no `approval` gate is refused at validation.
- An operator recheck requires the D7 approval predicate, creates a distinct verification attempt under the same adopted policy, and consumes the policy's recheck allowance across restart. A recheck beyond that allowance is refused; late evidence from an earlier attempt cannot satisfy it, and a passing recheck clears verification only when the adopted aggregation rule permits, preserving earlier failures.
- A recheck beyond the adopted bound leaves the hold in place for the human decision; an unresolvable or unverifiable approval policy holds the decision.
- An expired exception is no longer treated as current, and an exception cannot convert a target-identity, checker-identity or evidence-authentication failure into valid verification evidence, and cannot release a promotion after one.
- A temporary exception releases only the promotion it names and only until it expires, and never marks the release verified; with no current exception, the dependent promotion stays held.
- Callback and polled deploy completion, backend restart, deadline expiry, fail-then-pass, exhausted retries and zero required checks each leave the hold and promotion eligibility as D1 and D5 state.
- A smoke result carrying synthetic secrets projects only permitted metadata through ingestion, audit, logs, gate views, notifications, MCP reads and prompts, including on error and retry paths.
- The external runner and target permissions prevent operations beyond the suite's declared side effects, and dump-bearing submissions are refused before ordinary persistence.
- The checker stops at the declared observation-window boundary, recording unavailable monitoring as insufficient evidence.
- A non-Fishhawk service uses its own identity verifier, endpoints, and metrics through declarations; `/healthz` with Fishhawk's `git_sha` is not a product requirement.
