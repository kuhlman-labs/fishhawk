# runner/internal/agent

The agent abstraction (`Invoker`, `Invocation`, `Result`, `Event`) shared by the provider adapters (`claudecode/`, `codex/` — see their READMEs for adapter internals).

## Trace-line reader (`linereader.go`, #3020)

`TraceLineReader` replaces `bufio.Scanner` in both adapters. It reads the child's newline-delimited trace stream one logical line at a time over `bufio.Reader.ReadSlice`, and — the one behaviour that matters — TRUNCATES a line whose CONTENT exceeds `MaxTraceLineBytes` (4 MiB, ~4x the prior scanner limit) rather than aborting the whole read the way `bufio.Scanner`'s `ErrTooLong` did. It retains the first `max` bytes, discards the rest of the physical line, and CONTINUES on the next line, so an over-long line costs one log line, not the whole pass. `Truncated()` reports the truncation; `OriginalBytes()`/`RetainedBytes()` carry the counts an adapter puts in the `trace_line_truncated` event.

BYTE ACCOUNTING is content-only: neither the terminating `\n` nor a `\r` that pairs with it (a CRLF terminator) is counted or retained; `OriginalBytes` is the full content length INCLUDING bytes discarded past the cap, and `RetainedBytes == len(Bytes()) == min(Original, max)`. The **pending-CR rule** makes that hold when a CRLF terminator is split across a `ReadSlice` fragment boundary: a `\r` at the end of a non-terminating fragment is HELD and resolved on the next fragment — dropped if a `\n` follows (terminator), appended-and-counted otherwise (genuine content, and at EOF). Retained memory is bounded: once the cap is hit, further bytes are counted into `OriginalBytes` but discarded, so the buffer never exceeds `max`. `ReadSlice` returns a slice into `bufio`'s internal buffer that the next read invalidates, so every retained fragment is copied immediately.

`Err()` reports ONLY a genuine non-EOF read error; a clean `io.EOF` terminates with `Err() == nil` and a final unterminated line is returned first. Adapters map that non-EOF error to the peer sentinel **`ErrTraceStreamRead`** (below), NOT `ErrAgentFailed`.

`ErrTraceStreamRead` is a PEER sentinel (like `ErrLoopDetected` / `ErrExternalAPI`): it deliberately does NOT wrap `ErrAgentFailed`, so `err_class` classification is unambiguous and the label names the READER (`trace_stream_read`) rather than the agent. `Result.FailureCategory` stays `"A"` on that path, so stage retryability and the bundle signal are unchanged — only the label moves.

## Loop / duplicate-action detection (#653)

`loopdetect.go`'s `LoopDetector` is a pure, no-I/O detector that trips when the same tool-call signature recurs in an unbroken consecutive run of length ≥ the threshold in force for that signature's CLASS — `DefaultWaitPollThreshold = 60` for a wait-poll, `DefaultLoopThreshold = 8` for everything else (see the #2758 subsection below). The base default is conservative so legit repeats — re-reading a file, retrying a flaky command a couple of times — never false-abort; any differing signature resets the streak, as does the same signature observed with a different class (unreachable in practice — the class is a pure function of the signature — but specified so the state machine is total).

The claudecode adapter (`claudecode/claudecode.go`) builds a signature per `tool_use` block via `toolCallSignatures` = tool name + `canonicalInput` (keys sorted, so `Read a.go` ≠ `Read b.go` but two identical `Read a.go` calls collide), fail-open exactly like `outOfTreeWrites`.

The scan loop feeds each signature plus its class to the detector; on trip it appends a `loop_detected` trace event (signature + count + `wait_poll` + `threshold` + run/stage), kills `claude`, and the terminal switch maps `loopHit` to the peer sentinel `agent.ErrLoopDetected` with a category-A `failureResult` (outcome `loop_detected`, reason naming the count and the tier). `backend/internal/agenteval` reads this event by PRESENCE only, so the two payload fields are additive.

The sentinel does NOT wrap `ErrAgentFailed` (unambiguous `err_class`); unlike a thinking-block fault a loop is terminal and **not** retried — re-running the same prompt would just loop again. `Invoker.LoopThreshold` and `Invoker.WaitPollThreshold` (each 0 → its own default, independently) let tests lower them; setting the two equal collapses the tiers back to pre-#2758 behaviour, which is also the low-risk rollback short of a revert.

Cross-stage no-progress is out of scope (it belongs to the orchestrator); this is runner-side, per-invocation only.

### #2758 wait-poll tier

An agent that backgrounds a multi-minute gate (`scripts/test verify`) and polls its log has no instrument for the wait other than the repeated poll, and that poll is legitimately byte-identical for minutes at a time — verify runs lint first and is silent. So the flat threshold of 8 killed healthy stages at ~8 polls; run `3490416b` discarded a 31-minute pass on the signature `Bash {"command":"tail -2 /tmp/verify-2591.log","description":"Check verify progress"}`.

The claudecode adapter classifies each signature with the pure predicate `isWaitPoll`, and a wait-classed streak is held to `DefaultWaitPollThreshold = 60` instead of `DefaultLoopThreshold = 8`. Two forms qualify: the `BashOutput` tool (definitionally an await of a backgrounded command), and a `Bash` command that `isReadOnlyPollChain` accepts — a chain of allow-listed read-only inspection commands (`sleep`, `wait`, `ps`, `tail`, `head`, `cat`, `wc`, `grep`, `ls`, `stat`, `test`, `[`, `echo`).

**The allow-list has an ADMISSION RULE, and the rule is the reviewable artifact — the list is only its output.** A command earns a place only if it has NO documented mode that executes another command or mutates system state, checked against its own documentation before adding it. An argv[0] allow-list cannot express "this command in a read-only mode", because an allow-listed NAME carries every mode that name has. Three obviously-inert-looking names were rejected on exactly that ground: `jobs`, because `jobs -x command [args]` substitutes jobspecs and then EXECUTES the command (`jobs -x rm -rf x` has no newline, redirect, backtick, `$` or bare `&`, and its argv[0] is `jobs` — verified by execution, not by reading a man page); `date`, because GNU `date -s`/`--set` and BSD `date`'s bare time argument set the system clock; and `pgrep`, because procps-ng builds `pgrep`/`pkill`/`pidwait` from one source with one shared manual page that documents `--signal <sig>` for the family, so `pgrep --signal KILL pattern` is a documented signal-sending mode of the name. `pgrep` was initially admitted here on the reasoning that "the signalling variant is `pkill`" — which is precisely the failure the rule prevents, and why the check is made against the command's own documentation rather than against how the name reads. Narrowing to "`pgrep` without a signal flag" was rejected for the same reason `jobs -x` was not special-cased: matching a backgrounded command's process is already covered by `ps` and `BashOutput`. All three are pinned as NOT-wait-classed by `TestIsWaitPoll`, which must stay green if anyone ever re-adds them.

`isReadOnlyPollChain` is a deliberately narrow shell-lite parse, **fail-closed** on anything it does not fully understand — a parse gap can only under-classify (to the base threshold, i.e. pre-#2758 behaviour), never let a mutating command reach the higher limit. Rejected outright: a newline, redirection (`>`/`<`), a backtick, ANY `$` at all, and a `&` that is not part of `&&`. The `$` is rejected wholesale rather than only as the `$(`/`${` digraphs, because the stated ground for rejecting an expansion — its value is unknown at classification time — holds equally for a bare `$LOG`, `$@` or `$*`; treating them differently was an inconsistency rather than a hole (every segment's argv[0] must still be an allow-listed bare NAME, and `$CMD` is not one), but the consistent rule is the one that can be stated in a sentence and checked. Quoting is NOT interpreted: a separator inside single or double quotes still splits the chain, which errs fail-closed — the split can only manufacture a segment whose first token is not an allow-listed bare name. Otherwise it splits on `;`, `&&`, `||` and `|` and requires EVERY segment — not merely the first — to lead with an allow-listed bare name, which is also what rejects a `VAR=x cmd` env-assignment prefix and a path-qualified binary (`/bin/rm`, and equally `/usr/bin/tail`). A chain with no allow-listed segment at all (`""`, `";;;"`) is not wait-classed either.

**The wait threshold bounds REPETITIONS, not wall-clock**, because a wait-classed call may itself sleep: 60 polls at the 20-30s cadence an agent typically uses is an illustrative ~20-30 minutes, but 59 repeated `sleep 600` calls would sit in this tier far longer. The real time bound is the implement-stage budget (ADR-025). This is why the tier is a re-tiering of the control and not its removal — unlike the #1273 exemption above, which is TOTAL (the signature is never fed to the detector at all), a wait-poll here still accumulates and still trips, just at 60.

The "reset the streak when the observed OUTPUT changes" alternative (issue direction 1) was considered and rejected: `tail -2 <log>` returns byte-identical output across exactly the silent-lint window in which the stage died, so an observation-diff would never fire there. `TestInvoke_WaitPollTailSurvivesBaseThreshold` makes that falsifiable — it emits identical polls with identical (absent) observations, so an observation-diffing implementation alone would fail it.

### #1273 wait-poll exemption

The claudecode feed loop skips feeding the sanctioned scope-amendments `?wait=` long-poll signature to the detector (predicate `isSanctionedWaitPoll` — `Bash ` prefix + `scope-amendments` path + `wait=` as a query parameter of that path, narrow so a bare `wait=` elsewhere / a non-waiting GET / a non-Bash tool are NOT exempt).

That long-poll is a deliberately-repeated identical action the prompt instructs the agent to issue (`backend/internal/prompt/prompt.go`, ~line 1020), so without the exemption it tripped `loop_detected` (~8 polls / ~4 min) before the prompt's ~15-minute wait-poll cap.

The skip is a no-op exactly like the empty-signature case — it neither accumulates nor resets a streak — so an interleaved real loop still trips; a genuinely-stuck poller is reached by the agent's own EXPIRY branch at that cap (#2601 retired the older proceed-as-denied wording: an expired window is the absence of a decision, so the agent adapts-and-discloses or stops and fails loud, never treating operator silence as a refusal) and, failing that, backstopped by the implement-stage budget (ADR-025), not the loop detector.
