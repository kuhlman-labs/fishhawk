# backend/internal/webhook

GitHub webhook receipt, event → run/stage matching and dispatch, and the shared budget-admission decision core both admission seams use. Also the GitLab receiver's parse + match primitives (E45.6 / #1860).

## GitLab receiver (E45.6 / #1860)

`backend/internal/webhook/gitlab.go` holds the GitLab parse/verify primitives; the HTTP handler + MR review-gate consumer live in `backend/internal/server/webhook_gitlab.go` (`POST /webhooks/gitlab`, secret from `FISHHAWKD_GITLAB_WEBHOOK_SECRET`).

- **Auth is a verbatim token, NOT an HMAC.** GitLab sends the configured secret token verbatim in `X-Gitlab-Token`; `VerifyGitLabToken` compares it against the configured secret. This is the load-bearing difference from the GitHub `X-Hub-Signature-256` HMAC path. The compare hashes both sides to fixed-length SHA-256 digests before `subtle.ConstantTimeCompare` — a bare compare over the raw bytes short-circuits on a length mismatch, leaking the secret's length via timing (the same fixed-length-digest posture `VerifySignature` uses for HMAC sums).
- **Delivery-id namespacing.** `ParseGitLabEvent` prefixes the `X-Gitlab-Event-UUID` with `gitlab:` before it enters the SAME `DeliveryStore` the GitHub path uses, so a GitLab UUID and a GitHub UUID can never collide and dedup one another. A missing `X-Gitlab-Event` or `X-Gitlab-Event-UUID` fails closed (400) — a delivery with no id can't be deduped.
- **Record-then-dispatch, unmark on 5xx.** The receiver `Mark`s the delivery (dedup) BEFORE dispatch, so a concurrent redelivery dedups instead of double-dispatching. The cost is that a dispatch failure would otherwise leave the delivery recorded, so GitLab's retry of the `5xx` would hit the record, dedup to `202`, and permanently drop an event whose processing failed. `dispatchGitLabDelivery` closes that by `Unmark`ing the delivery on a dispatch error (the new `DeliveryStore.Unmark`, implemented by both `MemoryStore` and `PostgresStore`) so the retry re-records and re-processes. The record-store `Mark` failure `5xx` needs no unmark — nothing was recorded. (The dispatch-error branch is currently unreachable for GitLab — no `Handle` path returns a transient error yet — but goes live with E45.8 run creation.)
- **Event mapping.** `Type` normalizes to `object_kind` (`merge_request` / `note` / `issue` / `pipeline` / `build`); `Action` from `object_attributes.action` (MR/issue), `object_attributes.status` (pipeline), or `build_status` (job); `Repo` from `project.path_with_namespace`; `Sender` from `user.username`; `CredentialRef` = `gitlab:<project.id>` (lockstep with `forge/gitlab`'s `scopeRefPrefix`); `Forge` = `gitlab`.
- **Shared matcher.** `MatchGitLabEvent` classifies into the SAME `Match` vocabulary + `Dispatcher.Handle` pipeline. Issue-label adds and `/fishhawk` notes trigger; the note/approve/reject/reply command classification is the shared `classifyCommentCommand` helper (extracted from `matchIssueComment` so the two forges cannot drift). A GitLab access-token bot username (`^(project|group)_\d+_bot`) is skipped to avoid feedback loops.
- **The E45.8 dispatch boundary.** A GitLab `MatchActionRun` parks fail-closed BEFORE the spec-fetch step: the `forge.Forge` interface has no workflow-spec read, comment-backs are GitHub-only, and no `gitlab_ci` runner_kind exists yet, so actual run CREATION from a GitLab trigger is the CI/dispatch phase's work (E45.8 / #1861). Pipeline/job events are recognized-and-skipped naming the same consumer. `merge_request` skips in the matcher because the merge/close lifecycle is consumed server-side (see below).
- **MR merge/close → review stage.** `handleGitLabMergeRequest` drives the ADR-018 `resolveReviewStageOnMerge` shared with the GitHub merge reconciler: action `merge` → review succeeded, `close` → cancelled. The run is resolved by the DURABLE identity both surfaces carry — project path + MR **iid** (`findRunByGitLabMR`) — NOT by exact `object_attributes.url` vs stored `pull_request_url` string equality, because GitLab's webhook/API URL representations are not byte-identical across versions (the `/-/` infix). A normalized-URL pass supplements but never replaces the iid key. **`handleGitLabMergeRequest` now participates in the unmark-on-`5xx` retry contract on a TRANSIENT `RunRepo` lookup failure (E45.21 / #2038):** a `ListRuns` error (either the project-scoped scan or the exact-URL supplement) propagates as a returned error, and the receiver `Unmark`s the already-recorded delivery (via the shared `unmarkGitLabDelivery` helper) and answers `5xx` so GitLab redelivers and re-drives the transition — because this receiver is GitLab's ONLY review-gate signal (the GitHub path has the merge-reconciler poll as a backstop; GitLab has none), so a swallowed lookup error would strand the review stage permanently. A parse failure, a non-terminal action, or a genuine no-match stay best-effort `202`. The harmful consequence is dormant until E45.8 wires GitLab run creation (#1861), the named hard blocker that must land before it.

## workflow_run.failure → fail-C (#243)

`webhook.matchWorkflowRun` recognizes `workflow_run.completed` events for `fishhawk.yml` (the configured `DefaultActionsWorkflowFile`) with a non-success conclusion (`failure`, `timed_out`, `cancelled`, `action_required`, `startup_failure`, `stale`). Tagged as `MatchActionRunnerActionFailed` carrying the workflow_run's id + conclusion.

- `Dispatcher.handleRunnerActionFailed` calls `githubclient.Client.GetWorkflowRun` to recover the original `workflow_dispatch.inputs` — specifically the `stage_id` we fired with — then transitions that stage to failed-C via `run.FailStage`.
- Idempotent: a redelivered webhook hits a stage that's already terminal, and `FailStage` is a same-state no-op.
- Faster path than the dispatch watchdog: the watchdog times out on a clock; this fires within seconds of the GitHub Actions run terminating.
- Best-effort throughout: lookup failures log + return (the watchdog still cleans up).
- New App permission: none — `workflow_run` events are already in the App's `default_events` (per `manifest.go`); the webhook receiver was just dropping them as unrecognized.
- SPA gets the failure-C `<FailureBanner>` Retry affordance for free since #173 covers category-C retry.

## Required-checks resolution (`ResolveRequiredChecks`, #251 / #2506)

`dispatcher.go::ResolveRequiredChecks(ctx, api ProtectionAPI, scope, repo, branch, defaultBranch)` is the shared seam that unions classic branch-protection + ruleset required-status-check contexts into a `run.RequiredChecksSnapshot`. It returns the snapshot, an `authoritative` bool, and an error.

- **`authoritative`** is true only when BOTH surfaces answered definitively for `branch`: classic protection on a 200 or `ErrNotFound`, AND the rulesets list on a 200 with EVERY active branch ruleset's ref_name condition evaluatable. A rulesets 404 (GHES without the endpoint) OR a ruleset carrying an include token the v0 matcher can't evaluate (an unknown `~TOKEN` / an fnmatch glob) both yield `authoritative=false` — so a caller reading an empty snapshot as "nothing required" can't be misled by an un-queried or un-parsed surface. `~DEFAULT_BRANCH` rulesets match against the supplied `defaultBranch` (`githubclient.Client.ListRulesetRequiredChecksForDefault`), not a hardcoded `main`.
- **The dispatcher REFUSES an empty result** (`d.resolveRequiredChecks` — the thin wrapper — returns `errNoBranchProtection` when the snapshot has zero contexts, discarding `authoritative`; v0 won't dispatch into an ungated repo), **while the server DEGRADES to nil** (`server.captureRequiredChecks` returns a nil snapshot on any error OR a non-authoritative result, so a local/MCP/CLI/campaign run parks at #2497's `checks_unresolved` rather than a vacuous green). The dispatcher's refuse-on-empty contract is byte-identical to pre-#2506.

## Blocking periodic budget (admission gate, `run_rejected_budget` / `run_admitted_budget_override`)

Shared decision core: `backend/internal/webhook/budget_admission.go` (#688 / ADR-030) — `CostSummer` capability + `CheckBlockingBudget(ctx, summer, repo, workflowID, budgets, now, loc)`.
It iterates `Workflow.Budgets`, skips advisory/empty-enforcement entries (only `enforcement: blocking` gates), sums the current calendar period via `CostSummer.SumWorkflowCostInRange`, calls `budget.Evaluate`, and returns the FIRST blocking budget whose `Over` is true.
It lives in the **webhook** package because both admission seams need it and server already imports webhook (no import cycle); a sum error is fail-open (returns `blocked=false` + err so the caller logs and admits).

**Two admission seams gate a NEW run** — a workflow that crosses a blocking budget refuses the next run once the period's `cost_recorded` spend reaches `limit_usd`:

1. **HTTP handler** — `backend/internal/server/budget_admission.go::checkBlockingBudget`, called from `handleCreateRun` (`runs.go`) after the plan-reviewer guard and before `CreateRun`.
   On block it writes a `run_rejected_budget` global-chain audit and returns `402 budget_exhausted` (reason names the period, limit, spend, and how to clear it), unless the request carries `budget_override:true` (threaded from the CLI `--override-budget` flag / MCP `fishhawk_start_run budget_override`), which admits the run and records a `run_admitted_budget_override` audit instead.
2. **Webhook dispatcher** — `dispatcher.go::refusedByBlockingBudget`, called in the new-run dispatch flow after `resolveRequiredChecks` and before `d.Runs.CreateRun` (the dispatcher creates runs directly, bypassing the handler — a gate only at the handler would leak every webhook-dispatched run).
   On block it writes a `run_rejected_budget` audit and creates NO run row. **There is no override on the webhook path** (webhook triggers can't carry one).

- Both seams type-assert their run repo to `CostSummer` and ADMIT when it's absent (capability-absent skip, mirroring `checkBudgetAlerts`).
- **Never gated** (ADR-030: in-flight work finishes): in-flight runs, CI-retry re-dispatch, and decomposition-child creates — those continuation paths call `CreateRun` directly and skip the gate. The CI-retry half of that bullet is reasoned out below.
- Timezone reuses `server.Config.BudgetLocation` / `Dispatcher.BudgetLocation` (both fed from `FISHHAWKD_BUDGET_TIMEZONE` in `serve.go`).
- Both new audit kinds are admission-time global-chain entries (no Notifier method, no issue comment) — see `docs/issue-comment-surfaces.md`.

### Why the CI-retry paths are exempt (ADR-030, E45.27 / #2878)

Both CI-failure retry handlers — `dispatcher.go::handleCIFailureRetry` (GitHub) and `gitlab_ciretry.go::handleGitLabCIRetry` (GitLab) — mint their child run without calling `refusedByBlockingBudget`. That is deliberate, not an oversight, and it is the ADR-030 position rather than a new one. The record is here because the exemption was previously readable only by noticing which call the retry paths do NOT make.

- **The distinction is admission vs. continuation.** The two seams above gate whether NEW work *starts*. A CI-failure retry is the continuation of a lineage that already passed admission: the parent run was admitted under the budget, the runner already opened the PR, and the failing required check is the last thing between that work and a merge. ADR-030's stated position is that in-flight work finishes; a retry child is the mechanism by which it finishes, not a second admission.
- **The alternative strands the LINEAGE.** The webhook path carries no override (see seam 2 above — a webhook trigger cannot pass `budget_override`), so a budget refusal mid-lineage would leave a red PR with no in-product way to CONTINUE it: no retry and no override on that seam. The operator is not left without any recourse — seam 1, the server-side create, does carry `budget_override` (`run_admitted_budget_override`) — but that is an operator-initiated NEW create, which restarts the lineage rather than continuing the admitted one, discarding the in-flight run's parent linkage and its open PR's continuity. Worse, `CheckBlockingBudget` is fail-open on a sum error, so a flapping sum would make that stranding nondeterministic — a lineage would finish or not depending on whether the cost query happened to succeed.
- **The spend is bounded by construction, not by trust.** `retry_attempt` is always `parent.RetryAttempt + 1` (never derived from the latest existing CHILD), and `runs_retry_child_once_idx` is a partial unique index on `(parent_run_id, retry_attempt)`. So a lineage admits at most ONE child per attempt and at most `on_ci_failure.max_retries` children in total, REGARDLESS of delivery volume: a repeated or forged delivery derives the same `retry_attempt` from the same parent row and is absorbed as a benign unique violation (`run.IsRetryChildDuplicate`). The exemption therefore cannot be turned into unbounded spend by sending more deliveries — the only way to open a new lineage is the create seam, which IS gated.
- **The GitLab reason this was re-examined.** GitLab run creation is live, its deliveries are authenticated only by one deployment-shared `X-Gitlab-Token` with no HMAC over the body, and the retry path can end in a credentialed pipeline dispatch. But the population that can reach it is narrow: `GitLabProjectAuthorizer` binds the credential to the installation row's recorded project path EXACTLY (E45.26 / #2877 tightened this from namespace-level), and the retry additionally requires `(ref, sha)` correlation to an existing run branch and that run's recorded implement-stage head SHA. The blast radius is the remaining `max_retries` attempts of ONE already-admitted lineage in ONE registered project, not credentialed dispatch at large.
- **Both forges are exempt symmetrically, on purpose.** Unlike the E45.25 / #2876 pre-flight dispatchability divergence documented below — where the two paths differ in committed state for a ratified reason — there is no forge-specific budget behavior here, and there must not be one: a budget hole or a budget stranding on one forge only would be a worse defect than either uniform choice.
- **Machine-enforced, not just written down.** `TestCIFailureRetry_BlockingBudgetExhausted_StillRetries_ADR030Exemption` and `TestGitLabCIRetry_BlockingBudgetExhausted_StillRetries_ADR030Exemption` (`budget_admission_dispatch_test.go`) seed a parent whose cached spec declares an exhausted blocking budget, drive the retry delivery, and assert the child is minted and dispatched, no `run_rejected_budget` row is written, and the `CostSummer` is never consulted at all. Each also proves its own over-budget precondition by driving the CREATE path with the same spec and the same spend and observing the refusal.
- **Revisit trigger.** If a future change gates a retry on budget, it must gate BOTH forges and rewrite this subsection in the same commit — the two tests above go red first. Likewise, if `retry_attempt` ever stops being parent-derived, the per-lineage bound above dissolves and this rationale no longer holds.

## `applies_to` routing admission gate (`run_rejected_applies_to`, E53.10 / #2361)

`dispatcher.go::refusedByAppliesTo` (`applies_to_admission.go`) is the third admission gate, called in `Dispatcher.Handle` **after** the plan-reviewer capability gate and **before** the branch-protection snapshot gate (Step 3.45). The dispatcher creates runs directly, so without it an operator's `applies_to` routing declaration would silently not hold for webhook-triggered runs — the hole #2361 closes.

- **Shared core.** It delegates every evaluation to `backend/internal/appliesto` (the same package `server`'s `checkAppliesTo` and plan gate use), splitting to `appliesto.PhaseAdmission` (the `labels` / `trigger` half) and rendering through `appliesto.RenderRejection` with `SeamWebhook`. The message reads identically to the server seam except the trailing sentence, which names amending the declaration / re-starting through `POST /v0/runs` and does **not** advertise `applies_to_override` (a webhook trigger carries no way to pass one).
- **Forge-authoritative labels.** It evaluates against `m.IssueRef.IssueLabels` — captured in `matchIssue` (the UNION of `issue.labels[].name` and the triggering `label.name`, so the set is correct even if the payload's issue object predates the label) and `matchIssueComment` (`issue.labels[].name`). This is stronger provenance than the caller-attested labels the `POST /v0/runs` path receives.
- **Fail-closed.** A `Match` error refuses (never `if err != nil { admit }` by analogy with the package's advisory fail-open sweeps), and an unsatisfied criterion refuses. A workflow with no `applies_to`, or a `paths`-only declaration (which does not constrain admission), admits — the plan gate enforces `paths` for webhook-created runs like any other. The `Match`-error branch is defense in depth: `ParseBytes` runs `Validate` (rejecting malformed globs) and the admission half never carries `paths`, so it is unreachable at admission and pinned by a structural tripwire (`TestAppliesToWebhook_UnevaluablePredicate_FailsClosed`), mirroring the server's `TestAppliesTo_AdmissionPhase_CannotProduceAMatchError`. The branch cannot be driven end to end, but its two OBSERVABLE effects — the "could not be evaluated" fail-closed refusal message and the `evaluation_error` audit payload field — are covered behaviorally by `TestAppliesToWebhook_MatchError_RendersEvaluationErrorAndRefusesShape` (the webhook analog of the server's `TestAppliesTo_M13_MatchError_FailsClosed`), so they are not left to the tripwire's promise alone.
- **Placed BEFORE the protection gate on purpose** (operator ruling condition 2): routing answers whether the run should exist at all, which is more actionable than a protection complaint about a run that was never going to be admitted. `TestDispatcherHandle_AppliesTo_RunsBeforeProtectionGate` pins the order (a refusal short-circuits before `GetBranchProtection` is called).
- **Best-effort audit + comment, NEVER softening the refusal.** On refusal it writes a `run_rejected_applies_to` global-chain entry (system actor, `github-webhook` subject) — the SAME category the server seam writes, so one audit query covers both — and posts `NotifyRunNotApplicable` on the triggering issue. A nil/failing audit repo or a nil/failing notifier logs and leaves the refusal intact (the decision already went the safe way). This is the deliberate inverse of the override GRANT, which fails CLOSED on the same failure because it records an exception, not the safe outcome.

## GitLab run creation + CI-failure retry (E45.22 / #2043)

`gitlab_dispatch.go` (`handleGitLabCreateRun`) and `gitlab_ciretry.go` (`handleGitLabCIRetry`) unpark the GitLab half of the #1861 plumbing. `Dispatcher.Handle` routes to them on `ev.Forge == ForgeGitLab`; `MatchActionCIFailureRetry` is shared vocabulary, so the routing — not the matcher — chooses the handler.

- **Authorization FIRST (fail-closed).** `Dispatcher.GitLabProjects` (a `GitLabProjectAuthorizer`) must vouch for the payload's project before ANY forge call. The GitLab receiver authenticates a delivery by comparing `X-Gitlab-Token` to one shared deployment secret and GitLab signs no HMAC over the body, so the project a payload names is untrusted input — and it steers BOTH selectors: `ev.CredentialRef` (`gitlab:<project_id>`) picks the credential and the project the pipeline is created in, while `ev.Repo` (`path_with_namespace`) picks the project the executable spec is READ from. The gate binds the pair against the ADR-057 `installations` table (`gitLabProjectRegistry` in `backend/cmd/fishhawkd/serve.go`: a registered `provider='gitlab'` row whose recorded `project_path` equals the payload path EXACTLY, and whose account's `account_key` is still that path's namespace segment — E45.26 / #2877 tightened the path half from namespace-level to exact). Unlike the nil-means-off seams below, a NIL authorizer REFUSES — no registry, no GitLab run creation. Every refusal writes a `run_rejected_misconfigured` global-chain row whose `reason` names which of `gitlab_project_registry_unwired` / `gitlab_project_ref_absent` / `gitlab_project_authorization_lookup_failed` / `gitlab_project_not_registered` / `gitlab_project_path_unbound` applied.

  `gitlab_project_path_unbound` (E45.26 / #2877) is the one refusal carried on an ERROR value rather than a `false`: an authorizer returns the `ErrGitLabProjectPathUnbound` sentinel when the credential ref resolves to a registered installation that records NO project path — the shape every row registered before migration `0078` has. `authorizeGitLabProject` classifies it (via `errors.Is`, so a wrapped sentinel still lands) AHEAD of the generic error arm, so an operator who upgraded without re-registering gets a named, actionable reason instead of a generic lookup failure. The sentinel is declared in THIS package, beside the `GitLabProjectAuthorizer` interface, because the dispatcher must `errors.Is` it and the production implementation lives in package `main`. Both entry points route their refusal through that single reason-selection branch, so the reason is identical on `create_run` and `ci_failure_retry`. Remedy: `fishhawkd installation list` marks such rows `(unbound)`; re-register each with `--project-path` (`docs/deploy/gitlab.md`). The GitHub path needs no analogue: its `installation_id` arrives inside an HMAC-signed payload.
- **Spec read.** `Dispatcher.GitLabFiles` is a `forge.FileFetcher`, not the `GitHubAPI`: the GitHub client's scope parse rejects a `gitlab:<project_id>` ref. Nil leaves GitLab run creation OFF (log + skip), never a run minted against an unread spec.
- **Run shape.** `runner_kind=gitlab_ci` as an ADR-045 creation-time hint with `runner_kind_resolved` false; `installation_ref = "gitlab:<project_id>"`; nil `installation_id`. `auditcheckpublisher` routes this shape's commit status to the GitLab forge (`POST /projects/:id/statuses/:sha`) — pinned by `TestPublish_DispatcherMintedGitLabRun_RoutesToGitLabForge`.
- **No branch-protection snapshot.** GitLab's protected-branches API contributes no required-status contexts, so taking one would produce an empty snapshot and the ADR-017 refusal would reject every GitLab run. Consequence, accepted: the GitHub retry path's "is this check required?" filter has no GitLab analogue; the GitLab path's gate is the (ref, sha) correlation plus the `on_ci_failure` cap.
- **Classification.** `matchGitLabCIFailure` classifies `object_kind: "pipeline"` with `status: "failed"` and SKIPS `object_kind: "build"`. Both payload shapes decode (the Job Hook carries ref/sha/pipeline_id at the top level), so the build skip is a real control — see the counterfactual note in `docs/architecture/webhook-dispatcher.md`.
- **Correlation.** ref == the run's ADR-035 run branch AND sha == the run's recorded implement-stage head SHA. The merge-request iid narrows only. First-stage retry is DEFERRED (the first pipeline runs on the default ref); every non-correlation writes a `ci_retry_skipped` audit row naming its reason — one of `first_stage_pipeline_on_non_run_branch`, `merge_request_pipeline_ref_not_a_run_branch`, `no_candidate_run_owns_pipeline_ref`, `pipeline_sha_does_not_match_run_head_sha`, `run_head_sha_lookup_failed`, `run_lineage_cancelled`, `retry_policy_unresolvable_from_cached_spec`, `gitlab_pipeline_trigger_unconfigured`, `run_has_no_credential_scope`. A non-run-branch pipeline that is identifiably a MERGE-REQUEST pipeline — by `object_attributes.source == "merge_request_event"` (the documented Pipeline Hook discriminator and the primary signal) OR by a `refs/merge-requests/<iid>/{head,merge}` ref (a defensive breadth arm inferred from the CI-variable / merged-results docs, which may never fire on a real Pipeline Hook) — draws `merge_request_pipeline_ref_not_a_run_branch` instead of the first-stage reason, because an MR pipeline is neither first-stage nor on the default ref and the first-stage reason asserts something affirmatively false about it (E45.30 / #2881). A non-zero `merge_request.iid` is deliberately NOT a signal: GitLab attaches that block to branch pipelines with an associated open MR.
- **Pre-flight dispatchability, and the deliberate divergence from the GitHub path (E45.25 / #2876).** `runnerbackend.GitLabCI.TriggerStage` returns nil on BOTH of its fail-closed warn-skip branches (nil `Trigger`; zero `p.Scope`), which the caller cannot distinguish from a created pipeline — so a nil trigger or a legacy parent with a nil/empty `installation_ref` used to transition the first retry stage to `dispatched` and audit outcome `dispatched` with no pipeline behind it. `handleGitLabCIRetry` now refuses both preconditions BEFORE `run.ChildParamsFrom`, with reasons `gitlab_pipeline_trigger_unconfigured` and `run_has_no_credential_scope`. This does NOT match the GitHub path, on purpose and with operator ratification: GitHub mints the child and CONVERTS each warn-skip into a `dispatchErr` (`errCIRetryGitHubUnconfigured` / `errCIRetryNoInstallation`), leaving a persisted child with an untransitioned stage and a `dispatch_failed` row, whereas GitLab leaves no child at all. A minted child consumes the single retry slot `runs_retry_child_once_idx` enforces (`retry_attempt = parent.RetryAttempt + 1`), so a child that never dispatched permanently occupies the attempt a corrected deployment would otherwise use. The guard resolves the `gitlab_ci` backend ONCE and reads that instance's own `Trigger` field — the field `TriggerStage` consults on the instance actually dispatched — so guard and backend cannot diverge by construction; resolving `d.gitLabTrigger()` a second time would re-enter the process-global `forge.Get` and make the equivalence a matter of registry stability.
- **Dedup.** Constraint-based on BOTH retry paths via `runs_retry_child_once_idx`; `retry_attempt` is always `parent.RetryAttempt + 1` so both racing inserts collide. See the dispatcher doc for the full contract.
- **The retry path runs the SAME authorization gate as the create path**, before candidate lookup, child creation, or `TriggerStage`. It is not optional and the `(ref, sha)` correlation is not a substitute for it: a run branch (`fishhawk/run-<short>`) and its head SHA are both readable from a public branch listing, so correlation bounds the blast radius of a forged Pipeline Hook without binding its project identity to anything. The shared refusal audit's `path` field (`create_run` / `ci_failure_retry`) says which gate refused, since both write `run_rejected_misconfigured`.
- **Audit attribution.** A `ci_retry_skipped` row is chained to a run ONLY when that run owns the pipeline's ref; otherwise it is global-chained. Chaining to "the newest `gitlab_ci` run for the project" would deposit a row for every failed default-branch pipeline onto an unrelated run's audit stream.
- **`matchGitLabIssue` / `matchGitLabNote` MUST set `Match.TriggerSource`.** `handleGitLabCreateRun` passes it straight to `CreateRun`, and `runs_trigger_source_check` rejects the empty string — so a matcher that leaves it unset makes every GitLab run creation fail at the INSERT and 5xx into a redelivery loop. This shipped broken and no unit test saw it: every test in this package uses a fake run repository, which enforces no constraint. It was caught only by `orchestrator.TestGitLabTrigger_PersistedRunReachesGitLabPipelineDispatch`, which drives an admitted trigger through the real dispatcher into a real Postgres repository and back out into the orchestrator's dispatch path. **Keep that test**: it is the only coverage of the webhook↔storage↔orchestrator seam, and the per-layer tests on either side of it stay green through exactly the breakage it catches. The value is `github_issue` on both forges — the enum's issue-anchored member (`Run.IsIssueAnchored`), not a GitHub-only marker.
