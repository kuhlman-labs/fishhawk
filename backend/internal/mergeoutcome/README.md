# mergeoutcome

Post-merge OUTCOME facts for a merged run (ADR-085 / #3777 rules 3 and 6; E82.2 / [#3779](https://github.com/kuhlman-labs/fishhawk/issues/3779)). Two chained, system-actor (`merge-outcome-observer`) audit categories, both registered in `backend/internal/audit/categories.go`, both INTERNAL fact records (not issue-comment surfaces):

| Category | One row per | Source | Writer |
|---|---|---|---|
| `run_merge_reverted` | (run, reverting commit) — deduped on `reverting_commit_sha` | `github_push_webhook` | `RevertObserver.ObservePush` (`revert.go`), driven by the server's `push` route |
| `run_merge_ci_observed` | (run, merge commit) — deduped on `merge_commit_sha` | `github_check_runs_poll` | `CITicker.Tick` (`ticker.go`, classification in `ci.go`), off by default |

**Forge-attested facts only.** Rows carry SHAs, PR numbers and URLs, file-level diff counts, check names and conclusions, forge timestamps and Fishhawk-derived enums. No commit message, PR title/body, check output or other prose is recorded: commit text is at most a POINTER to a candidate run that is then confirmed against forge state. The observer and ticker dependency interfaces carry no artifact, review-concern or plan store. Pinned by `TestRunMergeReverted_PayloadKeyAllowList` and `TestRunMergeCIObserved_PayloadKeyAllowList` (each recorded payload's key set equals the allow-list). Incident attribution is out of scope (#3959).

Both appends go through `appendDeduped` (`mergeoutcome.go`): the Postgres store's `audit.DedupedChainAppender` scans and appends in one transaction under the run-row lock; the fallback (test fakes) lists then appends and fails closed on a list error.

## `run_merge_reverted` — revert detection

Inputs: a GitHub `push` delivery to the repository's DEFAULT branch (`ref == refs/heads/<repository.default_branch>`, not a delete; a missing `default_branch` fails closed). The server route, execution model and redelivery semantics live in `backend/internal/server/README.md` § "Default-branch revert detection".

- **Signals (pointers).** `This reverts commit <sha>` trailers (7–40 hex) resolve through `ListPullRequestsForCommit`; a `Revert "... (#N)"` subject, used only when the commit carries no trailer, resolves to `<repository.html_url>/pull/N`. A revert-of-revert subject without a trailer yields no signal. Commits with no signal cost zero forge calls. At most `DefaultMaxRevertSignals = 50` signals are resolved per push; the rest are dropped with a `revert_signals_truncated` log event.
- **Confirmation.** Candidate runs are `ListRuns{Repo, PullRequestURL}`; each candidate PR is confirmed by `GetPullRequest`: merged, a `merge_commit_sha`, and on the trailer path that SHA must start with the trailer SHA. Unconfirmed candidates record nothing.
- **Attestation (operator condition 1).** For every confirmed candidate the reverting commit's and the merge commit's file lists (`githubclient.GetCommitFiles`) are compared by `ClassifyAttestation`: `inverse_diff` (every file the revert touches is in the merge, each with additions/deletions swapped, and every merge file covered), `partial_inverse` (the same over a strict subset of the merge's files) or `signal_only` (anything else — a file not in the merge, counts not inverted, a revert touching no files, or an unavailable/truncated file list on either side). The row is recorded in every case with `attestation` and `attestation_reason`. **The beta projection must count only `inverse_diff` or `partial_inverse` as a revert outcome**; `signal_only` is a recorded pointer the forge diffs do not corroborate.
- **Forge calls** get 3 attempts with exponential backoff, retrying only network errors and 5xx (`withRetry`, `isTransient`).
- **Payload:** `repo, pull_request_url, pull_request_number, merge_commit_sha, merged_at, reverting_commit_sha, pushed_ref, push_after_sha, delivery_id, detection (revert_trailer|revert_subject), attestation, attestation_reason, observed_at, source`.

Residuals: a revert whose message carries NO signal is not detected (follow-up: signal-less inverse-diff scanning); detection is push-webhook only, so a delivery lost while fishhawkd is down, a local install without the webhook relay (`docs/local-webhook-relay.md`), or an observation that fails after the 202 records nothing, and a same-GUID redelivery cannot recover it; the `push` payload's `commits` array holds at most 2048 commits; only the first page (300 files) of a commit's files is read, and a truncated list attests `signal_only`; GitHub only.

## `run_merge_ci_observed` — merge-commit CI at maturity

`CITicker` runs only with `--enable-merge-outcome-observer` (`FISHHAWKD_ENABLE_MERGE_OUTCOME_OBSERVER=true`). `NewCITicker` is the flag-to-ticker constructor `fishhawkd serve` calls: it returns nil and a named reason (`disabled`, `RunRepo unconfigured`, `AuditRepo unconfigured`, `GitHub client unconfigured (no app id?)`) — the GitHub client is taken as the CONCRETE `*githubclient.Client` so a nil one is caught before the `CIForge` interface wrap. Defaults: interval `10m` (`--merge-outcome-interval`), window `6h` (`--merge-outcome-ci-window`), lookback 14 days, 20 forge evaluations per tick, terminal deadline 7 days after maturity, backoff cap 12h.

**Eligibility keys on MERGE-EVIDENCE time, not `created_at` (operator condition 4).** Each tick reads, via `audit.Repository.ListAll` by category, every `pr_merged`, `post_merge_observed` and `merge_observation_recorded` row and every existing `run_merge_ci_observed` row. A run's merge-evidence time is the timestamp of its EARLIEST merge-evidence row; it is a candidate when that time is within the lookback, it has no `run_merge_ci_observed` row (zero forge calls otherwise), and evidence + window is at or before now (a DB-only maturity pre-filter). The run's `created_at`/`updated_at` are never consulted, so a run created long before it merged is evaluated (`TestTick_OldCreatedRecentlyMerged_Evaluated`). The lookback is never narrower than window + terminal deadline + 1 day, so a run reaches its terminal row before it leaves the scan. Cost: four category listings per tick (DB-only), growing with the number of merged runs.

**Per candidate.** The run must have a `pull_request_url` naming its own repository, a github credential family (a `<forge>:<id>` `installation_ref` other than `github:` is skipped) and an installation id; a run failing these is skipped for the process lifetime. Then `GetPullRequest` (merged, `merge_commit_sha` and `merged_at` required); maturity is re-derived from the FORGE: `matures_at = merged_at + window`, and a run not yet forge-mature is held until then without counting a failure. Then `ListCheckRunsForRef(merge_commit_sha)` with `filter=all`, then `ClassifyMergeCI`, then one deduped append.

**Conclusion fixed at maturity (operator condition 3).** Check runs are listed with `filter=all` — every attempt. Per check name, attempts are grouped by check suite (a re-run lands in the same suite): attempts STARTED after `matures_at` are ignored, and the most recent attempt (highest check-run id) whose `completed_at` is at or before `matures_at` decides. A suite with attempts but none completed by maturity is `missing` with reason `not_concluded_by_maturity`, even if it later succeeded; a check that failed before maturity and was re-run green after maturity is `red`. The same name in several suites (another workflow or app) is a duplicate: any failed suite fails the name, else any missing suite makes it missing. Conclusions: `success|neutral|skipped` pass; `failure|timed_out|action_required|startup_failure` fail; anything else (`cancelled`, `stale`, empty, unknown, never completed) is missing (`unconcluded`), never green.

**Verdict**, in order: `missing` / `required_checks_unknown` when the run has no required-checks snapshot (even if every observed check passed); `missing` / `checks_truncated` when the listing was incomplete (5-page cap); `red` when any required check failed; `missing` when any required check is missing (`required_check_absent`, `not_concluded_by_maturity` or `required_check_unconcluded`, from the first missing check in snapshot order; `missing_check_reasons` holds every one); else `green`. The required set is `snapshot.Contexts` minus Fishhawk's own PR-head merge gate `fishhawk_audit_complete` (`auditcheckpublisher.CheckName`, recorded in `excluded_checks`), which never runs on a merge commit. An empty required set — authoritatively empty, or emptied by that exclusion — evaluates the observed set instead (names with an attempt started by maturity); nothing observed is `missing` / `no_checks_reported`.

**No starvation (operator condition 5).** Candidates are evaluated oldest-maturity-first. A per-run failure (forge error after its 3 attempts, unmerged PR, missing merge facts, audit append error) enters an in-memory exponential backoff (interval × 2^(failures−1), capped at 12h); a run in backoff is skipped WITHOUT spending the per-tick cap. A run still unobservable `DefaultCITerminalAfter` (7 days) after maturity records a terminal `missing` row with `missing_reason: observation_failed` and `observation_error_class` set to the last failure's class (`not_found`, `forbidden`, `not_installed`, `validation`, `transient`, `forge_error`, `pr_not_merged`, `merge_facts_missing`, `audit_append`), so it leaves the queue. The backoff is per-process: a restart retries every queued run once; the terminal deadline is computed from the chain, so it survives a restart.

**Payload:** `repo, pull_request_url, pull_request_number, merge_commit_sha, merged_at, merge_evidence_at, matures_at, observed_at, window_seconds, conclusion (green|red|missing), missing_reason, missing_check_reasons, observation_error_class, required_checks, required_checks_source (run_snapshot|run_snapshot_empty|run_snapshot_absent), excluded_checks, passed_checks, failed_checks, missing_checks, checks_observed, checks_truncated, source`. `observed_at` is recorded alongside `matures_at`; a projection counts the outcome only once its class window has elapsed.

**Rate-limit cost.** After the backfill, one `GetPullRequest` plus 1–5 check-run pages per merged run, once. The first enabled tick starts backfilling up to 14 days of merged runs at 20 evaluations per tick.

**Residuals (operator condition 7).**
- **PR-only required checks.** A required check that runs only on `pull_request` events and never on default-branch pushes records `missing` (`required_check_absent`) on EVERY merge; the projection must read `missing_check_reasons` rather than treat such a `missing` as a CI regression.
- **Check runs only.** Only the Checks API is read; commit STATUSES (the legacy Statuses API) are not, so a required context reported only as a commit status reads as absent.
- `cancelled` (often a concurrency-group supersession on the default branch) and `stale` record `missing`, not `red`.
- GitHub only; GitLab-family runs are skipped. The done-means holds only where the operator enables the flag.

## Tests

`ci_test.go` pins the classifier (exclusion, nil snapshot, red/missing precedence, unconcluded table, empty snapshot, truncation, the maturity cut-off and re-run cases, duplicate names). `ticker_test.go` pins the maturity gate, already-observed skip, per-tick cap, family skip, merge-evidence eligibility, lookback, ordering, backoff, terminal row, constructor reasons, and `TestTick_PG_RealClient_RecordsCommittedRow` — a REAL `githubclient.Client` against an httptest mux with pgtest-backed run and audit repositories, asserting the committed row. `revert_test.go` / `mergeoutcome_test.go` pin the revert observer and `appendDeduped`; the webhook cross-boundary tests live in `backend/internal/server/merge_outcome_test.go`.
