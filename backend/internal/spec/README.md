# backend/internal/spec

Workflow-spec parsing, semantic validation, and version-routed embedded JSON Schemas for `.fishhawk/workflows.yaml`.

## Version routing (ADR-046 / ADR-067)

`parse.go` embeds the `workflow-v0`, `workflow-v1`, and `workflow-v2` schemas and compiles each at package init. `ParseBytes` reads the spec's `version`, parses its **major** component, and validates against the schema for that major via the `embeddedSchemas` routing table:

- `0.x` → `workflow-v0.schema.json`
- `1.x` → `workflow-v1.schema.json`
- `2.x` → `workflow-v2.schema.json`
- missing / non-string / unparseable `version` → falls through to v0 (preserving the existing required-version error, so a malformed version never silently passes)
- well-formed but unrecognized major (`≥ 3`) → **fails closed** with a `*SchemaError` naming the supported majors (derived from the table)

Adding a major means embedding its schema, appending a `{Major, Path}` row to `embeddedSchemas`, and adding an `EmbeddedSchemaHashVN()` accessor + `/healthz` `schemas` entry — everything else (`computeSupportedMajors`, `computeSchemaHashes`, `schemaForVersion`) derives from the table. See the "A NEW workflow MAJOR" checklist in `AGENTS.md`.

**workflow-v2 (ADR-067 / #2213)** BEGAN as a structural copy of v1: at the copy every `$defs` entry and non-`version` property was validation-identical (same keys, types, enums, `required`, `additionalProperties`, and `oneOf`/`anyOf`/`allOf` branches), with only the descriptions, `$id`, `title`, and the `version` property differing. Its enum is the single token `"2"` (no minor chain; the dotted `"2.0"` form routes here by major but the enum rejects it). The E52 children now diverge it, so the copy-fidelity check is an ALLOW-LIST diff rather than deep equality: `TestV2DivergesFromV1OnlyByLicensedDeltas` (the re-scoped `TestV2StructurallyMatchesV1`, per the #2320 disposition) walks both decoded mirrors and asserts the divergence set equals EXACTLY the declared `licensedV2Deltas` table. The assertion is two-directional — an unlisted divergence fails (the accidental-drop net #2213 bought) and a listed path that no longer diverges fails (a stale entry cannot rot) — and its normalizer is position-aware, so a `description` key is stripped only as a schema annotation, never as a property NAME inside a `properties` / `$defs` map. Guardrail: past roughly 15 licensed entries the allow-list stops being a readable statement of intent, and #2320 should be revisited to retire the test rather than keep appending.

## workflow-v2 removed back-compat forms (E52.3 / #2215)

`v2removed.go` holds the version-gated raw-document sweep for the two back-compat surfaces v2 deletes.

| Removed in v2 | Replacement |
| --- | --- |
| `operator_agent.must_page_human: [reviewer_reject]` | `gating_reviewer_reject` / `advisory_reviewer_reject` |
| `reviewers.agent: <N>` | `reviewers.agents[]` (effective count = `len(agents)`) |

- **Why a sweep at all.** The schema already rejects both — the bare token falls out of the `must_page_human` enum, and `agent` becomes an undeclared property of an `additionalProperties: false` block — but neither generic message names the replacement. `checkV2RemovedForms` returns a `*SchemaError` that does.
- **Ordering.** `ParseBytes` runs the sweep AFTER version routing and BEFORE `schema.Validate`, so the actionable message wins over the generic one. Asserted by the message-content tests in `v2removed_test.go`, not assumed.
- **Version gate.** The sweep runs only for a routed major `>= 2`. `schemaForVersion` returns the routed major alongside the schema; the fall-through-to-v0 branches (missing / non-string / unparseable `version`) return major 0, so those paths keep their pre-existing required-version error verbatim, and an unsupported major fails closed at routing before the sweep.
- **Matching contract.** The walk is GENERIC — it matches by key name at any depth, reaching the workflow-level `operator_agent`, any per-gate `operator_agent`, and any stage's `reviewers` without encoding their positions. It deliberately OVER-TRIGGERS in exchange for never missing a legacy form: a legacy form in a position v2 does not permit is still reported with the removed-form message, so in an already-invalid document the legacy-form message may precede the genuine structural error. That trade is intentional (a position-aware sweep would re-encode schema structure E52 is actively restructuring) and is pinned by `TestCheckV2RemovedForms_MatchesByKeyNameNotPosition`. Map keys are walked in sorted order so the reported first match is deterministic.
- **CLI mirror.** `cli/internal/spec/validate.go` carries a byte-identical pair of messages and the same walk, wired into `ValidateBytes` under the same major gate and ordering — `fishhawk validate` is where a spec author most often meets these errors. The modules are deliberately separate, so both copies carry message-content assertions rather than sharing a constant.
- **Retained Go symbols.** No type, constant, or method is deleted. `PageEventReviewerReject`, `ReviewersConfig.Agent`, `AgentCount()`'s bare-count fallback, and `delegation.reviewerRejectClass` all stay — v0 and v1 documents still parse into the shared types. A v2 document simply cannot reach them, which is what satisfies the done-means structurally.

## workflow-v2 shape normalization (E52.6 / #2218)

`v2shape.go` holds the version-gated rewrite of the three surfaces v2 reshapes for legibility. Each is rewritten on the RAW decoded document into the representation v0/v1 already use, so the typed structs, every consumer, the `runs.drive` column and every read site are untouched — the reshape's blast radius outside that one file is zero by construction.

| v2 surface | Rewritten to |
| --- | --- |
| `constraints` as one OBJECT keyed by kind | a ONE-ELEMENT `[]any` carrying that object |
| workflow `auto_advance` | the `drive` key (`spec.Workflow.Drive`) |
| stage `needs: [<stage_id>]` | appended `inputs` entries `{artifact, from_stage}`; the key is DELETED |

- **Ordering is load-bearing.** `ParseBytes` runs, in this order: `checkV2RemovedForms` (before schema validation, so its actionable messages win) → `schema.Validate` → `normalizeV2Shapes` → the typed decode → `Validate`. Normalization runs AFTER validation so it never sees an unvalidated shape — a `constraints` value that is a string is the SCHEMA's error, not a normalizer panic (`TestParseV2_ConstraintsScalarIsSchemaError`) — and BEFORE the typed decode, which uses `DisallowUnknownFields`, so `auto_advance` and `needs` must be gone by then.
- **Version gate.** Like the removed-forms sweep, it runs only for a routed major `>= 2`. A v0/v1 document is never normalized and never re-resolved.
- **Why the constraints rewrite goes in THAT direction.** Collapsing the v0/v1 LIST into one canonical object needs a merge rule, and there is no rule that preserves current behaviour: five consumers fold a duplicate-kind document differently (`mergeConstraints` concat + min/max-wins, `flattenPathConstraints` concat + min-wins, `resolveDiffCoverageConfig` max-wins, `approvals.go` preflightDeploy **last**-wins, `trace.go` `deployEnvironmentForRun` **first**-wins), and on `[{allowed_environments: [staging]}, {allowed_environments: [prod]}]` the two deploy sites already disagree with each other — `prod` at the gate, `staging` on the deploy record. Concatenating would have silently loosened that gate. Rewriting an object INTO a one-element list is exact instead: an object's keys are unique, so it denotes exactly one `Constraint`, and one entry is the case all five folds agree on. The preservation proof is the characterization tests in `spec_test.go` and `backend/internal/server/deploy_legacy_constraints_test.go`, written and run green against unmodified HEAD before any production edit.
- **`needs` artifact derivation.** `plan` → `plan`, `implement` → `pull_request` (the whole of `$defs/input`'s artifact enum). Any other referent type has no default input artifact and is the ONE error the normalizer itself raises, at `/workflows/<wf>/stages/<i>/needs/<j>`, naming longhand `inputs:` as the escape.
- **TRADEOFF — a nonexistent `needs` referent.** It is expanded into an `inputs` entry with an EMPTY artifact and its `from_stage` set, so the EXISTING `from_stage` graph-shape rule fires with its unchanged message. The cost is that the error reports at `/inputs/<post-expansion-index>/from_stage` — an index into a position the author never wrote, carrying an artifact value the schema's own `input` enum would reject if it were re-validated (it is not; normalization runs after validation). This is deliberate, not a bug: one canonical error beats two competing ones, and no earlier semantic check trips on the empty artifact, so the error genuinely fires (`TestParseV2_NeedsRejectionModes`). Naming the offending `needs` entry as well would mean either editing that binding message — which #2219 depends on staying verbatim — or emitting a second competing error, so it was not done.
- **Constraint binding PATHS are version-aware, MESSAGES are not.** `validate.go` reports a v2 binding violation at `/constraints/<kind>` (from `Constraint.preflightKindName` / `postHocKindName`, fixed declaration order so a multi-kind object reports deterministically) and keeps the `/constraints/<index>` form below major 2. The three ADR-038 / #1888 messages are verbatim unchanged. A programmatically built `*Spec` with an empty `Version` resolves to major 0, preserving the index form for `Validate`-only callers.
- **CLI asymmetry (RATIFIED, #2323).** `cli/internal/spec` mirrors the two new rejection messages byte-identically and validates the `needs` SHAPE, but it is schema-only — no typed decode, no graph-shape pass — so it does not resolve `needs` referents at all. Both referent errors surface server-side only. Documented for spec authors in `docs/spec/workflow-v2.md`.

## workflow-v2 produced-artifact constraint binding (E52.7 / #2219)

`validate.go` binds the POST-HOC diff constraints (`max_files_changed`, `forbidden_paths`, `allowed_paths`, `required_outcomes`, `diff_coverage`) to what a stage PRODUCES rather than to its type name, at routed major `>= 2` only. A v2 stage carrying one must declare the `pull_request` artifact; the violation reports at `/constraints/<kind>` naming the kind, the reason, and both fixes (declare the artifact, or remove the constraint).

- **Why artifact-keyed.** The stage-type enum is unchanged and the names are RETAINED (ADR-067 §2 — no rename), but they are general: plan / implement / review read as propose / apply / gate. A grooming-shaped workflow runs on those same types and produces no diff at all (`docs/spec/examples/workflow-v2-backlog-grooming.yaml`), so a type-keyed rule silently accepts a constraint that can never be evaluated. `Stage.producesDiff` is the predicate: `pull_request` is the diff signal because it is the only member of the closed artifact set that DENOTES a code change — `deployment` is delegated, `acceptance` is a verdict, `plan` is a proposal.
- **Absent `produces` reads as NO DIFF (ratified).** Omitting the list does not exempt a stage. The permissive "absent means unknown" reading would let any stage keep a diff constraint by staying silent — the exact case #2219 wants rejected. It IS a real behaviour change for a v2 author, which is why the rule is version-gated and the message names the fix explicitly. Documented for spec authors in `docs/spec/workflow-v2.md` under a callout, not buried in a table.
- **Version gate (major `>= 2`).** v0/v1 documents legitimately declare post-hoc constraints on an implement stage with NO `produces` list — the v1.5 document in `TestParse_DiffCoverage_NoRegression` is the concrete case — so applying the rule below major 2 would newly reject valid specs. Below 2 the binding stays type-keyed, unchanged. `TestValidate_ProducedArtifactBinding_NotAppliedBelowMajor2` pins both majors.
- **ORDER IN THE CONSTRAINT LOOP IS A CONTRACT**, not an artifact of where the branch landed. The two ADR-038 checks run FIRST, the produced-artifact rule SECOND, the #1888 `diff_coverage` block LAST:
  1. A **deploy** stage keeps its existing ADR-038 post-hoc message and never sees the new one (it declares no `pull_request` either, so an unguarded rule would shadow it).
  2. A **mixed v2 constraints OBJECT** — one `Constraint` declaring both a pre-flight and a post-hoc kind, expressible only since E52.6 normalized the object into a single value — reports the PRE-FLIGHT diagnosis, at `/constraints/<pre-flight kind>`. DELIBERATE: a pre-flight deploy constraint on a non-deploy stage is wrong regardless of what the stage produces, and fixing it is a prerequisite for the produced-artifact question even arising, so the older and more specific diagnosis wins. This holds whether or not the stage produces a diff. Pinned characterization-style by `TestValidate_MixedPreflightPostHocConstraintObject_BindingOrderPinned` (cases (a) and (b) captured green against the pre-#2219 loop, so they are a preservation proof; case (c) is the new interaction, chosen rather than inherited from insertion position).
  3. A stage that DOES produce `pull_request` but is typed other than `implement` still gets the verbatim #1888 implement-only `diff_coverage` message — the older rule stays reachable at v2. Both directions are pinned by `TestValidate_V2DiffCoverageOrdering_NeitherRuleShadowsTheOther`; the consequence for the v2 fixtures in `TestValidate_DiffCoveragePathsAreVersionAware` is that each now declares `pull_request` to reach that branch.
- **The three pre-existing binding MESSAGES are still verbatim unchanged.** This rule was added as a fourth branch, never by editing them. `TestValidate_V2ExistingBindingMessagesUnchanged` pins all five bindings at version `"2"`.
- **CLI asymmetry (#2323).** `cli/internal/spec` is schema-only, so `fishhawk validate` does NOT report this binding — it surfaces server-side at run creation. Only the mirrored schema descriptions changed on the CLI side; the edit is `description`-only (a pure Draft 2020-12 annotation), which is why it adds no `licensedV2Deltas` entry.

## Agent-version compatibility ranges (v1.4, E32.13 / #1743)

`executor.agent_version` + `reviewers.agents[i].agent_version` declare the semver comparator RANGE (e.g. `">=2.1 <2.2"`) of agent CLI versions a workflow was validated against, failing dispatch loudly when the resolved CLI version falls outside it (the #1741 opaque-CLI-drift diagnosis).

- Matcher/validator: `spec.ValidAgentVersionRange` / `spec.MatchAgentVersionRange` in `backend/internal/spec/agentversion.go`, with a byte-parity twin in `cli/internal/spec/agentversion.go`. Called by the semantic validator (`validate.go`).
- The executor range is threaded to the runner via `promptResponse.agent_version_range` (`backend/internal/server/prompt.go`).
- The runner's own duplicated `matchAgentVersionRange` (`runner/cmd/fishhawk-runner/main.go`) fails the stage **pre-spawn category-C** (`agent_version_mismatch`) on an out-of-range resolved (#1769-probed) version, or degrades-and-proceeds (`agent_version_uncomparable`) on an unprobeable one.
- Absent range = no constraint.
- The binary pin stays a host concern via `FISHHAWK_AGENT_BIN` / `FISHHAWK_CODEX_BIN` (#1741 / #1769).
- The reviewer-side (codex-only) enforcement is a sibling change.
