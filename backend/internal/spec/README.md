# backend/internal/spec

Workflow-spec parsing, semantic validation, and version-routed embedded JSON Schemas for `.fishhawk/workflows.yaml`.

## Version routing (ADR-046 / ADR-067)

`parse.go` embeds the `workflow-v0`, `workflow-v1`, and `workflow-v2` schemas and compiles each at package init. `ParseBytes` reads the spec's `version`, parses its **major** component, and validates against the schema for that major via the `embeddedSchemas` routing table:

- `0.x` → `workflow-v0.schema.json`
- `1.x` → `workflow-v1.schema.json`
- `2.x` → `workflow-v2.schema.json`
- missing / non-string / unparseable `version` → falls through to v0 (preserving the existing required-version error, so a malformed version never silently passes)
- well-formed but unrecognized major (`≥ 3`) → **fails closed** with a `*SchemaError` naming the supported majors (derived from the table)

Adding a major means embedding its schema, appending a `{Major, Path}` row to `embeddedSchemas`, and adding an `EmbeddedSchemaHashVN()` accessor + `/healthz` `schemas` entry — everything else (`computeSupportedMajors`, `computeSchemaHashes`, `schemaForVersion`) derives from the table. See the "A NEW workflow MAJOR" checklist in `AGENTS.md`.

**Deprecation posture: v0 and v1 are FROZEN, not removed, and no removal is planned (E52.9 / #2221).** Both schemas stay embedded, compiled, routed and validated forever, so every audit-log run and every already-committed spec keeps working with no action — that is the reason the routing table carries every major rather than the newest one. A **new** spec on v0 or v1 is still **accepted**: nothing in `ParseBytes` rejects a `0.x` / `1.x` document, and the version-gated v2 passes (`checkV2RemovedForms`, `resolveV2Reuse`, `normalizeV2Shapes`, `deriveV2Autonomy`) are all no-ops below major 2. It is nonetheless **discouraged** — `fishhawk init` emits v2 presets, the reuse / shape / autonomy work exists only at v2, and `fishhawk migrate-spec` (E52.8 / #2220) translates a v1 document with an approval-eligibility report. No removal date is set. The spec-author-facing statement of the same posture is `docs/spec/workflow-v2.md` § *v0 and v1: deprecation posture*, and the operator-facing one is `docs/spec/README.md` § *Versioning*; keep the three in agreement.

**workflow-v2 (ADR-067 / #2213)** BEGAN as a structural copy of v1: at the copy every `$defs` entry and non-`version` property was validation-identical (same keys, types, enums, `required`, `additionalProperties`, and `oneOf`/`anyOf`/`allOf` branches), with only the descriptions, `$id`, `title`, and the `version` property differing. Its enum is the single token `"2"` (no minor chain; the dotted `"2.0"` form routes here by major but the enum rejects it). **v2 is no longer a copy, and the copy-fidelity check is RETIRED (#2320, settled).** The net #2213 bought was against an ACCIDENTAL drop *during the copy*; five E52 children have since edited v2 deliberately, so the interim allow-list diff (`TestV2DivergesFromV1OnlyByLicensedDeltas` against the `licensedV2Deltas` table — the #2320 option-2 disposition ratified at #2215's gate) had become a 15-entry changelog of intended divergences rather than a statement of an invariant, and its own guardrail said to retire it rather than keep appending. It, the allow-list, the position-aware normalizer and the diff walker are gone.

What replaced it is `TestFrozenMajorsV0AndV1AreImmutable` (#2320 option 1): the still-live, permanent invariant is that **v0 and v1 are FROZEN**, asserted in prose by every E52 child and enforced mechanically by nothing. It pins the canonical-JSON SHA-256 of the embedded v0 and v1 mirrors against literals read off the production `EmbeddedSchemaHash()` / `EmbeddedSchemaHashV1()` accessors, so reformatting or reordering a frozen schema does not fire it but changing what it SAYS does. `TestFrozenMajorPinDetectsContentChange` proves the pins have teeth (an added or removed `$defs` entry changes the digest; the control case re-derives both pins from the shipped bytes, so a mistyped constant cannot pass). It needs no CLI twin: `scripts/sync-schemas` makes the canonical copy and both module mirrors byte-identical, so a canonical edit reaches the backend mirror and trips the pin, while a mirror-only edit trips the schema-sync drift check in `scripts/test verify` and CI. v2 is deliberately unpinned — it is the LIVE major, and its own grammar is covered directly by the version-gated `TestParseV2_*` / `v2removed` / `v2reuse` / `v2shape` suites, which assert what v2 ships rather than how closely it still resembles a frozen ancestor. **The per-child sections below are now the only record of what each child licensed and why.**

**The frozen pin is a tripwire, not a prohibition — and E52.12 / #2322 is the first edit to trip it deliberately.** Its failure message states the path: justify editing a shipped major in the PR body, then update the pin in `frozenMajorSchemaHashes`. #2322 corrected `$defs.reviewers_config.description` on **all three** majors, v0 and v1 included, so both frozen digests were re-pinned from the values the failing run of each accessor reported. The edit is **DESCRIPTION-ONLY**: no property, enum, constraint, `required` list or `$defs` entry changed on either frozen major, and a JSON Schema `description` is an annotation (Draft 2020-12 §10.3), so every document that validated before still validates. Leaving v0/v1 stale was rejected because `docs/spec/workflow-v0.schema.json` is a surface an operator reads directly. After re-pinning, `TestFrozenMajorPinDetectsContentChange` (including its `control` case) and `TestFrozenMajorsV0AndV1AreImmutable/distinct` were re-run GREEN — they are what proves the new constants still detect a real content change and were not copy-pasted from each other or from the live v2 digest.

**What #2322 corrected: an absent `reviewers` block configures NO reviewers.** The schema descriptions and `ReviewersConfig`'s doc comment had claimed the backend "defaults to `{human:1}`" for an absent block. Nothing has ever honoured that: `Stage.Reviewers` stays nil, the effective agent count is 0, and `planreview.ResolveAuthority` resolves **gateless**. `ReviewersConfig.Human` is read at exactly one site (`planreview.ResolveAuthorityWithSource`), which short-circuits on `AgentCount()==0` *before* reaching it — so materializing the default would have been observationally inert while the docs kept promising an approval that never arrives. Human approval gating is declared by a stage gate of type `approval` (read by `webhook.hasApprovalGate`), never by `reviewers.human`. This is also the same supplementation §"reviewers is taken whole" already refuses at the `defaults` ladder, applied more broadly. Pinned behaviorally by `TestParse_NoReviewersBlockIsGatelessOnEveryMajor` here and its cross-layer companion `TestResolveAuthority_ParsedSpec_NoReviewersBlockGatelessOnEveryMajor` in `planreview`, which drive real schema-validated bytes at v0, v1 and v2 through parse and authority resolution.

## workflow-v2 removed / renamed back-compat forms (E52.3 / #2215, E52.5 / #2217)

`v2removed.go` holds the version-gated raw-document sweep for the eight back-compat surfaces v2 deletes, reshapes or renames. Two are the E52.3 removals; two are the E52.6 reshapes (`drive`, list-form `constraints`); the fifth is the E52.5 stage-budget rename below; two are the E52.2 approval removals (gate `approvers`, top-level `roles`) — see *workflow-v2 approval predicate consolidation* below; the eighth is the E52.10 `operator_agent` removal — see *workflow-v2 autonomy grammar* below.

| Removed / renamed in v2 | Replacement |
| --- | --- |
| `operator_agent.must_page_human: [reviewer_reject]` | `gating_reviewer_reject` / `advisory_reviewer_reject` |
| `reviewers.agent: <N>` | `reviewers.agents[]` (effective count = `len(agents)`) |
| `budget.max_runtime_minutes: <N>` | `budget.max_runtime` (Go duration; `15` → `15m`) — E52.5 / #2217 |
| `operator_agent: {may_*, must_page_human, model_policy}` | `actions: {<class>: {mode, when}}` + `autonomy: <tier>` — E52.10 / #2222 |

- **Why a sweep at all.** The schema already rejects all — the bare token falls out of the `must_page_human` enum, and `agent` / `max_runtime_minutes` become undeclared properties of an `additionalProperties: false` block — but no generic message names the replacement. `checkV2RemovedForms` returns a `*SchemaError` that does.
- **Ordering.** `ParseBytes` runs the sweep AFTER version routing and BEFORE `schema.Validate`, so the actionable message wins over the generic one. Asserted by the message-content tests in `v2removed_test.go`, not assumed.
- **Version gate.** The sweep runs only for a routed major `>= 2`. `schemaForVersion` returns the routed major alongside the schema; the fall-through-to-v0 branches (missing / non-string / unparseable `version`) return major 0, so those paths keep their pre-existing required-version error verbatim, and an unsupported major fails closed at routing before the sweep.
- **Matching contract.** The walk is GENERIC — it matches by key name at any depth, reaching the workflow-level `operator_agent`, any per-gate `operator_agent`, and any stage's `reviewers` without encoding their positions. It deliberately OVER-TRIGGERS in exchange for never missing a legacy form: a legacy form in a position v2 does not permit is still reported with the removed-form message, so in an already-invalid document the legacy-form message may precede the genuine structural error. That trade is intentional (a position-aware sweep would re-encode schema structure E52 is actively restructuring) and is pinned by `TestCheckV2RemovedForms_MatchesByKeyNameNotPosition`. Map keys are walked in sorted order so the reported first match is deterministic.
- **CLI mirror.** `cli/internal/spec/validate.go` carries a byte-identical pair of messages and the same walk, wired into `ValidateBytes` under the same major gate and ordering — `fishhawk validate` is where a spec author most often meets these errors. The modules are deliberately separate, so both copies carry message-content assertions rather than sharing a constant.
- **Retained Go symbols.** No type, constant, or method is deleted. `PageEventReviewerReject`, `ReviewersConfig.Agent`, `AgentCount()`'s bare-count fallback, and `delegation.reviewerRejectClass` all stay — v0 and v1 documents still parse into the shared types. A v2 document simply cannot reach them, which is what satisfies the done-means structurally.

## workflow-v2 stage-budget unit unification (E52.5 / #2217)

v2 unifies the per-stage `budget` units into the same forms the rest of v2 uses: `max_runtime_minutes` (bare integer minutes) becomes `max_runtime` (a Go duration string), and `limit_usd` is added as the primary USD cost lever with `max_tokens` demoted to an optional secondary lever. This slice changes the GRAMMAR only — no runtime check reads a stage budget on any major, so no run's behaviour changes. Stage-budget enforcement (spending against the `limit_usd` ceiling, cost accounting) is #2328's (E48.55) work.

- **The fifth removed-form sweep message.** `msgV2RenamedBudgetMaxRuntimeMinutes` (`v2removed.go`, byte-identical CLI mirror in `cli/internal/spec/validate.go`) names `max_runtime` and shows the equivalence (`max_runtime_minutes: 15` → `max_runtime: 15m`). Its detection branch is appended LAST in `checkV2RemovedAtNode`, so the existing four-form report order is preserved.
- **The shared `spec.Budget` struct carries all four fields.** `MaxTokens`, `MaxRuntimeMinutes` (v0/v1), `MaxRuntime` (`spec.Duration`) and `LimitUSD` all live on one type; the per-major schemas, not Go, partition the spellings, because each major's `$defs/budget` is `additionalProperties: false`. `Budget.Runtime()` resolves the runtime cap through a single `time.ParseDuration` code path — `MaxRuntime` when set, else `MaxRuntimeMinutes` converted, else zero. The `MaxRuntime` pattern is a strict SUBSET of what `time.ParseDuration` accepts, matching the convention of the three existing v2 duration fields (`policy.max_stage_runtime`, `executor.timeout`, `executor.verify.timeout`). **DECODED ONLY:** no reader of `Stage.Budget` exists in the repo, and this slice adds none.
- **REJECTED ALTERNATIVE — normalizing `max_runtime` back into `max_runtime_minutes` in `v2shape.go`** (the pattern E52.6 used for `constraints` / `auto_advance` / `needs`) is **LOSSY**: `time.ParseDuration` accepts sub-minute values, so `90s` would floor to 1 minute and `30s` to 0, silently re-introducing the very integer-minutes unit this change deletes. A typed `spec.Duration` field partitioned by the per-major schemas is exact. That is why the budget change widens the Go struct rather than rewriting the raw document.
- **Three grammar deltas from v1** (`budget/properties/max_runtime_minutes` removed, `max_runtime` and `limit_usd` added). Historical: these took the interim `licensedV2Deltas` allow-list to 12 of its ~15 guardrail. That table and its test were **retired by #2320** — this bullet is now the record of what E52.5 licensed, not a pointer to a live count.

## workflow-v2 approval predicate consolidation (E52.2 / #2214)

v2 deletes the legacy GitHub-handle gate `approvers` role allow-list and the top-level `roles` map it referenced, leaving the forge-neutral `approvals` block (ADR-055 / #1707) as the **sole** approval predicate at major 2. `approvals` is the only remaining way to declare an approval gate's requirement.

- **Four grammar deltas from v1** (all in the canonical `docs/spec/workflow-v2.schema.json`, mirrored by `scripts/sync-schemas`): the gate approval branch drops the `approvers` property AND its inner mutual-exclusion `oneOf`, and gains `approvals` in its `required` list (`[type, approvals]`); the now-orphan `$defs/approvers`, `$defs/role` and `$defs/member-ref` are removed; and the top-level `roles` property is removed. Listing `approvals` in `required` preserves exactly the never-a-no-op property the deleted inner `oneOf` used to guarantee (pinned by `TestParse_V2ApprovalGate_NeitherPredicate_Rejected`).
- **Two new sweep messages, appended LAST.** `msgV2RemovedApprovers` (names `approvals`, states the translation shape and that it is NOT mechanical) and `msgV2RemovedRolesMap` (names `approvals.member_of` / `approvals.members`) are added to `v2removed.go` with a byte-identical CLI mirror. Their detection branches are appended LAST in `checkV2RemovedAtNode` (`approvers` before `roles`) so the existing five-form report order is byte-preserved — `TestCheckV2RemovedAtNode_FixedOrder` pins the seven-form order.
- **Retained, not deleted — the shared Go types.** `Spec.Roles`, `Gate.Approvers` and the `Approvers` struct all stay: the typed structs are shared across every major and v0/v1 documents still carry both surfaces. A routed major `>= 2` document can never populate them — the sweep rejects the raw key before the typed decode — so they are structurally unreachable at v2 (proved by a cached-v2-spec test rather than by deletion), not gone.
- **Retained, not deleted — `validateApproverRefs`.** The semantic rule that every `approvers.any_of` / `all_of` entry references a defined role is version-agnostic in code and stays. The issue's step 3 said to remove it because "it has nothing left to check"; that is true only within v2. `spec.Validate` and the `Spec` struct are shared, and v0/v1 documents still carry both surfaces, so deleting it would break the existing `TestParse_UndefinedApproverRole` and acceptance criterion 5. It is retained and re-documented as unreachable at major `>= 2` — the deliberate divergence from the issue's literal step 3.
- **Retained, not deleted — the two eligibility branch sites.** `server.fetchGateForStage`'s `gate.Approvers != nil` branch and `role.Resolver.CanApprove` remain the v0/v1 legacy role-check path. For a cached v2 spec they are structurally unreachable: a v2 gate always carries `Approvals` and never `Approvers`, so `fetchGateForStage` returns the no-approvers context and eligibility flows entirely through `fetchApprovalsForStage` + `resolvePredicates` (acceptance criterion 6, proved end to end by `TestFetchGateForStage_V2ApprovalsGate_NoLegacyContext`, `TestFetchApprovalsForStage_V2ApprovalsGate`, and `TestV2ApprovalsPredicateDecidesEligibility`).

## workflow-v2 shape normalization (E52.6 / #2218)

`v2shape.go` holds the version-gated rewrite of the three surfaces v2 reshapes for legibility. Each is rewritten on the RAW decoded document into the representation v0/v1 already use, so the typed structs, every consumer, the `runs.drive` column and every read site are untouched — the reshape's blast radius outside that one file is zero by construction.

| v2 surface | Rewritten to |
| --- | --- |
| `constraints` as one OBJECT keyed by kind | a ONE-ELEMENT `[]any` carrying that object |
| workflow `auto_advance` | the `drive` key (`spec.Workflow.Drive`) |
| stage `needs: [<stage_id>]` | appended `inputs` entries `{artifact, from_stage}`; the key is DELETED |

- **Ordering is load-bearing.** `ParseBytes` runs, in this order: `checkV2RemovedForms` (before schema validation, so its actionable messages win) → `schema.Validate` → `normalizeV2Shapes` → the typed decode → `Validate`. Normalization runs AFTER validation so it never sees an unvalidated shape — a `constraints` value that is a string is the SCHEMA's error, not a normalizer panic (`TestParseV2_ConstraintsScalarIsSchemaError`) — and BEFORE the typed decode, which uses `DisallowUnknownFields`, so `auto_advance` and `needs` must be gone by then.
- **Version gate.** Like the removed-forms sweep, it runs only for a routed major `>= 2`. A v0/v1 document is never normalized and never re-resolved.
- **Why the constraints rewrite goes in THAT direction.** Collapsing the v0/v1 LIST into one canonical object needs a merge rule, and there is no rule that preserves current behaviour: five consumers fold a duplicate-kind document differently (`mergeConstraints` concat + min/max-wins, `flattenPathConstraints` concat + min-wins, `resolveDiffCoverageConfig` max-wins, `approvals.go` preflightDeploy **last**-wins, `trace.go` `deployEnvironmentForRun` **first**-wins), and on `[{allowed_environments: [staging]}, {allowed_environments: [prod]}]` the two deploy sites already disagree with each other — `prod` at the gate, `staging` on the deploy record. Concatenating would have silently loosened that gate. Rewriting an object INTO a one-element list is exact instead: an object's keys are unique, so it denotes exactly one `Constraint`, and one entry is the case all five folds agree on. The preservation proof is the characterization tests in `spec_test.go` and `backend/internal/server/deploy_legacy_constraints_test.go`, written and run green against unmodified HEAD before any production edit.
- **`needs` artifact derivation.** `plan` → `plan`, `implement` → `pull_request` (the whole of `$defs/input`'s artifact enum). Any other referent type has no default input artifact and is the ONE error the normalizer itself raises, at `/workflows/<wf>/stages/<i>/needs/<j>`, naming longhand `inputs:` as the escape.
- **TRADEOFF — a nonexistent `needs` referent.** It is expanded into an `inputs` entry with an EMPTY artifact and its `from_stage` set, so the EXISTING `from_stage` graph-shape rule fires with its unchanged message. The cost is that the error reports at `/inputs/<post-expansion-index>/from_stage` — an index into a position the author never wrote, carrying an artifact value the schema's own `input` enum would reject if it were re-validated (it is not; normalization runs after validation). This is deliberate, not a bug: one canonical error beats two competing ones, and no earlier semantic check trips on the empty artifact, so the error genuinely fires (`TestParseV2_NeedsRejectionModes`). Naming the offending `needs` entry as well would mean either editing that binding message — which #2219 depends on staying verbatim — or emitting a second competing error, so it was not done.
- **Constraint binding PATHS are version-aware, MESSAGES are not.** `validate.go` reports a v2 binding violation at `/constraints/<kind>` (from `Constraint.preflightKindName` / `postHocKindName`, fixed declaration order so a multi-kind object reports deterministically) and keeps the `/constraints/<index>` form below major 2. The three ADR-038 / #1888 messages are verbatim unchanged. A programmatically built `*Spec` with an empty `Version` resolves to major 0, preserving the index form for `Validate`-only callers.
- **CLI asymmetry CLOSED for referent resolution (E52.13 / #2323).** `cli/internal/spec/graphshape.go` now ports this file's `needs`-expansion and `validate.go`'s duplicate-id + `from_stage` rules onto the raw tree, so `fishhawk validate` resolves `needs` / `from_stage` referents locally and reports the identical messages at the identical paths. The four rejection messages and three JSON-pointer path formats are extracted to exported constants (`MsgFmt*`, `PathFmt*`) declared byte-identically on both sides and pinned by `TestGraphShapeMessageParity`. What is STILL asymmetric is the stage-BINDING class (type/executor/constraint, produces-artifact, plan schema, `max_autonomy`), which stays backend-only. Documented for spec authors in `docs/spec/workflow-v2.md`.

## workflow-v2 same-document reuse (E52.4 / #2216)

`v2reuse.go` holds the version-gated resolution of v2's two reuse primitives: `defaults` (declarable at FILE level and at WORKFLOW level, scoped to `executor` / `reviewers` / `budget`) and `extends` on a workflow (naming another workflow key in the SAME document as its base). Cross-FILE `include:` is out of scope (ADR-067). The CLI carries a byte-parity twin at `cli/internal/spec/v2reuse.go`. Spec-author-facing docs: `docs/spec/workflow-v2.md` § *Reuse: `defaults` and `extends`*.

**PIPELINE ORDER — and why this pass sits BEFORE `schema.Validate` while `normalizeV2Shapes` sits after it.** `ParseBytes` runs: `checkV2RemovedForms` → **`resolveV2Reuse`** → `schema.Validate` → `normalizeV2Shapes` → `stripV2Reuse` → typed decode → `Validate`. Resolution is deliberately the INVERSE placement of the E52.6 normalizer, whose doc comment argues for running after validation. The schema must see the RESOLVED document, because that is what makes the whole design cost zero schema relaxation: (a) a stage inheriting its executor from `defaults` still satisfies `$defs/stage`'s `required: [id, type, executor]`; (b) a merged executor is checked against the real branch `oneOf` / `unevaluatedProperties` rules instead of a weakened copy of them re-implemented in Go on both sides; (c) a deriving workflow may omit `stages` entirely and still satisfy `$defs/workflow`'s `required: [stages]`. The existing graph-shape checks in `validate.go` then run against the resolved document unchanged — `inputs[].from_stage` may reference a base-only stage, and stage-id uniqueness plus the type↔executor↔constraint↔artifact bindings all evaluate post-resolution. Resolution also precedes normalization, so a base stage carrying the v2 `constraints` OBJECT or the `needs:` shorthand is inherited verbatim and normalized once, afterwards, in its resolved position (`TestParseV2_ResolutionPrecedesNormalization`).
- **The cost of that inversion is BOUNDED, not waved away.** This pass sees an unvalidated document, so every shape mismatch is SKIPPED — never panicked on, never reported. A `defaults: "oops"` or a non-string `extends` is still a schema error one rung later, pinned by `TestParseV2_MalformedReuseKeysAreSchemaErrors`. Only three errors are raised here, all of them ones no later layer can diagnose: an unknown `extends` base, an `extends` cycle, and a duplicate stage id.
  - **SKIPPING a malformed shape must never mean OVERWRITING it.** `stages` is the one key resolution WRITES, so a workflow declaring `extends: base` plus a malformed `stages: nope` / `stages: null` would have had the resolved base stages written over its invalid declaration — parsing as though the key had been omitted and turning an invalid document into an executable inherited workflow, the one way this pass's before-validation placement could actually bypass the schema rather than merely defer to it. A `stages` key that is PRESENT but not a list therefore suppresses the stages write entirely and is left exactly as authored for the schema to reject at `/workflows/<name>/stages`. Pinned end to end (`TestParseV2_MalformedReuseKeysAreSchemaErrors`, the two `extends with a …` cases) and at the resolver (`TestResolveV2Reuse_MalformedShapesAreSkippedNotCrashes`, whose every case asserts the malformed value SURVIVES resolution rather than merely that nothing panicked).
    - **A PRESENT-but-null block is the same rule one level down (E52.14 / #2331).** A key written with NO value — `reviewers:` / `executor:` / `budget:` / a deriving `type:` — decodes to a key PRESENT with a nil value, which is a DISTINCT input from an ABSENT key. It is PRESERVED, never overwritten by a `defaults` block or an inherited base value, and a null INSIDE a `defaults` block is never FABRICATED onto a stage at a path the author never wrote. Four decision sites carry it, all guarded by a comma-ok presence test rather than a `== nil` value test: `applyDefaults` (skips a null default and a present-null stage key, in both ladder directions; the absent-key path is bit-for-bit unchanged, and its full four-combination decision table is in the function's doc comment), `mergeStage` (a deriving stage's present-null wins over the base), `mergeKeyWise`'s recursive loop (a nested null under a present key wins, so the top-level `over == nil` guard now unambiguously means the over side is ABSENT), and `mergeDefaultsBlocks` (a null at the workflow rung does not silently fall back to the file rung). Ratifying `null` as "absent" was REJECTED: it reintroduces the action-at-a-distance whereby the same stage text validates or fails depending on an unrelated `defaults` block elsewhere in the file, and for `reviewers` it is the accumulate-a-reviewer-the-author-did-not-write hazard above arriving through the null door. Pinned on both sides at the resolver (`TestResolveV2Reuse_MalformedShapesAreSkippedNotCrashes` cases (a)–(h), (g)/(h) as negative fabrication assertions), end to end at the AUTHORED path (`TestParseV2_MalformedReuseKeysAreSchemaErrors` / CLI `TestValidateV2_MalformedReuseKeysAreSchemaErrors`, the three present-null cases), and against over-broadening by the positive control `TestParseV2_AbsentKeyStillInheritsDefaults` / CLI `TestValidateV2_AbsentKeyStillInheritsDefaults` plus the shared golden, which is NOT regenerated so any absent-key drift fails it byte-for-byte on both modules.
- **Resolution ladder**, later winning: file `defaults` → `extends` base → workflow `defaults` → the stage's own declaration. Rung 3 above rung 2 is a ratified precedence call: a workflow-level default overrides a value the inherited BASE stage declared explicitly, which is what makes "extend the base but swap the agent everywhere" expressible. Pinned rung by rung by `TestParseV2_WorkflowDefaultsOverrideFileDefaults`.

| Value | Merge rule |
| --- | --- |
| object | key-wise, recursively; the winning rung takes each key |
| array | REPLACES wholesale — never concatenated |
| `stages` | the ONE keyed array: merged by stage `id`, base order preserved, new ids appended, reordering not expressible |
| `reviewers` | taken WHOLE from exactly one rung — never blended |
| `executor` | key-wise, minus the branch rule below |

- **`reviewers` is block-level; `executor` and `budget` are key-wise. The asymmetry is deliberate.** The principle: *a block that determines review AUTHORITY is taken as authored or not at all; blocks that carry only execution parameters merge key-wise.* A key-wise merge of file defaults `{human: 1, agents: [a, b]}` into a stage declaring `{agents: [c]}` resolves to `{human: 1, agents: [c]}` — the agents correctly replace, but `human: 1` is SUPPLEMENTED from a block the author never wrote on that stage, and `planreview.ResolveAuthority` keys on `AgentCount() > 0 && Human == 0`, so the supplement silently converts a GATING stage into an ADVISORY one. It is the array-replace hazard one level up. Block-level replacement was NOT extended to `executor`/`budget` because it would make a file-level `defaults.executor.timeout` useless for every stage that declares an executor — nearly all of them — gutting the de-duplication this change exists to enable. `TestParseV2_DeclaredReviewersBlockTakenWhole` (in `spec_test.go`, the EXTERNAL package — `planreview` imports `spec`, so only that package can import it back) asserts the resolved AUTHORITY, not just the field. **An explicit `reviewers.authority` (`advisory | gating`; E53.2 / #2225) rides the same rule for the same reason:** it is authority, so it travels WHOLE with the block and is never supplemented onto a stage that declared its own `reviewers` — a key-wise merge of a default's `authority` onto a stage that omitted it would declare a gating/advisory policy the author never wrote, the identical hazard as the supplemented `human`. When present, `authority` WINS over the counts (`planreview.ResolveAuthorityWithSource`), so the count-derived flip argument above is the *default*, not the only reading; `TestParse_Reviewers_Authority_DefaultsTakenWhole` pins that a `defaults.reviewers.authority` is taken whole onto an inheriting stage and NOT supplemented onto a self-declaring one.
- **The executor BRANCH RULE, in TWO halves.** (1) *Different branch*: when a defaults or base executor selects a different `$defs/executor` oneOf branch (`agent` / `human` / `delegate`) than the stage's own, it is dropped WHOLESALE for that stage. Draft 2020-12 collects `unevaluatedProperties` against every successfully-evaluated subschema (Core §11.3), so a file-level `{agent: …}` grafted onto a `human: true` gate or a DELEGATING deploy stage fails the branch `oneOf` on a document whose author wrote nothing wrong. The drop is wholesale rather than branch-key-only because the human and delegate branches set `unevaluatedProperties: false`, so even a stray surviving `timeout` fails. Both non-agent branches are pinned (`..._HumanStageUnderAgentDefault`, `..._DelegateStageUnderAgentDefault`) — the delegate case is the deploy stage, where a grafted `agent` key would also misrepresent who executes a deploy. (2) *Closed branch*: a default of ANY shape — including the branchless `{timeout: 30m}` the schema's own `defaults.executor` description advertises — is dropped wholesale for a stage on the `human` or `delegate` branch. Half 1 cannot see a branchless fragment (it fires only when BOTH sides declare a branch), so without half 2 a bare `{timeout: 30m}` merges key-wise into `{human: true}` and produces `{human: true, timeout: 30m}`, rejected by the human arm exactly as a grafted `agent` would be — and essentially every real workflow carries a human gate stage, so the advertised bare-timeout default would reject nearly every realistic document with an opaque `oneOf` error. Pinned by `TestParseV2_ExecutorBranchRule_BranchlessDefaultDroppedOnClosedBranches` on both sides.
- **Duplicate stage ids are rejected in the RESOLVER, before merging.** The keyed merge would otherwise swallow the authoring error: two deriving stages both with id `implement` would both fold onto the one base `implement` and collapse into a single resolved stage, so `validate.go`'s post-resolution uniqueness check would see one id and PASS. Both the standalone and the DERIVING case are pinned (`TestResolveV2Reuse_DuplicateStageIDs`, `TestParseV2_DuplicateStageIDInDerivingWorkflowRejected`); only the second exercises the collapse.
- **Version gate.** Like the two sibling passes, resolution runs only for a routed major `>= 2`. This repo's own `.fishhawk/workflows.yaml` is still v1.x, so a leak below the gate would touch the spec that runs today; both lower majors are asserted rejected-and-never-resolved by `TestParseV2_VersionGate_ReuseKeysRejectedBelowMajor2`. The three shipped presets ARE v2 since E52.8 (#2220) but deliberately declare NO `defaults` block: reuse is available to an operator's own document, while a shipped governance file keeps an `executor` on every stage so a reader that resolves no reuse — a bare `check-jsonschema` run — still sees one (`fishhawk doctor`'s `execution path configured` rung now resolves reuse first, #2340, so it is no longer such a reader) (`TestPresetsDeclarePerStageExecutors`, `docs/spec/workflow-preset.md`).
- **CLI parity is held by TEST CONTENT, never a shared constant.** The two resolvers are duplicated across two Go modules, so a divergent edit compiles fine on both sides. Lockstep comes from (a) the shared golden fixture — `docs/spec/examples/workflow-v2-reuse.yaml` plus the generated `workflow-v2-reuse.resolved.json`, read over the module wall by `TestV2Reuse_SharedFixtureResolvesIdenticallyAcrossValidators` on BOTH sides, each comparing its own resolution to the golden as a THIRD PARTY rather than to the other module — and (b) verbatim rejection-message assertions on both sides. The golden is GENERATED: regenerate it, never hand-edit it.
- **Three grammar deltas from v1** (`$/properties/defaults`, `$/$defs/workflow/properties/defaults`, `$/$defs/workflow/properties/extends`). Historical: these took the interim `licensedV2Deltas` allow-list to 15, exhausting its ~15 guardrail — which is why the `defaults` block is INLINED at both schema sites rather than factored into a shared `$defs/defaults` entry, since a fourth divergent path would have tripped the allow-list outright. **That constraint is GONE:** #2320 retired the table and its test, so the inlining is now a free choice rather than a forced one, and #2214 / #2222 need not copy the pattern. The inlined form is retained here because changing it would be churn, not a fix.
- **REJECTED ALTERNATIVES.** *YAML anchors/aliases* — they are a serializer feature, invisible to the schema and to every downstream reader, express no merge semantics, and cannot be validated or error-reported. *Array concatenation* — the GitLab `extends:` / Actions matrix-include pitfall; a governance file must never accumulate an approver or reviewer by inheritance. *Relaxing `$defs/stage.required`* (the alternative to resolving before validation) — it would cost a fourth licensed delta AND force the executor `oneOf` semantics to be re-implemented in Go on both sides.
- **Error PATHS point at the RESOLVED document**, which for a deriving workflow may not be a position the author wrote — the same tradeoff #2218 accepted for expanded `needs` entries. Mitigated by documenting it in `docs/spec/workflow-v2.md`, not by weakening validation.

## workflow-v2 produced-artifact constraint binding (E52.7 / #2219)

`validate.go` binds the POST-HOC diff constraints (`max_files_changed`, `forbidden_paths`, `allowed_paths`, `required_outcomes`, `diff_coverage`) to what a stage PRODUCES rather than to its type name, at routed major `>= 2` only. A v2 stage carrying one must declare the `pull_request` artifact; the violation reports at `/constraints/<kind>` naming the kind, the reason, and both fixes (declare the artifact, or remove the constraint).

- **Why artifact-keyed.** The stage-type enum is unchanged and the names are RETAINED (ADR-067 §2 — no rename), but they are general: plan / implement / review read as propose / apply / gate. A grooming-shaped workflow runs on those same types and produces no diff at all (`docs/spec/examples/workflow-v2-backlog-grooming.yaml`), so a type-keyed rule silently accepts a constraint that can never be evaluated. `Stage.producesDiff` is the predicate: `pull_request` is the diff signal because it is the only member of the closed artifact set that DENOTES a code change — `deployment` is delegated, `acceptance` is a verdict, `plan` is a proposal.
- **Absent `produces` reads as NO DIFF (ratified).** Omitting the list does not exempt a stage. The permissive "absent means unknown" reading would let any stage keep a diff constraint by staying silent — the exact case #2219 wants rejected. It IS a real behaviour change for a v2 author, which is why the rule is version-gated and the message names the fix explicitly. Documented for spec authors in `docs/spec/workflow-v2.md` under a callout, not buried in a table.
- **Version gate (major `>= 2`).** v0/v1 documents legitimately declare post-hoc constraints on an implement stage with NO `produces` list — the v1.5 document in `TestParse_DiffCoverage_NoRegression` is the concrete case — so applying the rule below major 2 would newly reject valid specs. Below 2 the binding stays type-keyed, unchanged. `TestValidate_ProducedArtifactBinding_NotAppliedBelowMajor2` pins both majors.
- **ORDER IN THE CONSTRAINT LOOP IS A CONTRACT**, not an artifact of where the branch landed. The two ADR-038 checks run FIRST, the produced-artifact rule SECOND, the #1888 `diff_coverage` block LAST:
  1. A **deploy** stage keeps its existing ADR-038 post-hoc message and never sees the new one (it declares no `pull_request` either, so an unguarded rule would shadow it).
  2. A **mixed v2 constraints OBJECT** — one `Constraint` declaring both a pre-flight and a post-hoc kind, expressible only since E52.6 normalized the object into a single value — reports the PRE-FLIGHT diagnosis, at `/constraints/<pre-flight kind>`. DELIBERATE: a pre-flight deploy constraint on a non-deploy stage is wrong regardless of what the stage produces, and fixing it is a prerequisite for the produced-artifact question even arising, so the older and more specific diagnosis wins. This holds whether or not the stage produces a diff. Pinned characterization-style by `TestValidate_MixedPreflightPostHocConstraintObject_BindingOrderPinned` (cases (a) and (b) captured green against the pre-#2219 loop, so they are a preservation proof; case (c) is the new interaction, chosen rather than inherited from insertion position).
  3. A stage that DOES produce `pull_request` but is typed other than `implement` still gets the verbatim #1888 implement-only `diff_coverage` message — the older rule stays reachable at v2. Both directions are pinned by `TestValidate_V2DiffCoverageOrdering_NeitherRuleShadowsTheOther`; the consequence for the v2 fixtures in `TestValidate_DiffCoveragePathsAreVersionAware` is that each now declares `pull_request` to reach that branch.
- **The three pre-existing binding MESSAGES are still verbatim unchanged.** This rule was added as a fourth branch, never by editing them. `TestValidate_V2ExistingBindingMessagesUnchanged` pins all five bindings at version `"2"`.
- **CLI asymmetry (#2323): this binding STAYS backend-only.** `fishhawk validate` now resolves stage references (duplicate ids, `needs`, `from_stage`) locally, but the produced-artifact binding is a stage-BINDING rule and the whole binding class stays backend-only — it surfaces server-side at run creation. On the CLI side only the mirrored schema descriptions changed; the edit is `description`-only (a pure Draft 2020-12 annotation), which is why it added no entry to the interim `licensedV2Deltas` allow-list (since retired by #2320).

## workflow-v2 autonomy grammar (ADR-066 / E52.10 / #2222)

`v2autonomy.go` holds v2's replacement for the removed `operator_agent` block: an `autonomy: low | medium | high` tier shorthand plus a per-action-class `actions` matrix whose entries declare `mode: report | gated | auto` and, for `auto` only, the closed `when` condition that makes delegation evaluable. Spec-author-facing docs: `docs/spec/workflow-v2.md` § *Autonomy: tier shorthand and action matrix*.

- **The DERIVED-OperatorAgent bridge is the load-bearing decision.** Rather than teaching `delegation.Evaluate`, the four `checkDelegation` action handlers, `AutoDriveRunGate` and the campaign driver a second grammar, a v2 workflow's RESOLVED matrix is projected back onto the existing `spec.OperatorAgent` struct by `DerivedOperatorAgent`. Every enforcement site keeps reading the field it already reads. Both non-`auto` modes project to an EMPTY knob — exactly today's knob-absence — so nothing expressible in the new grammar widens agent authority beyond what a `may_*` knob could, and a consumer this change missed keeps reading a nil/empty block and REFUSES (fail-closed, never a widening).
- **Pipeline ORDER.** `deriveV2Autonomy` runs AFTER the typed decode and BEFORE `Validate` — the inverse of the three sibling v2 passes, and for a concrete reason: it consumes `ActionMatrix.UnmarshalJSON`'s partitioned output (below), not the raw map. A level declaring NEITHER surface derives `nil`, so `delegation.Configured` stays false and the run-status delegation block stays omitted, byte-identically to today.
- **The reserved-key partitioning unmarshaller.** `actions` is ONE JSON object mixing arbitrary class names with two RESERVED keys (`page_human_on`, `model_policy`), and no struct-tag arrangement routes an arbitrary sibling property into a named field. `ActionMatrix.UnmarshalJSON` therefore decodes into `map[string]json.RawMessage` and partitions: reserved keys into typed fields, every other property into `Classes`. Without it, `actions: {approve: {mode: gated}}` would decode to an EMPTY map — the explicit entry vanishing before validation AND before resolution, so an author tightening one class on an `autonomy: medium` workflow would silently get medium's `approve: auto`. Implementing `json.Unmarshaler` also takes over decoding of the value entirely, which is what lets the open class-name set survive `ParseBytes`' `DisallowUnknownFields` decoder. `reservedMatrixKeys` is the ONE list the unmarshaller, the symmetric marshaller and the validator all consult. Pinned directly by `TestActionMatrix_UnmarshalPartitionsReservedKeys` and, at the parse layer, by `TestParseV2_ExplicitEntrySurvivesTheTypedDecode`.
- **Resolution ladder + provenance.** A gate declaring EITHER `autonomy` or `actions` supplies the WHOLE block; otherwise the workflow's. Entries are NEVER merged across levels (the same wholesale semantics the `operator_agent` gate override had), so a gate naming one class leaves every other class at the fail-closed default rather than at the workflow tier's value. Within a block: tier expansion (`Source=tier`) → explicit entries (`Source=explicit`, winning for THAT CLASS ONLY) → `mode: gated` for every known class still unaccounted for (`Source=default`). The per-class `ResolutionSource` is the provenance #2267's `min(workflow tier, issue label, escalation ceiling)` composition needs a field to record its clamp in; the value set is left open-ended so a later rung adds a source without reshaping the carrier.
- **The class-name set is OPEN (ADR-065), and unknown classes are safe BY CONSTRUCTION, not by enumeration.** An extension class maps to no knob, so at `mode: gated` / `mode: report` it delegates nothing; at `mode: auto` it is REJECTED, because no backend-evaluable condition exists for it. That is why the registry needs no workflow-type dimension yet.
- **What the schema deliberately does NOT express.** The per-class `when` binding cannot be written against an open class-name set, so `validateAutonomy` enforces it in Go and names the class and its legal condition. A raw `check-jsonschema` run therefore accepts a document the backend rejects; the schema's `action_entry` description says so.
- **Tier expansions emit V2 vocabulary.** `expandTier`'s page list carries `gating_reviewer_reject`, never the bare `reviewer_reject` E52.3 removed from v2's enum — a tier must not expand to a value undeclarable under the grammar it belongs to.
- **The BACKLOG-GROOMING class registry (ADR-065 / E54.4 / #2236; `milestone` added by E54.9 / #2309) makes a destructive class's `mode: auto` unwritable BY CONSTRUCTION, not merely defaulted away.** Five grooming classes are registered: `hygiene` carries `ConditionObjectiveReversible` in `classConditions`, and `ordering` / `dedup` / `scoping` / `milestone` live in `nonDelegableGroomingClasses` carrying NO condition (`milestone` scopes a release milestone against a human-supplied release definition — a judgment call, not an objectively reversible mutation). A conservative default (`scoping: gated` in the shipped example, say) is a value a later refactor can drift; a class for which no condition exists, and whose `mode: auto` is refused at parse time, is a property. TWO INDEPENDENT CONTROLS refuse `<non-delegable>: auto`, and each has its OWN delete/flip-observe-red proof, because the first fires before the second and would otherwise mask it: (1) the explicit `nonDelegableGroomingClasses` branch in `validateAutonomy`, rejecting with `MsgNonDelegableGroomingClassAuto` at `/actions/<class>/mode` — pinned by `TestValidateAutonomy_GroomingNonDelegableClassesRefuseAuto`, which asserts the EXACT message so deleting the branch (leaving the adjacent extension-class branch to reject with different text) reddens it; (2) the classes' ABSENCE from `classConditions` — pinned by `TestGroomingRegistry_NonDelegableClassesCarryNoCondition`, which reddens the moment any of them is given a condition. A presence-only "an error occurred" assertion would discriminate neither.
- **No grooming class is in `knownActionOrder`, and none reaches a `may_*` knob.** `knownActionOrder` drives `resolveBlock`'s always-emit-a-`gated`-default loop AND `DerivedOperatorAgent`'s knob switch, so registering the five there would attach permanently-gated entries to EVERY workflow's resolved matrix and to every run-status delegation block for no safety gain; extension-ordered rendering already surfaces them (sorted) when declared. The knob switch is likewise untouched, which is what makes shipping `ConditionObjectiveReversible` with **no evaluator** fail-CLOSED rather than a gap: a `hygiene: {mode: auto}` class derives an EMPTY `OperatorAgent`, so it widens authority at no enforcement site. The in-tree precedent is `appliesto.TriggerFormForSource`'s `scheduled` form, which no trigger source maps to — it is accepted as declarable grammar with no producer. (`on_demand` LEFT that class in E54.22 / #2826: `run.TriggerOnDemand` maps to it, so only `scheduled` carries the precedent now.) `TestDerivedOperatorAgent_GroomingClassesDeriveNoKnob` is the invariant's proof: adding a `case ActionGroomHygiene:` arm to the switch reddens it.
- **The SHIPPED grooming declaration is `docs/spec/examples/workflow-v2-backlog-grooming.yaml`, and it is read from disk under test.** The `TestShippedGroomingExample_*` family in `spec_test.go` parses those bytes and asserts the RESOLVED outcome per class — `hygiene` auto/`objective_reversible`, `ordering` and `dedup` gated, `scoping` report EXACTLY (not gated-or-report: a disjunction would stay green when the destructive default drifts). A workflow tier and the grooming classes are DISJOINT sets — `autonomy: low` expands to the five run-driving classes only — so the example declaring both is not an explicit-overrides-tier conflict; an escalation `max_autonomy: low` CEILING is a separate operation and DOES clamp `hygiene` to `gated` via the extension-class fail-closed arm (`TestClampResolvedMatrix_LowCeilingClampsGroomingHygiene`).
- **The presets are workflow-v2 and declare `autonomy: <tier>` (E52.8 / #2220).** That REPLACED the old shipped-preset round-trip: the parser now DERIVES each preset's `operator_agent` block via `expandTier`, so comparing a preset-derived block against `expandTier` would compare the function under test against itself. The expectation is instead a FROZEN literal table written out longhand in the test — `frozenTierBlocks` in `v2autonomy_test.go`. Its byte-level companion, `TestShippedPresetsDeclareTheirTier` in `preset_test.go`, pins WHICH tier each preset chose (and that none declares an `operator_agent` key). `TestExpandTier_MatchesFrozenTierTable` asserts both halves per tier, so the presets and the tier expansions are proved to agree without either side supplying the other's answer. The presets' own shape — per-stage executors and reviewers, no `defaults` block, the lockstep base-plus-one-line invariant — is documented in `docs/spec/workflow-preset.md`.
- **`expandTier` is duplicated across the backend/cli module wall (E52.18 / #2341).** `cli/internal/spec/migrate.go`'s `tierExpansion` is a structural twin: same three tiers, same class entries, same page list — but it returns `map[string]actionEntry` and `[]string` (string fields) rather than `ActionMatrix` (typed enums), so the two cannot share a Go implementation. The shared proof surface is `docs/spec/tier-expansion-fixtures.json`, mirrored verbatim into `backend/internal/spec/testdata/` and `cli/internal/spec/testdata/` by `scripts/sync-schemas`. `TestTierExpansionCorpus_BackendMatches` in `v2autonomy_test.go` asserts this module's `expandTier` and `ResolveAutonomy` against every corpus row; the CLI asserts its own `tierExpansion` independently. Both loaders include a shape guard (`t.Fatal` naming the discrepancy) so an emptied corpus cannot produce a vacuous green. `frozenTierBlocks` and `tierPageList` are kept as independent frozen literals — the corpus does not replace them, it cross-checks them: a corpus row authored wrong immediately reddens against `frozenTierBlocks` rather than silently becoming the new truth.

## Shared path predicate (E53.1 / #2224)

`predicate.go` is the E53 keystone: ONE declarative path predicate — type, validator, matcher — that E53.3 (`applies_to` routing, #2226), E53.4 (`escalations`, #2227) and ADR-068's review-conventions (#2211) all consume instead of each growing a subtly different matcher. Its FIRST consumer is a workflow's `applies_to` (see the next section); #2227 and #2211 wire the other two.

- **The grammar.** A `Predicate` declares four optional criteria — `paths` (doublestar globs, `**` crossing `/`), `labels`, `change_kind`, and `trigger` — matched against a `Change`. Match semantics are RATIFIED (ADR-066 / #2209): **AND across criteria TYPES** (every declared type must be satisfied), **OR WITHIN a list** (any one entry satisfies its type); an undeclared type does not constrain. An **empty predicate is a validation ERROR, never match-all** — enforced by `Predicate.Validate` and, at the schema layer, by `minProperties: 1`.

- **Non-diff triggers.** `trigger` carries `scheduled` and `on_demand` alongside `diff` from the start: ADR-067 decoupled stage types from "produces a diff", so a non-code workflow (ADR-065's groomer, ADR-053's incident intake) is routable by the same mechanism. A `Change` with an empty `Trigger` normalizes to `diff` at match time — the back-compat seam E53.3 depends on. A paths-declaring predicate therefore does NOT match a no-diff (zero-path) change: the paths type is declared and unsatisfiable against zero paths.

- **The path matcher is `doublestar.Match(glob, path)`** — the IDENTICAL call `backend/internal/server/test_sweep.go` makes for `test_conventions`, against repo-relative slash-separated paths. `TestPredicatePathsMatchDoublestarSemantics` proves that identity row-by-row rather than asserting it in a comment. `Match` **FAILS CLOSED** for a caller that skipped `Validate`: an **empty predicate** returns `(false, error)` rather than matching everything, and a **malformed `paths` glob** returns `(false, error)` naming the pattern — validated up front so a valid glob earlier in the list cannot short-circuit a `true` return past a malformed glob later. This is the deliberate divergence from `isTestFileBasename`'s advisory fail-OPEN, which is correct for a sweep and wrong for a governance control.

- **Binary-safe path layer.** `SplitNULPaths` splits a `git … -z` stream (dropping the trailing terminator record, so a newline-bearing path stays one path), and `DecodeGitPath` decodes git's C-quoted form, failing closed with an actionable error naming any undecodable path — the three modes (`trailing backslash`, `bad octal escape`, `unknown escape`) `scripts/check-coverage.py`'s `decode_git_path` raises for (ADR-059 / #2124), plus a byte-range guard rejecting an octal escape `> \377` rather than truncating it via `byte(v)` (unreachable from genuine git output, which emits only per-byte escapes, but the contract forbids a silent mis-decode of a hand-crafted or corrupted input). Go strings are byte slices, so a non-UTF-8 path round-trips without the surrogateescape handling the Python side needs.

- **Byte-parity duplication.** The file is duplicated BYTE-FOR-BYTE into `cli/internal/spec/predicate.go` (the two modules cannot share a package, the convention `agentversion.go` and `v2removed.go` already set). Parity is held MECHANICALLY, not by inspection: (a) `predicate_test.go` is itself byte-identical across both modules and `TestPredicateSourceParityAcrossModules` reads both copies of `predicate.go` AND `predicate_test.go` over the repo root and asserts exact equality, failing with the first differing line; (b) the canonical fixture corpus `docs/spec/predicate-fixtures.json` is mirrored by `scripts/sync-schemas` into both modules' `testdata/`, so CI's schema-sync gate red-lines if the two sides ever run different fixtures. `TestPredicateFixtureCorpus` runs the same rows in both modules; a matcher that drifts on one side fails there.

- **The fixture corpus is byte-safe.** A JSON string cannot carry arbitrary invalid UTF-8 (`encoding/json` replaces invalid bytes with U+FFFD), so a fixture string may be a bare JSON string OR an object with a `hex`/`b64`/`str` field (precedence `hex > b64 > str`), decoded identically by both module loaders. At least one row carries a genuinely invalid UTF-8 sequence (`0xFF 0xFE`), and `TestPredicateFixtureEncodingRoundTrips` proves the ENCODING itself round-trips so a loader that silently mangles a value fails rather than quietly weakening every row that depends on it.

## Workflow routing declaration — `applies_to` (E53.3 / #2226)

`$defs/workflow` gains an optional `applies_to` that `$ref`s `$defs/predicate` unchanged, decoding onto `Workflow.AppliesTo *Predicate`. It declares which changes a workflow may be used for. **This package owns the SPEC SURFACE** — the property parses, round-trips and validates here; the two fail-closed enforcement points that consume it are LIVE and live in `backend/internal/server` (`labels`/`trigger` at run admission in `applies_to.go`, `paths` at the plan gate in `applies_to_plan_gate.go`), with the audited `applies_to_override` as the one sanctioned way past either.

- **`$ref`, not a second matcher.** The consumer points at the shared definition and leaves it untouched. Where `applies_to` needs a narrower grammar than the predicate offers it refuses the criterion at ITS OWN declaration site rather than editing the shared shape — which is what keeps #2227 and #2211 able to use the full grammar. Nothing in `predicate.go` changed for this consumer.

- **The struct field is load-bearing, not decorative.** `ParseBytes`' typed decode runs with `DisallowUnknownFields`, so a property the schema permits but `Workflow` omits fails the decode outright. `AppliesTo` is a POINTER because nil (no declaration) and an empty predicate are different things: nil means *accepts any change* — the reading every pre-#2226 document gets — while an empty predicate is a validation error, never match-all. A value-typed field would have made the zero `Predicate{}`, which `Match` rejects with an error, the default for the whole corpus.

- **`change_kind` is rejected inside `applies_to`, and the shared grammar is not.** `validateAppliesTo` refuses the criterion with `MsgAppliesToChangeKindUnsupported`, naming the missing producer. Nothing populates `Change.ChangeKind` today, so a workflow declaring it would be selectable by no run — indistinguishable, from the operator's side, from the routing control being broken. This is the narrow-consumer principle above in practice: the criterion stays in `$defs/predicate` for the other two consumers.

- **`paths` is refused on a workflow that declares no plan stage (E53.15 / #2377).** `paths` is evaluated at the plan gate against the approved plan's `scope.files`; a workflow that ships no plan stage never produces that set, so the criterion is never evaluated — no rejection, no audit entry, no signal that the declaration did nothing, which is the control-that-silently-does-nothing failure E53 exists to prevent. `validateAppliesTo` refuses it with `MsgFmtAppliesToPathsNoPlanStage`, naming the workflow, the missing plan stage and both real alternatives: `labels` / `trigger`, evaluated at run admission on every workflow whatever its shape, and the stage's `constraints.allowed_paths`, a post-hoc envelope checked against the produced diff after the agent has run. **THERE IS NO POST-HOC-ENVELOPE EXEMPTION.** A `constraints.allowed_paths` elsewhere in the workflow does NOT admit the declaration: the routing criterion is still never evaluated, and a declaration admitted because a different control with different timing holds a similar envelope is exactly the admitted-but-never-evaluated state the rule closes. The rule reads `wf.Stages` AFTER v2 reuse resolution, so a plan stage inherited through `extends` satisfies it (`TestParse_AppliesTo_PathsWithInheritedPlanStage_Accepted`), and a plan-less BASE's declaration is reported against the base (`TestParse_AppliesTo_PlanlessBaseAttribution`). It composes forward: a future stage type producing an authoritative pre-implementation path set relaxes the refusal by joining the producer set, without repealing the rule. This is a CROSS-MEMBER rule — a criterion's validity conditioned on the workflow's stage list — which is why it lives here and touches no schema file.

- **Rung order is a contract.** `change_kind` is checked BEFORE `Predicate.Validate`, so a predicate wrong in two ways reports the change_kind diagnosis — it names a fix (route on `paths`, `labels` or `trigger`) that the generic predicate error cannot. The plan-stage rule is the THIRD rung, after `Predicate.Validate`, matching where `validateEscalations` puts its own structural-impossibility check (`require.approvals` on a workflow with no approval gate): the diagnosis is about the workflow's shape rather than the criterion's spelling, so it is only worth reporting once the criterion is well-formed. `TestValidate_AppliesTo_ChangeKindWinsOverGlob`, `TestValidate_AppliesTo_ChangeKindWinsOverNoPlanStage` and `TestValidate_AppliesTo_MalformedGlobWinsOverNoPlanStage` pin the direction; the mirrored CLI check keeps the same order.

- **The Go rung is exercised where the schema masks it.** `minProperties: 1`, the `trigger` enum and `minLength: 1` mean an empty predicate, an unknown trigger form and an empty label are SCHEMA errors on the parse path — the Go branches for them are never reached through `ParseBytes`. They are reached through the exported `Validate` over a hand-built `Spec` (`TestValidate_AppliesTo_GoLayerBranches`), so the fail-closed code is proved rather than assumed dead behind the schema. Only the malformed glob — a plain string to JSON Schema — reaches `Predicate.Validate` through a parse.

- **CLI parity is mirrored, not shared.** `cli/internal/spec/validate.go`'s `checkAppliesTo` re-implements the same two rungs over the raw yaml tree (that package validates an `any` tree and has no typed `Spec`), so `fishhawk validate` cannot accept a spec the backend refuses at dispatch. Rung 2 reuses the CLI module's byte-identical `Predicate.Validate`, so its messages match by construction; only `MsgAppliesToChangeKindUnsupported` and `MsgFmtAppliesToPathsNoPlanStage` are hand-duplicated, and `TestAppliesToChangeKindMessageParity` / `TestAppliesToPathsNoPlanStageMessageParity` read BOTH `validate.go` files over the repo root and fail on any drift. Rung 3 carries ONE deliberate divergence, documented on `checkAppliesTo`: when the raw `stages` node is not a list the CLI SKIPS the rung rather than reporting no-plan-stage, because that document was already rejected structurally upstream and a second semantic diagnosis would mislead; the typed backend has no equivalent leg. The two `validate.go` files are NOT byte-identical and are not meant to be — that is why the guard is scoped to the one constant rather than the whole file.

- **`extends` does not inherit it.** Reuse resolution folds `stages` only, so a deriving workflow does not pick up its base's `applies_to` — consistent with `budgets`, `policy`, `decomposition` and `autonomy`, none of which are inherited either. `TestValidateBytes_AppliesTo_ExtendsDoesNotInherit` pins that a base's declaration is reported against the BASE and never attributed to the deriving workflow.

## Per-path escalations — `escalations` (E53.4 / #2227)

`$defs/workflow` gains an optional `escalations` array of `{match: <predicate>, require: {...}}` rules, decoding onto `Workflow.Escalations []Escalation`. Each entry RAISES the requirements applying to a change its predicate matches. **This package owns the DECLARATION side** — the grammar, its only-ever-raise validation family, the strictest composition, and the pure autonomy clamp (`escalation.go`); the two enforcement seams that consume them live in `backend/internal/server` (the approval gate) and `backend/internal/delegation` (the ceiling). Reference prose: `docs/spec/workflow-v2.md` § 'Escalations'.

- **The `match:` wrapper is STRUCTURALLY FORCED, not stylistic.** `$defs/predicate` is `additionalProperties: false`, and Draft 2020-12 evaluates `additionalProperties` against the WHOLE instance object rather than the referencing subschema's own scope — so an escalation cannot `$ref` the predicate and carry a sibling `require` key. The issue's original hoisted-`paths:` example is not implementable, and `TestSchema_Escalations_StructuralRejections` pins its rejection. Hoisting would have meant re-declaring the predicate's properties inline: the second-matcher drift E53.1 exists to prevent.

- **`minProperties: 1` at BOTH levels.** The outer one rejects `require: {}`; the NESTED one on `approvals` rejects `require: {approvals: {}}`. Without the nested rule the claim "a no-op escalation is refused structurally" would be only mostly true — the inner empty block satisfies the outer rule while requiring nothing.

- **Only-ever-raise is enforced at DECLARATION time, in four checks of TWO different shapes.** `count` and `min_permission` are RAISE-checks against the workflow's LEAST-RESTRICTIVE baseline (the max count and the strictest tier over EVERY approval gate — a workflow-level escalation applies to every gate, so one that raised gate A while leaving gate B alone would not hold the invariant workflow-wide). `member_of` and `max_autonomy` are NO-OP checks. A fifth rejection covers `require.approvals` on a workflow with no approval gate at all. All five report at `/workflows/<n>/escalations/<i>/…` in a fixed documented order, and every no-raise rejection renders from ONE shared shape (`MsgFmtEscalationNoRaise` + `escalationNoRaiseMessage`), asserted mechanically by `assertNoRaiseShape` rather than by eyeball.

- **The two no-op checks are NOT lowering checks, and the distinction must not be conflated in review.** Membership composes as a CONJUNCTION over a de-duplicated set, so adding a group can only ever narrow the eligible approver set — no lowering is expressible. The clamp only ever downgrades `auto` to `gated`, so a ceiling is monotone-decreasing by construction — again no lowering is expressible. What IS expressible on both is an escalation that raises NOTHING: a group every applicable gate already requires de-duplicates away to the identical set, and a ceiling no stricter than what the workflow resolves to leaves every class as it was. The boundary pair is pinned: a group named by EVERY approval gate is refused, the same group named by only ONE of two gates is ACCEPTED.

- **The ceiling's no-op check spans the workflow AND every gate-declared block.** A gate declaring `autonomy` / `actions` overrides the workflow's WHOLESALE (`ResolveAutonomy`'s ladder), so a ceiling inert at workflow level can still genuinely restrict such a gate. `resolvedMatricesOf` therefore tests every matrix a ceiling could apply to and refuses only a ceiling that clamps NOTHING ANYWHERE — the one outcome an only-ever-raise validator must never produce is rejecting an escalation that demonstrably raises something.

- **`ClampResolvedMatrix` is pure, defined over the RESOLVED matrix, and returns a COPY.** Resolved-matrix placement is load-bearing: applying the ceiling to the tier or to the declared entries would let an explicit `actions: {merge: {mode: auto}}` re-widen the class afterwards. The consumer must ALSO re-derive `DerivedOperatorAgent(clamped)` — every enforcement site reads the derived knobs, not the surfaced matrix, so clamping only the matrix would show `gated` on the run read while the agent stayed authorized to act (`TestDerivedOperatorAgent_AfterClamp_EmptiesTheKnob`). A clamped class is stamped `Source: SourceEscalation`; `gated` and `report` are untouched; an extension class clamps to `gated`, fail-closed by construction rather than by enumeration.

- **Composition is order-independent BY CONSTRUCTION.** `ComposeEscalations` takes the max count, the sorted de-duplicated union of `member_of`, the strictest `min_permission` and the lowest `max_autonomy`. Max, min and set union are commutative and associative, so "never last-match-wins" is a property of the composition rather than a convention — pinned by a shuffled-order fixture. The union being a CONJUNCTION has an intended consequence: two escalations naming disjoint groups produce a requirement no single approver can satisfy, surfacing as a gate that cannot clear rather than one silently weakened.

- **`match.paths` is refused on a workflow that declares no plan stage (E53.16 / #2382)** — the escalation twin of `applies_to`'s plan-stage rule. `match.paths` is evaluated at the approval gate against the approved plan's `scope.files` (`planGateScopePaths` via `resolveStageEscalations` in `backend/internal/server/escalation_gate.go`); a workflow that ships no plan stage never produces that set, so the escalation is never evaluated — it never FIRES, with no rejection and no audit entry, which is worse than the routing case because the control fails to RAISE. `validateEscalations` refuses it with `MsgFmtEscalationPathsNoPlanStage` (`escalationPathsNoPlanStageMessage`), naming the workflow, the escalation index, the missing plan stage, `labels` / `trigger` and the non-paths `require` dimensions that still hold. **THERE IS NO POST-HOC-ENVELOPE EXEMPTION** (`TestParse_Escalations_PlanlessPathsNotAdmittedByPostHocEnvelope`): a stage's `constraints.allowed_paths` does NOT admit it, because the escalation is still never evaluated — the admitted-but-never-evaluated state the rule closes. It reads `wf.Stages` AFTER v2 reuse resolution, so a plan stage inherited through `extends` satisfies it (`TestParse_Escalations_PathsWithInheritedPlanStage_Accepted`), and a plan-less BASE's declaration is reported against the base (`TestParse_Escalations_PlanlessBaseAttribution`). It is the EIGHTH and LAST rung of `validateEscalations` — after `change_kind`, the shared `Predicate.Validate` and the four require-side checks, so a sharper spelling or only-ever-raise diagnosis wins; `TestValidate_Escalations_ChangeKindWinsOverNoPlanStage`, `TestValidate_Escalations_MalformedGlobWinsOverNoPlanStage` and `TestValidate_Escalations_NoRaiseWinsOverNoPlanStage` pin all three directions, and `TestParse_Escalations_PlanlessLabelsOnlyAccepted` / `TestParse_Escalations_PlanlessTriggerOnlyAccepted` are the positive controls proving the fix removes no escalation form a plan-less workflow can carry. It composes forward, joining the producer set rather than repealing the rule when a future stage type produces an authoritative pre-implementation path set.

- **CLI parity is mirrored, not shared, with ONE documented gap.** `cli/internal/spec/validate.go`'s `checkEscalations` re-implements the `change_kind` refusal, the shared `Predicate.Validate`, the no-approval-gate rejection, the count / `min_permission` / `member_of` checks and the plan-stage `match.paths` refusal over the raw yaml tree, with the four hand-duplicated message constants (`MsgEscalationChangeKindUnsupported`, `MsgFmtEscalationNoRaise`, `MsgFmtEscalationApprovalsNoApprovalGate`, `MsgFmtEscalationPathsNoPlanStage`) guarded by `TestEscalationMessageParity` and `TestEscalationPathsNoPlanStageMessageParity` — the latter reads `backend/internal/spec/escalation.go` (NOT `validate.go`: the escalation constants live there) and `cli/internal/spec/validate.go`. The plan-stage rung reuses the existing `hasPlanStageFromRaw` and handles two raw-tree traps the typed backend never meets: it runs after `checkEscalatedApprovals` regardless of whether the `require` node was a readable map (a naive trailing append would be dead on that leg), and it gates on the pre-rung error count so the accumulating sweep still emits ONE entry per escalation in the backend's dimension order. It carries the SAME ONE divergence as `checkAppliesTo`: when the raw `stages` node is not a list the CLI SKIPS the rung rather than stacking a semantic no-plan-stage diagnosis on the structural one upstream (unreachable through `ValidateBytes`, which the schema gates first — `TestValidateBytes_Escalations_StagesNotAList_NoStackedDiagnosis` asserts the user-visible contract). The `max_autonomy` no-op check stays BACKEND-ONLY: it needs the v2 tier expansion and a resolved-matrix comparison, and `cli/internal/spec` deliberately carries no `v2autonomy.go` — mirroring the resolver there would be exactly the duplicate-implementation drift E53 exists to prevent. The gap is pinned by `TestValidateBytes_Escalations_MaxAutonomy_NotCheckedByTheCLI` so it is a decision, not an oversight; the mirrored schema still gives the CLI every structural rule for free.

- **`extends` does not inherit it.** Reuse resolution folds `stages` only, so a deriving workflow does not pick up its base's `escalations` — consistent with `applies_to`, `budgets`, `policy`, `decomposition` and `autonomy`. Pinned in `escalation_test.go` (deliberately sited there rather than in `v2reuse_test.go`) by both halves: the deriving workflow's field is nil, and a base's invalid escalation is reported against the BASE.

## Declared per-stage permissions — `permissions` (E53.5 / #2228)

`$defs/stage` gains an optional `permissions` object (`network` / `write` / `shell`), decoding onto `Stage.Permissions *StagePermissions`, and the acceptance-stage-only `egress` binding is GENERALIZED at major `>= 2` off its type keying. The block is **DECLARATION-ONLY**: validated, audited and surfaced but **NOT enforced until E51 (#2133)** — no surface calls it containment, sandboxing, isolation, or a security control; it is a legibility/quality aid, not an adversary-proof control. Enforcement is a sibling epic. Reference prose: `docs/spec/workflow-v2.md` § 'Permissions (network / write / shell)'; the honesty wording is machine-checked by `TestPermissionsSchemaHonesty` against the SHIPPED canonical schema (`permissions.go` / `permissions_test.go`).

- **`permissions.network` is a SPELLING of `egress`, not a parallel key.** `normalizeStagePermissions` (run in `parse.go` after the typed decode, before `Validate`) copies `Permissions.Network` into the existing `Stage.Egress`, so every enforcement consumer (`resolveAcceptanceStageSpec` → `resolveAcceptanceEgressTargetHosts` → the acceptance prompt's `egress_target_hosts` → `egressproxy.BuildAllowlist`) keeps reading ONE field and an acceptance stage can never be routed onto an unenforced path by choosing the new spelling. Declaring BOTH `egress` and `permissions.network` on one stage is a validation error (`MsgFmtPermissionsEgressConflict`), never a precedence rule.

- **The egress binding is version-gated.** Below major 2 an `egress` block stays acceptance-stage-only (frozen; `TestParse_V13Egress_On{Implement,Deploy}Stage_Rejected` pin it). At major `>= 2` an `egress` block or a `permissions` block is valid on any AGENT-executor stage and rejected on a `human` or `delegate` executor (`MsgFmtPermissionsExecutorBinding`); the v2 `egress_off_acceptance` case moved out of `TestValidate_V2ExistingBindingMessagesUnchanged` into the positive `TestValidate_V2Egress_OnImplementStage_Accepted`.

- **`permissions.write` runs through the shared `Predicate`.** `StagePermissions.WritePredicate()` returns `Predicate{Paths: write}`, so the write glob dialect and match semantics cannot drift from `applies_to`/`escalations`; a malformed glob is caught by `doublestar.ValidatePattern` at declaration time. The executor-binding and conflict messages carry the non-enforcement disclaimer (operator condition 4); a pure syntax error (malformed glob, unknown `shell` posture) does NOT.

- **CLI parity** mirrors the two schema-inexpressible checks — the `egress`+`permissions.network` conflict (`MsgFmtPermissionsEgressConflict`, byte-parity via `TestPermissionsMessageParity`) and `write` glob validity through the byte-identical `predicate.go`. The executor binding is left to the backend (as the deploy binding is) and the `shell` enum to the schema.

## Agent-version compatibility ranges (v1.4, E32.13 / #1743)

`executor.agent_version` + `reviewers.agents[i].agent_version` declare the semver comparator RANGE (e.g. `">=2.1 <2.2"`) of agent CLI versions a workflow was validated against, failing dispatch loudly when the resolved CLI version falls outside it (the #1741 opaque-CLI-drift diagnosis).

- Matcher/validator: `spec.ValidAgentVersionRange` / `spec.MatchAgentVersionRange` in `backend/internal/spec/agentversion.go`, with a byte-parity twin in `cli/internal/spec/agentversion.go`. Called by the semantic validator (`validate.go`).
- The executor range is threaded to the runner via `promptResponse.agent_version_range` (`backend/internal/server/prompt.go`).
- The runner's own duplicated `matchAgentVersionRange` (`runner/cmd/fishhawk-runner/main.go`) fails the stage **pre-spawn category-C** (`agent_version_mismatch`) on an out-of-range resolved (#1769-probed) version, or degrades-and-proceeds (`agent_version_uncomparable`) on an unprobeable one.
- Absent range = no constraint.
- The binary pin stays a host concern via `FISHHAWK_AGENT_BIN` / `FISHHAWK_CODEX_BIN` (#1741 / #1769).
- The reviewer-side (codex-only) enforcement is a sibling change.
