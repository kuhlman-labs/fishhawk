# backend/internal/workmgmt

Work-management conventions + provider abstraction: canonical work-item model, conventions rendering (`Apply`), and the `Provider` interface with optional capabilities (`Transitioner`, `EpicChildrenQuerier`, `IssueSetDependencyResolver`, `NumberDiscoverer`). Provider impls live in `github/` and `jira/` (see their READMEs).

## Board-state sync (#1012: run-lifecycle-driven work-item board transitions)

- **Config:** the `states` (canonical state → provider board option) + `transitions` (run-lifecycle event → canonical state) blocks in `docs/spec/work-management-v0.{md,schema.json}` + the shipped default, typed onto `workmgmt.Conventions.{States,Transitions}` with a transitions→states cross-reference semantic check.
- **Capability:** the optional `workmgmt.Transitioner` interface (`Transition(ctx, TransitionRequest) (*TransitionResult, error)`) — distinct from `Provider` so a non-boarding provider (jira) need not implement it. The `github_projects` impl in `backend/internal/workmgmt/github/provider.go` moves ONLY the Status column and honors never-fight-the-human: it advances only from a status in the request's expected-source set; an unset Status counts as Backlog.
- **Hook:** `backend/internal/server/boardsync.go::notifyBoardTransition` — best-effort (modelled on `notifyStatusUpdate`). It resolves the run's repo/issue/installation, maps the lifecycle event through `Conventions.Transitions`, derives the expected-source set from the prior lifecycle edges, dispatches the `Transitioner`, and appends a `work_item_transitioned` audit entry (every move AND every DECISION skip; see `docs/issue-comment-surfaces.md`). **Carve-out (#2494):** a `TransitionResult.NotApplicable` result — set by the provider for exactly the `no project configured` and `issue is not on the project board` skips — is logged at INFO and appends NOTHING, at all three emitters (run-, campaign-, and issue-scoped). A transition that touched no work item has no work-item transition to record, and on a repo with no board every lifecycle edge of every run wrote one, so the flood dominated the audit tail. Every other skip is a DECISION about a work item that DOES exist (never-fight-the-human source mismatch, already-at-target, unmapped canonical state, target status absent from the board, and the operator-actionable unreachable-user-board skip) and keeps auditing unchanged.
- **Call sites:**
  - run created → `run_started` (webhook `Dispatcher.BoardSyncer`, wired in `serve.go`, AND `handleCreateRun` in `runs.go` for local-runner / API-created issue runs, closing the #1123 webhook-exclusive gap)
  - PR opened → `pr_opened` (`pullrequest.go`)
  - run failed → `run_failed` (`trace.go::advanceAfterFailure`, only when the run reached terminal `failed`)
  - PR merged → `run_merged` (`pullrequest_review_events.go`)
- Errors log and never unwind the run.

## Issue-level `depends_on` relation + epic-children query (ADR-047 / #1437, E25.1: the campaign DAG source)

- **Model:** `workmgmt.Relations.DependsOn []string` (`model.go`) — the issue-level dependency edge a campaign derives its wave DAG from. Entries are issue refs (`#N`/`N`) among the epic's children, threaded through `fishhawk_file_issue` → `POST /v0/work-items` → `FilingRequest.Relations`.
- **Validation:** `apply.go::resolveRelations` format-validates each entry (positive `#N`/`N`). Cycle and existence checks are deferred to campaign-assembly time (E25.3) because `Apply` is pure and cycle detection needs the full DAG.
- **Persistence:** GitHub has no native depends_on relation, so `github/provider.go::File` stamps a `Depends on: #X, #Y` body marker (the single-source-of-truth `renderDependsOnMarker`/`parseDependsOnMarker` pair, idempotent via `ensureDependsOnMarker`), mirroring the `Parent epic: #N` convention.
- **Query:** the optional `workmgmt.EpicChildrenQuerier` capability (`EpicChildren(ctx, EpicChildrenRequest) (*EpicChildrenResult, error)`) — distinct from `Provider` like `Transitioner`/`NumberDiscoverer`. The `github_projects` impl resolves the epic node id, reads `githubclient.ListSubIssues` (which PAGINATES the `subIssues` connection under a bounded page cap, following `pageInfo.endCursor` until `hasNextPage:false`, so an epic with >100 children yields its COMPLETE child set — #2102), parses each child body's marker, and returns the children (ascending) plus the depends_on edges restricted to the sibling set. Because the child set is complete, a `depends_on` edge to an overflow sibling classifies into `Edges` rather than being truncated out and mis-dropped; cap exhaustion is a fail-closed error, never a silently-partial read.
- A reference to a non-child is kept OUT of `Edges` and surfaced in `EpicChildrenResult.DroppedEdges` (deterministically sorted, not silently discarded) so campaign assembly can fail closed on a dangling/mis-targeted dependency. E25.3 feeds the result into `plan.Waves`.
- **Completion signal (`EpicChild.Complete`, #2120):** each child carries `Complete = (GitHub IssueState == CLOSED && IssueStateReason == COMPLETED)` — the closed-and-completed "already merged/done" state read off the same `ListSubIssues` query (which selects `state`/`stateReason` on every paginated page, no extra round trip per child). A close as `NOT_PLANNED`/`DUPLICATE` is NOT complete (its work did not land). The campaign subset filter reads it to treat an included item's `depends_on` on an EXCLUDED-but-completed sibling as a satisfied dependency rather than a dangling one. Absent/unknown signal ⇒ `false` (fail-safe, restores the pre-#2120 fail-closed behavior).
- **`DependsEdge.Reason` (`DropReason`, #2120):** categorizes a DROPPED edge — `DropNotChild` (out-of-epic/typo'd target; the provider stamps every non-child dropped edge with it) or `DropExcludedIncomplete` (an included subset item depending on an excluded, incomplete sibling; stamped by the subset filter). It is `""` on a satisfied edge in `Edges` (additive: existing equality assertions on `Edges` are unchanged). Campaign `Assemble` groups dropped edges by this reason to name the cause+remedy per edge.
- **No-epic issue-set resolution (`IssueSetDependencyResolver`, E48.36 / #2051):** the optional capability (`ResolveDependencies(ctx, IssueSetRequest) (*EpicChildrenResult, error)`) — distinct from `Provider` like the others — resolves the `depends_on` edges over an ARBITRARY, explicitly-named set of issues that share NO epic parent (the items-without-`epic_ref` campaign variant deferred from #2003). Where `EpicChildren` derives its sibling set from an epic's sub-issue graph, `ResolveDependencies` is HANDED the exact set (`IssueSetRequest.Items`, in bare-`N` / `issue:N` form) and resolves each named issue directly: it fetches each body via `githubclient.GetIssue` and REUSES the same `parseDependsOnMarker` / `parseAutonomyLabel` / `parseIssueRef` helpers `EpicChildren` uses (no regex duplication), emitting the SAME `*EpicChildrenResult` shape `campaign.Assemble` consumes. The named set IS the sibling set: an in-set `depends_on` ref is an `Edge`, an out-of-set ref is a `DroppedEdge` stamped `DropNotChild` — the issue-literal contract fails closed on EVERY out-of-set target, deliberately WITHOUT the #2120 excluded-but-completed refinement the epic path applies (there is no epic child set to derive an out-of-set target's completion state from). `Complete = closed-AND-completed`, matched case-insensitively because `GetIssue` returns GitHub's LOWERCASE REST `state`/`state_reason` (unlike `ListSubIssues`' uppercase GraphQL enums). The `github_projects` impl implements it; jira (interface-only in v0) does not, so the create handler answers `501 issue_set_resolution_unsupported`.
- **Child-number derivation (#1958):** `EpicChildrenQuerier` ALSO feeds server-side `{n}` discovery for `[E<epic>.<n>]` child filings. The server hook (`server/workitems.go::deriveChildNumberTitleVar`) enumerates the parent epic's children (open AND closed — the same authoritative sub-issue-link source campaign assembly uses, deliberately NOT a fuzzy title search) and the pure `NextChildNumber` (`childnumber.go`) returns `(max+1, true)` over the matched numbered child titles, so `fishhawk_defer_concern`/`fishhawk_file_issue` no longer make the operator guess `{n}`. A caller-supplied `n` short-circuits discovery. **Zero-match fail-closed (#2101):** `NextChildNumber` allocates `1` ONLY for a genuinely-EMPTY child set; when children EXIST but none carry the numbered `[E<epic>.<n>]` form (e.g. epic #389's 100 placeholder `[E22.X]` sub-issues, or a title whose digit run overflows `strconv.Atoi`) it returns `(0, false)` and the server hook fails closed with a 422 `work_item_invalid` / `details.n_discovery_failed` naming the epic and the unmatched-child count, telling the operator to pass `title_vars.n` explicitly — mirroring #1265's empty-list guard for ADR numbering, instead of silently allocating `1` and colliding with an existing child. Discovery stays sub-issue-link-scoped: legacy body-only and cap-orphaned children are invisible to it, so widening discovery beyond the sub-issues connection is deferred (cross-ref #2101 Proposal 2 / #2102). It reads the same paginated `ListSubIssues` call, so an epic with >100 children now feeds `{n}` discovery its COMPLETE child set (the prior single-page truncation is gone — #2102); cap exhaustion fails closed rather than truncating discovery. The number is **collision-free within one deployment, not globally impossible**: two concurrent omitted-`n` filings against the same epic are serialized by an in-process per-parent-epic mutex in `applyAndFileWorkItem` (taken ONLY when `n` is discovered); a hosted multi-instance deployment (multiple `fishhawkd` processes sharing one tracker) would need a Postgres advisory lock instead, since the in-process map is invisible across processes.

## Product-report boarding (#1737: a filed product report reaches the board like a work item)

`fishhawk_file_issue` has always placed its work item on the tracker board; `fishhawk_report_product_issue` filed a bare issue that never appeared there, so a filed report only existed if someone remembered the URL. The feedback egress now boards its report on the same best-effort terms.

- **Request:** `FeedbackReport.BoardPlacement` (`feedback.go`) carries the desired placement. `backend/internal/server/product_report.go` sets `Status: "Backlog"` (the `productReportBoardStatus` constant) and builds the `Target` with `Project: conv.Project`, so the destination board is the repo conventions' board — the same one the work-item path uses.
- **Placement:** `github/feedback.go::(*FeedbackProvider).File` calls the shared `placeIssueOnBoard` helper in `github/provider.go`. That helper is the extracted body of `(*Provider).placeOnBoard`, which now delegates to it — one placement routine, two callers, so the work-item and product-report paths cannot drift. It is reached through the `boardAPI` slice (`ProjectFields` / `AddProjectItem` / `SetProjectItemSingleSelect`), which both `API` and `FeedbackAPI` carry; the production `feedbackAPIAdapter` (`backend/cmd/fishhawkd/workmgmt_wiring.go`) delegates all three straight to `*githubclient.Client`. User-owned boards still route through `githubclient.WithProjectsToken` — an App installation token cannot reach a user-owned Projects v2 board (#1114), so `FISHHAWKD_PROJECTS_TOKEN` remains the requirement, and its absence degrades to a recorded placement failure rather than a lost report.
- **Best-effort, exactly as #1107:** the filed report is the durable result. Once the issue exists `File` always returns it with a nil error, recording the outcome on `CreatedItem.Boarded` / `BoardingError`. The handler returns **201 with the report's number and URL intact** even when placement failed, and logs the cause server-side (`product report board placement failed`) so `boarded=false` is diagnosable from the logs as well as the response.
- **`boarded=false` is disambiguated, because the false cases need different operator actions.** `workmgmt.BoardingStatusOf(target, created)` is the single classifier (so the response, the docs, and the tests cannot drift) and the response echoes its verdict as `boarding_status`:

  | `boarding_status` | Meaning | `boarding_error` | Operator action |
  |---|---|---|---|
  | `boarded` | Placed on the board at Backlog. | absent | none |
  | `not_attempted_no_project` | The repo's conventions declare no project. A **configuration state, not an error** — placement was never attempted. | **absent, by construction** | none, unless they want a board |
  | `not_attempted_no_report` | A dedup hit appended an occurrence comment, so nothing was created to board. | absent | none |
  | `failed` | Placement was attempted and failed. | **present** — the cause | investigate |

  `failed` is the ONLY status that carries `boarding_error`; the handler clears the field on every other status, so an empty cause always means "not attempted" and never "attempted and quietly fine".

## Product-report wedge evidence (#1737)

The report body and the dedup-hit occurrence comment render the diagnostic bundle's `wedge_context` block (red required-check names, campaign item state, blocked-dependent count, a closed fan-in marker) when the run is wedged, and omit it entirely otherwise — an un-wedged run's body is byte-identical to the pre-#1737 rendering. The block is assembled by `backend/internal/diagnostics` from typed state only, so it inherits that package's redaction-safe-by-construction contract; a stage's free-text `FailureReason` never reaches it.

**The dedup fingerprint is deliberately unchanged.** `bundleFingerprint` hashes only (failure category, failure surface, failure detail class, version family) and never the bundle as a whole, so every currently-open deduped report keeps matching its recurrences across this change. `TestProductReport_FingerprintStableAcrossWedge` pins it.
