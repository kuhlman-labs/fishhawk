# backend/internal/workmgmt

Work-management conventions + provider abstraction: canonical work-item model, conventions rendering (`Apply`), and the `Provider` interface with optional capabilities (`Transitioner`, `EpicChildrenQuerier`, `IssueSetDependencyResolver`, `NumberDiscoverer`, `WorkItemReader`). Provider impls live in `github/`, `gitlab/` and `jira/` (see their READMEs).

## Board-state sync (#1012: run-lifecycle-driven work-item board transitions)

- **Config:** the `states` (canonical state → provider board option) + `transitions` (run-lifecycle event → canonical state) blocks in `docs/spec/work-management-v0.{md,schema.json}` + the shipped default, typed onto `workmgmt.Conventions.{States,Transitions}` with a transitions→states cross-reference semantic check.
- **Capability:** the optional `workmgmt.Transitioner` interface (`Transition(ctx, TransitionRequest) (*TransitionResult, error)`) — distinct from `Provider` so a non-boarding provider (jira) need not implement it. The `github_projects` impl in `backend/internal/workmgmt/github/provider.go` moves ONLY the Status column and honors never-fight-the-human: it advances only from a status in the request's expected-source set; an unset Status counts as Backlog.
- **Hook:** `backend/internal/server/boardsync.go::notifyBoardTransition` — best-effort (modelled on `notifyStatusUpdate`). It resolves the run's repo/issue/installation, maps the lifecycle event through `Conventions.Transitions`, derives the expected-source set from the prior lifecycle edges, dispatches the `Transitioner`, and appends a `work_item_transitioned` audit entry (every move AND every DECISION skip; see `docs/issue-comment-surfaces.md`). **Carve-out (#2494):** a `TransitionResult.NotApplicable` result — set by the provider for exactly the `no project configured` and `issue is not on the project board` skips — is logged at INFO and appends NOTHING, at all three emitters (run-, campaign-, and issue-scoped). A transition that touched no work item has no work-item transition to record, and on a repo with no board every lifecycle edge of every run wrote one, so the flood dominated the audit tail. Every other skip is a DECISION about a work item that DOES exist (never-fight-the-human source mismatch, already-at-target, unmapped canonical state, target status absent from the board, and the operator-actionable unreachable-user-board skip) and keeps auditing unchanged.
- **Call sites:**
  - run created → `run_started` (webhook `Dispatcher.BoardSyncer`, wired in `serve.go`, AND `handleCreateRun` in `runs.go` for local-runner / API-created issue runs, closing the #1123 webhook-exclusive gap)
  - PR opened → `pr_opened` (`pullrequest.go`)
  - run failed → `run_failed` (`trace.go::advanceAfterFailure`, only when the run reached terminal `failed`)
  - PR merged → `run_merged` (`pullrequest_review_events.go`)
- Errors log and never unwind the run.

## Issue-level `depends_on` relation + epic-children query (ADR-047 / #1437, E25.1: the campaign DAG source)

- **Model:** `workmgmt.Relations.DependsOn []string` (`model.go`) — the issue-level dependency edge a campaign derives its wave DAG from. Entries are issue refs (`#N`/`N`) among the epic's children, threaded through `fishhawk_file_issue` → `POST /v0/work-items` → `FilingRequest.Relations`.
- **Validation:** `apply.go::resolveRelations` format-validates each entry (positive `#N`/`N`). Cycle and existence checks are deferred to campaign-assembly time (E25.3) because `Apply` is pure and cycle detection needs the full DAG.
- **Persistence:** GitHub has no native depends_on relation, so `github/provider.go::File` stamps a `Depends on: #X, #Y` body marker (the single-source-of-truth `renderDependsOnMarker`/`parseDependsOnMarker` pair, idempotent via `ensureDependsOnMarker`), mirroring the `Parent epic: #N` convention.
- **Query:** the optional `workmgmt.EpicChildrenQuerier` capability (`EpicChildren(ctx, EpicChildrenRequest) (*EpicChildrenResult, error)`) — distinct from `Provider` like `Transitioner`/`NumberDiscoverer`. The `github_projects` impl resolves the epic node id, reads `githubclient.ListSubIssues` (which PAGINATES the `subIssues` connection under a bounded page cap, following `pageInfo.endCursor` until `hasNextPage:false`, so an epic with >100 children yields its COMPLETE child set — #2102), parses each child body's marker, and returns the children (ascending) plus the depends_on edges restricted to the sibling set. Because the child set is complete, a `depends_on` edge to an overflow sibling classifies into `Edges` rather than being truncated out and mis-dropped; cap exhaustion is a fail-closed error, never a silently-partial read.
- A reference to a non-child is kept OUT of `Edges` and surfaced in `EpicChildrenResult.DroppedEdges` (deterministically sorted, not silently discarded) so campaign assembly can fail closed on a dangling/mis-targeted dependency. E25.3 feeds the result into `plan.Waves`.
- **Completion signal (`EpicChild.Complete`, #2120):** each child carries `Complete = (GitHub IssueState == CLOSED && IssueStateReason == COMPLETED)` — the closed-and-completed "already merged/done" state read off the same `ListSubIssues` query (which selects `state`/`stateReason` on every paginated page, no extra round trip per child). A close as `NOT_PLANNED`/`DUPLICATE` is NOT complete (its work did not land). The campaign subset filter reads it to treat an included item's `depends_on` on an EXCLUDED-but-completed sibling as a satisfied dependency rather than a dangling one. Absent/unknown signal ⇒ `false` (fail-safe, restores the pre-#2120 fail-closed behavior).
- **`DependsEdge.Reason` (`DropReason`, #2120):** categorizes a DROPPED edge — `DropNotChild` (out-of-epic/typo'd target; the provider stamps every non-child dropped edge with it) or `DropExcludedIncomplete` (an included subset item depending on an excluded, incomplete sibling; stamped by the subset filter). It is `""` on a satisfied edge in `Edges` (additive: existing equality assertions on `Edges` are unchanged). Campaign `Assemble` groups dropped edges by this reason to name the cause+remedy per edge.
- **No-epic issue-set resolution (`IssueSetDependencyResolver`, E48.36 / #2051):** the optional capability (`ResolveDependencies(ctx, IssueSetRequest) (*EpicChildrenResult, error)`) — distinct from `Provider` like the others — resolves the `depends_on` edges over an ARBITRARY, explicitly-named set of issues that share NO epic parent (the items-without-`epic_ref` campaign variant deferred from #2003). Where `EpicChildren` derives its sibling set from an epic's sub-issue graph, `ResolveDependencies` is HANDED the exact set (`IssueSetRequest.Items`, in bare-`N` / `issue:N` form) and resolves each named issue directly: it fetches each body via `githubclient.GetIssue` and REUSES the same `parseDependsOnMarker` / `parseAutonomyLabel` / `parseIssueRef` helpers `EpicChildren` uses (no regex duplication), emitting the SAME `*EpicChildrenResult` shape `campaign.Assemble` consumes. The named set IS the sibling set: an in-set `depends_on` ref is an `Edge`, an out-of-set ref is a `DroppedEdge` stamped `DropNotChild` — the issue-literal contract fails closed on EVERY out-of-set target, deliberately WITHOUT the #2120 excluded-but-completed refinement the epic path applies (there is no epic child set to derive an out-of-set target's completion state from). `Complete = closed-AND-completed`, matched case-insensitively because `GetIssue` returns GitHub's LOWERCASE REST `state`/`state_reason` (unlike `ListSubIssues`' uppercase GraphQL enums). The `github_projects` impl implements it; jira (interface-only in v0) does not, so the create handler answers `501 issue_set_resolution_unsupported`.
- **Child-number derivation (#1958):** `EpicChildrenQuerier` ALSO feeds server-side `{n}` discovery for `[E<epic>.<n>]` child filings. The server hook (`server/workitems.go::deriveChildNumberTitleVar`) enumerates the parent epic's children (open AND closed — the same authoritative sub-issue-link source campaign assembly uses, deliberately NOT a fuzzy title search) and the pure `NextChildNumber` (`childnumber.go`) returns `(max+1, true)` over the matched numbered child titles, so `fishhawk_defer_concern`/`fishhawk_file_issue` no longer make the operator guess `{n}`. A caller-supplied `n` short-circuits discovery. **Zero-match fail-closed (#2101):** `NextChildNumber` allocates `1` ONLY for a genuinely-EMPTY child set; when children EXIST but none carry the numbered `[E<epic>.<n>]` form (e.g. epic #389's 100 placeholder `[E22.X]` sub-issues, or a title whose digit run overflows `strconv.Atoi`) it returns `(0, false)` and the server hook fails closed with a 422 `work_item_invalid` / `details.n_discovery_failed` naming the epic and the unmatched-child count, telling the operator to pass `title_vars.n` explicitly — mirroring #1265's empty-list guard for ADR numbering, instead of silently allocating `1` and colliding with an existing child. Discovery stays sub-issue-link-scoped: legacy body-only and cap-orphaned children are invisible to it, so widening discovery beyond the sub-issues connection is deferred (cross-ref #2101 Proposal 2 / #2102). It reads the same paginated `ListSubIssues` call, so an epic with >100 children now feeds `{n}` discovery its COMPLETE child set (the prior single-page truncation is gone — #2102); cap exhaustion fails closed rather than truncating discovery. The number is **collision-free within one deployment, not globally impossible**: two concurrent omitted-`n` filings against the same epic are serialized by an in-process per-parent-epic mutex in `applyAndFileWorkItem` (taken ONLY when `n` is discovered); a hosted multi-instance deployment (multiple `fishhawkd` processes sharing one tracker) would need a Postgres advisory lock instead, since the in-process map is invisible across processes.

## Work-item read/list capability (#2230 / ADR-064)

`reader.go` grows the provider abstraction from create-only to read/list. **Nothing in production calls it.** #2230 reserves the board-as-input seam; no HTTP route, MCP tool, CLI verb, env var, config field or migration resolves a reader.

- **Shape: a SEPARATE optional capability interface, not a `Provider` widening.** `WorkItemReader` (`ReadWorkItem(ctx, ReadWorkItemRequest) (*WorkItemRecord, error)` + `ListWorkItems(ctx, ListWorkItemsRequest) (*WorkItemPage, error)`) joins `Transitioner`/`NumberDiscoverer`/`EpicChildrenQuerier`/`IssueSetDependencyResolver`. The rationale is theirs: gitlab and jira are File-only in v0, and widening `Provider` would force every registered fake in every sibling package's tests to grow both methods. Here it is also the acceptance requirement that a second implementation not be forced into a GitHub-shaped contract — pinned executably by `gitlab/provider_test.go::TestProvider_DoesNotImplementWorkItemReader`, which would not COMPILE had the methods been folded into `Provider`.
- **Resolution chokepoint: `ReaderFor(id)`.** It resolves via `Get` and type-asserts the capability, returning a typed `*UnavailableError{Reason: ReasonNotImplemented}` for a File-only provider — never a nil interface a caller could dispatch against, and never an empty page it could misread. An unregistered id still yields the existing `*UnknownProviderError`. Routing every consumer through one chokepoint is what makes "never an empty list on a permissions failure" enforceable rather than conventional.
- **Typed degradation: `UnavailableError` + `UnavailableReason`.** Every read degradation returns a NIL result and this error. The closed reason set: `ReasonNotImplemented` (File-only provider), `ReasonNoProjectConfigured` (board state requested, no project on the target), `ReasonNoProjectsToken` (user-owned board, no `FISHHAWKD_PROJECTS_TOKEN` — the #1114 case), `ReasonForbidden` (the forge refused), `ReasonNoInstallation` (no credential scope), `ReasonBoardStateUndecidable` (the forge answered but ambiguously — the truncated-`projectItems` case below; a distinct reason from `ReasonForbidden` because nothing is wrong with the credential, so prompting for a token would be the wrong remedy). `Cause` retains the underlying forge error and `Unwrap` exposes it, so on ONE value `errors.As` yields the typed reason a caller switches on AND `errors.Is(err, githubclient.ErrForbidden)` still holds for existing forge-level handling. Note the deliberate asymmetry with `Transitioner`: a board transition degrades to a best-effort SKIP on an unreachable user-owned board, but a READ fails typed — a silent empty answer from a permissions failure is indistinguishable from an empty backlog, and acting on it drives the wrong decision.
- **Enumeration rule: ISSUES, never a board item list.** The GitHub impl enumerates through `githubclient.ListRepoIssues` (the GraphQL `repository.issues` connection, cursor-paginated to completion under a fail-closed page cap). A ProjectV2 board item list caps at 100 and truncates silently — the AGENTS.md Project #7 pagination trap — and the search REST API caps a result set at 1000. The rule is a convention compilation cannot enforce, so it is pinned behaviorally: `TestListRepoIssues_QueriesIssuesNotBoardItems` asserts on the GraphQL DOCUMENT the server received, and `TestProvider_ListWorkItems_ReturnsBeyondBoardItemListCap` replays a 150-issue two-page corpus at the consumer surface.
- **Nested-connection truncation FAILS CLOSED (not paginated).** Per-issue board status reads a bounded `projectItems(first:20)` page. An issue can sit on more projects than that, and a truncated page omitting the target project would report `OnBoard=false` for an item that IS on the board — a silent wrong answer of exactly the class this capability exists to eliminate. `ListRepoIssues` therefore REFUSES rather than paginating: a FULL page that does not carry the target project id returns a TYPED `*githubclient.BoardMembershipUndecidableError` naming the issue, the repo, the cap and the target project. The GitHub provider matches that type with `errors.As` and re-surfaces it as `*UnavailableError{Reason: ReasonBoardStateUndecidable}` with the githubclient error retained in `Cause`, so BOTH classifications hold on one value — a caller switches on the reason, or unwraps for the offending issue number. Typed at both layers on purpose: this is a classifiable degradation, and a caller that had to grep the message text to recognize it would have no contract at all. Pagination was rejected because it costs one extra round trip PER ISSUE on every page for a case that is pathological in practice; failing closed keeps the answer either correct or absent. `TestListRepoIssues_TruncatedProjectItemsFailsClosed` pins it, and `..._FullProjectItemsPageContainingTargetIsFine` pins that the guard is not over-broad.
- **Board-state filtering is an honest CLIENT-SIDE post-filter.** GitHub accepts no ProjectV2 single-select predicate on either the search API or the `repository.issues` connection, so `ListWorkItemsRequest.BoardStates` (CANONICAL states from `model.go`, never provider option strings) is applied after enumeration. The real cost — the full issue set is fetched before filtering — is acceptable at Fishhawk's scale and is stated here rather than hidden. `WorkItemRecord.BoardColumn` is the provider's raw option; `BoardState` is that option reverse-mapped through the request's `States` (the same `Conventions.States` map `TransitionRequest` carries) and is EMPTY when off-board, unmapped, or not requested — never guessed. `WorkItemPage.BoardStateResolved` distinguishes "not asked" from "asked and nothing found".
- **Label filtering: the FORWARDING is tested, the AND semantics are NOT.** `ListWorkItemsRequest.Labels` reaches the GraphQL `labels:` argument verbatim (asserted on the recorded request). GitHub AND-s that argument server-side, but that is *its* behaviour — an httptest fixture cannot prove it, so no test here does. A consumer must not read the passing tests as evidence of AND semantics.
- **`feedback.go`'s `FeedbackProvider` stays SEPARATE, deliberately.** It has its own registry and models product-feedback REPORTS (fingerprint dedup, wedge evidence), not backlog work items. Composing the two would force the feedback provider to grow a read surface with no consumer and widen exactly the blast radius the capability-interface pattern exists to avoid. Recorded here so the decision is durable and challengeable rather than implicit.
- **ADR-064 invariant: no board-read path on the MCP agent tool surface.** An agent acting on a stale, unaudited, rate-limited, truncation-prone board column would be acting on unreconciled run state. Enforced by `backend/internal/mcpserver/board_read_guard_test.go`, which walks the FULL in-repo dependency closure of `mcpserver`'s non-test code (so an intermediary package cannot route around it) and additionally checks direct symbol references. It is a source-level, tamper-EVIDENT check, not a runtime capability boundary; its own doc comment states what it does and does not establish, including that `githubclient` is already in that closure for unrelated reasons so the guard covers the workmgmt capability rather than the raw transport.

## Grooming apply (E54.5 / #2237)

`grooming_mutator.go` + `grooming_apply.go` execute the mutations an APPROVED `plan.GroomingReport` proposes. **Nothing in production calls it.** #2237 reserves the apply seam; no HTTP route, MCP tool, CLI verb, env var, config field or migration resolves a `GroomingMutator` or calls `ApplyGrooming`.

- **Shape: the SIXTH optional capability interface, not a `Provider` widening.** `GroomingMutator` (`ApplyGroomingMutation(ctx, GroomingMutationRequest) (*GroomingMutationResult, error)`) joins `Transitioner`/`NumberDiscoverer`/`EpicChildrenQuerier`/`IssueSetDependencyResolver`/`WorkItemReader`, for their reasons: gitlab and jira are File-only in v0, and widening `Provider` would force every registered fake in every sibling package's tests to grow the method. Pinned executably by `gitlab/provider_test.go::TestProvider_DoesNotImplementGroomingMutator`, which would not COMPILE had the method been folded into `Provider`.
- **Resolution chokepoint: `MutatorFor(id)`**, mirroring `ReaderFor`. A File-only provider yields a typed `*UnavailableError{Capability: GroomingCapability, Reason: ReasonNotImplemented}`; an unregistered id still yields `*UnknownProviderError`.
- **Two layers.** `deriveGroomingMutations` is PURE (no I/O, no provider, no clock) so the report→mutation mapping is unit-testable on its own; every side effect goes through the capability, so the containment rules live in ONE place rather than once per provider. Naming: `ApplyGrooming`/`GroomingApplyRequest`, never `Apply`/`FilingRequest` — `apply.go` already owns the pure FILING `Apply`.

### The seven containment rules and what pins each

| # | Rule | Behaviour | Pinned by |
|---|---|---|---|
| 1 | **Join** (AC1) | A decision naming an entry absent from the report — **or a REPEATED decision for one entry** — REFUSES the whole apply (`*GroomingJoinError`) before any dispatch — fail-closed, not a per-candidate skip | `TestApplyGrooming_DecisionForUnknownEntryIsRefused`, `..._ContradictoryDuplicateDecisionsAreRefused` |
| 2 | **Not approved** (AC2) | `rejected` / `amended` / no-decision / an unrecognized verdict are recorded skipped and never dispatched | `TestApplyGrooming_RejectedAndAmendedEntriesAreNotApplied`, `..._UnrecognizedVerdictIsNotAnApproval` |
| 3 | **Report mode** (inherited #2236 AC7) | A `report`-mode class SURFACES its proposal and acts on nothing. Surfacing is BOTH sides: it still performs the pre-dispatch READ so `Before` carries the current value next to the proposed `After`, and the resolved item ref is recorded even when resolution itself ended in a skip. Checked **BEFORE** any gate-approval check — see below. It never parks: `ApplyGrooming` has no awaiting-decision return path | `TestApplyGrooming_ReportModeSurfacesAndDoesNotAct`, `..._ReportModeSurfacesBeforeDespiteAReadFailure`, `..._SurfacedRecordNamesItsSubjectWhenResolutionSkips`, the report-mode row of `..._EveryMutationIsAudited`, and the `report+gate-approved` rows of the destructive table |
| 4 | **Destructive authorization** (AC5) | `close_duplicate` / `close_not_planned` / `icebox` dispatch only under mode `auto` + an approved entry, or an explicit per-entry `GateApproved`. An absent or unrecognized class mode resolves to `gated` | `TestApplyGrooming_DestructiveKindRequiresAutoOrGateApproval` (table over both destructive kinds) |
| 5 | **Idempotence** (AC7) | Every OBSERVABLE candidate is diffed against current state read through `WorkItemReader` before dispatch; an already-satisfied proposal is skipped `already_applied`. A reader degradation fails the candidate CLOSED — never a blind dispatch | `TestApplyGrooming_ReApplyingAnAppliedReportIsANoOp`, `..._ReaderUnavailableFailsCandidateClosed`, `..._NilReaderFailsObservableCandidatesClosed`, `..._MarkerObservationMatchesTheProviderParse`, `..._SecondDependencyEdgeIsSettledByTheProviderSkip` |
| 6 | **Manual placement** (AC6) | A board move whose card sits outside the expected source set is left alone — the same never-fight-the-human courtesy `Transitioner` honors. **Icebox is routed through it** | `TestApplyGrooming_ManualBoardPlacementIsPreserved` (paired refuse/dispatch cases for `board_place` AND `icebox`) |
| 7 | **Audit** (AC3) | One record per SETTLED candidate — applied, failed AND skipped — written immediately so a mid-run failure leaves everything before it audited; a sink error is collected and surfaced as `*GroomingAuditError` AFTER the loop | `TestApplyGrooming_EveryMutationIsAudited`, `..._AuditSinkErrorSurfacesAfterLoop`, `..._SummarySinkErrorSurfaces` |

**A surfaced proposal carries both values, or it is not a proposal.** A record showing only what *would* be written is not something an operator can act on — they cannot see what would change. So the report-mode arm performs the pre-dispatch read to populate `Before` before skipping. A read is not a mutation, so this does not weaken the rule; a read *failure* is not one either, so it degrades to an empty `Before` rather than failing the candidate (the mode dispatches nothing whatever the read says, so there is no blind-write risk to fail closed against). `IdempotenceChecked` stays **false** — the mode settled the candidate, not a diff. `resolveGroomingRequest` likewise returns its partial request alongside every skip reason rather than discarding it, so a surfaced or refused record still names its subject.

**Report mode beats gate approval, and the ORDER is the control.** The destructive rule permits a dispatch when the entry is gate-approved; report mode prohibits EVERY mutation. They disagree on exactly one input — `mode: report` together with `GateApproved=true` — so an implementation that checked gate approval first would mutate a report-mode destructive entry while every other row still passed. The mode check therefore short-circuits first, and that one combination is an explicit table row for both destructive kinds.

**A repeated decision id is an authorization defect, not untidiness.** `Decisions` is indexed into a map keyed by entry id, and a map insert is last-write-wins — so without the join's duplicate check a set carrying both `{id, rejected}` and `{id, approved}` would dispatch or refuse purely by ARRAY ORDER, at exactly the point AC2 is decided. The check refuses IDENTICAL repeats too: "which of these two rows did the operator mean" has no safe answer worth encoding, and a caller that meant one decision can send one. `TestApplyGrooming_ContradictoryDuplicateDecisionsAreRefused` sends both orders and requires the SAME answer (typed error, zero dispatches) from each — order-independence is the discriminating property, since with the guard removed the rejected-last rows still dispatch nothing and only the approved-last one reddens.

**Exactly one of `Applied`/`Skipped` must be true, and the apply layer VALIDATES it.** `settleGroomingCandidate` turns `GroomingMutationResult` straight into the load-bearing audit outcome, so a malformed result becomes a false audit row. A ZERO-VALUE result (both false) previously fell through to the applied-by-default arm and recorded a tracker write that provably did not happen; both-true was recorded skipped, hiding a provider that believes it wrote. Both are now recorded FAILED with an error naming the state, pinned by `TestApplyGrooming_MalformedProviderResultIsFailedNotFabricated` (which reads the settled OUTCOME and the buckets, not an error identity — the call returns nil either way).

**Continue and report, never abort (AC4).** A provider error records the candidate FAILED and the loop moves on; there is no abort path. Abort was rejected because a half-executed apply that stops at the first forge hiccup leaves the tracker in a state nobody enumerated, while continue-and-report leaves a complete, audited account of what landed and what did not. `TestApplyGrooming_ContinuesPastAMidRunProviderFailure` errors on the third of five candidates and asserts all five settled and were audited.

### Stated residuals — read these before assuming coverage

- **`rank_set` and `priority_set` are FIELD WRITES, not queue reordering.** GitHub's ProjectV2 GraphQL surface does expose a positional mutation, but this repository's provider implements NO positional primitive and #2237 adds none. An ordering entry's `rank` is written as a board FIELD VALUE; the board's own item order does not move. E54.6 / #2238's campaign feed must therefore READ the rank field back and sort on it, not expect a reordered board.
- **Idempotence covers the seven OBSERVABLE kinds, not all ten.** `WorkItemRecord` carries labels, body, state and the board Status column — no arbitrary project FIELD value — so `field_set` / `rank_set` / `priority_set` cannot be diffed and DO re-dispatch on a re-apply. Repeating a scalar field write is last-write-wins with no duplicate side effect, which is why the residual is acceptable; it is made visible per row by `GroomingMutationRecord.IdempotenceChecked` and pinned by `TestApplyGrooming_ValueSetKindsAreNotIdempotenceObservable` rather than left to prose.
- **No icebox column configured is an explicit, audited SKIP** (`icebox_column_unavailable`), never a silent no-op and never a misroute to another column. `work-management-v0`'s `states` map declares no icebox canonical state, so `GroomingApplyRequest.IceboxColumn` is supplied by the caller; a provider handed an unhandled kind returns a typed error rather than a no-op. `TestApplyGrooming_IceboxWithoutColumnIsRefused` seeds the item ON the board in an expected source state, so with the refusal deleted the mutation genuinely dispatches to the empty column.
- **A relationship is only idempotent if the WRITE and the READ observe the same persistence.** `WorkItemRecord` exposes labels, body, state and board column — no parent-edge or dependency graph — so `epic_link` and `depends_on_add` are diffed through their `Parent epic: #N` / `Depends on: #N` BODY MARKERS. That is why the GitHub provider stamps the epic marker alongside the sub-issue edge rather than relying on `AddSubIssue` alone: a write persisted somewhere the reader cannot see re-dispatches on every apply. Refs are compared NORMALIZED (`1437` ≡ `#1437`), since the agent's suggested fix and the persisted marker need not share a shape. **The read side observes what the PROVIDER's parse observes, not a narrower subset of it.** `parentEpicMarkerRE` / `dependsOnMarkerRE` are `(?im)` — case-insensitive and line-anchored — and `renderDependsOnMarker` emits a COMMA-SEPARATED ref list, so a body can legitimately carry `Depends on: #5, #6`, a lower-case marker, or a second marker line. `groomingMarkerObserved` therefore collects EVERY marker line case-insensitively, splits each value on commas, and `groomingSatisfied` asks a MEMBERSHIP question of the normalized refs; `Before.Scalar` still carries the first line's raw value so a surfaced record reads as the body does. A first-line, exact-case, whole-value compare observed a non-match for all three shapes and re-dispatched a relationship already recorded — AC7's zero-dispatch re-apply guarantee narrowed to single-ref canonical-case bodies (#2237 fix-up). Pinned by `TestApplyGrooming_MarkerRefShapeDoesNotDefeatIdempotence` and `TestApplyGrooming_MarkerObservationMatchesTheProviderParse` (whose last two rows are the over-broadness control: a ref the marker does not name still dispatches) here, and by a real-provider round trip in `github/grooming_test.go`. **A test fake must never persist something the provider does not** — `statefulGroomingForge` stamping a marker production did not write is how this gap survived #2237's first pass, and a fake that manufactures the evidence of correctness is worse than one that misses a defect.
- **A SECOND `depends_on` edge out of the same item is settled by the PROVIDER's skip, not by the core diff, and re-dispatches on every apply.** `ensureDependsOnMarker` writes a marker only when the body carries NONE — it never merges a ref into an existing line — so once `#1` records `Depends on: #5`, an approved `#1 -> #6` edge dispatches, reads the body, and comes back `depends_on marker already present`. The containment that matters holds by defence in depth: NO duplicate write reaches the tracker and the body keeps exactly one marker line. The cost is a redundant round trip per apply and an audit row naming the provider skip instead of `already_applied`. Stated rather than silently absorbed, and pinned as behaviour by `TestApplyGrooming_SecondDependencyEdgeIsSettledByTheProviderSkip`; merging refs into an existing marker is a PROVIDER-side change #2237 does not make.
- **An `epic_link` onto an item that already names a DIFFERENT parent is REFUSED, not corrected and not skipped.** `ensureParentEpicMarker` is idempotent on the MARKER, not on the PARENT — it returns any marker-bearing body unchanged — so reading that unchanged return as "the requested relationship exists" reported a body naming `#999` as already linked to a proposed `#1437`, which is precisely the state the core dispatches ON (its pre-dispatch read diffs the marker VALUE). The GitHub provider now compares every marker line's value NORMALIZED and returns a typed `*github.ParentEpicConflictError` naming both parents; the candidate is recorded FAILED. It refuses rather than re-parents because the provider has no primitive to re-parent with — `AddSubIssue` only ADDS an edge, and there is no removal or replace-parent option — so overwriting the marker would leave the body claiming one parent while the sub-issue graph held another. Pinned by `github/grooming_test.go::TestApplyGroomingMutation_EpicLinkRefusesADifferentExistingParent` with `..._EpicLinkMatchesTheParentAcrossRefShapes` as the normalization control.
- **Which item of a duplicate pair to close is NOT derivable.** The report states that two items overlap, with no direction, so `GroomingDecision.CloseTarget` carries the operator's choice; an absent or out-of-pair choice skips rather than closing an arbitrary member.
- **Two vocabulary members have no v0 derivation source**: `close_not_planned` (no report entry class carries a not-planned signal — vision drift is a FINDING and derives nothing) and `priority_set`. Both remain provider-executable kinds for an explicit future source; `TestDeriveGroomingMutations_MapsEveryEntryClass` asserts the derivation emits neither, so the gap is machine-checked rather than asserted here.
- **The `GroomingMode` mirror is not an import of `backend/internal/spec`.** The provider layer stays free of the workflow-spec dependency and the runtime consumer does the one-line mapping. If spec ever adds a fourth mode, `ResolveGroomingMode` under-approximates it in the FAIL-CLOSED direction (`gated`), pinned by a table row asserting an unrecognized mode never authorizes a dispatch.
- **`GroomingApplyRequest.Decisions` has no producer today.** No surface emits a per-entry approve/reject/amend set, so this slice DEFINES the contract a future gate surface must satisfy rather than consuming an existing one. If that surface models an amendment as a modified entry rather than a verdict, `amended` here is conservatively treated as not-applied — the safe direction.

**ADR-064 extended to board WRITES.** `backend/internal/mcpserver/board_read_guard_test.go` now also forbids the apply symbols (`GroomingMutator`, `ApplyGroomingMutation`, `MutatorFor`, `ApplyGrooming`, `GroomingMutation*`) on the MCP agent tool surface: an agent tool that could dispatch a grooming mutation would be acting outside the gate this whole layer exists to enforce. `GroomingReport` is deliberately NOT banned — ingesting the artifact is not dispatching a mutation.

## Product-report boarding (#1737: a filed product report reaches the board like a work item)

`fishhawk_file_issue` has always placed its work item on the tracker board; `fishhawk_report_product_issue` filed a bare issue that never appeared there, so a filed report only existed if someone remembered the URL. The feedback egress now boards its report on the same best-effort terms.

- **Request:** `FeedbackReport.BoardPlacement` (`feedback.go`) carries the desired placement. `backend/internal/server/product_report.go` sets `Status: "Backlog"` (the `productReportBoardStatus` constant) and builds the `Target` with the board the repo conventions declare — the same one the work-item path uses.
- **The destination board is independently authorized (`productReportBoard`).** A product report always lands in the FIXED product tracker (`productRepo`), but the board coordinates come from the SOURCE run's repo conventions — a different repo whose `.fishhawk` config this deployment does not own. Handing those straight to `placeIssueOnBoard` would let any repo Fishhawk runs against name an arbitrary Projects-v2 board and have the server write to it under a privileged credential — and for a user-owned board that credential is the operator's static `FISHHAWKD_PROJECTS_TOKEN` (#1114), not the run's scoped installation token. So the coordinates are honored only when they came from the DESTINATION repo's own conventions (the source run's repo IS the product tracker: the dogfood case the feature was built for). A withheld board reports `boarding_status=not_attempted_project_not_authorized` rather than `not_attempted_no_project`, because "you configured a board I will not use" and "you configured no board" send an operator to different places.
- **Placement:** `github/feedback.go::(*FeedbackProvider).File` calls the shared `placeIssueOnBoard` helper in `github/provider.go`. That helper is the extracted body of `(*Provider).placeOnBoard`, which now delegates to it — one placement routine, two callers, so the work-item and product-report paths cannot drift. It is reached through the `boardAPI` slice (`ProjectFields` / `AddProjectItem` / `SetProjectItemSingleSelect`), which both `API` and `FeedbackAPI` carry; the production `feedbackAPIAdapter` (`backend/cmd/fishhawkd/workmgmt_wiring.go`) delegates all three straight to `*githubclient.Client`. User-owned boards still route through `githubclient.WithProjectsToken` — an App installation token cannot reach a user-owned Projects v2 board (#1114), so `FISHHAWKD_PROJECTS_TOKEN` remains the requirement, and its absence degrades to a recorded placement failure rather than a lost report.
- **Best-effort, exactly as #1107:** the filed report is the durable result. Once the issue exists `File` always returns it with a nil error, recording the outcome on `CreatedItem.Boarded` / `BoardingError`. The handler returns **201 with the report's number and URL intact** even when placement failed, and logs the cause server-side (`product report board placement failed`) so `boarded=false` is diagnosable from the logs as well as the response.
- **`boarded=false` is disambiguated, because the false cases need different operator actions.** `workmgmt.BoardingStatusOf(target, created)` is the single classifier (so the response, the docs, and the tests cannot drift) and the response echoes its verdict as `boarding_status`:

  | `boarding_status` | Meaning | `boarding_error` | Operator action |
  |---|---|---|---|
  | `boarded` | Placed on the board at Backlog. | absent | none |
  | `not_attempted_no_project` | The repo's conventions declare no project. A **configuration state, not an error** — placement was never attempted. | **absent, by construction** | none, unless they want a board |
  | `not_attempted_no_report` | A dedup hit appended an occurrence comment, so nothing was created to board. | absent | none |
  | `not_attempted_project_not_authorized` | A board IS configured, but its coordinates did not come from the destination repo's own conventions, so placement was refused before any privileged call (see above). Also a configuration state. | **absent, by construction** | none |
  | `failed` | Placement was attempted and failed. | **present, always non-empty** — the cause | investigate |

  `failed` is the ONLY status that carries `boarding_error`; the handler clears the field on every other status, so an empty cause always means "not attempted" and never "attempted and quietly fine". Conversely `failed` is never cause-free: `BoardingStatusOf`'s defensive default arm (a project is configured and the provider reported neither placement nor cause) would otherwise produce a `failed` with nothing to act on, so the handler synthesizes `provider_reported_neither_placement_nor_cause`. `TestProductReport_FailedStatusAlwaysCarriesACause` and `TestProductReport_NotAttemptedStatusIsAlwaysCauseFree` pin the two directions.

- **`boarding_error` on the wire is a CLOSED literal, never the provider's raw error (`safeBoardingCause`).** The 201 is a SUCCESS response, so `writeError`'s default-deny detail allow-list never runs on it. A raw placement error carries third-party API text and — on the unknown-status path — the project's own Status field OPTION NAMES, private board metadata reachable only through the operator's privileged token. So the response carries one of `project_fields_unavailable` | `add_project_item_failed` | `status_option_unknown` | `set_status_failed` | `placement_failed` | `provider_reported_neither_placement_nor_cause`, naming WHICH STEP failed, while the raw cause goes to the `product report board placement failed` WARN log the operator already reads. Classification keys on `placeIssueOnBoard`'s own wrapper messages and the default arm is FAIL-SAFE: an unrecognized or reworded provider error degrades to `placement_failed` rather than falling back to an echo, so a new error string can never become a disclosure by omission.

## Charter declaration (E54.1 / #2233)

`Conventions.Charter` declares where a repo's checked-in charter document lives — the prioritization anchor a backlog-grooming run (ADR-065 / E54) reads so every ranking it proposes cites a rubric line by id. **Nothing in this package reads, injects, or renders that document.** This is the declaration and its typed parse; the mechanism is `backend/internal/repodoc` (#2796).

- **Shape:** `Charter *Charter` (`conventions.go`), where `Charter` is `{Path string}` with json tag `path`. The `charter` block is optional at the schema level, but `path` is `required` and `minLength: 1` **when the block is present**, so a non-nil `Charter` always carries a non-empty path. Config surfaces: the canonical `docs/spec/work-management-v0.schema.json` + its embedded mirror, and the shipped default, which declares the conventional `.fishhawk/charter.md`.
- **Why a POINTER.** A value-typed field would render a config that omits the block as a zero-valued *present* one, and a consumer could not tell "no charter declared" from "charter declared with an empty path" — the absent / present-but-empty distinction. `TestParseWithoutCharter` pins `Charter == nil` for an omitting config; a value type could not satisfy that assertion.
- **Schema-optional, feature-mandatory.** The block is absent from the schema's top-level `required` array purely because a new required field in an existing major is a breaking change. It is not a fail-open: `backlog_grooming` fails closed when no charter resolves, and that enforcement lives in #2234/#2236, not here.
- **Why no path-shape semantic check lives here.** `validateSemantics` adds **no** rule for `charter`; structural validation is the whole declaration-time contract. Rejecting absolute / `..`-bearing / backslash paths at parse time would give an earlier error, but `repodoc.validatePath` already enforces exactly that rule fail-closed at the single point where the declared path is used to fetch anything. A second copy here would be a second owner of one invariant, free to drift from the enforcing one. `TestParseCharterNoSemanticPathRule` records this side of the decision as behaviour — a traversal-, absolute-, or backslash-bearing declaration parses here without error — while `repodoc`'s own `validatePath` table pins the refusal at resolve time. This is a design choice, not something the issue mandates — if a future change wants declaration-time rejection, delete that test deliberately rather than around it.
- **Consumers (both now shipped):** `backend/internal/server/charter_injection.go` (E54.2 / #2234) reads `Charter.Path` at PROMPT-SERVE time — it is the `Config.DocumentDeclarations` implementation that declares the charter for a backlog-grooming propose stage, resolving it through `repodoc` at a pinned commit and refusing the prompt when the block is absent (`charter_absent`), its path is empty (`charter_path_empty`) or the conventions cannot be read (`conventions_unavailable`); `backend/internal/server/charter_gate.go` (E54.4 / #2236) is the RUN-ADMISSION half, refusing a grooming run 422 before any run row exists using the same three reasons. Both reach this package through the process-wide `conventionsLoader` seam, and neither adds a second path-shape rule. See `backend/internal/repodoc/README.md`, whose declaration-site table already names `charter.path` in `.fishhawk/work-management.yaml`, and the content contract in `docs/spec/work-management-v0.md` ("Charter"), worked against this repo's own `.fishhawk/charter.md`.

## Grooming churn guard (E54.8 / #2240)

`grooming_churn.go` is the run-over-run filter that turns a schema-valid `plan.GroomingReport` into the **proposal set** an operator actually sees. It is the mitigation ADR-065 names for its own sharpest adoption risk: a scoring agent re-run over a large backlog perturbs the ranking every time, and a report full of trivia teaches the operator to approve without reading — at which point the grooming gate is decorative and every other control in E54 rests on it.

**It runs in production.** `Server.handleGroomingReport` (`backend/internal/server/grooming_report.go`) invokes `FilterGroomingChurn` on every ingested grooming report and writes the verdict to the audit chain as one `grooming_churn_filtered` entry, carrying the proposed / suppressed / resurfaced counts and ids, the resolved thresholds, the `charter_changed` flag, and the `no_changes_proposed` flag that IS #2240 AC1's visible "no changes proposed" outcome. An operator arms `fishhawk_await_audit` on that one category to learn what a run actually proposes, as distinct from what the agent emitted.

### The moving parts

| Symbol | Role |
|---|---|
| `Conventions.ResolveGroomingThresholds` | resolves the operator-declared bar (`conventions.go`), substituting the shipped defaults for absent fields and CLAMPING a sub-floor declared value to the default while naming it in `Clamped` |
| `NewGroomingBaseline` | pure constructor of the three-state baseline from the prior report + the operator's decisions + the apply result |
| `groomingEntryBasis` (per class) | the structural fingerprint, prose deliberately excluded |
| `FilterGroomingChurn` | the guard itself: pure, no I/O, no clock, no provider |
| `Server.groomingChurnBaseline` | the production baseline assembly, built only from query surfaces that already exist |

The decision order, the three-state baseline, the per-class fingerprint table and the charter-change lift are documented normatively in `docs/spec/work-management-v0.md` § "Grooming churn thresholds". Two rules are worth repeating next to the code:

- **The hygiene significance bar runs FIRST**, ahead of the baseline lookup, so it governs a NEW finding as well as a repeat one (#2240 approval condition J2). An operator who declares a defect class insignificant expects not to see it, not to see it once.
- **Absence from the baseline is the third state.** This guard suppresses, so every ambiguity resolves toward proposing: a failed apply, a containment skip, an unrecognized class, an unrecognized disposition and an unreadable prior report all leave the entry proposed, with the anomaly named in the summary.
- **Both baseline-integrity checks run ahead of EVERY suppression path.** The unrecognized-class and unrecognized-disposition checks sit together, before the basis comparison and before the ordering thresholds — not inside the disposition switch that names the final suppression. The ordering branch returns `below_ordering_threshold` without ever reading the disposition, so validating it only at the end suppressed a degraded record whenever its rank and score movement happened to be sub-threshold (#2240 fix-up).

### Production baseline assembly, and its stated gap

`Server.groomingChurnBaseline` walks `ListRuns(repo)` → `ListStagesForRun` → `artifact.ListForStage` to find the most recent prior run's grooming report, then reads that run's `grooming_mutation_applied` audit rows for the dispositions. That one category carries both halves: an `applied` outcome (or a skip whose reason is `already_applied`) is an APPLIED disposition; a skip whose reason is `not_approved` or `amended` is a REJECTED one. No new DB query, sqlc regeneration, or repository-interface widening rides along.

**A repo string is not an identity, so candidate selection is tenant-scoped twice (#2240 fix-up).** ADR-057 hangs a nullable `account_id` off every root entity and installations route to different `forge_base_url`s (GHES and github.com), so two tenants can legitimately own runs whose `Repo` is the same `owner/name`. Adopting one as another's baseline would both corrupt the verdict and copy that tenant's entry ids into this run's audit payload. The `ListRuns` filter therefore carries `AccountID`, AND every candidate is re-checked against the current run's account **and** installation before it can become a baseline — the second check is not redundant, because the query's account predicate deliberately keeps `account_id IS NULL` rows visible (right for a listing surface, wrong for a suppression control), and an untenanted current run constrains the query not at all. Tenant equality is exact, an unset installation included: an over-strict mismatch costs a baseline and therefore proposes, which is the fail-safe direction.

**Recency is enforced here, not inherited.** The candidate set is sorted `created_at DESC, id DESC` in the function rather than trusting query order. The production `ListRuns` does declare that ORDER BY — but a suppression control that silently diffs against the OLDEST baseline if the clause ever changes fails in the unsafe direction (suppressing against stale dispositions), and nothing else binds this function to that clause.

**The gap, stated rather than implied: nothing in production calls `ApplyGrooming` yet.** #2237 shipped the apply layer with its seam deliberately unwired, so no `grooming_mutation_applied` row exists today and every baseline currently resolves empty — which correctly proposes everything, since nothing has in fact been applied or rejected. The wiring above reads the real category, so dispositions populate the instant an apply consumer lands, with no change to this package or to the handler.

### Stated residuals

1. **No apply consumer**, per above: dispositions are structurally empty until one lands.
2. **The decomposition fingerprint is the child COUNT**, not their titles, so a re-worded split of the same item into the same number of children does not resurface. This is the coarsest choice in the design and a deliberate trade against re-litigating wording every run; switching to normalized titles is a one-line change.
3. **A rejected proposal whose only change is re-worded justification does not resurface.** That is the direct consequence of excluding prose, and excluding prose is what makes the guard work at all.
4. **`GroomingProposalSet` is a projection, not a `grooming_report_v1` document.** That schema requires `ordering` with `minItems: 1`, and an EMPTY proposal set is precisely the outcome AC1 demands, so the empty case cannot be expressed as a valid report artifact. Making it one is a grooming-report-v1 change belonging to #2235.
5. **The guard does not alter what is persisted.** The report artifact is stored as the agent emitted it; the guard's verdict is a separate audit record. Nothing here mutates a tracker or rewrites an artifact.
