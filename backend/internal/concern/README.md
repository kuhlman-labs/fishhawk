# backend/internal/concern

Durable concern lifecycle with stable IDs: every review verdict's `concerns[]` persisted so fix-up routing addresses concerns by ID.

## v1 slice — stable IDs and lifecycle (#964, E22.X)

Every `plan_reviewed` / `implement_reviewed` verdict's `concerns[]` is persisted with a server-minted stable UUID so fix-up routing addresses concerns by ID instead of a flattened positional index (ambiguous once multiple heterogeneous review entries exist per stage — the run-73456dc8 mis-route).

Storage: this package (domain `Concern`/`State`/`Transition` + `Repository` {InsertRaised, GetByIDs, ListByRun, ListOpenByRun, MarkAddressedPending, ApplyResolution, plus ImportRolledUp and StampOpenAtMerge since #4692}; sqlc `db/`; migration `0030_review_concerns` — severity/category/state are tolerant plain TEXT, validity enforced by the Go state machine only).

The lifecycle enum ships in full (`raised`, `addressed_pending`, `addressed`, `reopened`, `waived`, `superseded`, `deferred`, `addressed_by_condition`) with **reopen-wins-over-confirm** encoded order-independently: `addressed → reopened` is a valid edge (a reopen applies even after a confirm landed first) while `reopened → addressed` is rejected with a loggable `InvalidTransitionError` (a late confirm never silently downgrades a reopen).

`superseded`'s first production writer is the plan-gate revise handler (`server/revise.go::supersedeReplanConcerns`, `fishhawk_revise_plan`, #2065): a `revise` re-plans IN PLACE, re-opening the SAME plan stage (same `stage_id`), so the store cannot distinguish the discarded revision's plan-review concerns from the new round's. On a successful revise the handler best-effort transitions every OPEN plan-stage concern of that stage to `superseded` (CLOSED; see the routability note below — a PLAN-stage superseded id is still refused by the implement fix-up on its stage kind) (from `raised`/`addressed_pending`/`reopened`) BEFORE the re-plan review mints fresh `raised` rows, dropping them out of every open-concern surface (`ListOpenByRun`, the run-status open block, the merge gate's `len(open)==0` check) so the operator does not hand-waive concerns from a discarded revision. Warn-only, matching the store's best-effort posture: a nil repo, a `ListByRun` read error, or a per-concern `ApplyResolution` failure never fails the revise.

**`superseded` is CLOSED but NOT terminal (E45.83 / #3618).** It is the ONE closed state with an outgoing edge: `superseded → addressed_pending`, added so an operator fix-up can RECOVER a retry-discarded concern. Everything else about it is unchanged — `State.IsOpen()` still returns `false` for `superseded`, so no open-concern surface (`ListOpenByRun`, the run-status open block, the merge gate's `len(open)==0` check), no auto-resolve path and no settled-ledger consumer observes a difference until an operator deliberately names the id. The edge is reachable ONLY through `MarkAddressedPending`, whose sole production caller is `server/fixup.go`, which already scopes ids to implement-stage concerns of the fix-up's target stage; a routed row re-enters the open set keeping its `reviewer_model`, `origin_review_sequence` and `severity`, with the operator's fix-up reason as its new `state_reason`, and is then tracked to closure by the existing delta-verification machinery exactly like any routed concern. Deliberately ABSENT are `superseded → addressed` (a discarded concern was never answered, so it cannot be confirmed), `→ reopened` (recovery goes through `addressed_pending`, the state the fix-up machinery keys on) and `→ waived`/`deferred`/`addressed_by_condition` (a closed concern needs no second disposition). `waived`, `deferred` and `addressed_by_condition` remain genuinely terminal with NO outgoing edge at all. Pinned by `concern_test.go::TestTransition_SupersededExitsAreNarrow` + `TestTransition_TerminalStatesAdmitNoExit` and, through the real store's from-state-guarded UPDATE, by `postgres_test.go::TestPostgres_SupersededReRoutesToAddressedPending` + `TestPostgres_MarkAddressedPending_RefusesWaived`. No migration was needed: `review_concerns.state` is plain TEXT with no CHECK.

**Two more `superseded` writers exist for the IMPLEMENT-stage retry analog (#3593),** both routed through the shared `server/trace.go::supersedeOpenImplementConcerns` best-effort primitive (same posture: nil repo / `ListByRun` error / per-row `ApplyResolution` failure warn-and-continue, the caller's outcome never gated on it):

- **The retry-time sweep** — `server/retry.go::retryStageAs`, after the `stage_retried` / `stage_override_retried` audit write and BEFORE the run un-terminal, when the retry re-opened an implement stage to `pending` (a D-timeout `awaiting_approval` re-open and non-implement stages supersede nothing). A retried implement stage USUALLY discards the tree the prior attempt's review round judged, so its OPEN implement concerns describe a tree that no longer exists — leaving them `raised` strands them at the merge gate (the retry round's `confirmed` resolutions cannot legally drive `raised → addressed`). When it fires, the sweep matches ALL open implement concerns of the re-opened stage. **It is CONDITIONAL since E45.86 / [#3621](https://github.com/kuhlman-labs/fishhawk/issues/3621):** when the next dispatch will RESUME from a held commit — `newestPushCheckpoint` reports `checkpointResumable`, i.e. a complete `pr_open` or `push` checkpoint is still the stage's newest terminal outcome — the concerns still describe the tree about to be pushed, so the sweep is SKIPPED and they stay `raised`. Every undecidable audit state maps to `checkpointNone`, so the fail-safe direction is the historical one: supersede. A retry that DOES discard additionally appends a `verified_tree_discarded` audit row naming the thrown-away tree.
- **The post-persist re-check** — `server/trace.go::runImplementReviewInvocations`, after `persistReviewConcerns` mints a verdict's rows, RE-READS the latest same-stage retry sequence and supersedes ONLY the just-minted rows (`OriginReviewSequence == entry.Sequence`) when it exceeds the round-start sequence. This pairs with the retry-time sweep to cover the window where a retry lands DURING persistence (after the `implement_reviewed` payload was already written UNMARKED): a retry at any instant is caught by whichever of {sweep, re-check} runs second. The verdict-build-time arm stamps `superseded_by_retry` on the payload when the retry is already visible; the accepted unmarked window is safe because the PR relay also consults the retry rows against the recorded `review_round_sequence`, not the flag alone.

Persistence rides the review loops (`server/trace.go::persistReviewConcerns`, called from `runImplementReviewInvocations` + `plan.go::runPlanReviewLoop`): rows are inserted AFTER the audit append using the sequence `AppendChained` RETURNs (`origin_review_sequence` NOT NULL — the audit chain stays the sole sequence authority), best-effort/warn-only (the audit payload remains the authoritative record; the store is a derived index).

Surfaces:

- `GET /v0/runs/{run_id}` attaches a `concerns` block ({open, by_state, items:[{id, stage_kind, severity, category, state}]}, OPEN states only, note text elided) on the single-run read ONLY — `toRunResponse` stays pure and the list endpoint never gains a per-row concern query; `fishhawk_get_run_status` mirrors it via the MCP `Run.Concerns` type.
- `POST /v0/stages/{id}/fixup` accepts `concern_ids` as the PRIMARY addressing scheme (`server/fixup.go::resolveConcernsByID` — scoped to the stage; unknown/foreign/plan-stage/non-open IDs → 400 `validation_failed`, so a plan-stage concern can never route into an implement fix-up; needs the store, else 503 `fixup_unconfigured`), marks routed concerns `addressed_pending` after the `stage_fixup_triggered` append (which now also records the routed `concern_ids`), and keeps positional `concerns` indices as a DEPRECATED fallback (both at once → 400).
- `GET /v0/runs/{run_id}/gate-view` (`server/gateview.go`, #1960; MCP verb `fishhawk_get_gate_view`) is the gate-scoped decision read: `ListByRun` partitions the run's rows into OPEN vs settled, each OPEN concern carrying its FULL `note` (unlike the run-status block above) plus per-concern `fixups[]`/`resolutions[]` reconstructed from the immutable audit payloads (history join, because `StateReason` is overwritten on every transition) and a derived `round`. Needs the store, else 503 `gate_view_unconfigured`; audit-read failures degrade visibly (`history_incomplete` + `history_gaps`) with the concerns intact.

Wiring: `server.Config.ConcernRepo`, constructed in `serve.go`.

## v2 slice — waive + delta-verifying re-reviews (#984, E22.X)

The deferred #964 verbs, landed with no migration (the enum + tolerant columns were shaped for it):

1. **Operator waiver** — `POST /v0/concerns/{concern_id}/waive` (`server/waive.go::handleWaiveConcern`; MCP verb `fishhawk_waive_concern`) transitions any OPEN concern to terminal `waived` with a REQUIRED reason, under fix-up's exact auth shape (`write:stages`/`write:fixups` + the `mcp:run:<uuid>` cross-run guard → 403 `cross_run_waive`); a `server_check` concern additionally refuses any agent token or delegated request (403 `concern_requires_human`, see the server-check provenance slice below).
   Audit-before-mutation: the `concern_waived` entry appends FIRST (append failure → 500 `audit_append_failed`, NO mutation); a transition that then fails appends a corrective `concern_waive_failed` entry (warn-only) and returns 422 `concern_waive_conflict` — a mutation can never exist without a durable record, in every interleaving.
2. **Delta-verifying re-reviews** — `trace.go::priorConcernsForReview` threads the stage's OPEN implement concerns into `prompt.Trigger.PriorConcerns` (warn-and-proceed on a list error — a store outage never blocks dispatch) — EXCEPT a `server_check` row (E80.3 / #3760), which no reviewer may resolve, so the delta-verification section never asks one to. (Since #1913 the settled rows — waived/deferred + addressed/superseded — are threaded separately by `settledConcernsForReview` into `Trigger.SettledConcerns`; see the "Settled-concerns ledger" slice below.)
   `buildImplementReview` renders a binding `### Prior concerns (delta verification)` section (every `addressed_pending` concern MUST get a `concern_resolutions` entry — confirmed/reopened/superseded; `concerns[]` never re-mints a listed concern) and extends the inline verdict schema with `concern_resolutions` — both only when the set is non-empty, so a first review's prompt stays byte-identical.
3. **Resolution processing** — `planreview.ReviewVerdict`/`ImplementReviewedPayload` gain tolerant-decode `ConcernResolutions` (omitempty; old reviewer output and old stored payloads stay valid — the audit payload remains the authoritative record).
   After each successful `implement_reviewed` append, `trace.go::applyConcernResolutions` maps `confirmed → addressed`, `reopened → reopened`, `superseded → superseded` through `ApplyResolution`, warn-and-skipping every malformed/unknown/foreign-stage/plan-stage/invalid-transition entry (valid siblings still apply) so a sloppy reviewer can never wedge the gate; reopen-wins-over-confirm needs no reconciliation pass — the state machine encodes it order-independently.

   **Since E48.103 / #2551 a `confirmed` no longer transitions unconditionally.** The state machine here is UNCHANGED — `addressed_pending → addressed` remains the only confirm edge and `ApplyResolution` validates it exactly as before — but the server now sits a round-level VETO in front of that edge: the resolutions of one implement-review round are buffered and applied once (`trace.go::applyRoundConcernResolutions`), and a `confirmed` is REFUSED (no `ApplyResolution` call, so the row keeps its state and `state_reason`) when the raising reviewer rejected in the same round, when the concern was routed with operator `operator_evidence`, when the routing pass recorded `fixup_no_changes`, or when the evidence lookup failed (fail-closed). `superseded` is never vetoed — with ONE exception since E80.3 / #3760: on a `server_check` row the `server_check_requires_human` arm (evaluated ahead of all others) refuses a reviewer `confirmed`, a reviewer `superseded` and the clean-round auto-close alike, because only a human waive or defer may clear a server-synthesized concern. **Since #3319 ONE `reopened` arm exists too, and it is decided PER RESOLUTION rather than from that round-level context**: a `reopened` is REFUSED (`reopen_without_named_concern`) exactly when `planreview.RejectSubstantiatesResolution` is false — the verdict is `reject`, `len(concerns) == 0`, and `strings.TrimSpace` of THIS resolution's own `note` is empty. Only this resolution's own note substantiates it: on a verdict pairing a noted `confirmed` for concern A with a blank-note `reopened` for concern B, A's confirm applies and B's reopen is refused. `free_form` substantiates nothing (it is unmatched to any concern id), and the VERDICT-LEVEL `planreview.RejectNamesNoConcern` is for the display-only `reject_without_concern` advisory and is never consulted by the veto. A vetoed concern stays OPEN and is resolvable only by a waive, a defer, or a genuine later fix; the refusal is recorded as a `concern_resolution_vetoed` audit entry and surfaces on the gate view as `disputed` + `disputes[]`.

## Defer slice — operator defer (#1202, E22.X)

The third concern-resolution verb, also no migration (`deferred` rides the tolerant TEXT `state` column): **operator defer** — `POST /v0/concerns/{concern_id}/defer` (`server/defer_concern.go::handleDeferConcern`; MCP verb `fishhawk_defer_concern`) converts any OPEN concern into a conventions-complete, boarded, epic-linked follow-up work item AND transitions it to terminal `deferred` in one call (consuming NO fix-up budget), sitting between `/fixup` (route back to the agent) and `/waive` (resolve with no follow-up).

- Auth byte-identical to `/waive` (`write:stages`/`write:fixups` + the `mcp:run:<uuid>` cross-run guard → 403 `cross_run_defer`), including the `server_check` human-only refusal (403 `concern_requires_human`, agent-token arm only — defer has no `delegated` flag).
- The follow-up body is auto-drafted from the concern (note, severity, category, reviewer model, evidence run id, source PR link); the operator supplies only `parent_epic` + `n` (the non-derivable title coordinates), `type` defaulting to `bug` for a defect category else `chore`.
- The filing pipeline is the extracted `workitems.go::applyAndFileWorkItem` (the #1005 confused-deputy egress gates stay on the HTTP filing handler verbatim — defer resolves its already-authorized run's installation directly).
- **Orphan-issue safety + audit-ordering (inverse of waive):** an open-state PRE-CHECK runs BEFORE any filing (a non-open concern → 422 `concern_defer_conflict`, provider `File` never called); the issue is filed FIRST then the concern transitions; a filing failure leaves the concern OPEN (no transition, no audit); the success `concern_deferred` entry is appended ONLY AFTER the transition succeeds (a fact, not an attempt); a post-filing transition race emits ONLY a corrective `concern_defer_failed` entry (naming the actual state + the orphaned issue url) and returns 422.
- Surfaced in `next_actions`' `implement_concerns_open` arm between fix-up and merge-with-follow-up, in both budget branches — and, since [#3116](https://github.com/kuhlman-labs/fishhawk/issues/3116), in the two GATE-CLOSED arms (`implement_concerns_open_acceptance_pending`, `implement_concerns_open_gate_closed`) as well. Those arms drop `fishhawk_fixup_stage`, which the endpoint refuses while the review gate is closed; defer survives precisely because it consumes NO fix-up budget and is legal the whole time, so it is the operator's one acting move in that window.

## Settled-concerns ledger + re-litigation guard (#1913, E22.X)

Re-review rounds churned because a round-N reviewer had no settled history and re-raised settled findings reworded (runs a04d5cbf: 5 reject rounds; 98704b0c: 3). Two changes make the rounds converge:

- **Settled-ledger threading.** `trace.go::settledConcernsForReview` gathers the stage's SETTLED implement concerns — `waived` + `deferred` (operator arbitrations) plus `addressed` + `superseded` (prior rounds' resolved rows) — into `prompt.Trigger.SettledConcerns`, each carrying its audited `StateReason`. Threaded into EVERY post-fixup round, it closes the two convergence gaps the issue measured: DEFERRED arbitrations reach the reviewer at all (they were dropped entirely before), and delta rounds N>=2 carry the full settled history instead of only the currently-open rows. Same best-effort posture as `priorConcernsForReview` (nil repo / list error → nil, warn-logged). `buildImplementReview` renders the two-tier `### Settled concerns` ledger; see `prompt/README.md`.
- **Deterministic re-litigation guard.** A reviewer concern may echo the id of a settled ledger entry via `planreview.Concern.SettledRef` and justify a re-raise via `NewEvidence` (both optional, omitempty, on the closed verdict schema). `trace.go::persistReviewConcerns` — via `suppressRelitigation` — checks each verdict concern before minting a durable open row: when `SettledRef` resolves to a **same-run/same-stage/same-stageKind** concern whose state is **`waived` or `deferred`** AND `NewEvidence` is empty, the concern is NOT inserted as a fresh open row; instead a best-effort `concern_relitigation_suppressed` audit entry records the suppression (never silent). The guard is **operator-arbitrated states ONLY** — a re-raise against an `addressed`/`superseded` concern stays insertable, because a genuine regression of an addressed fix must reach the operator (the `addressed → reopened` edge already models that). Every other case falls open to the normal insert: empty/unparsable/unknown `settled_ref`, a ref to another run/stage or a non-waived/deferred state, non-empty `new_evidence`, and any lookup/append error (warn-logged) — a sloppy or absent tag can never suppress a genuine finding, and a store outage never wedges the loop. The reviewer's verdict and its audit payload are recorded unchanged; the guard only stops the durable OPEN row that wedges the gate and drives repeat rounds.

## Condition-claim resolution slice (#1956, E48.9)

Closes the approval-condition-to-plan-concern lineage gap: an operator's binding approval condition that answers a plan-stage concern can now auto-resolve that concern once a re-review confirms the condition delivered, instead of demanding a hand waive at the merge gate. No migration (`addressed_by_condition` rides the tolerant TEXT `state` column):

- **New terminal state** `addressed_by_condition` — reachable from every open state (`raised`, `addressed_pending`, `reopened`) like `waived`/`deferred`, deliberately NOT from `addressed` (an already-confirmed concern needs no condition resolution), and `IsOpen()` false. Because `queries.sql::ListOpenReviewConcernsByRun` allowlists the OPEN states (`state IN ('raised','addressed_pending','reopened')`) rather than denylisting terminal ones, the new state is automatically excluded from `ListOpenByRun`, the run-status open-concerns block, and fix-up routing with zero SQL change; it lands in the gate-view settled ledger.
- **Claim declaration.** The operator's `fishhawk_approve_plan` / approvals endpoint accepts an optional `claims_concern_ids` — the plan-stage concern id(s) this approval's binding condition answers (operator-confirmed design; no NLP/heuristic matching). Validated pre-Submit (`server/condition_claims.go::validateClaimsConcernIDs`): approve-only, plan-stage-only, each id a UUID resolving to an OPEN plan-stage concern of the SAME run; a malformed claim inserts no approval row. The claim rides durably on the `approval_submitted` audit payload (the `binding_assertions` pattern), loaded back via `loadApprovalConcernClaims`.
- **Resolution.** After ONE implement review returns a confirming (non-reject) verdict, `server/trace.go::resolveConditionClaimedPlanConcerns` (fired once per review loop) appends a `concern_addressed_by_condition` audit entry FIRST (concern id, prior state, claiming approval sequence + approver subject, confirming review sequence + reviewer model, verdict, plus the settled row's own `category` and `severity` — E75.1 / #3729, recorded UNCONDITIONALLY including when empty, so a chain-only decision index can join a settled concern to what KIND of concern it was and can tell 'recorded and empty' apart from an entry predating the change, where both keys are ABSENT) and only then transitions the row to `addressed_by_condition`, so the concern → condition → confirming-review lineage is durable in the chain. Whole path is best-effort/warn-only (append failure skips the transition; an already-terminal claim — a waive/defer that won the race, or a later re-review round — is silently skipped for idempotency), matching `applyConcernResolutions`. The re-litigation suppression guard is deliberately NOT extended to `addressed_by_condition` (like `addressed`, a later re-raise with regression evidence must reach the operator).

- **Claim SHORTHAND** (E64.77 / [#3318](https://github.com/kuhlman-labs/fishhawk/issues/3318)). `claims_all_open_plan_concerns: true` claims EVERY open plan-stage concern of the run instead of naming ids — the read-both-reviews-then-approve case the per-id form cannot serve without hand-copying every id out of the gate view. `server/condition_claims.go::expandAllOpenPlanConcernClaims` resolves it at approve time via `ListOpenByRun` filtered to `StageKindPlan`, and records the EXPANDED ids under the same `claims_concern_ids` audit key, so everything above runs byte-identically. The semantics are a **SNAPSHOT taken during the approve request**, not a continuously-evaluated set: that is what lets the resolution path stay unchanged and makes the operator's claim reconstructable from the `approval_submitted` payload alone — and it means a concern raised AFTER the approval is **not** claimed (raise it, and it needs its own decision). The channel is mutually exclusive with `claims_concern_ids` (400, `details.rule` `claims_all_and_explicit_ids`) because the expansion is always a superset of any valid explicit list; approve-only and plan-stage-only; a concern-store outage fails closed (503 unwired / 500 read failure) rather than silently claiming nothing. An expansion resolving to ZERO open plan concerns is legal, and the additive intent keys `claims_all_open_plan_concerns` + `claims_all_open_plan_concerns_expanded` record that fact.
- **Operator-facing marker.** `GET /v0/runs/{run_id}`'s concerns items carry `claimed_by_approval` for a concern the run's newest claiming approval covers (#3318), so at the merge gate an operator can see which OPEN concerns will self-settle and need no hand waive. Best-effort: an approval-audit read failure omits the markers while the concerns block itself stays present (presence is authoritative, #3043).

## Operator-concern slice (#2623, E67.26)

Closes the last channel where a routed instruction had no durable identity: a free-text `operator_concern` (the #1311 escape hatch — a required CI/CodeQL/SAST finding, an ad-hoc steer) was folded into the fix-up ONLY as an ID-less `planreview.Concern` struct literal for the prompt renderer. `planreview.Concern` has no ID field, so unlike every id-routed concern the instruction never reached this store — it could not be marked `addressed_pending`, could not be keyed in a re-review's `concern_resolutions`, and left no open row and no gate signal when an agent silently skipped it (the twice-dropped instruction in run 3b790e10 / PR #2582, text provably intact). No migration — category `operator` rides the tolerant TEXT `category` column and every state used is existing:

- **Mint point + ordering.** `server/fixup.go::mintOperatorConcern` inserts the instruction as ONE durable row (`InsertRaised`, `StageKind` implement, category `operator`, severity `high`, `ReviewerModel` "" → stored NULL — an operator concern has no reviewer). It is called from `fixupStageAs` AFTER `run.FixupStage`'s transition commits (so a `fixup_budget_exhausted`/`fixup_ceiling_reached`/`fixup_not_applicable` refusal can never orphan an open concern row — there is no delete verb to unwind one) and BEFORE `writeFixupAudit`.
- **What it inherits (the whole point — no new machinery).** The minted UUID is folded into a CLONED routed-id set (`slices.Clone`, so the caller's `ConcernIDs` backing array is never mutated — `fixupActionParams` is shared with the auto-drive and acceptance-triage callers), which is then routed exactly like an id-routed concern: `writeFixupAudit` records it on `concern_ids` AND on its own `operator_concern_id` key; the existing `MarkAddressedPending` block (its guard relaxed from `len(ConcernIDs)>0` to `len(routedIDs)>0`) transitions it `raised → addressed_pending` with the operator's fix-up `reason` as `state_reason`. From there it rides `ListOpenByRun` (the run-status concerns block + merge gate), the gate view's `fixups[]` join (via `operator_concern_id`/`concern_ids`), `priorConcernsForReview` (so `hasFixupRoutedConcern` is now TRUE on an operator-concern-only pass → the re-review takes the delta path), and `applyConcernResolutions` (a re-review MUST emit a `concern_resolutions` entry; silence leaves it `addressed_pending` = OPEN at the gate).
- **`OriginReviewSequence` derivation.** `LastForRun(runID).Sequence + 1` — a prediction of the sequence the `stage_fixup_triggered` append (written just after the mint) will take, so the minted id rides that entry's `concern_ids`. The field drives `ListByRun` display ordering and `gateViewRound`'s `t.sequence < reviewSeq` round grouping ONLY — never routing/state/resolution — so the 0 fallback (nil `AuditRepo` or any read error, incl. `audit.ErrNotFound`) and any concurrent-append skew are cosmetic.
- **Best-effort degrade (never fails a committed fix-up).** `mintOperatorConcern` returns `(uuid.Nil, false)` on empty text or nil `ConcernRepo`, and warn-logs + returns false on an `InsertRaised` error (or empty/nil result row); the `operator_concern_id` key is omitted and `concern_ids` is left unwidened, so the payload is byte-identical to the pre-#2623 untracked delivery. A `MarkAddressedPending` error warn-logs and leaves the row `raised` (still OPEN). The store is a derived index; the audit payload stays authoritative.

## Reviewer-evidence data slice (#2353, E60.8)

A concern may carry `new_evidence` (the reviewer's supporting evidence) and `settled_ref` (the stable id of the settled concern it re-raises). Both already rode on the `plan_reviewed` / `implement_reviewed` audit payloads as `planreview.Concern` fields for the re-litigation guard (#1913), but they were DROPPED at the persistence boundary, so every surface reading a persisted row rendered `note` alone and a well-evidenced rejection read as an unsupported assertion:

- Persisted on `review_concerns.new_evidence` / `review_concerns.settled_ref` (migration `0069_concern_new_evidence`, the same additive `TEXT NOT NULL DEFAULT ''` shape 0033 used, so pre-existing rows read back `''` with no backfill) → carried through `persistReviewConcerns` and mapped in `concern.RaisedConcern`/`Concern`.
- **Read surfaces split by their source, which decides how far back the fix reaches.** The gate view (`GET /v0/runs/{run_id}/gate-view`, behind `fishhawk_get_gate_view`) reads PERSISTED ROWS on both the open list and the settled ledger, so it carries evidence only for concerns minted after 0069. The MCP verdict decode (`mcpserver.PlanReviewConcern`, behind `fishhawk_await_review` / `fishhawk_get_plan` / `fishhawk_get_run_status`) and the two markdown comment surfaces (`issuecomment`'s issue anchor and advisory PR review body) read the AUDIT PAYLOAD directly, so they are correct RETROACTIVELY for runs predating the migration. For an older row the originating audit entry remains the recovery path, as it is for every other dropped field.
- `settled_ref` is deliberately NOT rendered on the markdown surfaces — an opaque id prefix is noise in prose aimed at humans. It stays on the structured JSON surfaces, where the operator can follow the lineage.

## Suggested-patch data slice (#1165, E22.X)

An implement-review concern may optionally carry a `suggested_patch` (a unified diff that applies to the PR branch):

- `planreview.Concern.SuggestedPatch` (`json:"suggested_patch,omitempty"`) flows onto the `implement_reviewed`/`plan_reviewed` audit payloads via the embedded `[]Concern` with no payload-struct change, and old reviewer output decodes unchanged.
- Persisted on `review_concerns.suggested_patch` (migration `0033_concern_suggested_patch`, `TEXT NOT NULL DEFAULT ''` so pre-existing rows read back `''`) → decoded through `persistReviewConcerns` and mapped in `concern.RaisedConcern`/`Concern`.
- `buildImplementReview`'s verdict schema instructs reviewers to populate it ONLY for a mechanical concern whose fix is a small self-contained diff (leave absent otherwise); `buildPlanReview` is unchanged — plan-review concerns are about the plan artifact, not code.
- The `GET /v0/runs/{run_id}` concerns block surfaces a bounded `has_suggested_patch` boolean per item (the diff text stays elided like the note); it is the signal the near-deterministic fix-up apply path keys on (delivering and applying the patch is a separate behavior slice).

## Empty-note concern slice (#2555, E48.104)

A reviewer concern with an empty (or whitespace-only) `note` was persisted verbatim and then held the merge gate open carrying nothing an operator, a fix-up agent, or a later re-review could act on — its only available disposition was a waive of unknown content (run 9bba554d minted two such rows, one a genuine medium-severity test-vacuity finding; a later review reported it could not delta-verify two concerns because their notes were empty). Two independent controls plus a schema/prompt tightening close it at both ends. No migration — the substitution is text written into the existing `note` column.

- **Write side (load-bearing).** `server/trace.go::persistReviewConcerns` takes the emitting verdict's `free_form` and, for every concern whose note is blank after whitespace trimming, calls the pure `backfillConcernNote` before `InsertRaised`. Three branches: a note carrying anything but whitespace is returned **byte-identical** (the no-op path — a well-formed concern is never rewritten, and no audit entry is emitted); a blank note WITH `free_form` returns a marked recovery carrying that prose, bounded at `concernNoteFreeFormMaxBytes` (2000, rune-boundary-safe cut with `concernNoteTruncationMarker`) and explicitly warning that the free_form may cover other findings from the same round, so an operator never reads it as this concern's authored note; a blank note with NO free_form returns `concern.MissingNotePointer` — the same text the read side synthesizes, so both paths speak ONE vocabulary. The backfill runs AFTER `suppressRelitigation`, so a suppressed concern is still suppressed and never backfilled, and it NEVER drops a concern.
- **Fail direction is deliberately the INVERSE of `suppressRelitigation`.** That guard requires its audit entry to land before it acts, because falling open there merely inserts a concern. Here, refusing to backfill because an audit append failed would re-persist the blank row the control exists to prevent, so **the backfill applies regardless** and only warn-logs. The durable, operator-visible record of the substitution is the **synthesized note itself** — persisted on the row, rendered at every operator surface, and self-describing (it leads with `concern.MissingNoteMarker`). The best-effort `concern_note_backfilled` audit entry (source `free_form` | `none`, severity, category, the substituted note, the truncation flag, reviewer model, origin sequence) is a **traceability addition**, not that record: an append failure degrades traceability, never silence. That entry is nonetheless appended only **after** the batch `InsertRaised` succeeds — the substitutions accumulate as `pendingNoteBackfill` values while the batch is built and are recorded once the rows are durable, so an insert failure can never leave an audit entry describing a substitution onto a row that was never minted (the audit-disagrees-with-derived-state ordering slip, pinned by `TestPersistReviewConcerns_InsertFailureEmitsNoBackfillEntry`). Like `concern_relitigation_suppressed` it is an internal advisory audit kind — it posts no issue comment and adds no Notifier method, so it is NOT an issue-comment surface.
- **Read side (legacy rows minted before this change).** One chokepoint, `concern.Concern.DisplayNote()`, returns the stored note verbatim when non-blank and otherwise `MissingNotePointer(stageKind, reviewerModel, originSequence)` derived from the row itself (an explicit unknown-reviewer rendering when `ReviewerModel` is NULL or blank). It is pure — no ctx, no I/O — and never fabricates substance: it guarantees only a non-blank field carrying a pointer to the `*_reviewed` audit entry where the reviewer's actual output lives. **Five consumers**: the gate view's open-concern list (`gateview.go::gateViewOpenConcern`), the run-status `short_summary` label (`runs.go`, fed through the unchanged `concernShortSummary` collapse/bound/marker logic — the key was previously OMITTED for a blank note), the auto-drafted defer follow-up's title + quoted body (`defer_concern.go`), and BOTH prompt-facing threads, `priorConcernsForReview` and `settledConcernsForReview` (`trace.go`) — the last two are what stop a later re-review receiving an empty field for a pre-change row. Non-operator-facing reads of the raw `Note` (the audit payloads, which stay authoritative) are unchanged.
- **Schema + prompt.** `planreview.VerdictSchema()` promotes `note` into the concern object's `required` array (now `["severity","note"]`), so a schema-conforming reviewer can no longer LEGALLY omit it. Deliberately **no `minLength`**: codex 0.140's strict `--output-schema` rejects unsupported string keywords with HTTP 400 `invalid_json_schema` (the #1330 class), and the server-side backfill is the enforcing control anyway. Because `note` is now in the ORIGINAL required set, `StrictVerdictSchema()`'s derivation leaves it a plain `"string"` instead of widening it to `["string","null"]` — a nullable note would re-open the hole. The three reviewer prompts gain a required-note instruction; see `prompt/README.md`.
- **What this does NOT catch.** The controls are an EMPTINESS check. A non-empty note that states no claim — e.g. one containing only its own severity justification ("Low because the posture is explicitly documented … this is a coverage note, not a defect in the shipped behavior") — passes every check here and still reaches the gate unactionable. Substantive-content validation is out of scope for this slice.

## Persona-attribution slice (#3755, E55.10)

Migration `0092_review_concerns_persona_attribution` adds three ingest columns to `review_concerns`, each with the additive `NOT NULL DEFAULT` shape 0033/0069 used and **no backfill**. The `plan_reviewed` / `implement_reviewed` audit payload stays authoritative; these columns let the row-reading surfaces show the same facts.

- **`reviewer_role`** (`TEXT NOT NULL DEFAULT ''`) — WHICH reviewer raised the concern. Read it as THREE states: `''` = **unattributed** (every row minted before 0092, and any concern written by a path naming no role); `standard` (`concern.ReviewerRoleStandard`) = the stage's standard reviewer; any other value = a reviewer persona's name. `InsertRaisedParams.ReviewerRole` is stored **verbatim** — `''` is NOT defaulted to `standard` on write, because a legacy row's role is unknowable and a persona row minted since E55.8 must never be mislabelled. Identity comparisons (the raiser-vs-confirmer veto) go through `concern.NormalizedReviewerRole`, which maps `''` to `standard` for the comparison ONLY, so a legacy row keeps today's veto behaviour.
- **`quote_unverified`** (`BOOLEAN NOT NULL DEFAULT false`) — the reviewer quoted a document passage (`quoted_passage` + `document_ref`) the server could NOT find in the text it injected into that invocation; ingest demoted the concern to `low` (`planreview.VerifyQuotedPassages`).
- **`severity_clamped_from`** (`TEXT NOT NULL DEFAULT ''`) — the reviewer's original severity when ingest lowered it (persona `severity_cap` clamp or an unverified quote); `''` when untouched. Note the persisted `severity` is already the lowered value.
- Carried per concern on `RaisedConcern.QuoteUnverified` / `SeverityClampedFrom` and per entry on `InsertRaisedParams.ReviewerRole`; read back on `Concern.ReviewerRole` / `QuoteUnverified` / `SeverityClampedFrom` by every query returning `review_concerns` rows (`InsertReviewConcern` RETURNING, `GetReviewConcernsByIDs`, `ListReviewConcernsByRun`, `ListOpenReviewConcernsByRun`, `UpdateReviewConcernState` RETURNING — all five pinned by `TestPostgres_PersonaAttribution_RoundTripAllQueries` against the real migrated schema).
- **sqlc**: `db/queries.sql.go` was regenerated with a package-scoped sqlc v1.31.1 config (only this package's queries + the migrations dir); `db/models.go`'s `ReviewConcern` struct was hand-edited, because a package-scoped run also re-emits the rest of the (pre-existing, drifted) shared model set. Postgres APPENDS added columns, so the three trail `settled_ref` in every column list and Scan.

## Server-check provenance slice (#3760, E80.3)

Migration `0094_review_concerns_provenance` adds two columns to `review_concerns`, both `TEXT NOT NULL DEFAULT ''` with **no backfill** (no historical row was server-synthesized, so `''` is the true value for every one of them).

- **`provenance`** — who minted the concern when it was NOT a model reviewer's verdict. `''` = a reviewer verdict, an operator fix-up or a crew conversion, and every row minted before 0094. The one non-empty value is `server_check` (`concern.ProvenanceServerCheck`): the server synthesized the concern itself from a deterministic check, with no model call. It has THREE producers: the diff secrets check (E80.3, `check_key` `diff_secrets|…`) and the permission-drift check (E80.4 / #3761, `server/permission_drift.go`, `check_key` `permission_drift|…`; contract in `backend/internal/server/README.md` § "Permission-drift check") — both ADR-084 D5 / rule 5 — and the runner-observed counterfactual recorder (E85.3 / #4143, `server/counterfactual_observed.go`, `check_key` `control_unpinned|<index>|<control_path>`, concern category `control_unpinned`, raised for a plan-declared counterfactual the runner observed GREEN; contract in `backend/internal/server/README.md` § "Runner-observed counterfactuals"). All three share the human-only clearing contract below and the reviewer-side `server_check_requires_human` veto. Read it through `Concern.IsServerCheck()`, an EXACT comparison (provenance is written only by server code, never decoded from a verdict, so there is no tolerant-decode variant to normalize).
- **`check_key`** — the server check's de-duplication key, so re-running the check across review rounds does not mint a duplicate row; `''` for every non-server_check row. The three producers' keys are disjoint by their first field (`diff_secrets` vs `permission_drift` vs `control_unpinned`).
- Carried per entry on `InsertRaisedParams.Provenance` (stamped on every concern of the entry, stored verbatim) and per concern on `RaisedConcern.CheckKey`; read back on `Concern.Provenance` / `CheckKey` by all five row-returning queries (pinned by `TestPostgres_ProvenanceAndCheckKey_RoundTripAllQueries`, whose two concerns of ONE entry carry DIFFERENT keys so a key stamped entry-wide is caught). `TestMigrateDown_ReviewConcernsProvenanceReversal` (`backend/internal/postgres`) pins the up/down/re-apply. Postgres APPENDS added columns, so the two trail `severity_clamped_from` in every column list and Scan; `db/*.go` were hand-edited to that order.

**Human-only clearing contract.** A `server_check` concern can be cleared only by a HUMAN. `backend/internal/server/concern_human_only.go`'s `refuseNonHumanServerCheckClear` refuses with 403 `concern_requires_human` when the row `IsServerCheck()` AND either the subject is an agent identity (`isAgentSubject`: an `operator-agent/…` token or a run-bound `mcp:run:<uuid>` token, own run included — the same classification `captainActorIsAgent` uses) or the request is `delegated: true`. It has exactly one call site per clearing verb, each before any audit append, delegation evaluation or external side effect: single waive (after the run-binding guard, before `checkDelegation`), bulk waive (per row inside pre-validation, so ANY server_check row refuses the WHOLE batch) and defer (before the open-state pre-check and the work-item filing; defer has no delegated flag). A reviewer-raised row (provenance `''`) is untouched, so every existing agent / delegated path is byte-identical. A human waive of a server_check row stamps `provenance: server_check` on the `concern_waived` payload (absent for reviewer rows) so the chain records that a human cleared a server check. Residual, inherited from ADR-040: an agent session presenting a human operator's token is indistinguishable from that human and is treated as one.

## Child-slice rollup + the outcome column (#4692, E94.1, ADR-117 D2 + D1's open_at_merge)

Migration `0112_review_concerns_outcome_rollup` adds `outcome TEXT NOT NULL DEFAULT ''` and a nullable `rolled_up_from UUID` to `review_concerns`, plus the partial unique index `review_concerns_rolled_up_once_idx ON (run_id, rolled_up_from) WHERE rolled_up_from IS NOT NULL`. No CHECK, no backfill: `''` means no outcome is recorded, the true value for every earlier row (the tolerant 0030/0094 posture). Pinned by `TestMigrateDown_ReviewConcernsOutcomeRollupReversal` (`backend/internal/postgres`). Postgres appends added columns, so the two trail `check_key` in every column list and Scan.

- **`outcome`** (`Concern.Outcome`, type `Outcome`) is ORTHOGONAL to `state`: state is the lifecycle position every gate reads, outcome records what became of the concern. This change writes two values — `carried` (`OutcomeCarried`) and `open_at_merge` (`OutcomeOpenAtMerge`); the rest of the D1 vocabulary and the judgement axis land in the next child with no further migration of the column. An outcome write NEVER touches `state`, `state_reason` or `updated_at` ("nothing else about it changes"), and never overwrites a recorded outcome. Outcome reaches no review prompt: `server/trace.go::priorConcernsForReview` builds `prompt.PriorConcern` from fixed fields only.
- **`rolled_up_from`** (`Concern.RolledUpFrom`) is, on a parent copy, the id of the child concern it was copied from; nil everywhere else.
- **`ImportRolledUp`** copies each source into the parent run's ledger in ONE transaction: a raised implement-stage row on the given parent stage, with `RolledUpStateReason` (naming the child run and child concern) as its `state_reason`, keeping `origin_review_sequence`, `reviewer_model`, `reviewer_role`, `severity`, `category`, `note`, `suggested_patch`, `new_evidence`, `settled_ref`, `quote_unverified`, `severity_clamped_from`, `provenance` and `check_key` VERBATIM (`ImportRolledUpReviewConcern`, an `INSERT … SELECT`). Every source WITH a copy has its outcome set to `carried` (`MarkReviewConcernCarried`, guarded by an `EXISTS` on a row whose `rolled_up_from` names it; also when its copy already existed, so a pass interrupted between the two statements heals on retry). It returns only the newly inserted copies. **A source no longer OPEN when its copy is written is skipped** — no copy, no `carried` outcome — because the copy statement reads the source in a CTE under `FOR NO KEY UPDATE` with the open-state filter (`raised`/`addressed_pending`/`reopened`, duplicated from `IsOpen`; keep in sync). That closes the fan-in / detached-verdict race (concern 92d4e9da): a caller's snapshot read open, then a retry sweep's supersession, must not mint a raised copy. Under READ COMMITTED a supersession committed before the copy statement is re-checked and refused; one arriving after it blocks on the source's row lock until the import commits, so the sweep's later parent-ledger scan sees the copy. Idempotence lives in the DATABASE ONLY: `ON CONFLICT (run_id, rolled_up_from) WHERE rolled_up_from IS NOT NULL DO NOTHING` turns a re-import into `pgx.ErrNoRows`, skipped silently; there is no Go-side pre-filter. A nil parent run or stage is refused before any write. Pinned by `TestImportRolledUp_{CopiesFields,MarksSourceCarried,Idempotent,Concurrent,SkipsSourceNoLongerOpen,LocksSourceAgainstConcurrentSupersession,RequiresParent}`.
- **`StampOpenAtMerge`** sets `open_at_merge` on every concern of the given runs whose state is `raised`, `addressed_pending`, `reopened` or `superseded` and whose outcome is still `''` (`StampReviewConcernsOpenAtMerge`, `:execrows`). Idempotent across redeliveries by that filter; an empty run-id list runs no query. Pinned by `TestStampOpenAtMerge_{StampsOpenAndSuperseded,KeepsRecordedOutcome}`.
- **`check_key` on a copy.** Because a copy keeps `provenance` and `check_key` verbatim, a child `server_check` concern stays human-only on the parent, and the parent's own server check de-duplicates against the copy: a parent permission-drift raise for the same `check_key` on the parent implement stage adds no second row. The flip side is deliberate: a WAIVED (or deferred) copy suppresses the parent's own raise for that key, exactly as a waived parent-raised row would (`server`'s `TestSliceConcernRollup_CopyCheckKeySuppressesParentRaise`).
- **Copies follow their source's retry supersession (approval condition C1(b)).** When `server/trace.go::supersedeOpenImplementConcerns` (the retry-time sweep or the post-persist re-check) supersedes a child concern that has an OPEN parent copy, the copy is superseded in the same pass, with `RolledUpSupersededReason` naming the child concern and the child supersession, so no copy outlives its source. The sweep supersedes the sources BEFORE it scans the parent ledger, and `ImportRolledUp` locks and re-checks each source, so a fan-in import racing the sweep either finds the source closed (no copy) or commits its copy before the sweep's scan reads the parent (`server`'s `TestSliceConcernRollup_SweepBetweenReadAndImportLeavesNoOpenCopy` drives the read → sweep → import interleaving on Postgres).

The callers (the fan-in hook, the late child-review hook, the merge stamp) live in `backend/internal/server/concern_rollup.go`:

- **Fan-in.** `orchestrator.integrateSlices` calls `Server.ImportSliceConcerns` with every succeeded child immediately before `slices_integrated`, on every fan-in (the consolidate / integrate-wave verbs, the child-completion sweeper, the event-driven arm). It reads each child's OPEN concerns (`ListOpenByRun`), keeps HIGH and MEDIUM by exact match (the merge leg's vocabulary), imports them onto the parent implement stage (`consolidatedImplementStage`, the stage the consolidated review's concerns attach to) and, only when a copy was inserted, appends ONE system-actor `concern_rolled_up` row `{site, parent_stage_id, count, high, medium, concerns:[{concern_id, rolled_up_from, child_run_id, child_stage_id, slice_index, severity, category, reviewer_model, reviewer_role, origin_review_sequence}]}` — no note prose. An import error fails that fan-in pass closed (no `slices_integrated`; the parent stays parked). The copies are ordinary parent concerns, so fix-up routing, the consolidated round, waive / bulk waive / defer and the merge-eligibility leg (an open HIGH blocks merge) handle them unchanged.
- **Late child review.** Advisory implement reviews run detached and routinely land after the child succeeded and the fan-in ran. `trace.go::ingestImplementReview` calls `importLateSliceConcerns` for a verdict that minted rows, AFTER both retry-supersession reads and never for a verdict superseded at either (approval condition C1(a)); it imports only for a decomposition child whose run is succeeded and whose parent is not terminal (`site: child_review`). Residual: a child concern written by another path after the child succeeded is not imported, but it is still stamped `open_at_merge`.
- **Merge stamp.** `resolveReviewStageOnMerge` (right after `pr_merged`, so the ADR-036 and members holds defer it exactly as they defer that row) and `handleReconcileMerge` stamp the run and every decomposition child.
- **Signals and the no-reconcile trade-off (approval condition C5).** The copies are written before the `concern_rolled_up` row (a missing row, never a false one). A failed append logs at ERROR under the stable key `concern_rolled_up_audit_lost`; a failed merge stamp logs at WARN under `concern_open_at_merge_stamp_failed` with `run_id`. Neither is reconciled later: a re-run inserts nothing new so writes no row, and a later merge redelivery re-runs the idempotent stamp only if one arrives. The concern rows and the parent ledger stay correct; only the audit row or the outcome stamp is lost, and that loss is the logged signal.
- **Run-bound readability (approval condition C6, ADR-106).** A `concern_rolled_up` row sits on the PARENT's per-run chain and carries its child runs' and stages' ids; it is readable there like any parent row. It needs classifying when the ADR-106 registry flag lands; no read-surface change is made here.
