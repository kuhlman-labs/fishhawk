## Per-repo work-management conventions loader (`conventions_loader.go`, E45.16 / #2022)

`RepoConventionsLoader.Load` is what serve.go installs as the process-wide `conventionsLoader`
seam (`workitems.go`, signature `func(ctx, repo)`): it fetches `.fishhawk/work-management.yaml`
from the filing repo's **own** forge, breaking the chicken-and-egg the deployment override
sidestepped — the fetch-forge is resolved from **outside** the conventions file.

**Resolution chain per filing** (each fall-through is deliberate; each error is fail-closed):

1. **Provider discriminator** (the SOLE out-of-file hint in this pass; run-bound forge-context
   corroboration is explicitly out of scope): `account.Resolver.ResolveProvider` looks up
   `accounts.provider` by the repo owner as `account_key`. Exactly one row selects the forge;
   zero rows **or an ambiguous key** (legal under `accounts.UNIQUE(provider, account_key)`, the
   same key under both providers) fall through cleanly — never an arbitrary first row. A query
   error **fails closed** (propagated) rather than silently selecting a different provider on a
   transient DB fault.
2. **Self-resolved CredentialScope**: github routes through the server's existing
   `resolveRepoScope` (exposed as `Server.GitHubRepoScopeResolver`; zero scope = App not
   installed → fall through; a transient resolution *error* fails closed); gitlab uses the
   deployment-level scope serve.go wires when the gitlab forge is registered. No resolvable
   scope, a nil fetcher (forge absent from the registry), or an unknown provider are all treated
   exactly like an unregistered forge → fall through.
3. **Fetch + parse**: the provider's `forge.FileFetcher` reads the file (gitlab with the explicit
   `ref=HEAD` the Repository Files API requires). `forge.ErrNotFound` (no committed file) falls
   through; **any other fetch error and any parse error fail closed** — an auth/transport/server
   fault must not silently switch providers.
4. **Break-glass override** (`FISHHAWKD_WORKMGMT_CONVENTIONS`, retained from ADR-058 Phase 2
   #1856): served whenever the chain falls through, else `workmgmt.Default()`.

**Cache**: parsed conventions are cached per **`(provider, repo)`** key, TTL-gated (5 min default;
clock/TTL/parse injectable so `conventions_loader_test.go` asserts the counters): within TTL the
cached parse is served with **no fetch**; after TTL a refetch **reuses the cached parse when the
blob SHA is unchanged**. The key is **forge-qualified** so a repo reassigned to a different
provider never serves the prior forge's cached parse. A **per-key mutex** is held across the fetch
so concurrent same-repo filings do one fetch, not a thundering herd — but it is **per repo**, not
process-global, so a slow or hung forge round-trip for one repo does **not** stall filings for any
other repo (the short map-guarding `mu` is never held across the fetch). The per-key lock map, like
the cache, never evicts — bounded in practice by distinct authenticated filing targets.

### Destination authorization (`conventions_destination.go`, E44.14 / #2090)

Resolving where the file is READ FROM is not the same as authorizing where it FILES TO. A
repo-committed conventions file is **untrusted input**: without a binding, a file committed to
any repo the deployment can read could name any provider and any project reachable by deployment
credentials, redirecting filed work items and product reports out of the repo's tenancy boundary.
So a **repo-fetched** parse is destination-authorized immediately after `workmgmt.Parse` and
**before** it is cached or returned:

| Conventions provider | Destination key | Bound to |
|---|---|---|
| `github_projects` | `project.owner` | the repo's resolved account key (github family) |
| `gitlab` | the namespace root of `gitlab.project`, or the filing repo's own owner when the block omits `project` | the repo's resolved account key (gitlab family) |
| `jira` | `jira.project_key` | nothing — a jira destination has **no forge account to bind to**, so it is refused unless allow-listed |

The account key is the filing repo's owner segment — by construction exactly the `account_key`
the discriminator lookup used (`account.Resolver.ResolveProvider` cuts `repo` at the first `/`).
Comparison is case-insensitive (forge logins and namespace paths are case-preserving but
case-insensitive for identity). Both the forge **family** and the **key** must match; a
cross-forge destination (a gitlab file under a github account, or the reverse) is refused. A
provider outside the closed set, an empty provider, or a declared provider with a nil connection
block all fail closed.

**Not cached, no fall-through, on refusal.** A refused destination returns an error wrapping
`errConventionsDestinationUnauthorized` and is neither written to the cache nor allowed to fall
through to the break-glass override / `Default()` — caching would hide the redirect attempt
behind the TTL, and falling through would let repo-committed content *select* the deployment
default. That ordering is also why the cached-serve and unchanged-SHA branches need no re-check:
nothing enters the cache without having passed authorization. An edit that caches earlier
silently reopens the hole (`TestConventionsLoader_DestinationRedirect_Refused` asserts the second
`Load` refetches and re-parses).

**Escape hatch is administrator-controlled, never repo-controlled**:
`FISHHAWKD_WORKMGMT_ALLOWED_DESTINATIONS` carries comma-separated
`<account-key>:<provider>:<destination-key>` entries; a **malformed value fails boot** rather
than degrading to an empty (strict) allow-list. Every refusal names the exact entry to add. A
`gitlab` destination key must be the namespace **root** (`group`), not a project path
(`group/team`): the derived key is the namespace root, so a full-path entry could never match —
it is rejected at parse time, naming the root entry to use, rather than sitting silently inert.

**The administrator-controlled fallbacks are deliberately NOT validated.** The
`FISHHAWKD_WORKMGMT_CONVENTIONS` override and `workmgmt.Default()` are the trusted deployment
inputs whose displacement by untrusted repo input is the entire concern. The unvalidated
rationale holds for the **override**: validating it would break every deployment whose break-glass
file names a project outside the filing repo's owner. It no longer holds for `Default()`, which
declares no project (ADR-110 guard (i), #4606) and so binds to the filing repo's own owner; it
stays unvalidated because it is trusted product input, not because validating it would refuse it.

**Residual limitation**: the binding is enforced only when the discriminator resolves an account.
Until E44 populates repo→account rows, a repo with no account row still falls through to the
trusted override / `Default()`, unvalidated. This change therefore only ever tightens the current
posture — it never weakens it.

**Operator-accepted E44 posture**: the E44 `accounts` tables are not yet populated in
production, so the discriminator path resolves `found=false` and live filings degrade to the
break-glass override / `Default()` — production effect begins when E44 wires repo→account rows.
Until then the discriminator-driven end-to-end selection is exercised by
`conventions_loader_test.go` (per-failure-mode + the mixed-forge test driving one loader across
a github repo and a gitlab repo).

### Conventions-derived parses and the repository-literal guard (ADR-110 guard (i), #4626)

A repository's epic title shape and label namespaces come from its RESOLVED conventions, never from product literals:

- **Epic title parse** — `workmgmt.EpicTitleNumber(conv, title, closed)` builds an anchored pattern from the conventions' `epic` type `title_format` (the `childNumberRegexp` QuoteMeta precedent). `deriveEpicTitleVar` (`workitems.go`) uses the OPEN form (stops at the digit run, so a child-shaped parent title still yields its number); `resolveWalkParentEpic` (`live_validation_filing.go`) uses the CLOSED form (rejects a child title, #2179). A conventions set with no `epic` type, or an epic format without `{number}`, derives nothing: `{epic}` stays unset (the missing-placeholder 422) and the walk takes the companion arm. The child-number 422s name the filing type's `title_format` rather than a hard-coded `[E<epic>.<n>]` shape. Tests: `TestFileWorkItem_EpicTitleVarFromCustomEpicFormat`, `TestLiveValidationWalk_EpicArmUsesConventionsEpicFormat`.
- **Walk area** — `liveValidationWalkArea` (`area:backend`) STAYS (first-officer ruling): the conventions cannot express a walk-only area (a chore `label_defaults` area would relabel every chore filing). `TestLiveValidationWalk_RepoDeclarationKeepsAreaBackend` pins both arms under this repository's own declaration; removing it is remaining ADR-110 scope.
- **Upkeep advisory labels** — derived from the filing type's namespaces; see *On-approval upkeep apply* (`upkeepAdvisoryNamespaces`).
- **The guard** — `conventions_literal_guard_test.go` (`TestNoRepositorySpecificConventionLiterals`) parses every non-test `.go` file under `backend/`, `cli/` and `runner/` (skipping `db/` and `testdata/`) and fails on a string literal that is (a) exactly `"area:"`, `"type:"` or `"phase:"`, (b) a namespaced label matching `^(area|phase|type):\S`, or (c) escaped epic-title regex source containing backslash + `[E`. Every rule is CASE-INSENSITIVE (the value is lower-cased before it is classified, so `"AREA:"`, `"Type:Feature"` and a backslash + `[e` source are caught; exemption keys stay the exact original literal). A bare `[E` in prose or a format string is out of reach by design, as is a split literal such as `labelValue(c.Labels, "type") == "epic"` and a namespace spelled without its colon (`areaNamespace = "area"`). Its exemption table is FROZEN and SHRINK-ONLY (seven entries at #4626: `plan/commsreport.go` `CommsLabelNamespaces` ×3, `liveValidationWalkArea`, `product_report.go` `type:feature`/`type:bug`, `intakegroom/epic.go`'s epic regexp): a stale entry fails, the table may not exceed `literalGuardExemptionCeiling`, and the scan must read more than 500 files. `TestLiteralGuardScanner_DetectsEachRule` self-tests the scanner on in-memory sources. Remedy for a new hit: derive the value (`workmgmt.EpicTitleNumber`, `workmgmt.TypeLabelNamespaces`), never add an exemption.

## On-approval grooming apply (`grooming_apply.go`, E54.19 / [#2822](https://github.com/kuhlman-labs/fishhawk/issues/2822))

`applyApprovedGrooming` is `workmgmt.ApplyGrooming`'s **production caller**, and the fourth best-effort side effect of `finishApprovalAdvance`'s plan-stage block (beside `fileSplitProposalChildren` / `fileOrLinkLiveValidationWalk` / `recordPlanPredictedRuntime`). When the approved plan stage carries a `grooming_report` artifact, it settles the artifact's capture window, CONSUMES the operator's per-entry dispositions ([#2991](https://github.com/kuhlman-labs/fishhawk/issues/2991)) merged with an undispositioned default, and applies the resulting decisions through the work-management provider, auditing every one. Like its siblings it NEVER unwinds the approval: the gate already passed and its row is in place, so every failure logs and returns.

**Why the gate and not an agent stage.** The apply layer's eight containment rules ARE the authorization. Routing the call through an agent stage would put an agent between the operator's gate decision and the tracker write — the exact inversion the backlog-grooming workflow exists to prevent — and would need an implement-stage runner path that produces no diff. The gate approval was already the ratification signal (`campaign_grooming_source.go` reads the same predicate to build a campaign from a report); this makes it the apply trigger too, so the two surfaces agree on what "ratified" means by construction rather than by convention.

**What it authorizes (`mergeGroomingDecisions`, #2991).** The base layer synthesizes an `approved` decision per HYGIENE-action-class entry (hygiene defects + dependency edges, both routed through the exported `workmgmt.GroomingActionClassFor` so a remap out of that class fails in `TestGroomingActionClassFor` rather than silently widening). The overlay applies the operator's recorded dispositions for ANY class: `GateApproved[id]=true` is populated **ONLY by an explicit recorded `approved`** — never by a synthesized hygiene approval and never by `amended` — so `amended` cannot become an approval path and a whole-report approval alone never authorizes a destructive-class entry. An undispositioned gated-class entry gets no decision (`no_decision`, dispatches nothing). A disposition naming an entry the report does not declare is dropped (else `workmgmt` rule 1 would refuse the whole apply). `IceboxColumn` stays empty (no conventions source declares one), so an approved decomposition records `icebox_column_unavailable`. **Since #2855, `GateApproved` is what authorizes a hygiene entry proposing an `autonomy:` delegation-tier label (rule 8)** — an undispositioned such entry is still refused and audited `delegation_tier_not_authorized`; an operator now grants it by recording an `approved` disposition for it. The ingest census (`groomingEntryCounts`, `grooming_report_recorded`) gains a **`delegation_tier_proposals`** key counting the hygiene entries whose `fix.labels` satisfy `workmgmt.LabelsSetDelegationTier`, emitted **only when non-zero**. Pinned by `TestApproveGroomStage_DelegationTierLabelNotApplied` and `TestGroomingEntryCounts_DelegationTierProposals`. The ingest census (`groomingEntryCounts`, `grooming_report_recorded`) gains a **`delegation_tier_proposals`** key counting the hygiene entries whose `fix.labels` satisfy `workmgmt.LabelsSetDelegationTier` — the same predicate the refusal keys on — emitted **only when non-zero** (the milestone-counts precedent), so an ordinary report's audit payload stays byte-identical and the operator reading the gate sees both that the proposals exist and that none will land. Pinned by `TestApproveGroomStage_DelegationTierLabelNotApplied` (cross-boundary, pgtest) and `TestGroomingEntryCounts_DelegationTierProposals` (value + absent-when-zero, read back off the recorded payload). **Delegation is unchanged, structurally**: no file under `backend/internal/spec/` or `docs/spec/` is touched, so `ordering`/`dedup`/`scoping` remain refused at `mode: auto` by the two existing parse-time controls.

**The ladder is three rungs, each an explicitly deletable control.**

| # | Rung | Rule | Counterfactual test |
|---|---|---|---|
| C2 | **Report present** (evaluated FIRST) | *An early-out, NOT a control.* No `grooming_report` on the stage means an ordinary plan approval OR reject: return having written nothing (so a reject on an ordinary plan stage settles no window). Behaviour-PRESERVING under deletion | — |
| C1 | **Decision** | A decision other than `approve` applies NOTHING and settles the window `rejected` (issue AC4) | `TestApplyApprovedGrooming_RejectClosesWindowAndAppliesNothing` (settlement), `..._RejectDispatchesNothing` |
| C3 | **Re-ratification** | Re-read the stage's approval rows and require ≥ 1 grant and ZERO rejections — the identical predicate `campaign_grooming_source.go::approvedGroomingReport` ships | `TestApplyApprovedGrooming_ContestedGateDispatchesNothing`, `..._UngrantedGateDispatchesNothing` |

C2 is now evaluated BEFORE the decision branch, so a reject on an ordinary plan stage writes nothing. C1's placement is itself part of the control: the call sits in `finishApprovalAdvance`'s **type-only** plan block and is **passed** the decision, rather than nested inside the `DecisionApprove` block, precisely so its deletion (and the reject-path window settlement) is observable. C3's assertions read **committed state** — the audit rows after the call returns — because the hook returns nothing and a control whose effect is a write is only observable in what was written.

**Window settlement and the degrade asymmetry (#2991).** On approval, AFTER C3 passes and BEFORE any provider resolution, the hook settles the artifact-bound capture window (`settleGroomingWindow`, `approved`) and consumes the dispositions. A PRE-ratification degrade (approval read failure, contested/ungranted gate) does NOT close the window — nothing was decided, so a legitimate later capture must still be accepted (`..._PreRatificationDegradeLeavesWindowOpen`). A POST-ratification degrade (settled, then provider unresolvable) leaves the window CLOSED — the dispositions were consumed, and reopening on retry is the failure the protocol prevents (`..._PostRatificationDegradeLeavesWindowClosed`). A settlement APPEND failure is its own degrade `grooming_apply_window_unsettled` (window stays open, `..._WindowUnsettledDegrade`).

**The submission is not the gate.** `approval.SubmitResult` carries only `{Approval, Inserted}` and no gate-satisfied flag, so satisfaction is not inferable from one approve — hence the re-read. RESIDUAL, stated: under this repo's `count: 1` gate, grant-and-no-rejection and gate-satisfied coincide; under a `count: 2` gate a single grant would satisfy this predicate before the gate itself is satisfied. That is the SAME bar the campaign source already ships, so the two stay consistent rather than diverging, and tightening both to a real count check is a follow-up that must move them together.

**Five named degrade reasons.** Past every rung, each resolution failure degrades with NO dispatch and writes exactly ONE server-authored `grooming_apply_completed` row carrying `{applied:0, failed:0, skipped:0, refused:0, budget_exhausted:0, degraded:true, degrade_reason:<reason>}` (no `grooming_apply_started` row precedes it — a degrade launches no apply), so an operator reading the trail can tell "the apply did not happen, and why" from "the apply happened and applied nothing". No `grooming_mutation_applied` row is ever written on a degrade path, so the churn guard's disposition baseline is untouched and the entries correctly resurface next run. The reasons: `grooming_apply_report_unparseable`, `grooming_apply_run_unreadable`, `grooming_apply_conventions_unavailable`, `grooming_apply_mutator_unavailable`, `grooming_apply_reader_unavailable`, `grooming_apply_not_ratified` (C3), `grooming_apply_repo_unresolvable`, `grooming_apply_window_unsettled` (#2991: the post-ratification watermark append failed, so nothing was consumed and the window stays open), and `grooming_apply_prelaunch_timeout` (#3232: the synchronous half exceeded `groomingApplyPrelaunchBudget`; nothing launched, no started row). One case per reason in `TestApplyApprovedGrooming_DegradeModes` and its two siblings. An unreadable ARTIFACT LIST is deliberately silent rather than a degrade — it is indistinguishable from "this stage never had a report", and degrading every ordinary plan approval into a grooming audit row would be worse than the silence.

**The audit payload shape is load-bearing** ([#2813](https://github.com/kuhlman-labs/fishhawk/issues/2813)). `groomingApplyAuditSink` marshals the `workmgmt` record **BARE** — its own json tags, NOT wrapped in a run/stage envelope — because `grooming_report.go`'s `priorGroomingDispositions` decodes `entry_id` / `outcome` / `skip_reason` directly off the payload and the churn guard's whole idempotence baseline reads it. Run and stage identity ride the audit row's own columns. `TestApproveGroomStage_AppliesHygieneAndAuditsEndToEnd` feeds the written rows back through the UNCHANGED `priorGroomingDispositions` on a `pgtest` database — the seam per-layer units cannot cover, and the assertion that the payload the sink writes is the payload the guard reads.

**BARE is the RESOLVED shape, and the reader now refuses anything else.** `priorGroomingDispositions` reads through the named `groomingDispositionProjection`, documented BARE-ONLY: a nested or enveloped record decodes to an empty `entry_id`, and an unattributable row — undecodable payload OR empty `entry_id` — is now a `baseline_dispositions_unreadable` DEGRADE with an EMPTY baseline (propose everything), not a silent skip. The skip was fail-OPEN across runs: one corrupt row on the NEWEST prior candidate made that run look dispositionless, so `groomingChurnBaseline` walked PAST it and suppressed the current report against an OLDER settled run's dispositions — the unreadable-vs-absent conflation the #2240 fix-up closed for retrieval failures, reopened through a different door, and the same argument `priorGroomingPartialSteps` (#2810) already makes for its own scan. `TestGroomingChurnBaseline_UnreadableDispositionsDoNotFallThroughToStaleBaseline` pins the consequence (an OLDER settled run plus a NEWER corrupt one must propose everything and suppress NOTHING), `TestGroomingChurnBaseline_UnattributableDispositionRowDegrades` pins one subtest per named branch, and `TestGroomingMutationProjections_MatchWriterTags` pins the tags reflectively — every json key `groomingDispositionProjection` and `groomingStepsProjection` read must exist on `workmgmt.GroomingMutationRecord`, so a rename in EITHER direction reddens instead of emptying a baseline in silence. The churn fixture's seeded rows are marshalled from that writer struct rather than a hand-rolled map, so the unit corpus and the production writer share one serialization by construction.

**Detached and bounded, in two halves (E54.77 / [#3232](https://github.com/kuhlman-labs/fishhawk/issues/3232)).** The hook used to run `workmgmt.ApplyGrooming` SYNCHRONOUSLY on the operator's approve request under one 3m context shared with the audit sink — so past the budget every remaining candidate failed AND the write recording the failure failed on the same expired context, no `grooming_apply_completed` row landed, and `fishhawk_approve_plan` timed out client-side. Now: (i) the hook detaches from the request's cancellation at ENTRY (`context.WithoutCancel`), so a client disconnect can strand neither the window settlement nor the apply — with the ctx-honouring audit fake this is what `TestApplyApprovedGrooming_DetachedFromRequestCancellation` actually proves (delete it → the settlement append returns `Canceled` → `window_unsettled` → dialed 0); (ii) the SYNCHRONOUS half — ratification, window settlement, input resolution and the started row — runs under `groomingApplyPrelaunchBudget` (30s, `var`), so a stalled database cannot hold the approve request open; on expiry the hook degrades with `grooming_apply_prelaunch_timeout` and writes NO `grooming_apply_started` row (`TestApplyApprovedGrooming_PrelaunchTimeout_DegradesNamed` wedges the watermark append); (iii) it appends ONE `grooming_apply_started` row `{candidate_count, budget_seconds, started_at}` — the progress denominator `fishhawk_get_run_status`'s `grooming_apply_status` block reads; a failed append logs at Error and does not abort the apply; (iv) the APPLY half runs on a goroutine tracked by `Server.bgGroomingApply` (drained by `Shutdown` beside `bgReviews`, bounded by the shutdown context — `TestServer_ShutdownDrainsDetachedGroomingApply`) under `groomingApplyBudgetFor(n) = max(groomingApplyBudget (3m floor), n × groomingApplyPerCandidateBudget (3s))` (`TestGroomingApplyBudgetFor`), and the approve response returns once the goroutine is launched (`TestApplyApprovedGrooming_ReturnsBeforeApplyFinishes`: the hook returns while the forge is parked on the first dispatch). Inside `workmgmt.ApplyGrooming` every sink write runs on a FRESH per-write context (`auditWriteCtx`: the apply context's values, not its cancellation, bounded by `groomingAuditWriteBudget` 15s) and, once the apply context is exhausted, every remaining candidate is recorded skipped with `apply_budget_exhausted` WITHOUT dialing the mutator or reader — so exactly one `grooming_mutation_applied` row per entry always lands and `grooming_apply_completed` always lands with a `budget_exhausted` count. The done-means test is `TestApplyApprovedGrooming_OverBudget_EveryEntryAudited` under `groomingApplyAuditFake`, which now HONOURS ctx like the production repository (the old `_BoundedContext` test passed only because the fake ignored ctx); `TestApproveGroomStage_OverBudgetRowsDecodeEqualToGoldens` drives the same shape through the real handler and real Postgres. An exhausted entry RESURFACES on the next grooming run because `priorGroomingDispositions` maps no case for that skip reason — that is the resume path; nothing is hand-applied. **An operator awaits completion** with `fishhawk_await_audit` on `grooming_apply_completed` (or re-polls `fishhawk_get_run_status` until `grooming_apply_status.state` is `completed`) before checking the forge, and does not attest the confirm gate on a partial apply. **Cross-boundary goldens** (approval condition of #3232): the started payload, the `budget_exhausted` count and the `apply_budget_exhausted` skip reason cross to `mcpserver` with no shared type, so `backend/internal/audit/testdata/grooming_apply/{grooming_apply_started,grooming_mutation_applied,grooming_apply_completed}.json` are the SERVER structs' marshal output (`TestGroomingApplyGoldens_MatchServerPayloadStructs` pins the bytes; regenerate with `FISHHAWK_UPDATE_GOLDENS=1`), the pgtest (`TestApproveGroomStage_OverBudgetRowsDecodeEqualToGoldens`, driven over `groomingApplyGoldenReport` — four hygiene defects on issues #1..#4 plus the schema-mandated ordering entry, with every entry id in `plan.GroomingEntryID`'s derived form) asserts the rows it writes are VALUE-EQUAL to them through the struct type (strict decode, then `reflect.DeepEqual`), with an explicit allow-list of run-dependent fields each pinned to what the test configured before being normalised — the started row's `started_at` and sub-second `budget_seconds`, and the ordering candidate's `+1` on `candidate_count`/`skipped`/`budget_exhausted`/`skipped_ids` — so a changed count, outcome, skip reason, kind or id reddens it, not only a renamed key; and `mcpserver` LOADS its fixtures from those files — a key rename on either side reddens a test.

**An unreadable spec authorizes nothing.** `groomingModesForRun` projects the resolved autonomy matrix onto `map[string]workmgmt.GroomingMode`; an unparseable spec or absent autonomy block yields an EMPTY map, `workmgmt.ResolveGroomingMode` normalizes an absent class to `gated`, and the destructive rule then requires `auto` + an approved entry (or an explicit per-entry gate approval), neither of which this slice supplies.

**Known operational residual.** This repository's Project #7 is USER-owned, and a GitHub App installation token cannot reach a user-owned Projects v2 board — board placement routes onto `FISHHAWKD_PROJECTS_TOKEN` instead ([#1114](https://github.com/kuhlman-labs/fishhawk/issues/1114)). With that token unset, the `unboarded` and `missing_estimate` hygiene defects dispatch and are recorded outcome `failed`, not `applied`. That is correct continue-and-report behaviour, not a defect: label-set and epic-link mutations land first. It doubles as a **kill switch without a deploy** — leave the token unset, or reject the groom gate instead of approving it.

## Shared proposal-report seam (`report_seam.go`, [#4012](https://github.com/kuhlman-labs/fishhawk/issues/4012))

The protocol a proposal-report role runs (ingest a report on a stage that DECLARES it, record it on the chain, capture the captain's per-entry dispositions inside a window, settle the window and file on approval), with the report KIND, the recorded-row CATEGORY and the window FAMILY as parameters, so the comms role (#3775 phases 4-7) reuses it instead of a third copy. The upkeep files keep every existing function name as a thin wrapper over these helpers, so the upkeep sections below describe unchanged behavior; their unchanged tests are the preservation proof. Seam tests: `report_seam_test.go`.

| `collapseConsumed[T](entries, artifactID, decode)` | last-wins BY SEQUENCE per entry id; undecodable, id-less and other-artifact rows skipped | `collapseUpkeepConsumed` |
| `runScopedWorkTarget(ctx, runRow, owner, name, conv)` | the run-scoped `workmgmt.Target`: coordinates from the caller's owner/name split (never re-split), connections from the conventions, scope from the run's installation else the GitHub lookup; a failed lookup RETURNS the error with a zero scope and each caller keeps its posture (the dedupe degrades `reader_error`/`budget_exceeded`, the filing proceeds and fails closed per finding) | `upkeepDuplicates`, `resolveUpkeepFilingJob` |
| `startDetachedReportApply(base, budget, fn)` | runs `fn` on `Server.bgReportApply` under `context.WithTimeout(context.WithoutCancel(base), budget)`; `Shutdown` drains the group (bounded by its context) and `waitReportApply()` is the test barrier | `applyApprovedUpkeep`'s filing loop |

**Family descriptors.** `upkeepWindowFamily` asserts the TYPED `audit.UpkeepWindowAppender`, not `audit.FamilyWindowAppender`: the server's upkeep test fakes implement only the typed capability, and switching the assertion would silently move them onto the fallback. `commsWindowFamily` asserts the generic `audit.FamilyWindowAppender` with family `comms`. Both read their categories from `audit.LookupWindowFamily`, the same registry the atomic path resolves through.

**`Config.UserReportCursors`** (`userreport.CursorStore`, E81.1) is wired from `serve.go` (`userreport.NewStore(pool)`). It is read by the comms gather through a deferring wrapper (`commsDeferringCursors`, see § "Comms scan gather"), which never advances it; the comms apply (phase 7, #4017) is the only advancer. nil degrades every comms gather to `cursor_store_unwired` (nothing shown).

## Comms scan gather (`comms_scan.go` / `comms_record.go`, E81.5 / [#4014](https://github.com/kuhlman-labs/fishhawk/issues/4014))

What a `plan` stage declaring `produces: comms_report` is shown when its prompt is served (phase 4 of #3775). Both prompt handlers call `applyCommsScan` right after the upkeep fork; it is inert (`nil`) for every other stage.

**Binding, budget, cache.** `resolveCommsScanContext` returns `(nil, nil, nil)` for a non-plan stage (no read) and for a plan stage `resolveStageArtifactBinding(..., comms_report)` says does not declare it (one GetRun + spec parse); a binding transport error is returned verbatim and both handlers write `500 internal_error` ("resolve the stage's comms_report declaration failed"). A declaring stage is gathered through `commsScans`, a single-flight + TTL cache keyed (server, run, stage) that mirrors `upkeepScanCache`: the leader runs under `context.WithoutCancel` bounded by `commsScanBudget` (20s); publish is panic-safe; only a completed gather is cached (`commsScanCacheTTL`, 60s), never a refusal or a panic; `commsScanCacheMaxEntries` caps the map (a full map runs uncached). `/prompt` and `/prompt-render` therefore agree within the TTL.

**Charter refusal (fail closed, not retried).** A comms scan has no unanchored mode. The charter is read through the shared, LOG-FREE `resolveCharterDocument` (rubric ids + non-goal ids from one revision); the gather logs its own `comms scan gather: charter refused` WARN. Any charter failure, a conventions failure, a malformed `owner/name`, or no rubric id passing the prompt's own conformance filter (`^[A-Z][0-9]+$` and not `^N[0-9]+$`, capped at `prompt.CommsMaxRubricLines`) returns `*commsCharterRefusal`, and BOTH endpoints write `422 comms_charter_refused` with `details.reason` from the closed set `commsCharterRefusalReasons()` (`conventions_unavailable`, `repo_malformed`, `charter_undeclared`, `seam_unwired`, `charter_unresolved`, `budget_exceeded`, `charter_rubric_unparsed`, `charter_rubric_unconforming`) and `details.charter_path` when the declaration was read; the log-only detail never reaches the body. `writePromptBuildError` maps the prompt-layer backstop `prompt.ErrCommsRubricEmpty` onto the same 422 (`charter_rubric_unconforming`). The runner's `upload.FetchPrompt` returns immediately on a 4xx other than 401/404, so a refusal is not a 5xx backoff loop: the runner exits non-zero, the stage fails (category C on local host dispatch), and the next scheduled tick or a `retry_stage` after fixing the charter re-attempts. A transient charter read failure (`charter_unresolved`, `budget_exceeded`) refuses the same way, deliberately: one code, one contract. `TestCommsCharterRefusal_ReasonsDocumentedInOpenAPI` pins the reason set against `docs/api/v0.openapi.yaml`.

**Deferred cursor.** `userreport.Scan` runs with `commsDeferringCursors{inner}`: `Get` and `Init` pass through (`Init` is an idempotent insert-if-absent of now-14d on a repository's first gather, even on `/prompt-render`; it initialises, never advances) and `Advance` returns `(to, false, nil)` without writing. Serving NEVER moves `user_report_cursors`; the row's `pending_cursor` is what phase 7 advances to. A nil cursor store, an unresolvable reader (`commsUserReportReaderFor`), an unresolved target scope or an unparseable run account degrades the gather (`source: user_reports`) and Scan is not called; a Scan error degrades `budget_exceeded` on the deadline, else `scan_failed`. A scan-level degrade shows nothing and records no `pending_cursor`.

**Classification and issue text.** Only `external` reports are kept; `fishhawk_filed`, `bot` and `internal` are counted in `class_excluded`. For a comms stage `applyCommsScan` CLEARS the trigger's issue title, body and comments (the number stays): option (a) of the #4013 carry, so the column-0 `User report · ` attribution line is emitted only by the user-report envelope writer and no triggering-issue text can forge a shown report.

**Suppression memory and its bound.** A report is suppressed when its `(id, userreport.ContentHash)` is in a prior `comms_apply_completed` row's `suppressions[]` (basis `filed` / `rejected` / `n_drift`) or in trusted marker evidence (basis `marker`); a prior-apply basis wins over a marker, and a materially edited report (hash differs) re-enters. `loadCommsSuppressionMemory` / `loadCommsDraftFiled` read `AuditRepo.ListAll` filtered to the category (`comms_apply_completed` / `comms_draft_filed`, the indexed column) and keep rows whose entry account EQUALS the run's (nil matches only nil) and whose payload `repo` equals the run's. **The bound is a ROW cap on the category read, never a count of prior runs** (#4017, carried from #4014): each read passes `audit.ListAllParams.Limit = commsMemoryMaxRows` (2000), pushed into the SQL (`LIMIT sqlc.narg(row_limit)`, NULL = all) after the `ts DESC, id DESC` order, so it keeps the NEWEST rows of the category and an old suppression survives any number of newer runs that wrote no row of the category. **The cap counts ACCOUNT-category rows, not per-repo rows:** it is applied before the in-app filters, so rows of sibling repositories in the account and the NULL-account rows `ListAll` admits consume it (a nil account leaves the query unconstrained, so every account's rows do). A read that returns the cap returns the rows PLUS `*commsMemoryTruncatedError`, a named degradation (`source: audit`, `suppression_memory_truncated` / `draft_filed_truncated`, `count` = the cap) the gather records while keeping the partial memory: a suppression older than the cap stops suppressing. **Truncation weakens BOTH consumers:** the gather's suppression AND the apply's double-filing guard (below), which reads the same two categories inside its lock and records `guard_truncated: true`. A nil AuditRepo or a list error degrades (`source: audit`, `suppression_memory_unavailable` / `draft_filed_unavailable`) with empty memory: nothing is suppressed, the safe direction.

**Marker trust (server-controlled position only).** `trustedCommsMarkers` calls `userreport.ParseDraftMarkers` ONLY on items classified `fishhawk_filed` (an external item, including one with `MarkerFromExternal`, is never parsed) and honours a parsed `(id, content_hash)` ONLY when a `comms_draft_filed` row for the same `(issue_number, comment_id)` names it. The result is the intersection, so a marker an attacker plants in a title that a filed draft's intake Derives-from block quotes suppresses nothing. The malformed-marker count is observability only (`malformed_markers`).

**Caps, order and progress.** The gather keeps the OLDEST `commsScanMaxReports` (100) external, unsuppressed reports (one per id, the later update); the rest are omitted. The kept reports are rendered NEWEST-first, so `prompt.RenderUserReports`'s cap drops the newest and the oldest always render: the cursor can always advance past at least one report. The gather calls `RenderUserReports` itself to learn the render-omitted ids (it is deterministic, so `buildCommsScan` omits the same ones). `pending_cursor.cursor` = min(Scan's `NextCursor`, the earliest omitted report's `updated_at`) and `note_cursor` = min(Scan's `NextNoteCursor`, that held value), each then clamped to its own read bound (`since`, `note_since`) with `note_cursor` <= `cursor`. The note bound is taken BEFORE the `since` clamp: a GitLab note listed under a `note_since` earlier than `since` can be older than `since`, and clamping first would lift the floor past an omitted one. The reader's `Since` is INCLUSIVE (`workmgmt.ListUserReportsRequest`), so a report at the held cursor is re-listed. `commsCursorHoldBack(payload, ids)` is the hold-back the apply (#4017) applies for unaccounted reports, undecided drafts' sources and approved-but-unfiled drafts' sources (an id the row does not show returns the read bounds: no movement). Clusters are ADVISORY: pairwise `intakegroom.Duplicates` on titles (a comment's first non-empty line), medium confidence or higher, union-find.

**Recorded clusters ([#4016](https://github.com/kuhlman-labs/fishhawk/issues/4016)).** The row's `suggested_clusters` (`[{report_ids, score}]`) records the clusters the served prompt RENDERED, not the raw suggestions: `commsRecordableClusters` mirrors `prompt.writeCommsClusters`' filters in its order — a non-finite score drops the cluster; only `UserReportID`-shaped, shown, not-yet-seen ids are kept; a cluster left with fewer than two ids drops; at most `prompt.CommsMaxClusters` clusters (a dropped one does not count) and the first `prompt.CommsMaxClusterIDs` ids each, order preserved. Why: the phase-6 dispositions read derives `cluster_splits` (where the agent split a cluster it was shown) from it. The server mirrors rather than shares the render because `backend/internal/prompt/` is a review-prompt-eval trigger path; `TestCommsRecordableClusters_MatchRender` (every filter and both caps through `prompt.Build`) and `TestCommsScan_RecordedClustersMatchRender` (a real gather) go RED if either side changes alone. Dropping a non-finite score also keeps the payload encodable (encoding/json refuses NaN/Inf); `recordCommsScanGathered` refuses an unencodable payload rather than digest it. No clusters record as `[]`, never `null`. A row recorded before #4016 has no `suggested_clusters` key: the strict decoder still accepts it (field nil) and `commsGatheredClustersRecorded` reports false (also for a `null` or an undecodable row), so a reader tells "this gather predates the record" apart from "the prompt rendered no cluster".

**Record and digest dedupe (signed serve only).** After `prompt.Build` succeeds, the SIGNED `/prompt` stamps `stage_id` and `run.StageAttemptToken(stage.DispatchedAt)` onto the payload and calls `recordCommsScanGathered`: `gather_digest` = lowercase-hex sha256 of the normalized payload with the digest blank; under a process mutex it appends ONE `comms_scan_gathered` row per distinct digest for the run (a new stage attempt is a new digest). A record failure is `500 internal_error` ("record the comms scan gather failed"): a prompt whose gather cannot be bound is not served, and the runner's 5xx loop retries. `/prompt-render` never records — a preview is not a serve. Two fishhawkd replicas can append the same digest twice; the rows are content-identical, so lookups stay equivalent. **The stored `gather_digest` is authoritative; never re-digest a decoded row.** A row recorded before `suggested_clusters` existed, decoded and re-digested under the current `normalized()`, gains `"suggested_clusters":[]` and no longer equals its stored digest (`TestCommsGatheredClustersRecorded_LegacyRow` pins it), so no path may recompute a gather digest from a decoded row and compare it; bind by the stored value (`commsScanGatheredByDigest`).

**Read contracts phases 5 and 7 bind to.** `latestCommsScanGathered(run, stage)` (highest sequence for the stage, strict decode) and `commsScanGatheredByDigest(run, digest)` (exact). Phase 7 must WRITE `comms_draft_filed` as `{repo, issue_number, comment_id, reports[{id, content_hash}]}` and `comms_apply_completed` as `{repo, suppressions[{id, hash, basis}]}` (`commsDraftFiledRecord` / `commsApplyCompletedRecord`; extra fields tolerated). The apply (#4017, below) writes both; `TestApplyApprovedComms_SuppressionsReadableByGatherMemory` and the flow's rescans pin the writer to this reader.

**Empty scan.** Zero reports still serve the prompt (with the "No report was shown" instruction) and record a row with empty `shown` and the pending cursor; the stage still parks at its approval gate. Auto-settling an empty report is left to phases 5/7.

Tests: `comms_scan_test.go` (gather, cache, refusals, degrades, controls C1-C12, C19, recorded-cluster filters and render parity), `comms_record_test.go` (record, lookups, suppression and marker contracts, the clusters-recorded probe and legacy rows), `comms_scan_handler_test.go` (both endpoints end to end, C13-C16, the OpenAPI reason parity).

## On-approval comms apply (`comms_apply.go`, [#4017](https://github.com/kuhlman-labs/fishhawk/issues/4017), E81.5 / #3775)

The comms scan's last phase. `applyApprovedComms(ctx, stage, decision)` is called from `finishApprovalAdvance`'s TYPE-only plan block directly after `applyApprovedUpkeep` (the placement is part of the control: the reject path must be observable), mirrors that hook on the shared proposal-report seam (`report_seam.go`: `recordedReportArtifact`, `reportGateRatified`, `settleReportWindow`, `collapseConsumed`, `startDetachedReportApply` on `bgReportApply`, drained by `Shutdown`), and is best-effort: it never unwinds the approval. It files captain-approved drafts through `applyAndFileWorkItem` and nothing else: it **never creates a run and never labels, edits, closes or comments on a SOURCE report** (`TestCommsApply_SourceNeverReferencesRunCreationOrSourceMutation` pins the file's references). It detaches at entry (`context.WithoutCancel`) and bounds the synchronous half by `commsApplyPrelaunchBudget` (30s).

**Ladder (synchronous half, first match wins).**

| Rung | Condition | Effect |
|---|---|---|
| E0 | no `comms_report` artifact on the stage, an unreadable artifact list, no `comms_report_recorded` row, or the row names another stage's artifact | return; write nothing (an ordinary plan approval is untouched) |
| E0' | the newest recorded row is undecodable | degraded row `comms_apply_report_unreadable` |
| C1 | decision != approve | settle the window `rejected` BEFORE any body read, then one reject row (below); file nothing; the cursor never moves |
| C3a | approve, but `latestCommsReport` fails or names another artifact | degraded `comms_apply_report_unreadable`, window OPEN |
| C3b | approve, but `reportGateRatified` is not OK (no grant, any rejection row, unreadable, no repository) | degraded `comms_apply_not_ratified`, window OPEN |
| C4 | `settleReportWindow(..., approved)` fails | degraded `comms_apply_window_unsettled`, window OPEN |
| C5 | a post-ratification input fails | degraded with the window CLOSED and the cursor untouched (table below) |
| | else | the detached loop runs under `commsApplyBudgetFor(len(drafts))` = max(`commsApplyBudget` 3m, 3s per draft) |

**The reject row.** On a SETTLED reject the row is `{decision: reject, suppressions, cursor {advanced: false, reason: decision_reject}}`: `rejected` suppressions for every cited `(id, gathered hash)` of the drafts the captain individually rejected or, when the consumed set holds NO disposition for this artifact (a whole-gate reject), of EVERY draft. Approved or undecided drafts on a rejected gate get none and are re-proposed. **A FAILED reject settlement never suppresses** (approval condition 1): the consumed set is UNKNOWN, not empty, so treating it as a whole-gate reject would suppress drafts the captain approved; it writes one degraded row (`decision: reject`, `comms_apply_window_unsettled`, `suppressions: []`) and nothing else (`TestApplyApprovedComms_RejectSettlementFailureNeverSuppresses`). A report unreadable after a settled reject writes a degraded reject row with no suppressions.

**Degrade reasons** (closed set; every degraded row carries `repo`, `degraded: true`, `suppressions: []` and an untouched cursor):

| `degrade_reason` | When | Window |
|---|---|---|
| `comms_apply_report_unreadable` | recorded row, report or bound gather unresolvable | open (approve) |
| `comms_apply_not_ratified` | gate contested, ungranted or unreadable | open |
| `comms_apply_window_unsettled` | the watermark did not land | open (approve); unknown consumed set (reject) |
| `comms_apply_run_unreadable` / `comms_apply_account_unparseable` / `comms_apply_repo_unresolvable` / `comms_apply_conventions_unavailable` / `comms_apply_prior_filings_unreadable` | post-ratification input | closed |
| `comms_apply_guard_unavailable` | the suppression memory or draft-filed read failed inside the lock; nothing filed | closed |
| `comms_apply_lock_wait_exhausted` | the budget expired while queued for the per-repository lock | closed |
| `comms_apply_prelaunch_timeout` | the synchronous half's own budget expired (the rung's reason is kept in the log detail) | per rung |

**The gather is the EXACT bound row.** `latestCommsReport` loads the gather the recorded row names by its STORED `gather_digest` (`commsScanGatheredByDigest`, never re-digested), so a later gather for the same stage changes neither the hashes the apply suppresses nor the pending cursor it advances to (`TestApplyApprovedComms_BindsExactGatheredRow`).

**Per-draft rows (detached loop, REPORT order, first match wins).** Exactly one `comms_draft_filed` or `comms_draft_skipped` row per draft:

| `skip_reason` | When | Holds the cursor |
|---|---|---|
| `undecided` | no consumed disposition | yes |
| `rejected` | consumed verdict `rejected` (writes `rejected` suppressions) | no |
| `already_filed` | this run already filed this artifact's draft (`prior_issue_number`); writes `filed` suppressions | no |
| `filed_elsewhere` | a cited `(id, gathered hash)` carries a `filed` suppression or appears in a `comms_draft_filed` record (`conflicting_reports [{id, content_hash, basis, issue_number?}]`) | yes |
| `parent_epic_is_source` | the effective parent epic (the captain's override, else the proposal's, via `plan.CommsParentEpicNumber`) is the issue a cited report lives on | yes |
| `apply_budget_exhausted` | the loop's budget expired before this draft | yes |
| `filing_failed` | `code`: `filing_body_digest_absent` (no recorded digest), `filing_body_drift` (the re-rendered body hashes differently), `charter_unavailable` (the recorded body quoted the rubric and the charter is unreadable NOW — a transient read failure, distinct from drift), or the filing core's `*workItemError` code | yes |

The guard is PER REPORT: one filed cited report makes the whole draft `filed_elsewhere`; its unsuppressed remainder is re-proposed alone after the cursor hold-back. A draft-filed record citing `(id, hash)` is necessarily ANOTHER artifact's filing (approval condition 5): `CheckCommsReportSemantics` gives each shown report exactly one placement in a report, so no other draft of this artifact cites it, and this draft's own prior filing is caught first as `already_filed`; `commsDraftFiledRecord` therefore needs no `artifact_id`. A cited report holding a prior `rejected` / `n_drift` suppression from another apply is FILED and flagged (`prior_suppressions`): that apply necessarily preceded this approval, so the captain's approval here is the later decision.

**What is filed.** `commsFilingRequest(draft, EXACT gather, rubric text)`. Rubric text follows the RECORDED `charter_text`: ids alone unless the recorded row says `rendered`, in which case the current text is used only while the charter still has the gathered hash. The recomputed `commsFilingBodyDigest` must equal the recorded preview's `filing_body_digest`, else the draft is skipped `filing_failed` (nothing the captain did not review is filed). **The digest covers the PRE-INTAKE renderer output**; the intake advisory section `applyAndFileWorkItem` appends at filing is point-in-time and can differ from the preview's (`intakegroom.RenderBody` leaves the body unchanged only for DEGRADED signals with no findings; a successful empty evaluation still appends a section), so the filed body equals the reviewed preview body exactly when both intake runs add nothing (`comms_apply_pg_test.go` pins that case against real Postgres). Labels: `commsFilingLabels` then every `autonomy:*` dropped AGAIN. **Defaulted autonomy is suppressed** (approval condition 4): the request files with a deep-copied conventions value (`commsFilingConventions`) whose item type lacks the `autonomy` label default and every `autonomy:*` default label, and the row records what was removed as `suppressed_default_labels`. **The preview's defaulted autonomy label is NOT filed: the reviewed `labels` list differs from the filed one by exactly that label.** The shared loaded conventions are never mutated. `Relations.ParentEpic` is the normalized effective epic. NO `IdempotencyKey`: `workmgmt.StampIdempotencyKey` appends a marker to the body, which would make the filed body differ from the reviewed one.

**`comms_draft_filed`** carries the read contract `{repo, issue_number, comment_id: 0, reports [{id, content_hash}]}` (GATHERED hashes) plus `run_id, stage_id, artifact_id, draft_id, issue_url, provider, title, parent_epic, applied_labels, stripped_labels, suppressed_default_labels, filing_body_digest, prior_suppressions`. **`comms_draft_skipped`**: `{run_id, stage_id, artifact_id, draft_id, skip_reason, code?, message?, prior_issue_number?, conflicting_reports?}`.

**`comms_apply_completed`** (ONE per apply): `{repo, artifact_id, decision, counts {drafts, filed, skipped, failed, budget_exhausted}, degraded, degrade_reason?, guard_truncated?, suppressions [{id, hash, basis, entry_id}], cursor {advanced, cursor?, note_cursor?, held_report_ids, reason?, error?}}`. On a non-degraded approve `filed + skipped + failed + budget_exhausted == drafts`. Suppressions: filed and already_filed drafts → `filed`; rejected drafts → `rejected`; every n_drift entry → `n_drift`; hashes from the bound gather's `shown`, `entry_id` the draft or n_drift id. The keys are the ones `loadCommsSuppressionMemory` decodes (`id`, `hash`, `basis`), NOT the issue prose's `report_id` / `content_hash` / `outcome`.

**Cursor.** Only a ratified, non-degraded approve advances. Held ids = the recorded `unaccounted_report_ids` ∪ the sources of undecided drafts ∪ the sources of approved-but-unfiled drafts (`filed_elsewhere`, `parent_epic_is_source`, `apply_budget_exhausted`, `filing_failed`). `commsCursorHoldBack(bound gather, held)` holds the gather's `pending_cursor` back to the earliest held report's `updated_at`; then `Advance` the note floor (`SourceIssueNotes`) THEN the cursor (`SourceIssues`), so the floor never runs ahead of a cursor that failed to move. `cursor.reason`: `decision_reject`, `apply_degraded`, `scan_incomplete` (the gather recorded no pending cursor), `cursor_store_unwired`, `advance_failed` (+ `error`; the filings stand). The store is a monotonic watermark per (account, repo, source): overlapping applies resolve to the maximum, so a report one run held can be passed by another run that accounted for it; already-suppressed sources re-read past a held cursor are filtered by the memory.

**Guard and serialization.** The loop takes a dedicated per-(account, repo) lock (`acquireCommsApplyLock`, a 1-slot channel per key) whose wait SELECTS on the apply budget, unlike the context-blind `keyedLocks` (approval condition 3). On expiry while queued it writes `apply_budget_exhausted` for every draft and ONE degraded completion row (`comms_apply_lock_wait_exhausted`, every draft's sources and the unaccounted reports held, no advance). Inside the lock it reads the guard (`loadCommsSuppressionMemory` + `loadCommsDraftFiled` for the run's account and repo; unavailable → `comms_apply_guard_unavailable`, truncated → proceed with `guard_truncated: true`), files, writes the completion row and only then releases, so a second apply for the repository reads the first one's rows (`TestApplyApprovedComms_ConcurrentAppliesSerializePerRepo`, `TestApplyApprovedComms_LockWaitBoundedByBudget`). Each row is written on its own bounded context, so an expired budget never loses its own row.

**Residuals.**
- Serialization is IN-PROCESS: two fishhawkd replicas can race and double-file a report (the same class as `recordCommsScanGathered`'s two-replica note).
- At-least-once filing: a `File` that succeeds but whose `comms_draft_filed` row is lost could re-file on a later apply of the same artifact (unusual: the window is permanent); the filed issue carries the comms draft marker for manual dedupe.
- The row cap (above) weakens the double-filing guard once the account's category rows exceed it; the truncation is recorded, never silent.
- A charter changed between ingest and apply skips the drafts whose body quoted it (`filing_body_drift`); their sources hold the cursor and are re-proposed.
- A revert does not lower an advanced `user_report_cursors` value nor close an issue an apply filed.

Tests: `comms_apply_test.go` (every rung, degrade reason, skip reason and cursor reason, the serialization and lock-wait races, the writer↔reader contract), `comms_flow_test.go` (gather → ingest → dispositions → approve → apply → rescan through the real routes and the real `userreport.Scan`: approve, rescan-after-edit, per-draft and whole-gate reject, overlapping scans), `comms_apply_pg_test.go` (real Postgres: previews JSON-equal through JSONB, `sha256(decoded preview body) == filing_body_digest`, the filed body equals it, the defaulted autonomy suppressed).

## On-approval upkeep apply (`upkeep_apply.go`, [#3924](https://github.com/kuhlman-labs/fishhawk/issues/3924), E79 / #3726)

`applyApprovedUpkeep(ctx, stage, decision)` is the upkeep scan's last phase: a best-effort side effect of `finishApprovalAdvance`'s plan-stage block, called directly after `applyApprovedGrooming`. When the DECIDED plan stage carries the run's recorded `upkeep_report`, it settles the report's disposition-capture window and, on approve only, files every captain-approved finding that is not already covered through `applyAndFileWorkItem` — the same work-item core every other auto-file path uses. Like its siblings it never unwinds the approval: every failure degrades to a named audit row and returns. Normative wire contract: `docs/spec/upkeep-report-v1.md` § "Apply".

**It never creates a run.** An approved finding becomes a tracker issue that a human (or a later campaign) picks up — not a dispatched change. Nothing in `upkeep_apply.go` references `CreateRun` or a run-creation path, and two counters pin it at zero: `ukApplyRunRepo` in `upkeep_apply_test.go` and `ukFlowRunRepo` in `upkeep_flow_test.go`.

**Placement is part of the control, exactly as for grooming.** The call sits in the TYPE-only plan block (which runs on approve AND reject) and is PASSED the decision. "A rejected report files nothing and settles its window `rejected`" therefore lives in the hook as a guard whose deletion is observable on the reject path; nesting the call inside the approve-only block would make it untestable.

### The ladder

| # | Rung | Rule | Test |
|---|---|---|---|
| E0 | **Report present** | *An early-out, not a control.* No `upkeep_report` artifact on the stage (`ArtifactRepo.ListForStage`), no `upkeep_report_recorded` row, or the recorded row names an artifact on another stage → write NOTHING. It reads only the artifact LIST and the recorded ROW, and a nil `ArtifactRepo`/`AuditRepo`/stage returns at once, so every ordinary plan approval is untouched. An unreadable artifact list is silent (indistinguishable from "no report"). Detached through `startDetachedReportApply` on `Server.bgReportApply` (the shared proposal-report seam's group, #4012; drained by `Shutdown` beside `bgGroomingApply`; `waitUpkeepApply()`, now a wrapper over `bgReportApply.Wait()`, is the test barrier) under `upkeepApplyBudgetFor(n) = max(upkeepApplyBudget (3m), n × upkeepApplyPerFindingBudget (3s))`; the synchronous half is bounded by `upkeepApplyPrelaunchBudget` (30s). Skip and degrade reasons are payload VALUES, not audit categories; `upkeep_apply_completed` is registered in `backend/internal/audit/categories.go` and is INTERNAL — not an issue-comment activity category.

**What a filing carries.** `Type`/`Summary`/`Body` come from the proposal; the body gains `upkeep.FindingMarker(id)` on its own line (the marker the next scan's ingest dedupe matches) and is stamped with `workmgmt.MintIdempotencyKey("upkeep_finding", run_id, artifact_id, finding_id)` through `FilingRequest.IdempotencyKey`. **Advisory filings are server-rendered (#3750).** For a finding whose `source` is `advisory`, `upkeepFilingProse` IGNORES the agent's `proposed_issue.title` and `.body`: the summary is `upkeep.RenderAdvisoryTitle` (`<primary id>: <package> <version> (<severity> severity)`) and the body is `upkeep.RenderAdvisoryFacts` — a `### Advisory facts (server-rendered)` block of every advisory id, ecosystem, package, in-use version, fixed version or `no fix published`, reachability, severity and the cited MANIFEST paths (`upkeepAdvisoryManifestPaths`: a call-site source file cited as evidence is never listed) — then the marker. The renderers take no call path and withhold any value that is not a plain token, so neither agent prose nor a call-path frame naming the repository's own code reaches the tracker through the title or body, and no token guard is needed (`upkeep.CallPathDisclosure` is an UNWIRED helper in the `upkeep` package; nothing calls it). Its labels are narrowed by `upkeepAdvisoryLabels` to `upkeepAdvisoryNamespaces(conv, type)`, DERIVED from the resolved conventions since #4626 (ADR-110 guard (i)): the filing type's `workmgmt.TypeLabelNamespaces` minus `autonomy`; for a declared type naming no namespace (this repository's `adr` and `epic`) the repository's label vocabulary, the union over every declared type minus `autonomy`, so those advisories keep their labels (#4626 approval condition C5); and an EMPTY allow-list for a type the conventions do not declare (fail closed: every label stripped). For this repository's declaration every type yields `{area, phase, type}`, the retired fixed list (`TestUpkeepAdvisory_RepoDeclarationParity`; `TestUpkeepAdvisory_NamespacesFromConventions`, `TestUpkeepAdvisory_UnknownTypeStripsAll`). Every other label (a frame-shaped `server.serveH2`, an authorized `autonomy:*`) is recorded in `stripped_labels`; the suffix inside a kept namespace is still agent-chosen until the filing-label allow-list (#3956). The filed row carries `server_rendered: true`. Keyed on the SOURCE alone, so an advisory finding missing its object (unreachable past rule (l)) still files only rendered fields. Tests: `TestApplyApprovedUpkeep_AdvisoryFilingIsServerRendered` (an agent title, body and labels quoting the caller frame file none of it), `..._AdvisoryFactsBlock`, `TestUpkeepFilingProse` (a non-advisory finding files its proposal byte-identically).

### Marker provenance (a decision, #3924 carried item 1)

A marker match suppresses filing WITHOUT a provenance check. The title-similarity channel suppresses equally and CANNOT be provenance-gated — a human-filed similar issue IS the duplicate the dedupe exists to catch — so a provenance check on the marker alone would not reduce what an issue-opener can suppress. The effect is bounded to a SKIP: nothing is closed, edited or escalated. `TestApplyApprovedUpkeep_SkipsDuplicateOfOpenIssue` pins the decision with a marker-basis mark whose issue nothing in the run filed. The rejected alternative is a cross-run `upkeep_finding_filed` provenance scan for marker-basis marks.

### Residuals

- **(i) Marker dedupe has NO provenance check.** An issue planted by anyone who can open or edit an issue — carrying a finding's marker, or a near-identical title — suppresses that finding's filing. The upkeep apply's audit categories (`upkeep_finding_skipped` including `filing_failed` and `apply_budget_exhausted`, and a degraded `upkeep_apply_completed`) are INTERNAL: no UI and no issue comment surfaces them, so the captain sees them only through `GET /v0/runs/{id}/audit`. The operator accepted this at the #3924 plan gate as a suppression-only residual — it can stop a filing, never cause one or escalate one.
- **(ii) Lost apply — no re-drive.** After the window settles `approved`, a crash, a post-ratification degrade, `filing_failed` or budget exhaustion leaves approved findings unfiled, and nothing re-drives them (the consumed window is closed and permanent). Recovery is the NEXT `upkeep_scan`: it re-proposes the still-present findings, and its marker dedupe (plus `already_filed` on a re-apply of the same artifact) prevents a double filing.
- **(iii) Rollback.** Removing filing requires reverting the `s.applyApprovedUpkeep(...)` call in `approvals.go` (and `upkeep_apply.go`, #3924 slice 3) — reverting this flow test and these docs (slice 4) changes no behaviour. Issues already filed stay on the tracker and carry the marker, so the next scan still recognizes them while they are open.
- **(iv) Strict disposition decode.** #3924 made `POST /v0/runs/{id}/upkeep-dispositions` decode strictly: a body with an unknown or misspelled key that was previously accepted with `200` (the key silently dropped) is now `400 validation_failed`. In-repo callers (the `fishhawk_record_upkeep_dispositions` MCP tool) send only declared keys.
- **Settlement does not re-check the report binding.** The audit window-close transaction has no `checkReportBinding`, so if a newer report is recorded between `latestUpkeepReport` and the settlement, the apply settles and consumes against the report it resolved. Narrow: the approved stage's own ingest settled it.
- **At-least-once filing.** If `provider.File` succeeds but the `upkeep_finding_filed` append fails, a re-apply would file again. A second apply is unreachable in production — the approve compare-and-swap refuses a raced second approval (see "Approval-hook self-protection" above) — and the stamped key and marker make any duplicate identifiable; the next scan's dedupe marks it.
- **Count-1 ratification.** C3 shares grooming's grant-and-no-rejection predicate, which coincides with gate satisfaction only under a `count: 1` gate (the shipped `upkeep_scan` declares `count: 1`).

**Frontend handling.** The Web UI does not render any of this: `frontend/src/api/types.ts`'s `ArtifactKind` does not list `upkeep_report` (an unknown kind passes through `evidenceRefFor` as an opaque string, so nothing crashes), and the run narrative reads an allow-listed category set (`NARRATIVE_AUDIT_CATEGORIES` in `frontend/src/run-narrative/use-run-narrative.ts`), so the upkeep rows are never fetched. Rendering them is a follow-up for the operator to file.

## In-flight advisory findings (`upkeep_inflight.go`, [#3763](https://github.com/kuhlman-labs/fishhawk/issues/3763), E80.6)

After the captain approves an upkeep scan, every advisory finding the captain APPROVED is matched against the dependency changes of the repository's other RUNNING runs. A run whose own diff introduces an affected version gets ONE crew-message-v1 `finding` (sender `security`, recipient `reviewer`, anchored on that run, actor system `upkeep:advisory-watch`, no stage). E77.7's deferred delivery renders it in the run's next review round and in the gate view's `crew_messages` block. It is a crew_messages row, never a concern, so the merge gate is untouched (ADR-081 rule 2).

**Trigger: after the captain, not at ingest (a decision; prior-run approval condition 1).** `applyApprovedUpkeep` calls `startUpkeepInflightPass` once the disposition window settles `approved`, after the settlement and before the filing-job resolution. The pass receives only the advisory findings whose consumed disposition is `approved`. A rejected gate, a contested or ungranted gate, an unsettled window and a finding the captain rejected or left undisposed start nothing. The `upkeep_report` ingest starts nothing, so unratified scanner output never reaches another run. The call is detached: the apply's latency and outcome are unchanged. A re-apply of the same settled window runs the pass again, and the chain dedupe below sends nothing new (`TestApplyApprovedUpkeep_StartsInflightPassForApprovedAdvisories`).

**Run selection.** `RunRepo.ListRuns{Repo, AccountID, State: running}`, paged 100, at most `upkeepInflightMaxRuns` (50) runs, with `runs_window_truncated` set at the cap. `run.State` is only pending, running or terminal; gate parking lives on STAGE states, so a run parked at a plan, review or merge gate is `running` and IS examined (the pg test's run A is parked at `awaiting_approval`). The scan run is excluded silently. A decomposition child is skipped (its parent owns the PR and the gate). `upkeepRunOwnershipRefusal` is the account control, because the listing keeps NULL-account rows.

**Diff source.** The base is `cfg.DocumentBaseRef(repo)`. The head is `latestRunHeadSHA`. The diff is the forge compare `base...head`, which is merge-base anchored, so only the run's OWN manifest edits count. For every changed `go.mod` / `pnpm-lock.yaml` (not `removed`) in a directory an approved advisory of that ecosystem cites, the pass reads its patch section (`upkeep.SplitComparePatch`) and its content at the head COMMIT (never the branch name), and calls `upkeep.DependencyChanges`. No other manifest is fetched. The match rules (net-add only, inside a `require` directive, same version line, below the fix) live in `backend/internal/upkeep/README.md` § "In-flight advisory match".

**Dedupe.** A match is skipped as `already_sent` when the TARGET run's CHAIN (`crew_message_sent` entries, never the derived table) holds a `security`-sent `finding` whose summary equals `upkeep.InFlightFindingSummary`, which is keyed on primary advisory id + ecosystem + package. The sender filter is what makes planting impossible. **`crewSenderRoleForStage` (`server/crewmessage.go`) derives a run-bound token's sender role from its stage through an allow-list of `planner` (plan) and `reviewer` (review) only, so no run token can send as `security`; operators send as `captain`.** Only fishhawkd sends as `security`, so an agent cannot suppress a finding by planting its summary (`TestUpkeepInflight_DedupeIgnoresNonSecuritySender`). A `*crewmessage.ProjectionError` counts as SENT, because the entry committed and is never re-sent.

**Bounded wait.** Passes serialize on `upkeepInflightSlot`, a one-slot semaphore acquired via `select` on the pass context. The 60s `upkeepInflightBudget` clock starts at the CALL SITE, so a queued pass spends its own budget waiting and then degrades `pass_busy` instead of blocking. Every summary row, degrades included, is appended on a FRESH `upkeepInflightRowBudget` context derived from `context.WithoutCancel`, never on the possibly-expired pass context. Shutdown drains `bgUpkeepInflight`.

| `degrade_reason` | When | Test |
|---|---|---|
| `pass_busy` | another pass held the slot for this pass's whole budget | `TestUpkeepInflight_QueuedPassDegradesBusyWithinItsBudget` |
| `report_unreadable` | no `upkeep_report_recorded` row names the artifact | `TestUpkeepInflight_Degrades/report_unreadable` |

Arrays and the map are never null. A pass is not started, and no row is written, when the mailbox, audit or run repository is unwired or no approved advisory finding exists. INTERNAL and audit-only, not an issue-comment surface.

A run whose last review already settled sees the finding only in the gate view until a fix-up re-review. A later re-bump of the same advisory to another affected version is not re-sent (the dedupe key has no version). ## Per-entry grooming disposition capture (`grooming_dispositions.go`, E54.30 / [#2843](https://github.com/kuhlman-labs/fishhawk/issues/2843))

`POST` / `GET /v0/runs/{run_id}/grooming-dispositions` record and read back an operator's verdict on INDIVIDUAL entries of a run's grooming report, keyed by the entry's stable DERIVED id. Each disposition persists as one chained `grooming_disposition_recorded` audit row.

**The category is deliberately distinct from `grooming_mutation_applied`.** This row is what the OPERATOR DECIDED; that one is what was APPLIED, and the second derives from the first. Collapsing them would make "the operator approved this and the apply then failed" indistinguishable from "the operator never decided" — which is exactly the state the churn guard's baseline (`priorGroomingDispositions`) reads. `TestGroomingDispositionAuditCategoryDistinct` pins the literal category string, its registry membership, and that capture writes ZERO apply-family rows.

**These dispositions are CONSUMED on approval ([#2991](https://github.com/kuhlman-labs/fishhawk/issues/2991)).** The on-approval apply hook (`grooming_apply.go`) merges them with an undispositioned default (`mergeGroomingDecisions`): an undispositioned HYGIENE entry still auto-applies, an undispositioned GATED entry gets no decision, an explicit recorded `approved` is the ONLY thing that populates `GateApproved` (which unlocks `workmgmt` rule 4's gated destructive classes and rule 8's delegation-tier label), `rejected` skips and `amended` is NOT an approval path. Honest asymmetry with the issue's headline: dedup is `mode: gated` so an approved duplicate now DISPATCHES, but scoping is `mode: report` and rule 3 short-circuits before any gate-approval check, so "scoping icebox" does NOT become dispatchable in this repo.

**The capture/apply concurrency protocol gives three properties simultaneously**, via the audit-layer `GroomingWindowAppender` capability (`backend/internal/audit/grooming_window.go`): (1) ONE CAPTURE IS ONE TRANSACTION — the batch is appended under the run-row lock after a closing-watermark check, so a watermark cannot split it and a mid-batch failure records nothing; (2) THE FIRST WATERMARK IS PERMANENT — a repeated settlement returns the existing artifact-bound watermark unchanged, so rows outside the first window stay outside it; (3) REJECTION SETTLES AS DECISIVELY AS APPROVAL. The invariant: a capture `POST` returns success only if its dispositions are still consumable — a capture arriving after the artifact's window is settled is `409 grooming_window_closed`. The consumed set is ARTIFACT-SCOPED (a run may carry multiple grooming reports), so a stale disposition against a different artifact never enters another's consumed set.

**Which report a capture attaches to.** `newestGroomingReportArtifact` resolves the run's NEWEST `grooming_report` artifact — the maximum by `(CreatedAt, ID)` across the run's plan stages, a TOTAL order so two artifacts written in the same clock tick still order stably regardless of repository return order. BOTH verbs resolve through it, which is what makes `POST` and `GET` agree on WHICH report by construction rather than by convention. The resolved `artifact_id` + `content_hash` come back in the response and ride on every audit payload, so a later consumer can still distinguish captures across artifacts. It keeps three outcomes distinct exactly as `priorGroomingReport` does — found / genuinely absent / read-or-parse failure — because collapsing absent and unreadable is how a capture would silently attach to the wrong report. `TestGroomingDispositionsNewestArtifactWins` seeds two artifacts and fails if either verb attaches to the older one.

**The valid-entry-id set has one owner.** `plan.GroomingEntryIDs` / `plan.GroomingEntryClasses` are thin exports over the EXISTING unexported `collectGroomingEntries` — the same collector `groomingSemanticCheck` walks — so the ids capture accepts cannot drift from the ids `ValidateGroomingReport` already proved the report declares. A class added to the report domain without being routed through the shared derivation fails in `plan`'s own table test, not here.

**The ladder is eight rungs, every one evaluated BEFORE any write.**

**Batch-atomic validation AND atomic append.** The WHOLE batch is validated before ANY row is appended, so a request naming one unknown `entry_id` records NOTHING. On the production store the batch is ALSO appended in ONE transaction (`GroomingWindowAppender.AppendChainedGroomingDispositionBatch`), so an append that fails part-way records nothing either — the pre-#2991 per-row path that left durable partial rows and a `details.recorded` count survives only as the in-memory fallback for repositories lacking the capability. This control's effect is COMMITTED STATE, not error identity: the counterfactual vehicles READ the rows after the call returns and assert zero (`TestGroomingDispositionsUnknownEntryLeavesNoRows` for validation, `TestGroomingDispositionsMidBatchAppendFailure` for the atomic append). A capture after settlement is refused `409 grooming_window_closed` (`TestRecordGroomingDispositions_RefusedAfterWindowClosed`).

**The body must be ONE JSON document.** `json.Decoder` stops after the first value, so a body of two concatenated batches decoded the first, SILENTLY DISCARDED the second, and returned `200` — a success response for a capture that recorded half of what the operator sent, which is the exact failure shape this endpoint exists to prevent. G5 now re-Decodes after the first value and refuses anything but `io.EOF`, ahead of every write. Trailing WHITESPACE is still accepted: a trailing newline is what every curl heredoc and most HTTP clients send, and refusing it would break every real caller to fix a synthetic one. `TestGroomingDispositionsTrailingContentRejected` tables all five shapes (second object, garbage, array, newline, whitespace) and asserts on COMMITTED STATE — zero appended rows on each refusal, exactly one on each acceptance.

**The mid-batch append failure is the one place the batch-atomic guarantee is knowingly weakened**, and it is now pinned. Rows appended before an `AppendChained` failure ARE durable, so the `500 internal_error` reports `{recorded, requested}` — the operator's only evidence of what survived. `TestGroomingDispositionsMidBatchAppendFailure` wraps the REAL Postgres audit repository in a decorator that fails the k-th disposition append and passes every other call through, then asserts the counts OFF THE SHIPPED RESPONSE BYTES, that `recorded` equals the rows that actually persisted, that the failed entry did NOT persist, and that the documented recovery holds (re-POST the batch, last-wins resolves to the retried verdicts, all five rows stay in the chain). Asserting on the details map handed to `writeError` instead would have hidden the defect that test found: `recorded` / `requested` were NOT members of `redactableDetailKeys`, so the 5xx allow-list dropped both and the shipped body carried NO count at all while the handler comment claimed it did. Both keys are now allow-listed (product-owned integers computed from the caller's own batch, the `failed_ordinal` precedent). The read-back's `ListForRunByCategory` failure (`..._ReadBackListErrorIs500`, which also asserts the capture itself LANDED — the failure is on the projection read, and that distinction decides whether an operator should retry) and the GET's `run_id` parse (`..._GetInvalidRunIDRejected`) are pinned alongside.

**Last-wins supersession.** An `entry_id` may not repeat WITHIN one request — one request carrying two verdicts for one entry states no verdict, so it is `400 validation_failed`, not a supersession. A LATER request on the same entry DOES supersede, collapsed last-wins by audit sequence. Both rows stay in the chain, so the correction is itself auditable; refusing the repeat instead would make an operator's corrected verdict unrecordable. `TestGroomingDispositionsReadBackLastWins` fails if the read-back returns the earlier verdict or if either row is missing.

**The projection is tolerant in the fail-safe direction — and deliberately does NOT mirror `priorGroomingDispositions`.** `projectGroomingDispositions` skips a row whose payload cannot be decoded, contributing no disposition, and keeps only rows whose `artifact_id` matches the resolved artifact, so a capture against an older report never leaks into a newer report's read-back. Output is sorted by `entry_id` for a deterministic body. The divergence from `priorGroomingDispositions` (which since #2813 REFUSES an unattributable row) is principled, not drift: this is a READ-BACK for DISPLAY against ONE resolved artifact, where a skipped row suppresses nothing; the churn baseline's read DECIDES SUPPRESSION across runs, where a skipped row on the newest candidate lets the scan adopt an OLDER settled baseline. Both branches are pinned by `TestProjectGroomingDispositions_SkipsUndecodableAndForeignRows`, whose foreign-row fixture carries a DISTINCT `entry_id` on purpose: sharing one would let the last-wins collapse absorb it and the case would stay green with the artifact filter deleted.

**Operator-only means TWO refusals, and the second is the point.** G2 mirrors `merge_run.go` and `vouch.go`. G3 goes beyond what the issue asked: the grooming report is AGENT-AUTHORED, so an agent that could also disposition it would convert an operator gate into a rubber stamp. It is keyed on `operatorrole.IsTokenSubject` — the same predicate `actor.go` already uses to classify a delegated writer as `actor_kind=agent` — so it reuses the existing notion of agent identity rather than inventing one, and if that prefix convention changes, actor classification and this refusal move together. G4 mirrors `merge_run.go`'s posture verbatim: `write:approvals` enforced with NO cookie-session bypass, because a disposition is an approval-class judgment.

**The READ is not operator-only.** The issue states the requirement for CAPTURE, and the underlying `grooming_report` artifact is already agent-readable, so a refusal on the read would add a failure mode with no corresponding hazard. The `GET` is registered at `readAccess`.

**Delegation is unchanged, structurally.** No file under `backend/internal/spec/` or `docs/spec/` is touched, so `ordering` / `dedup` / `scoping` remain refused at `mode: auto` by the two existing parse-time controls — re-asserted by `TestGroomingRegistry_DispositionCaptureDoesNotWidenDelegation`.

## Plan-stage terminal settle is shared across artifact siblings (`grooming_report.go` / `plan.go`, E54.29 / #2837)

`handleGroomingReport` ingested, persisted, audited and churn-checked a `grooming_report` and then returned WITHOUT transitioning the stage, so a groom stage sat in `running` forever and its approval gate never opened (#2837). The fix REUSES the shared terminal settle rather than hand-rolling a per-sibling copy: `handleGroomingReport` calls `advancePlanStageTerminal` (`plan.go`) on BOTH success paths — the fresh-create path and the idempotent-retry path — which already owns the gated (`running → awaiting_approval`) and gateless (`running → succeeded` + orchestrator `Advance`) arms plus the sticky status-comment notify.

- **The settle is SHARED, not per-sibling.** `advancePlanStageTerminal` is THE plan-stage terminal settle for every artifact sibling that settles to the approval gate — today the plan artifact (#603) and the `grooming_report` (#2837). `clarification_request` is the deliberate EXCEPTION: it parks at `awaiting_input`, owned by `handleClarificationRequest`. A new sibling whose ingest settles to the gate MUST reuse `advancePlanStageTerminal`; #2837 (and #2833 before it, where the clarification sibling was special-cased by name) exist because a sibling was NOT wired to the shared settle.
- **Placement is fail-closed.** Both settle calls sit AFTER every validation guard and every storage-500 return, so an invalid or wrong-stage-type report fails category-B and NEVER reaches the gate, and an artifact-create / audit-append / churn-append failure leaves the stage in `running` for the runner's retry to heal — a not-durable report is never advanced to an approvable state. The retry path re-settles (a same-state re-application is a valid no-op via `ValidStageTransition`'s `from == to` short-circuit), so a retry after a partial first write cannot re-strand the stage.
- **No `notifyPlanReadyIfReady` on the grooming path.** `notifyPlanReady` resolves the run's PLAN artifact via `tryLoadPlanForRun`, which filters `a.Kind != artifact.KindPlan` (`prompt.go`), so on a grooming run it finds no plan and no-ops. `advancePlanStageTerminal`'s own `notifyStatusUpdate` is the operator-visible surface; a grooming-specific report-ready comment is a candidate follow-up.
- **A two-layer guard forces a future sibling to declare its settle.** (1) `plan.AllArtifactKinds()` + `TestAllArtifactKinds_EnumeratesEveryDeclaredConst` (parses the plan package's own non-test source across every file, not just `plan.go`) fails when an `ArtifactKind` const is declared without being enumerated. (2) `TestShipPlan_EverySiblingSettlesItsStage` iterates that enumeration — not its own table keys — driving every kind through the real signed router and `t.Fatalf`-ing on a kind with no declared settle row. So a fourth sibling cannot land without declaring the state its ingest settles to.
