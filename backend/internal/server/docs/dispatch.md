## Writer-side anchor intent marker + gate (`operator_visible.go`, #3406)

`issuecomment.activityCategories` is a closed set in another package: an audit category a writer here appends and refreshes the anchor for, but never registers there, renders NOTHING (the #3392 shape). Nothing bound the writer's intent to that registration, so `(*Server).notifyOperatorVisible(ctx, runID, category)` is the explicit marker — "I appended category X and intend the operator to see it on the anchor / status comment." It logs at ERROR naming the category when `issuecomment.RendersActivity` rejects it (runtime defence in depth, checked BEFORE and independent of the notifier nil-guard) and then delegates to `notifyStatusUpdate` unconditionally, so the refresh is byte-identical to a direct call; the rendered-category writers (`acceptance_scenario_retirement_dropped` ×2, `fixup_pushed`, `deployment_rollback_initiated`, `pr_merged`, `pr_closed_without_merge`, `run_revived_on_reopen`, among others) use it, and every existing call-count test on the `pageClassRecorder` fake is unaffected. `notifyStatusUpdate`'s `source` is a call-site TRANSITION tag, never an audit category.

The static gate `operator_visible_gate_test.go` (in-loop via `go test -race ./...`) type-checks this package's non-test files with `go/types` (`importer.ForCompiler(fset, "source", nil)`, one cached check shared by both gate tests, ~25s) and sweeps every call of both helpers. `resolveStringArg` accepts ONLY a string `BasicLit` or an `Ident`/`SelectorExpr` whose `types.Info.Uses` object is a string-kinded `*types.Const` (value via `constant.StringVal`) — a `*types.Var`, parameter, shadowing local, call or concatenation fails closed naming `file:line`; resolution is never by identifier name, and `TestCollectNotifyCalls_ShapeCoverage`'s two-package fixture (literal, in-package const, cross-package selector, local, parameter, field, call, concatenation, conversion, and a SHADOWING row whose local `category` must never resolve to the package const `"fixup_pushed"`) is the counterfactual for that. `TestNotifyOperatorVisibleCategoriesRender` asserts each marked category is admitted by `issuecomment.RendersActivity` AND `audit.IsKnownCategory` (floor 5 sites). `TestNotifyStatusUpdateSourceIsNotAnAuditCategory` asserts no `notifyStatusUpdate` source (outside the delegating call in `operator_visible.go`) is an `audit.KnownCategories` member unless the `auditOnlyStatusRefreshSources` table names it with a per-category reason (floor 30 sites); the table is kept honest by three checks — a key that is now `RendersActivity` fails as STALE (convert the site to `notifyOperatorVisible`, drop the exemption), a key no site references fails as ORPHANED, and a key that is not a Known category fails as inert. Every degrade (parse error, type error, no files, unresolvable argument) is `t.Fatalf`/`t.Errorf`, never a skip. The runtime branch is pinned by `operator_visible_test.go` (unrenderable → ERROR + refresh still fires; renderable → silent + one refresh; nil notifier → ERROR still emitted). Residual, stated: a writer that appends a new category and refreshes with a non-category transition tag is bound by neither half.

## Preview/dev-mode host-dispatch refusal (`devmode.go`, E72.13 / #3500)

#3500: the acceptance agent host-dispatched stages on the PREVIEW fishhawkd
(`scripts/dev preview`), whose spawned runners pushed branches and opened pull
requests on the real forge with the operator's credentials. The controls here
are deliberately identity-independent — the escape did not depend on which
credential the agent held (the preview's fixed Postgres role can mint a
`write:runs` operator token), so nothing below keys on identity.

- **Dev mode IS the presence of a dev surface.** `devModeSurfaces()` returns
  the mounted dev-only surfaces in fixed order (`dev_fixtures` when
  `Config.DevFixtures != nil`, `dev_stub_forge` when `Config.DevStubForge !=
  nil`); `devModeActive()` is `len > 0`. There is no separate flag or env var:
  `scripts/dev preview` mounts both (`FISHHAWKD_DEV_FIXTURES=1` +
  `FISHHAWKD_DEV_STUB_FORGE=1`) and a production deployment mounts neither, so
  the posture cannot drift from the surfaces that define it.
- **Host-dispatch refuses every caller.** `handleHostDispatchStage` checks
  `devModeActive()` FIRST — after the run_id/stage_id parse (a malformed id
  still answers 400) but BEFORE the auth ladder and every dependency guard —
  and answers **403 `host_dispatch_refused_dev_mode`** with `details
  {reason: dev_mode, dev_surfaces: [...]}`. An anonymous caller, an `fhm_`
  token and a `write:runs` operator bearer are refused identically. The stage
  row is never read on that path, so its state is untouched (the regression
  test re-reads it and asserts `awaiting_host_dispatch`, committed state not
  error identity). Because every MCP host-spawn verb (`fishhawk_run_stage` /
  `dispatch_stage` / `run_children` / `drive_run`, the embedded `/mcp` route
  included) calls the marker fail-closed before `cmd.Start`, no runner is
  spawned — that fail-closed behaviour is pre-existing and pinned in
  `backend/internal/mcpserver`, untouched here.
- **Audit row.** `refuseHostDispatchDevMode` appends a `host_dispatch_refused`
  row (`CategoryHostDispatchRefused`, registered in `audit.KnownCategories`)
  on the run chain — ActorKind system, stage-scoped, payload `{reason:
  dev_mode, dev_surfaces, stage_id, subject (the caller's subject or
  "anonymous"), source: host_dispatch}`. Best-effort, mirroring
  `emitHostDispatchAcceptanceAnchor`: a nil `AuditRepo` or a failed append
  WARN-logs and the 403 is still written. Placing the refusal before auth
  means an anonymous caller learns the daemon is in dev mode and causes a row
  to be written; on a dev-mode daemon the credential-less `/v0/dev/*` routes
  already reveal and mutate dev state, and the row is bounded to an existing
  run's chain.
- **`/healthz` `dev_mode: true`** (`handleHealth`, omitempty) advertises the
  posture; **`forge_writes: "deny"`** is stamped on EVERY prompt response
  (`forgeWritesPolicy()`, both `handleGetStagePrompt` and
  `handleGetStagePromptRender`) — a CROSS-MODULE WIRE field mirrored by
  `runner/internal/upload.FetchedPrompt.ForgeWrites` and registered in the
  `wirecontract` `prompt_response` ModeSubset pair, so a tag drift fails
  `TestCrossModuleWireParity`. The runner's pre-spawn gate that refuses on it
  (`runner_failed` reason `forge_writes_denied`, category C) is the sibling
  slice, documented in `runner/README.md`; since E72.16 / #3510 the runner
  ALSO probes the `/healthz` `dev_mode` field once pre-spawn on both launch
  paths, so that gate no longer depends on a prompt fetch (a `--prompt-file`
  launch with a scrubbed env is refused by the probe). Both fields are
  omitted on a production daemon, keeping its wire surfaces byte-identical.
- **MCP-token pin.** `TestHandleIssueMCPToken_ScopesNeverReachHostDispatch`
  pins that the run-bound MCP token — the one token the acceptance sandbox can
  mint via its signing key — never carries `write:runs` or `write:approvals`
  on any stage type, so it cannot reach the marker (#3500 done-means 2).
- **Tests** (`host_dispatch_test.go`): refuses anonymous / `write:runs`
  bearer / each surface alone; nil `AuditRepo` and a failing append still
  refuse; a malformed id still 400s with no row; and the no-dev-surface
  control (`TestHostDispatch_ProductionNoDevSurface_Unchanged`) proves the
  production path still transitions `awaiting_host_dispatch → dispatched`
  with no refusal row. Counterfactual: deleting the `devModeActive()` branch
  answers 200 with the stage `dispatched`.

## Interim host memory hold (`host_dispatch.go`, E85.11 / [#4330](https://github.com/kuhlman-labs/fishhawk/issues/4330))

An optional, default-off dispatch hold on the host-dispatch marker. It is
**INTERIM**: ADR-100's adaptive concurrency controller absorbs it, and #4330
stays open (this is a partial delivery; the first-officer seat half is
remaining scope).

- **Seam.** `Config.HostAdmissionHold` is the package-local interface
  `HostAdmissionHold { Held(now) (bool, reason string) }`; nil (the default)
  leaves the marker byte-identical. fishhawkd wires it only under
  `--enable-ops-monitor --ops-monitor-dispatch-hold` on a `local` deployment,
  with the SAME `*opsmonitor.AdmissionHold` the ops monitor ticker updates
  (`backend/cmd/fishhawkd/README.md` § "Interim dispatch hold"). That hold is
  held while the memory probe reads CRITICAL pressure and reads not-held once
  the ticker has not updated it for 3 × its effective interval, so a dead
  ticker cannot pin admissions shut (`backend/internal/opsmonitor/README.md`).
- **Where it fires.** After every eligibility and dependency guard (dev mode,
  auth, runner_kind/executor, terminal run, wave order, post-deploy hold,
  decomposed-parent acceptance) and the state switch, and BEFORE the bare CAS
  or the concurrency slot admission. Only the two admissible arms reach it —
  `pending` (a first plan-stage spawn) and `awaiting_host_dispatch` — so it
  refuses EVERY new admission, and it commits nothing: no transition, no
  queue row, no slot.
- **Refusal.** `409 host_memory_pressure`, details `{stage_id, state, reason,
  retry: "re-dispatch once the ops monitor clears the condition"}`. A plain
  409, not the queued `concurrency_slot_queued`: an MCP slot waiter stops on
  it and the operator re-dispatches once the condition clears; the stage stays
  where it was.
- **What it never touches.** The idempotent already-`dispatched` arm returns
  before the hold is consulted (a spawn attempt exists; a dead-runner
  re-dispatch proceeds), and nothing in flight is refused or killed.
- **Tests** (`host_dispatch_test.go`):
  `TestHostDispatch_HostMemoryHold_RefusesBothAdmissibleArms` (a held hold on a
  `pending` and on an `awaiting_host_dispatch` stage: 409 with reason + retry,
  and the re-read stage is unchanged — committed state, since with the check
  deleted the CAS moves it to `dispatched`), `…_NotHeldAdmits`,
  `…_NilIsDefault`, `…_AlreadyDispatchedUntouched` (the hold is not even
  consulted) and `…_PrecedesSlotAdmission` (a grouped implement stage: a held
  hold never calls `concurrency.Store.Admit`; the not-held control does).

## Decomposition wave-order host-dispatch guard (`decomposition_dispatch_guard.go`, E48.99 / #2546)

The host-dispatch marker is the fail-closed chokepoint every host-spawn verb
(`fishhawk_dispatch_stage`, `fishhawk_run_stage`, `fishhawk_drive_run`,
`fishhawk_run_children`) calls immediately before spawning a runner. For a run
carrying `decomposed_from` + `slice_index`, `guardDecompositionWaveOrder`
resolves the child's declared dependencies from the parent's approved plan
(`decomposition.sub_plans[slice_index].depends_on` — the same authority
`plan.Waves` topologically sorts into the `plan_decomposed` `waves` payload),
maps each dependency slice onto its minted sibling child run, and refuses `409
dependency_not_satisfied` naming the LOWEST-indexed blocking sibling when any
dependency has not reached run state `succeeded`. Mirrors
`start_campaign_item_run`'s `item_not_eligible` "blocked on dependency issue:N"
precedent on a different surface.

- **Authority**: the parent's approved plan, loaded via `loadApprovedPlanForRun(*decomposed_from)` — the parent OWNS the plan stage, so the walk resolves on its first hop. Siblings are enumerated with the paged `listDecomposedSiblings` (mandatory explicit page size: `postgresRepo.ListRuns` rejects `Limit<=0`), mirroring `listAllDecomposedChildren`.
- **The absent / errored / unmet partition** (`resolveSliceDependencies`): an ABSENT input is NOT a violation — admit and log (not a fan-out child, plan resolves nil / no decomposition, or `slice_index` out of range, the same defensive degrade `matchDecomposedSubPlan` takes; the prompt-fetch path stays the fail-closed authority for a slice/plan mismatch via `409 decomposed_scope_unresolved`). An ERRORED read is retryable — `500 dependency_check_failed`, never a silent admit. Only a positively-UNMET dependency refuses. Refusing on absence instead would wedge every legitimate dispatch behind an unresolvable plan — a strictly worse failure than the operator error being guarded.
- **Ordering relative to the CAS**: wired into `handleHostDispatchStage` AFTER the runner_kind/executor eligibility checks and BEFORE the state switch/CAS, inside the already-held stage-admission lock. A refusal commits NO state and the stage stays parked at `awaiting_host_dispatch` (pinned by the committed-state handler assertion — error identity alone is insufficient, since a guard placed after the CAS would 409 with the stage already flipped). Because it precedes the `switch stage.State`, it also runs AHEAD of the idempotent already-`dispatched` no-op branch: a fan-out child already `dispatched` whose dependency has since regressed out of `succeeded` (a revived/re-opened sibling) is refused `409 dependency_not_satisfied` on re-dispatch rather than returning the `200 {transitioned:false}` dead-runner no-op — wave order is re-validated on the re-dispatch path, and the `dispatched` state is left unchanged (pinned by `TestHostDispatch_DecompositionAlreadyDispatched_RegressedDependency_Refuses`).
- **The deliberate no-N+1 split**: `slice_index` is a pure row projection surfaced by `toRunResponse` (so it rides both `GET /v0/runs/{id}` and the list endpoint), while `slice_depends_on` is resolved by `handleGetRun` ONLY (the single-run read, best-effort like Concerns/Delegation) — the list endpoint never pays the per-row plan load.
- **Atomicity of the predicate vs the CAS (#2586)**: the guard's `ListRuns` sibling snapshot is NOT atomic with the caller's stage CAS, and NO lock spans the two rows — the guard reads sibling RUN rows while the caller writes this child's STAGE row, and the held stage-admission lock is keyed to the stage and serializes no sibling-run write. The window is real. What makes it safe is run-state MONOTONICITY, not serialization: run state `succeeded` is **absorbing** — `runs.state` is written by exactly one query (`UpdateRunState`) reached by exactly two repository methods, each inside a `SELECT … FOR UPDATE` transaction (`TransitionRun`, gated by `ValidRunTransition`, which refuses any terminal `from`; `RetryRun`, gated by `ValidRunRetryTransition`, which admits only `failed → running`), `ReviveRun` refuses a non-failed run outright, and there is no run-deletion path. Enumerated window directions: a dependency **reaching** `succeeded`, or a dependency slice gaining a freshly-minted (`pending`) sibling, leaves the guard deciding on a stale snapshot and **refusing** — fail closed, a spurious 409 the operator clears by re-dispatching; a dependency **leaving** `succeeded` would admit out of wave order and is the dangerous direction, unreachable precisely because `succeeded` is absorbing. Because enforcement is repository-layer under a row lock rather than an in-process mutex, this argument survives multiple `fishhawkd` replicas — unlike the #1936 stage-admission fence, whose residual is single-process by construction. **Scope**: this covers SIBLING-RUN-STATE staleness only. NOT covered — the dependency SET is read from the parent's approved plan, so a parent plan revised between that read and the CAS can change `depends_on` and leave the guard deciding against a stale dependency set; the absorbing-succeeded argument constrains run STATE, not plan CONTENT. That plan-revision window is an operator-level anomaly rather than a caller-drivable race, and it is untested and unfixed here.
- **What the concurrency test does and does not pin (#2586)**: `TestHostDispatch_ConcurrentDecomposedDispatch_AdmitsExactlyOne` fires 8 concurrent host-dispatch POSTs at one fan-out child stage and asserts exactly one `transitioned:true`, with the rest 200-idempotent or 409 and the stage settled at `dispatched`. That pins **the stage CAS admits one dispatcher** — and nothing more. Deleting the `LockStageAdmission` acquisition was run as a counterfactual and the test still PASSES without `-race` (under `-race` the deletion fails, but on an unsynchronized counter in the `guardCountingRepo` test fake, not on a second transition). So no admission-lock serialization claim is made from it; the #1936 fence's own contract is pinned separately by `TestHostDispatch_AdmissionWalkInFlight_MarkerBlocksThen409`.

Tests: `decomposition_dispatch_guard_test.go` (one case per branch, plus the three window directions — `TestGuard_Window_DependencyReachesSucceeded_StillRefuses`, `TestGuard_Window_DependencySiblingMintedLate_StillRefuses`, `TestGuard_Window_DependencyLeavesSucceeded_AdmitsOnSnapshot` — driven through a deterministic `onListRuns` hook rather than sleep-based racing), `host_dispatch_test.go` (the handler refusal/admit + committed-state, `TestHostDispatch_ConcurrentDecomposedDispatch_AdmitsExactlyOne`, and the pgtest-backed cross-layer round trip whose step (c) asserts a satisfied dependency cannot be falsified after the fact), `runs_get_test.go` / `runs_list_test.go` (the run-row surface + the no-N+1 pin). The absorbing-succeeded premise itself is pinned in the run package by `TestRunSucceededIsAbsorbing` and `TestPostgres_SucceededRunNeverLeavesSucceeded`.

## Per-wave integration guard + `base_branch` derivation (`decomposition_dispatch_guard.go`, E50.13 / #2363)

The wave-ORDER guard above proves a dependent child's dependency slices have
SUCCEEDED. That is deliberately NOT sufficient to spawn it. Run state flips to
`succeeded` BEFORE the between-wave integration merges the slice branches onto
the parent's consolidated branch, so a child admitted on state alone would build
on a base missing its predecessors' symbols (#1302). `resolveDependentChildBase`
closes that gap and, in the same step, makes the marker the AUTHORITY on the
per-wave re-base: the 200 body gains `base_branch`, and the client derives
nothing.

- **The admission rule**: for a fan-out child with a non-empty resolved
  `depends_on`, read the parent's NEWEST `slices_integrated` audit entry and
  ADMIT with `base_branch = consolidated_branch` only when (a) that branch is
  non-empty AND (b) `wavecoverage.Covered(depends_on, sliceRunID, child_run_ids)`
  holds. **A non-empty consolidated branch is NOT on its own sufficient** — that
  is precisely the STALE case (wave 1 integrated; this wave-2 child's
  newly-succeeded dependency not yet merged), which `consolidatedBranchFromAudit`
  cannot distinguish because it reads only the branch name. Anything else
  refuses `409 wave_not_integrated` with `details` `{slice_index, depends_on,
  missing_dependency_slices, consolidated_branch_present}`.
- **One predicate, three callers**: the coverage question is answered by the
  shared leaf package `backend/internal/wavecoverage`, the SAME function the
  child-completion sweeper's steady-state short-circuit and the MCP await verb's
  `children_dispatchable` release use. A reconstruction here — or a caller keying
  on predecessor run STATE — would announce dispatchability this endpoint then
  refuses; that drift is the class the repo already names load-bearing (the
  `SliceBranch`/`childSliceBranch` "MUST stay byte-identical" note).
- **One entry, both fields**: `latestSlicesIntegrated` decodes
  `consolidated_branch` AND `child_run_ids` from THE SAME newest entry. Reading
  them through separate walks would let a child be admitted onto a branch whose
  coverage was proved by a different integration (pinned by
  `TestResolveDependentChildBase_DoesNotSpliceAcrossEntries`).
- **Ordering relative to the CAS**: derived AFTER `guardDecompositionWaveOrder`
  and BEFORE the state switch/CAS, so a refusal commits NO state and the child
  stays cleanly re-dispatchable once the sweeper integrates — and the wave-ORDER
  refusal still decides first when a dependency has not succeeded (a
  wave-order violation must never be reported as an integration wait, since
  waiting would never clear it). `base_branch` also rides the idempotent
  already-`dispatched` arm, because that caller re-spawns.
- **Absent vs errored**, the same partition the wave-order guard uses: a
  non-fan-out run, an empty `depends_on`, or an unresolvable parent plan are
  ABSENT — admit with no `base_branch`, i.e. byte-identical to pre-#2363
  behaviour. A DEPENDENT child (non-empty `depends_on`) with an UNCONFIGURED
  `AuditRepo` is NOT absent — it REFUSES (fail-closed): with no audit repository
  there is no integration record to prove its predecessors merged, and admitting
  would spawn it onto an unproven base (the #1302 stale-base class the guard
  exists to close). A wave-0 child with no dependencies still admits, so an
  unconfigured deployment's INDEPENDENT dispatches are never wedged — only a
  genuinely dependent child is refused, and in practice `AuditRepo` is always
  configured (`serve.go`), so this is a test-posture fail-closed. An undecodable
  newest payload is ABSENT for the coverage question and therefore REFUSES
  (it must not admit on bytes the server could not read). An ERRORED read
  (plan load, audit list, sibling list) is `500 dependency_check_failed`,
  retryable, never a silent admit.
- **Wire fixture (#2660 lesson)**: `testdata/host_dispatch_dependent_child.json`
  is proven byte-identical to the handler's own 200 body by
  `TestHostDispatch_DependentChild_ResponseMatchesWireFixture`, and the MCP
  client test serves THOSE bytes to a real `apiClient` — so the client cannot
  share a wrong json tag with a fake that re-marshals its own struct. The
  sibling decode (`child_run_ids`) is tied to the emitter the same way by
  `TestLatestSlicesIntegrated_DecodesRealEmitterPayload`, which drives the REAL
  fan-in and decodes its genuine entry: drifting the decoder tag and the
  hand-seeded fixture key TOGETHER leaves every coverage test green and reddens
  only that test.

Tests: `decomposition_dispatch_guard_test.go` (`TestResolveDependentChildBase_*`
— one case per admit/refuse/degrade branch, including the unconfigured-audit
refusal for a dependent child, the undecodable payload, the
covered-but-empty-branch refusal and the cross-entry splice pin),
`host_dispatch_test.go`
(`TestHostDispatch_DependentChild_EndToEnd`, the two counterfactual controls
`TestHostDispatch_RefusesDependentChildWhenWaveNotIntegrated` /
`…WhenIntegrationIsStale` — each asserting error IDENTITY *and* reading the
stage row back, since the control's effect is committed state — the wave-order
precedence pin, the wire-fixture equality and the emitter-fidelity decode), and
`mcpserver/client_test.go` (`TestHostDispatchStage_WireShape`: the fixture-bytes
decode and the `wave_not_integrated` annotation).

## Decomposed-parent fix-up policy increment (#4391)

- **What.** `promptResponse.fixup_policy_increment` (`prompt.go`) is set ONLY on a decomposed PARENT's fix-up serve — the runner-facing dispatch and the SPA preview — and is the parent analogue of [#765](https://github.com/kuhlman-labs/fishhawk/issues/765)'s per-child increment base. A parent fix-up commits onto the consolidated head, which already carries every slice's fan-in commit, so a policy diff measured against the base branch counts the WHOLE fan-out and fails `max_files_changed` on an over-cap decomposed change however small the fix-up is.
- **One predicate.** The flag and `fixup_branch`'s consolidated branch both derive from `isDecomposedParentRun`, so they cannot disagree. A verify-only merge-candidate pass, an ordinary implement dispatch, an ordinary run's fix-up and a decomposed CHILD's fix-up never carry it; a probe error omits it (today's cumulative diff).
- **Effect.** The runner measures both `git_diff` emitters against the consolidated tip it fetched for the pass (`runner/cmd/fishhawk-runner/README.md` § "Decomposed-parent fix-up policy increment"), so the in-band constraint check and `reEvaluatePolicy` — which reads the bundle's LAST `git_diff` — see only the increment, with no backend policy change. The backend keeps re-evaluating the runner-reported diff, exactly as for #765's child increments; a runner predating the field ignores it and keeps the cumulative diff. Fix-up re-reviews are unaffected: they source their diff from `ComparePatch(base, pushedHead)`, not the bundle. `prompt_fixup_increment_test.go` pins the serve and, through the trace-upload path, the persisted policy result.

### Decomposed-parent fix-up scope union (#4338)

- **What.** `parent_fixup_scope.go::decomposedParentFixupScope` widens a decomposed PARENT's fix-up `scope_files` on BOTH prompt surfaces (`handleGetStagePrompt`, `handleGetStagePromptRender`), called in the fix-up block just before `effectiveFixupScope`. The parent's own sources are its plan's TOP-LEVEL `scope.files`, its flat `add_scope_files` and its own stage's amendments, so a fix-up editing a path a SLICE owned or was granted was drift-excluded and failed category B (run af08d34e / #4250). The union adds: every sub_plan's declared scope (`scopeFilesFromApprovedPlanFull`, operations preserved); every slice's `add_scope_files_to_slice` paths (`parentSliceGrantPaths`, read from the parent's plan-stage approval behind the #2598 wall, flattened in ascending slice-index order so the served order never follows Go map order); and every child's APPROVED mid-stage amendment with its operation preserved (`childApprovedAmendmentEntries`, the operation-preserving projection of the #2820 walk). The gate-time `remove_scope_files` is then subtracted AGAIN, because the sub_plan union can re-introduce a removed path and a removal must win exactly as it does in each child's slice scope. `effectiveFixupScope`'s coupled `*_test.go`, `allow_create` and stage-amendment folds run over the union.
- **Why `modify` is the right operation for a slice grant.** On the consolidated branch the slice's commit has already made the granted path TRACKED, so the runner's #818 untracked-path (created-out-of-scope) gate does not apply to it, and drift exclusion is decided by path membership in `cfg.scopeFiles` alone, never by the declared operation.
- **One predicate.** Gated on `isDecomposedParentRun`, the same predicate behind `fixupBranchForRun`'s consolidated branch and the `fixup_policy_increment` flag (#4391). A non-fix-up parent dispatch, a merge-candidate verify-only pass (no fix-up block), an ordinary run and a decomposed CHILD keep today's `scope_files` byte-for-byte; a child's slice narrowing and single-owner-file property are untouched.
- **Degrade: fail toward today.** A children-probe error reads the predicate false and serves today's narrower scope; a per-child amendment list error makes only that child contribute nothing. An empty scope or a missing plan stays unchanged (the runner's `git add -A` fallback). Refusing the prompt would block every parent fix-up on a transient read error.
- **No runner or backend-policy change.** The runner's `cfg.scopeFiles` has a single writer: the served `scope_files` plus `refreshScopeAmendments` over the run's OWN amendments (which never sees a child's). `reEvaluatePolicy` and the plan-gate scope precheck evaluate `forbidden_paths`, `allowed_paths`, `max_files_changed` and `agent_instruction_paths` against the diff or plan, never `scope.files` membership.
- **`max_files_changed` stays bounded.** The approval gate already counted every slice grant (`checkPlanScopeCap`, with `effectiveScopePathSet` folding a prior approval's per-slice paths), and on a parent fix-up the cap measures the fix-up's own increment (#4391), so widening the permission set cannot let a pass exceed it; `forbidden_paths` and `agent_instruction_paths` still run on the real diff. The conflict-resolution pass is authorized by its conflicted-path set, not `scope_files`.
- **Not done.** The REVIEW-side baseline (`amendedScopeFilesForReview` / `scopeProvenanceForReview`) still omits slice grants and sub_plan-only paths for a parent; that gap is [#4425](https://github.com/kuhlman-labs/fishhawk/issues/4425) and is deliberately not widened here.
- **Tests.** `parent_fixup_scope_test.go` drives both surfaces (served union, the five unchanged shapes, removal-wins, deterministic slice-grant order); `child_scope_amendment_test.go` pins the entries projection and, unmodified, the review projection.

## Concurrency-group promote (`stage_concurrency_promote.go`, E83.81 / [#4191](https://github.com/kuhlman-labs/fishhawk/issues/4191))

`POST /v0/stages/{stage_id}/concurrency/promote` moves one QUEUED waiter in a local stage concurrency group (ADR-087 `stage_concurrency_slots`) to the front of its group, so a stage that unblocks everyone else is admitted at the next free slot. The ordering, lock order and refusal semantics are the store's: `backend/internal/concurrency/README.md` § "Promote". This file owns the HTTP ladder, the error mapping and the audit row.

- **Ladder, each rung decided before any write.** 503 `concurrency_promote_unconfigured` (nil `Config.Concurrency` or `RunRepo` — without the run repo `requireStageAccount` cannot resolve the account, so the verb refuses rather than run untenanted); 401 `authentication_required`; 403 `run_token_forbidden` (`runBoundTokenRunID`, even for the token's own run — reordering a queue is an operator action); 403 `insufficient_scope` (`id.TokenID != "" && !hasScope(id, "write:runs")`, the `review_rerun.go` shape); 400 `validation_failed` (non-UUID `stage_id`; a body that is not exactly one `{"reason": string}` object; a reason empty after `TrimSpace` or over 1000 bytes). Route tier: `requireStageAccount(memberWrite, …)`, the sibling `/v0/stages` operator controls' (retry, fixup).
- **Strict body decoder (approval condition 2).** `parsePromoteBody` uses its OWN `json.Decoder` with `DisallowUnknownFields` plus a trailing-document check, NOT `decodeSingleJSONBody`, which accepts unknown keys. `{"reason":"x","unexpected":true}` is 400.
- **Delegated operator-agent tokens are ADMITTED**, unlike `review_rerun.go` (which refuses `operator_agent_forbidden`). This is an operational ordering control like dispatch and retry, not an approval; the audit row records `actor` and `actor_kind` (`agent`). Pinned by `TestPromoteQueuedStage_OperatorAgentAdmitted`, so a later tightening is deliberate.
- **Store error mapping.** `run.ErrNotFound` → 404 `stage_not_found`; `concurrency.ErrSlotHeld` → 409 `concurrency_slot_held` (holders are never preempted); `ErrNotQueued` → 409 `concurrency_slot_not_queued`; `ErrWaiterNotLive` → 409 `concurrency_waiter_not_live` (the message tells the operator to re-dispatch first, which re-queues at the tail, then promote); `ErrSlotChanged` → 409 `concurrency_slot_changed`; anything else → 500 `concurrency_promote_failed`, its cause carried only through `internalCauseKey` (the store's transaction rolled back, so nothing changed).
- **Atomic audit.** The handler passes `concurrency.PromoteRequest.Record`, which the store calls INSIDE the promotion transaction after writing `order_key`. It appends `stage_concurrency_promoted` `{stage_id, run_id, group, limit, old_position, new_position, reason, actor}` (actor_kind from `actorKindForSubject`, actor_subject the caller) through `(*Server).promoteAuditAppend` — `audit.AppendChainedTx` in production, or the test-only `promoteAuditAppendOverride` seam on `Server`. A failed append returns an error from `Record`, so the promotion rolls back and the caller sees 500. Lock order is the store's: group lock → stage row → slot row → run row (the append's `LockRunForUpdate`). Unlike `stage_concurrency_queued` / `_admitted` (post-commit, best-effort), the promoted row is never skipped: no promotion commits unaudited.
- **Response.** 200 `{stage_id, run_id, group, limit, promoted, old_position, new_position, holders, audit_sequence}`; a stage already first is `promoted:false` with no `audit_sequence` and nothing written (the store does not call `Record`).
- **Read surface.** `stageConcurrency.Promoted` (`promoted,omitempty`) mirrors `concurrency.Status.Promoted` on the queued arm only; `position` already reflects the new order with no read-path change.
- **Not the merge queue.** This verb never touches `backend/internal/mergequeue`; ADR-093 D7's `merge_queue_promoted` belongs to #4297's own verb.
- **Tests** (`stage_concurrency_promote_test.go`, the `newSCPG` real-Postgres harness): the cross-layer case (handler → store → Postgres → audit → stage reads → host-dispatch marker), one case per auth/body rung and per store refusal (each reads back `order_key` NULL and zero audit rows), the injected append failure (500 and `order_key` read back NULL), the operator-agent admission, the no-op, a mux-level route check, and the OpenAPI assertion for the path and `StageConcurrency.promoted`.

## Stage terminal-wait long-poll (#1252, E24.X)

The SDK-independent REST analogue of the scope-amendment `?wait` long-poll, applied to stage settledness so a DETACHED operator-side watcher (a backgrounded shell poll) has ONE authoritative completion signal.

`GET /v0/runs/{run_id}/stages/{stage_id}` (`run_stage_wait.go::handleGetRunStage`) resolves a stage by the durable ADR-037 `(run_id, stage_id)` handle and returns the canonical `Stage` shape plus a wait envelope (`state`, `terminal`, optional `next_action`).

- `terminal` is keyed off the `run.StageState.IsSettled()` classifier (`backend/internal/run/run.go`) — true for the three terminal states (`succeeded`/`failed`/`cancelled`) AND the parked states (`awaiting_approval`/`awaiting_children`/`awaiting_input`/`awaiting_scope_decision`/`awaiting_deploy_approval`/`awaiting_host_dispatch`), false for the in-flight states (`pending`/`dispatched`/`running`/`awaiting_deployment`). `awaiting_host_dispatch` (#1912) is settled — a runner_kind-locked-`local` agent stage parked for a host/operator spawn, released by the host-dispatch marker. `IsTerminal()` is left UNTOUCHED for its narrower transition-table callers.
- Optional `?wait=<0..30>` (`parseRunStageWaitSeconds`, clamped) holds the connection via `awaitStageSettled` — a `time.After(deadline)` / `time.NewTicker(runStageWaitPollInterval)` / `r.Context().Done()` select modeled byte-for-byte on `awaitScopeAmendmentDecision` — returning the moment the stage settles, at the cap (last-read still-unsettled stage), or on client disconnect. A transient re-read error returns the last-good stage at 200 (never a 500).
- Auth mirrors `handleListScopeAmendments`: anonymous → 401; a run-bound `fhm_` token needs `mcp:read` (else 403 `insufficient_scope`) AND must match the path run (else 403 `cross_run_stage`); operator bearers pass. A stage whose `RunID` != the path run is 404 `stage_not_found` (handle consistency).
- `next_action` reuses `applyDriveSurfaces` (`runs.go`) — best-effort, omitted for non-drive/terminal runs, never fabricated.
- Composes existing repo reads only (`RunRepo.GetStage`/`GetRun`, `AuditRepo.ListForRunByCategory`); no orchestration/runner/MCP-tool contract change.
- Companion to the `dispatch_stage` durable non-blocking dispatch work (#1232) that will make the single-session in-band decision native.

## Runner terminal-failure self-report on reap-failure (`reap_failure.go`, E45.73 / #3598)

`POST /v0/runs/{run_id}/stages/{stage_id}/reap-failure` gains a second caller: the runner itself, when a terminal signed-egress upload (the trace upload that would otherwise settle the stage) is what failed, so the stage no longer sits `running` behind a dead process until the dispatch watchdog.

- **Entitlement switch (mirrors `handleFileProductReport`, #1274).** Anonymous → 401 first. A run-bound `fhm_` token (`runBoundTokenRunID`) for ANOTHER run → 403 `run_not_entitled`; for ITS OWN run → admitted WITHOUT `write:runs` (run-bound tokens carry `mcp:read`, never `write:runs`); any other bearer keeps the `write:runs` requirement (403 `insufficient_scope`); an empty-`TokenID` cookie session is admitted. The route stays `requireRunAccount(adminWrite, …)`: `enforceAccount` role-bounds only a resolved OAuth cookie, so a bearer is governed by ownership plus this switch. Nothing is tightened — the auth-change impact inventory is empty.
- **Both pins are REQUIRED on the run-bound arm.** `expected_state` (400 `expected_state_required`) and `expected_attempt` (400 `expected_attempt_required`), the latter decoded as `json.RawMessage` with the same absent/null/empty three-state discipline as `expected_state` (`validateReapExpectedAttempt`). WHY a state pin alone is insufficient: a retried attempt is ALSO `running`, so attempt A's late report satisfies `expected_state=running` against attempt B.
- **The attempt identity** is `run.StageAttemptToken(stage.DispatchedAt)` — migration 0072's trigger re-stamps `dispatched_at` on every transition INTO `dispatched`. The prompt envelope echoes it as `stage_attempt`; the runner sends it back verbatim; it is compared only as an opaque string rendered by that one helper (no cross-clock comparison, #3048).
- **The control is the in-transaction predicate, not the pre-check.** With an attempt pin, `failStageForReap` routes EVERY write of the walk (both `dispatched → running` and `→ failed`) through `run.StageAttemptCASTransitioner.TransitionStageFromAttempt`, which compares state and attempt against ONE row-locked read inside the write's own transaction. A `StageAttemptChangedError` → 409 `stage_attempt_superseded` (`details {stage_id, expected_attempt, actual_attempt}`), no audit, no advance. The handler ALSO compares the pin against its loaded row, answering the byte-identical 409 — a FAST PATH only: the load and the write are separate reads, and a full running(A) → failed → retry → pending → dispatched → running(B) cycle between them satisfies a state-only predicate. Deleting the pre-check leaves behaviour identical (`TestReapStageFailure_RunBoundStaleAttemptAfterRetryRefused` stays green); reverting the predicate to state-only reddens `TestReapStageFailure_RunBoundReDispatchBetweenLoadAndWriteRefused`, whose repo wrapper re-dispatches between the load and the write.
- **Capability absent → loud refusal.** A repo that implements `StageCASTransitioner` but not the attempt sibling makes an attempt-pinned reap return `errReapRepoNotAttemptCAS` → 503 `attempt_pinned_reap_unsupported`, nothing transitioned — never a degrade to a state-only write. An EMPTY pin never probes for the capability, so the detached reaper's and `run_children`'s unconditional walk is byte-for-byte unchanged. Unreachable against postgres (compile-time assertion in `run/postgres.go`).
- **Audit provenance, run-bound arm only.** The `dispatch_reaper_failed` payload adds `reported_by: "runner"` and `reported_attempt` (the accepted token) — derived from the verified identity and the verified precondition, never a caller field — and NOT in the shared `reapFailureAuditPayload`, so the operator payload key set (`_UnconditionalAuditPayloadKeySet`) is unchanged.
- **Why the category is reused.** `dispatch_reaper_failed` with category C is what the fix-up delivered-nothing refund (#1957) and its mcpserver `review_action_hint` mirror union on; a new category would be invisible to both.
- **Wire contract.** `reapFailureRequest` ↔ the runner's `upload.reapFailureRequestBody` is the `reap_failure_request` `ModeExact` pair in `backend/internal/wirecontract` (tag parity holds across the `json.RawMessage`/`string` type asymmetry), and the shared golden `testdata/wire/reap_failure_self_report.json` is read by the prompt-envelope test, the end-to-end handler test and the runner's client test.

## Verify-failure (reverify) held-commit resume (`prompt.go` / `pullrequest.go`, E83.80 / [#4190](https://github.com/kuhlman-labs/fishhawk/issues/4190))

A verify failure after a SUCCESSFUL implement agent pass used to discard the agent's work: the retry re-ran the whole agent. The runner now pins the last `verify_run` head (the throwaway `fishhawk verify wip` commit) at `refs/fishhawk/checkpoints/<run>/<stage>-verify` when it is the agent pass's own change (no fix-iteration edit, no scope fold), and a standalone open-PR stage whose committed gate failed category C reports it as a third held-commit resume kind, `reverify`. The backend half is a sibling of the #3621 push resume, and every decision mirrors that kind's.

- **Recording (`pullrequest.go`).** A `/pull-request` failure report with `resume_kind: "reverify"` records `{branch, head_sha, base_sha}` (+ the optional agent PR text) under its OWN audit category, `verify_resume_checkpoint` (`CategoryVerifyResumeCheckpoint`), appended AFTER `pull_request_failed` so it wins newest-wins — and ONLY when the report newly fails the stage category C (`newlyFailedC`: the handler-loaded state is not `failed` and `FailStage` succeeded). A stage the trace upload already failed (a category-B policy violation or gating-review reject), a category-B report, or a `FailStage` error records nothing, so a later override retry is never served a rejected tree. The loaded state decides because `FailStage` on an already-failed stage is a same-state no-op that returns nil. `recordPushResumeCheckpoint` is generalized over `(category, kind)`; the push call's payload is byte-identical. A reverify checkpoint records NO `verified_tree_sha`, even when the report sends one: the held tree is the one that FAILED verify, and a recorded tree would be named as "verified" by any later `verified_tree_discarded` row. The empty-kind allow-list on the `pull_request_failed` payload is unchanged, so `reverify` can never be laundered into a `pr_open` `push_checkpoint`.
- **Rollback property.** Same as `push_resume_checkpoint`: a backend that predates the category never queries it, so a reverted resolver sees only a checkpoint-less `pull_request_failed` and the retry is a full agent re-run. An OLD backend receiving `resume_kind: reverify` records nothing (the allow-list skips it and the post-append switch has no default).
- **Resolution (`prompt.go`).** `newestPushCheckpoint` walks the category as a carrier AND an invalidator (`pushCheckpointCategories`) and derives `resumeKindReverify` from the category alone. `resolvePushCheckpointResume` serves it as `held_commit_resume_kind: reverify` with the held coordinates and PR text and NO `held_commit_verified_tree_sha`. TOTAL DECLINES (no held-commit fields; the retry is an ordinary agent re-run): no `reverify-resume` token in `X-Fishhawk-Runner-Capabilities` → `runner_capability_absent`; a decomposition child → `child_resume_kind_unsupported` (the runner never arms reverify for a child, and its consume arm ends in the standalone PR-open tail); a fix-up dispatch → refused by the existing `fixup` guard. With no recorded tree, a decline writes no `verified_tree_discarded` row.
- **Retry.** `retryStageAs`' keep-concerns decision reads `newestPushCheckpoint`, so a resumable reverify checkpoint keeps the prior round's implement-review concerns exactly like a push one (the optimistic #3621 rule: if the dispatch later falls back to an agent pass, the concerns are stale and get waived).
- **Not an activity category.** `verify_resume_checkpoint` is registered in `backend/internal/audit/categories.go` and deliberately NOT in `issuecomment`'s `activityCategories`, like `push_resume_checkpoint`.
- **Wire.** `resumeKindReverify = "reverify"`, `capabilityReverifyResume = "reverify-resume"` and the category are pinned by `TestResumeKindWireValues` against the same literals the runner's twin test pins; the full capability header a current runner sends is `push-resume,merge-candidate-verify,child-push-resume,reverify-resume`. The shared golden `testdata/wire/reverify_failure_report.json` is the runner-marshalled failure body: the backend posts it through the real handler (`TestShipPullRequest_FailedReverifyRecordsVerifyResumeCheckpoint`, and the handler → audit → resolver crossing `TestReverifyCheckpoint_FailureReportThenPromptServes`), the runner asserts its marshalled body equals it. No struct field is added on either side, so `wirecontract` gains no row.

## Stage progress heartbeat ingest (`stage_progress.go`, E48.96 / #2541)

`POST /v0/runs/{run_id}/stages/{stage_id}/progress` (`handleReportStageProgress`) projects the runner's mid-execution `stage_progress` heartbeat onto the stage row so an operator poll returns `last_event` / `turns_this_attempt` / `tokens_this_attempt` (via the `Stage.progress` field, and the derived `elapsed_seconds` on the MCP stage-wait status) instead of a single `running` bit.

- **Tier + own-run entitlement (#4483).** Registered at `memberWrite` on the byte-identical path shape as the sibling host-dispatch route; the tier bounds the tenant account only. `authorizeStageProgress` then runs right after `run_id` parses, before `stage_id` parsing and the body decode: a run-bound `mcp:run:<uuid>` token (the runner's heartbeat bearer, `mcp:read` only) is admitted when its run equals the path `run_id` and refused 403 `run_not_entitled` (`details.run_id`) otherwise; every other caller goes through `requireWriteScope("write:runs")` (anonymous 401, a bearer without `write:runs` 403 `insufficient_scope`, a cookie session admitted). **No new token capability is introduced**: `runner/internal/upload`'s `ReportStageProgress` already sends the `fhm_` token minted for its own run. Tests: `TestReportStageProgress_ForeignRunBoundToken_Refused`, `_ReadOnlyToken_Refused`, `_Anonymous_Unauthorized` (each reads the stage's committed progress back) and `_WriteRunsOperator_Admitted`; the mux-driven suite carries the run's own run-bound bearer through the real `bearerAuth`.
- **Consumer-side narrow capability.** The handler type-asserts `s.cfg.RunRepo` for `stageProgressStore` (the `runCostRecorder` / `runnerKindResolver` precedent); a RunRepo that does not implement it answers `503 progress_unsupported` rather than panicking. `run.StageProgressStore` is the concrete-repo capability it mirrors.
- **Input validation.** `run_id`/`stage_id` are parsed as UUIDs (400 `validation_failed`); the body is decoded with `DisallowUnknownFields` (an unknown field → 400); a negative `turns_this_attempt`/`tokens_this_attempt` → 400; the optional #4023 phase fields are checked by `validateProgressPhase` right after the counters and before the stage lookup — a `phase` other than empty / `agent` / `gate`, or a negative `phase_elapsed_seconds` / `gate_budget_seconds` / `gate_remaining_seconds`, → 400 `validation_failed` with `details.field` naming it; `last_event` is CLAMPED to `progressLastEventMaxLen = 128` runes; `reported_at` is NOT read from the body at all — the ingest UPDATE stamps it from the DATABASE clock (`jsonb_set(..., to_jsonb(now()))`, #3084), so the runner cannot set it and the backend process contributes no timestamp either.
- **Phase fields + wire contract (#4023).** `stageProgressReport` carries `phase`, `phase_elapsed_seconds`, `gate_budget_seconds`, `gate_remaining_seconds` and `gate_verifying`, all `omitempty`, mapped one-for-one onto `run.StageProgress` and served back on the stage read (`reads.go` `stageProgress`, omitempty, so a phase-less row serves the pre-#4023 shape). The struct is the consumer of the `stage_progress_report` ModeExact pair in `backend/internal/wirecontract` (emitter: the runner's `reportStageProgressBody`), and the gate-phase bytes are the shared golden `testdata/wire/stage_progress_phase.json`, which the runner asserts its marshalled body against and `TestReportStageProgress_GatePhaseGoldenPersisted` POSTs through the real mux. Version skew: an OLD fishhawkd 400s a phase-bearing heartbeat under `DisallowUnknownFields`; the runner's reporter logs and drops it, so only the display is lost. Tests: `TestReportStageProgress_InvalidPhaseRejected`, `_NegativePhaseElapsedRejected`, `_NegativeGateBudgetRejected`, `_NegativeGateRemainingRejected` (each reads the seeded progress back unchanged), `_AgentPhaseAccepted`, and `TestGetStage_ProgressCarriesPhaseFields` (raw read bytes).
- **The 409 `stage_terminal` refusal IS the UPDATE's own `WHERE state NOT IN (...)` predicate** (`RecordStageProgress`, `:execrows`): a heartbeat that arrives after the stage settled matches zero rows (`applied=false`) and is answered 409 with `details {stage_id, state}` — no read-then-write window (#2536). Success is `204 No Content` (the reader is the stage read). The stage-belongs-to-run handle is verified (404 `stage_not_found` on mismatch), mirroring host-dispatch.
- **`updated_at` side effect (condition 4).** The heartbeat UPDATE bumps `stages.updated_at` every ~15s via the `stages_set_updated_at` trigger. The one consumer that observes it is the dispatch watchdog (`state='dispatched'`, which a stage holds during agent execution); the audit + the design-question note live in `run/README.md` and migration 0070.

## Fix-up concern delivery: route-time fit + id pairing (#4284)

The fix-up prompt carries EVERY routed concern. Before #4284 the renderer packed the operator concern and every routed note into one 4000-byte block and tail-dropped the rest, so a pass could mark a concern `addressed_pending` that the agent never saw (run `ea938249` lost the operator's liveness concern, run `1f4c218c` the executor items). The renderer now never drops a list item (`backend/internal/prompt/README.md`, `MaxFixupConcernBytes = 12000`); the server side is three pieces.

- **One mapping (`prompt.go::fixupPromptConcerns`).** The prompt-serve resolver and the route-time check map `[]planreview.Concern` onto `[]prompt.FixupConcern` through the same helper: `Text = fixupConcernLine(c)`, `AcceptanceDerived` from the acceptance provenance, `Operator` for an `operator`-category concern that is not acceptance-derived (rendered first and never trimmed). The server's `selected` order and the audit `concerns` array are never reordered — the operator-first partition happens inside the renderer.
- **Id pairing (`resolveFixupConcerns`).** The newest stage-bound `stage_fixup_triggered` payload's `concern_ids[i]` is stamped on `concerns[i]` ONLY when the two arrays have the same length — the rule `resolveRoutedFixupConcerns` already applies. The HTTP `concern_ids` path (with or without a minted operator concern) and auto-drive are length-matched, so each concern renders as `(concern <id>) [sev/cat] …`. The deferred-acceptance release (id-less acceptance concerns beside id'd review concerns), a degraded operator-concern mint, the positional path and merge-candidate are not, and render every concern id-less rather than under a misattributed id.
- **Route-time fit (`fixup.go::fixupStageAs`, before `run.FixupStage`).** `fixupRouteFit` renders the pass's concerns with the REAL renderer (`prompt.FixupConcernsFit`), with `prompt.FixupConcernIDPlaceholder` (36 bytes) on every concern: the operator concern's id is minted only after the transition, and a block never shrinks as an id grows, so a set that fits here fits at serve time. When the trusted block cannot fit even at its minimum (every summary line, operator concerns in full), `fixupStageAs` returns `*fixupConcernsOverflowError`. Because the check precedes the transition, a refusal spends no pass, writes no `stage_fixup_triggered` entry, mints no operator concern and marks nothing `addressed_pending` — a concern the agent cannot see can no longer be recorded as routed. The HTTP handler maps it to **422 `fixup_concerns_overflow`** (details `bytes`, `max_bytes`, `overflow_bytes`, `concern_count`, `concern_ids` bounded at `maxOverflowDetailConcernIDs = 50`, `remedy`); the auto-drive `route_fixup` arm maps it to `DecisionRequired` / `DecisionState: "fixup_concerns_overflow"`, mirroring the #2091 budget/ceiling arms; merge-candidate logs the refusal like any other route refusal.
- **Acceptance exemption (#4284 C9).** Acceptance triage must not newly page. Acceptance-derived concerns are not measured for the refusal (the trusted-block fit excludes them), and an acceptance triage pass (`FixupOptions.AcceptanceStageID` set — `routeAcceptanceFixupPass`, both its immediate route and the deferred release that folds review concerns in) is never refused: the no-drop renderer lists every concern even past the budget.
- **Truncation record (#4284 C4).** An ADMITTED pass whose note bodies the fit trimmed records `concern_bodies_truncated: true` and `truncated_concern_ids` on its `stage_fixup_triggered` entry (both keys absent otherwise, so other payloads stay byte-identical). The list comes from the same route-time fit over both blocks. It is a CONSERVATIVE SUPERSET: the fit renders with the longest id the serve-time render can carry, and when the routed ids do not pair with the concerns by position every caller-routed id is listed if any reviewer concern was trimmed (`fixupTruncatedConcernIDs`). It may be empty when only id-less (acceptance) concerns were trimmed. The minted operator id is never listed — an operator concern is never trimmed.
- **Cap relationship.** `maxOperatorConcernBytes` (4000, the 400 cap on `operator_concern` / `operator_evidence`) no longer mirrors the renderer cap; it must stay AT MOST `prompt.MaxFixupConcernBytes` so a lone operator concern always fits — pinned by `TestFixupStage_OperatorConcernCapWithinRendererBudget`.

## Fix-up delivered-nothing refund — one chokepoint (#3085)

`fixup.go::fixupRefundedPasses(ctx, runID, stageID) (refunded, crashedWithoutPush int, err error)` is the SINGLE derivation behind the fix-up budget refund. It replaces the earlier `countFixupNoChangeRefunds` + `countFixupInfraRefunds` pair, whose independently **summed** counts double-counted a window holding more than one delivered-nothing signal, and it is called by BOTH `handleFixupStage` and the in-process campaign auto-driver (`autodrive.go::autoFixup`) so the two cannot disagree — the auto-driver previously counted only the #967 no-change refund and so already diverged from the HTTP handler by missing the #1957 category-C refund entirely.

- **One question per window, not a sum.** Each `stage_fixup_triggered` entry opens a window `(trigger[i].Sequence, trigger[i+1].Sequence)` — open-ended (`math.MaxInt64`) for the newest. Exactly one question is asked per window: does it hold at least one DELIVERED-NOTHING signal and **no** `fixup_pushed` entry? A window refunds **at most once** however many signals of however many kinds land inside it. Window matching is STRICT on both sides (`sig > lo && sig < hi`), so a signal sequenced before the first trigger — an original-dispatch death, not a fix-up — matches no window.
- **Four unioned signal shapes.** `fixup_no_changes` (#967 — the re-dispatch produced no commit; **not** a crash, the agent ran); `dispatch_reaper_failed` with `failure_category` `C` (#1957 — the #1747 pre-agent spawn-phase reaper death); `stage_fixup_recovered` with `source_failure_category` `C` (#1957 — the #788 post-agent-work death on the push/report); and `stage_fixup_recovered` with `source_failure_category` **`A`** (#3085 — the harness death: a 400, a zero-token hang). Category **B** (policy) still consumes a pass: it is a verdict on delivered work, not a delivery failure.
- **Push veto, applied UNIFORMLY — a deliberate behaviour correction, not a refactor side effect.** A window holding a `fixup_pushed` entry contributes nothing: that pass DID land a commit and a later death does not undo the push. `countFixupInfraRefunds` documented exactly this invariant ("a category-C death that landed no commit on the PR branch") but never read `fixup_pushed` at all, so it did not enforce what it documented. **A category-C pass that pushed and then died now CONSUMES budget where it previously did not** — a real tightening of an operator-visible limit, pinned by its own test (`TestFixupStage_InfraRefund_CategoryCAfterPushNotRefunded`), not left incidental.
- **`crashed_without_push`** counts the refunding windows whose delivered-nothing signal was a **death** (category A or category C), and deliberately EXCLUDES a window that refunded only on `fixup_no_changes` — that pass did not crash, the agent ran and produced nothing. It rides the `422 fixup_budget_exhausted` details alongside `max_passes`, `used` and `refunded_passes`, so an operator reaching for `force_additional_pass` can see whether they are overriding a real limit or a crash. The zero case is pinned by `TestFixupStage_BudgetExhaustedDetailsNameCrashedWithoutPush`.
- **Every read FAILS CLOSED.** All five audit reads (`stage_fixup_triggered`, `fixup_no_changes`, `dispatch_reaper_failed`, `stage_fixup_recovered`, `fixup_pushed`) return a wrapped error → `500 internal_error` with NO state transition and NO `stage_fixup_triggered` entry. A read failure must never silently produce a smaller refund (wrongly refusing an admissible pass) or a smaller veto set (wrongly admitting one); the `fixup_pushed` read runs unconditionally rather than behind a no-signal early return for exactly that reason. Per-entry `StageID` double-checks keep another stage's signal out, and an entry whose payload fails to unmarshal is SKIPPED (never counted). One test per named read/skip branch (`TestFixupStage_RefundReadErrorsFailClosed`, `TestFixupStage_RefundSignalSkipBranches`).
- **A refund credits the HARD CEILING too, bounded (#3335).** `MaxPasses` is `defaultMaxFixupPasses + refunded`, and the ceiling comparison is now credited: the handler passes `FixupOptions.CeilingRefundedPasses = min(refunded, maxCeilingRefundCredits)` so `run.FixupStage` compares `priorPasses - credit >= HardCeiling`. The runaway-cost guard `maxCeilingRefundCredits = 3` keeps the **absolute** cap at `defaultFixupCeiling + maxCeilingRefundCredits = 6` triggered passes, so a pathologically crashing agent can never loop unbounded, while two harness loop-detector kills that pushed nothing no longer exhaust a run's whole remediation budget (the run-26663b11 strand). Three triggers with three refunding windows are now ADMITTED (`TestFixupStage_CrashRefundCreditsRawCeiling` / `TestFixupStage_InfraRefundCreditsCeiling`); the cap still refuses at seven (`TestFixupStage_CeilingRefundCreditsAreCapped`). Both 422s (`fixup_ceiling_reached`, `fixup_budget_exhausted`) and the `stage_fixup_triggered` receipt carry `ceiling_refunded_passes` + `remaining_ceiling_slots`. The push veto survives the credit — a pushed-then-crashed pass credits neither budget nor ceiling (`TestFixupStage_PushedThenCrashedStillConsumesCeiling`). `maxCeilingRefundCredits` is a single named constant here and mirrored in `mcpserver.maxCeilingRefundCredits` (RATIFIED POLICY NUMBER, KEEP IN SYNC).
- **The MCP `review_action_hint` mirrors the SAME single unioned per-window evaluation** (`mcpserver/review_action_hint.go::fixupRefundedPasses`), so `remaining_fixup_budget` / `override_available` agree with the backend's admit decision. A mirror that double-counts where the backend does not is worse than no mirror.

## Fix-up delivered-nothing round closure (#3395)

A fix-up trigger writes NO `implement_review_started` entry — the "round" it opens is purely the floor `mcpserver.reviewStatusFor` applies at the trigger's sequence (#894). So a pass that died having pushed nothing left the prior round's real verdicts BELOW that floor: `implement_review_status` read `pending` with `reviews:[]` forever, `await_review` held, `reconcile_reviews` (correctly) found no server-side round to synthesize, and the routed concerns sat in `addressed_pending` looking addressed. The recovery already restores two states; the orphaned round is the third, so `fixup.go::maybeRecoverFixupFailure` closes it AFTER `run.RestoreFixupStage` commits — every step best-effort (WARN + continue), the return value unchanged (true iff the restore landed).

- **Delivered-nothing decision** (`fixupDeliveredNothing`): true iff NO `fixup_pushed` entry for the stage is sequenced after the recovered trigger — the IDENTICAL push veto `fixupRefundedPasses` applies per window, so the refund, the MCP marker and the round closure can never disagree about whether a pass delivered. A pass that pushed and THEN died keeps its trigger as the floor (the pushed head's re-review round governs) and keeps its concerns `addressed_pending`. A `fixup_pushed` read failure leaves the decision UNDECIDED: the key is omitted and nothing else runs (fail toward pre-#3395 behaviour, never a guess).
- **Concern reopen** (`reopenRoutedConcernsAfterDeliveredNothing`): the trigger payload's `concern_ids` still in `addressed_pending` are rolled back to the existing open state `reopened` (the state machine has `addressed_pending → reopened`; no `→ raised` edge, and `reopened` already means "open again after a fix-up round" and is routable) via `ConcernRepo.ApplyResolution`, with a `state_reason` naming the pass ordinal, source failure category/reason and "re-opened, not addressed". The reason is UNTRUSTED (produced while an agent ran commands against an untrusted repository) and `state_reason` travels with the row onto the gate view and issue-comment surfaces, so `fixupRecoveryReasonLabel` runs it through `neutralizeUntrustedFixupText` — a byte-for-byte duplicate of `mcpserver.neutralizeUntrustedFailureText` (control characters → single spaces; runs of 3+ `<`/`>`/`` ` ``/`~` run-split into pairs, so no live `<<<…>>>` delimiter or fence can survive) — BEFORE the 200-byte `truncate`, never length-bounded alone (`TestMaybeRecoverFixupFailure_ReopenReasonIsStructureNeutralized` drives a crafted reason end to end and asserts on the committed row). Rows in any other state (waived / deferred / addressed during the pass) are untouched. Per-row failures WARN and continue.
- **Three new payload keys on `stage_fixup_recovered`:** `delivered_nothing` (bool; present only when the push read succeeded), `reopened_concern_ids` (present only when non-empty) and `concern_reopen_error` (present only when the reopen could not be ATTEMPTED — no concern store while ids were routed — or partially failed; names each failure). The third key is what lets a reader tell "no concern needed reopening" from "reopening did not happen": an empty `reopened_concern_ids` is NEVER a clean-ledger claim while `concern_reopen_error` is set, and the MCP `fixup_recovery` marker renders the two distinctly (`mcpserver/fixup_recovery_surface.go::fixupRoundClosureSentence`). An empty `concern_ids` list with no store is a CLEAN outcome (nothing to reopen), not an error.
- **Reconcile reporting reorder** (`review_reconcile.go`): the round's landed-terminal count now runs BEFORE the boot-marker gate, so `round_already_settled` takes precedence over `review_dispatched_by_this_process` and `landed_before` is real on every skip past the anchor checks (it always reported 0 on an in-flight skip, which the #3395 report read as "the round is genuinely empty"). Synthesis behaviour is unchanged; `TestReconcileRunReviews_Endpoint_RefusesLiveRound` is the pin.
- **Gate view** (`gateview.go`): `stage_fixup_recovered` joins as a third fix-up outcome `recovered` so a delivered-nothing pass stops rendering `pending` forever; only the entry's sequence/stage are read (a malformed payload cannot hide it), and `earliestOutcomeAfter` still lets a `fixup_pushed` that precedes the recovery win as `pushed`.
- Tests: `TestMaybeRecoverFixupFailure_DeliveredNothing_ReopensRoutedConcerns` / `_PushedPass_KeepsConcernsAddressedPending` / `_PushBeforeTriggerStillDeliveredNothing` / `_PushedReadError_OmitsDeliveredNothing` / `_NilConcernRepo_StillStampsDeliveredNothing` / `_ApplyResolutionError_ContinuesBestEffort` / `_NoRoutedConcerns_NoReopenError` (one per branch), `TestReconcileStageOrphanedReviews_SkipReasons` (the two after-boot rows), `TestGateView_FixupJoin_RecoveredOutcome`, and end to end over real Postgres + the real `fishhawk-mcp` binary `TestE2E_Fixup_FailedRedispatchRestoresReviewGate` / `TestE2E_Fixup_DeliveredNothingRecoveryReopensConcern` (`integration/mcp/fixup_test.go`).

## Fix-up re-review backstop (#1932)

Post-fix-up implement re-review is dispatched from `succeedFixupPushStage`'s path (`trace.go::maybeBackstopFixupReReview`) against the PUSHED head. **Since #2884 this is the PRIMARY path, not a backstop:** `trace.go::advanceStageAfterTrace` now SKIPS the trace-time review hook (the `#793` raw-variant gate) for any `push_fixup` manifest. That hook keyed on `bundle.ExtractHeadSHA` — the throwaway `fishhawk verify wip` verify sha, which the fix-up ships BEFORE the push and which may never reach the branch. On run 8ae65577 (PR #2883) it certified fixes against that orphan sha: `implement_review_started` recorded the verify sha, the review read the fixed code from the dangling commit, and the concern ledger marked all three routed concerns `addressed` — while the PR head carried none of it. Sourcing the re-review diff from `ComparePatch(base, pushedHead)` — the commit the PR will merge — is the fix. A manifest read error leaves the old trace-time dispatch (an older bundle without the flag is indistinguishable from a non-fix-up one; over-reviewing is the safe direction).

**Accepted consequence (#2884 condition 2): a fix-up stage no longer has a trace-time GATING-reject path.** `runImplementReviews` returns "gating reject" only when reviewers reject AND `human == 0`, which the trace handler turns into a category-B stage failure. The push-report path deliberately IGNORES that return (the stage is terminal/restored at push-report time, so there is no in-flight transition to fail — the `#1932` rationale). So suppressing the trace-time dispatch removes the only path by which a rejecting fix-up re-review could FAIL the stage under a spec with zero human approvers on implement. **Every implement stage in this repo declares `reviewers: agents:[…] human: 1`** (`.fishhawk/workflows.yaml` and all three `backend/internal/spec/presets/workflow-preset-*.yaml`), so agent reviewers are ADVISORY and the practical regression is NIL here — this is a real semantic change only for a hypothetical spec with zero human approvers on implement. The protection that holds in an advisory-reviewer deployment is that a rejecting re-review still leaves its concerns OPEN, so they surface at the operator's merge gate (pinned by `TestImplementReviewLoop_AdvisoryReject_LeavesConcernOpenForMergeGate`: a rejecting advisory review's raised concern stays in an `IsOpen()` state that `ListOpenByRun` — the merge gate's source — returns). The trace-time dispatch is NOT preserved as a fallback: it read the wrong artifact, so it is not a safety property worth keeping.

**Ledger provenance (#2884 control 3).** `applyConcernResolutions` stamps the reviewed head sha into a `confirmed` resolution's `state_reason` — that function's only writer of `StateAddressed` (since E45.84 / #3619 the clean-round auto-close is a second writer, and it appends the byte-identical suffix, so both closing paths speak one provenance vocabulary) — as a ` [verified at <headSHA>]` suffix (`applyRoundConcernResolutions` threads the head through from `runImplementReviewInvocations`). So when a future review reads a head that has diverged from the PR head, the divergence is visible IN THE LEDGER instead of requiring a hand diff of the PR head against the ledger's claims (the manual detection path that surfaced #2884). An empty head passes the reason through byte-identical; `reopened`/`superseded` are never stamped.

- **Why a second path (the run-1-vs-run-3 distinction).** The trace-time hook only runs when control reaches the review block. On the observed wedge (run 98020210, audit seq 34408–34418) the retried fix-up's raw trace failed backend **policy re-evaluation as category-B** — the bundle diff spanned 79 files against `max_files_changed: 45`, a **stale-base diff** — so the handler routed to `failStageCategoryB` and never reached the hook. `#788` fix-up recovery then restored the implement stage to `succeeded` (`stage_fixup_recovered`), and the later `fixup_pushed` report (new head `5d33d25f`) recorded the head with **nothing re-arming the review**, so `implement_review_status` stayed `pending` forever and the `fishhawk_audit_complete` merge gate wedged. A DIFFERENT run whose fix-up raw trace passed policy re-eval fired the trace-time hook normally and never wedged — the category-B-on-stale-base-diff is the whole difference. The separate runner-side stale-base-diff defect (the spurious policy violation) is out of scope here; the backstop makes the re-review contract robust to ANY trace-time miss, whatever its cause.
- **Trigger.** `fixup_pushed` report with no `implement_review_started` entry for the new head (`implementReviewAlreadyStarted(started, stage.ID, headSHA)` false).
- **Four skip modes**, each fail-closed to no-second-review (a double dispatch is the worse failure — 2× cost, divergent verdicts, `#777` hint over-fire): (a) nil `AuditRepo` (started ledger unreadable — a list error skips too); (b) an `implement_review_started` entry already exists for `(stage, new head)` — the normal path where the trace-time hook already dispatched, so the backstop is a no-op and review cost is unchanged; (c) the NEWEST `implement_review_started` for the stage carries an empty `head_sha` (`newestImplementReviewStartedHead`) — an unkeyed prior round is indistinguishable from a missed one, WARN-logged; (d) GitHub client / run installation not wired (CLI/dev posture). When NO started entry exists for the stage the trace-time hook never fired at all, so the backstop proceeds (a genuine miss).
- **Delta diff source.** `githubclient.ComparePatch(base_sha, head_sha)` where `base_sha` is the `fixup_pushed` report's base (the branch head the fix-up committed onto), so the compare result IS the fix-up delta — coherent with the `#1725` delta re-review framing — mapped through `consolidatedReviewDiff`. It reuses the existing `implement_review_started` audit kind via `emitReviewStarted` inside `runImplementReviews` (NO new audit or comment surface). The backstop review carries `gateEvidence=nil` — the PR-report path has no bundle in hand, and the failed attempt's trace-time evidence would be misleading (it described a bundle that failed policy re-evaluation); nil is the documented byte-identical omit case in `prompt.Build`.
- **Dispatch shape.** Detached, shutdown-tracked goroutine (`context.WithoutCancel` + `s.bgReviews`), mirroring `DispatchConsolidatedReview`; the `runImplementReviews` `(stage_id, head_sha)` guard (`#797`) is the second line against a double dispatch, and the gating-reject return is intentionally ignored (the stage is already terminal/restored at push-report time). Called AFTER the `fixup_pushed` audit entry so a `fishhawk_await_audit` anchored on `fixup_pushed` observes the backstop's `implement_review_started` strictly after its anchor; the handler's `(stage_id, head_sha)` dedup early-return structurally prevents the backstop from running twice on a redelivered report.
- **Check-and-start atomicity across the two dispatchers.** The backstop's pre-goroutine absence check (skip mode (b)) is only a fast no-op path — it does NOT by itself make the combined check-and-start atomic against the trace-time hook. A `fixup_pushed` report arriving while the trace-time hook is between its own `#797` absence check and its `emitReviewStarted` could otherwise slip past both and double-dispatch. The load-bearing guarantee is `trace.go::reviewDispatchMu`, a process-global mutex held across the `#797` read-then-append **inside `runImplementReviews`** — where both dispatchers converge. The loser of the race observes the winner's `implement_review_started` under the lock and returns without a second review. Process-global because one backend serves both the trace upload and the PR report for a run; the critical section is a single list + append, so the coarse scope is throughput-neutral at v0 review volumes (mirrors `p95CacheMu`). A multi-replica deployment splitting the two reports across replicas would need a DB-level uniqueness guard for the durable dedup; the in-process lock is the proportionate v0 fix. `TestRunImplementReviews_ConcurrentDispatch_SingleStarted` pins it (N concurrent same-head dispatchers → exactly one started + one reviewer invocation).

## Default-branch resolution (`default_branch.go`, #4660)

- `Config.DefaultBranch` (`defaultbranch.Source`) is the run repository's base-branch source. fishhawkd wires the GitHub client's shared resolver (`githubclient.Client.DefaultBranches()`), the SAME instance the orchestrator holds; `server.New` derives nothing, so a fixture that wires no source reads `resolver_unconfigured` instead of guessing a branch or reading its forge fake.
- `resolveRunDefaultBranch(ctx, run)` is the one server-side read: an unparseable `owner/name` → `repository_invalid`; a GitLab run (`isGitLabRun`) → `forge_unsupported` (these consumers are GitHub-only, ADR-110 3(c)); otherwise the scope from the run's installation id (nil → `no_installation`) and the resolver decides (`repository_not_visible`, `forbidden`, `default_branch_missing`, `lookup_failed`). Every refusal is a typed `*defaultbranch.UnresolvedError`; callers surface `defaultbranch.ReasonOf` on their own existing failure surface. No audit category is added.
- Slice A consumer: the first-round review re-run (`review_rerun.go`), which resolves BEFORE its `review_round_rerun_requested` append and refuses `409 review_rerun_ineligible` / `default_branch_unresolved` write-free (§ "Operator re-run"). The deploy trigger, rollback and the `GET /v0/runs/{run_id}` fields are slice B of #4660.
- A skipped consolidated-review dispatch (the orchestrator's WARN `orchestrator: consolidated review not dispatched: default branch unresolved`, `orchestrator/README.md` § "Base-branch resolution") surfaces here as a parent whose implement review status stays `none`; the re-run verb is the remedy.
- Pinned by `default_branch_test.go` (one arm per reason) and `review_rerun_test.go` (`TestRerunReview_FirstConsolidatedRound`'s acme/widgets → `trunk` arm through the production resolver; `TestRerunReview_FirstRoundDefaultBranchUnresolved`).
